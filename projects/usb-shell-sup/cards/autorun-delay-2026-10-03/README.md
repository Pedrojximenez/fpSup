外部建議（Discord，「rear wheel jitter」討論串）：AutoRun 每讀一個字元延遲 1 ms；拿掉註解、在第一行把延遲 NOP 掉、最後一行還原，
他量到開機從約 13 秒變約 2 秒。

## 韌體上查到的 [離線]

- `C04211D8` 是 console 的行編輯器（ANSI 游標左右 `\x1b[%dD`/`\x1b[%dC`、重畫行尾 `%s`）。插入每個可列印字元（0x20–0x7E）時，
  `C04215F4 bl C0421770` 延遲 1 ms：旗標 `[0xC3756904+0x28]`（= `0xC375692C`，開機時清成 0）為 0 時 `C03705D8` 睡 1 ms，非 0 時 `C0000A08` 忙等 1000 µs。
- console 主迴圈 `C03D9D50`：程式塞進佇列的指令（`[C2F20FBC]+0x18 > 0`）走 `C04210D0` 整行複製、無延遲；其他輸入一律經行編輯器。
  AutoRun 走行編輯器 → **註解與補空間行也逐字延遲**（編輯器整行讀完才知道是註解）。
- **`0xEB00005D` 是原廠字**（`bl 0xC0421770`），拿來還原；拿掉延遲寫 `0xE1A00000`（NOP）。NOP 之後 `C04215F8` 起不用 r0，安全。

我們的 AutoRun（補到 32,768 B）：指令 ~3,200 字元、註解 ~2,600、補空間 ~26,000（在 loader 之後）。
慢速路徑 15–16 s ≈ 開機 ~8 s + loader 前 ~6 s 字元；一般卡載入後還要再「打字」~26 s；FS2 命中時腳本中途中止。

## 兩張卡（合併網頁離線組：shell + raw-view v0.2.3test，**不帶** Fast Start 2，每次開機都完整跑 AutoRun）

| | AutoRun | fpSup.BIN |
|---|---|---|
| `A-stock` | 原樣 | 相同 |
| `B-nodelay` | 第一條指令前 `mem set 0xC04215F4 0xE1A00000`；**檔案最後一行** `mem set 0xC04215F4 0xEB00005D`（補空間也不延遲）；長度仍 32,768 | 相同 |

設定區：**兩張都不寫**（沒有 Fast Start 2、沒有 store）。改的是記憶體裡的一個程式字，關機重開即回原廠。

## 量什麼（每張冷開機 3 次，拔 USB 開機、開完再插）

```
mem get 0xC072F6F8,,4      LOAD_DONE_US：開機到載入完成（μs），A 與 B 比
mem get 0xC375692C,,4      延遲模式旗標（低位元組 0 = 睡 1 ms）
mem get 0xC04215F4,,4      B 跑完後應是 0xEB00005D（已還原）
```
另外：開機到畫面可操作、到 banner 出現的時間（碼表）；raw-view 選單（RAW 列、SA/GA、更多選項）照常；shell 能回應。

## 注意

- 這個字是在行編輯器正在執行的程式碼上改；I-cache 可能還留著舊指令一陣子（對方實測有效）。
- 如果 B 在還原那行之前被中止（FS2 的 abort、錯誤），延遲會留在拿掉的狀態直到關機——無害，只是 console 不再節流輸出。
- 結果好的話再放進共用範本（`fp_usb_shell/build_autorun.py`）：第一行 NOP、最後一行還原、FS2 中止點前也還原；給使用者的卡考慮不補空間。
