# 開機時間:儀器、單價、以及「載入其實是免費的」

> **2026-10-11 現行 v3 複核**：目前七個候選 Sup 約 937 KB，Sup 載入／初始化實測 4.28–4.89 s；下文單一 shell 的 3.5 ms 不能套用。完成動畫固定 2 秒已從共用來源移除，並更新／完整讀回目前相機。v3 與 worker entry 會返回 AutoRun，約 29 KB 補白在恢復逐字延遲後繼續執行；實機 reboot 回覆後約 61.85 s 仍找到 AutoRun callback，112.36 s 採樣已收尾。Merge v3 尚無 Fast Start，既有頁面內嵌的凍結 loader 未重建。見 [本次時間與成品證據](../../res-lab/validation/20261011-boot-speed/RESULTS.md)。

> **2026-10-04 部分推翻**:「相機自己開機約 8.9 s、完全不歸我們管」大部分其實是原廠 shell 讀 AutoRun 時每個可見字元睡 ~1.9 ms(註解也算)。拿掉註解並 NOP 掉延遲後 `LOAD_DONE_US` 11.5 → 3.0 s。見 [AUTORUN_CHAR_DELAY.md](AUTORUN_CHAR_DELAY.md)。

## 0. 一句話

**開機 11.7 秒裡,我們的載入只佔 3.5 毫秒。** 其餘是相機自己開機(約 8.9 s)
加上 AutoRun 那幾十條指令(約 2.8 s)。所以唯一能動的是 AutoRun 的條數,
而 `fpSup.BIN` 裡塞多少東西幾乎不影響開機。

## 1. 儀器

### 相機自己的時鐘

`TICK_US = 0xC002B6E0`,無參數,回傳微秒,**開機歸零**
(實測:重開前 `time tickm` 12,722,392 ms,重開後 304,362 ms)。
`recprobe.S` 早就在用它,只是沒人拿它量開機。

### 兩個戳記

| 位址 | 誰寫 | 意思 |
|---|---|---|
| `0xC072F6F4` | loader 的第一段(`--profile` 才編進來) | 通電 → loader 拿到控制權 |
| `0xC072F6F8` | stage2 的最後(一律編進來) | 通電 → 載入完成 |

```
mem get 0xC072F6F4,,8      ← 一次讀完兩個
```

`0xC072F6F8` 原本是 `STORE_FROM`,快載入改用雜湊當 magic 之後那個握手字就死了,
**現成的空位**。兩個字相鄰是故意的。

**兩個都免費**:stage2 在檔案裡;loader 在快卡上是從設定區複製過來的,
不是 AutoRun 拼出來的。只有慢路徑會為 `--profile` 多付 7 條 `mem set`(約 500 ms),
所以它是旗標不是預設。

### 為什麼不用主機量

主機看不到通電。它最多只能輪詢 worker 何時開始答話,而那裡面夾著 USB 列舉
和輪詢間隔:

```
輪詢法      三次全距 165~627 ms,而且比戳記高約 580 ms
戳記        三次全距 35~142 ms
```

`scratchpad/bootmeasure.py` 是輪詢那一版,現在只拿來觸發 reboot;
真正的數字一律讀戳記。

### 帶著線重開機是可以的

`reboot` 之後 shell 回不來,**那是主機的問題不是相機的**:
描述元還是原廠 `06/01/01` 的時候,macOS 的 `ptpcamerad` 會搶走 interface 0。
開一個 watchdog(每 0.1 秒 `kill -9 ptpcamerad`)之後,
帶線重開、原廠 class、shell 照樣通。

**這推翻了 README 那句「開機要拔 USB」** —— 卡一直跑得好好的,叫不到它的是主機。
(代價:Image Capture / Photos 的相機匯入會失效,量完要收掉。)

## 2. 單價

三張卡,`mem set` 條數完全相同(30),只有畫面不同,解聯立:

| 卡 | 快路徑 | text | osd | 載入完成 |
|---|---|---|---|---|
| 完整進度條 | 69 | 15 | 21 | 12,646 ms |
| `FPSUP_MIN_BAR=1` | 51 | 6 | 12 | 11,617 ms |
| `FPSUP_NO_BAR=1` | 42 | 3 | 6 | 11,045 ms |

```
display osd     76 ms/條     ← 貴的是這個
display text    38 ms/條
display monitor 83 ms        (畫面全關那張的殘差)
mem set         72 ms/條     (另外用 50 條無害寫入的探針量的)
```

**貴的是 `display osd` 不是文字**,這正好證實了 `boot-time-levers` 裡那個
一直沒解決的懷疑:`display osd` 的用法字串是 `(on/off) (color)`,
它是「打開圖層」不是「呈現」,而 AutoRun 每條 `display text` 後面都跟一條 ——
**三緩衝要送三次,等於每格付三次開圖層的錢。**

⚠ 舊筆記的「display 約 283 ms、mem set 便宜得多」兩個都是錯的。

### 已排除:`mem set` 不能一次寫多個字

實機試過:三個參數直接印 `[usage]` 而且一個字都沒寫,
逗號形式 `0x11112222,0x33334444` 只寫進第一個。
所以「把 64 條 loader 寫入壓成幾條」這條路不通。

## 3. 快載入到底值多少

**必須拿「沒有快載入」當基準,不能拿快卡自己的第一次。** 三張卡同一個畫面組態:

| | 指令 | 載入完成 |
|---|---|---|
| 不用快載入 | 82 | **13,261 ms** |
| 快卡的第一次(magic 不合) | 123 | **17,615 ms** |
| 快卡的第二次之後 | 42 | **11,076 ms** |

```
每次開機省   2.18 秒
第一次多付   4.35 秒
回本         第 2 次打平,第 3 次開始淨賺
```

「快卡第一次 vs 之後差 6.5 秒」這個講法**沒有意義** —— 它拿自己多付的成本當基準。

**所以預設不開是對的**:開發一天重開幾十次,明顯值得;
使用者一天開一兩次幾乎打平,而代價是設定區被寫進東西、撐過拔電池。
現行政策(發行版不帶、網頁上讓人自己勾)站得住腳。

順帶驗到:把 store 的 magic 打掉,下次開機真的退回慢路徑,
而且 stage2 在那次開機把它重新種回去。「壞掉自己修回來」是真的。

## 4. 階段拆解 —— 載入是免費的

快路徑,三次:

```
loader 進來 11,689 ms   載入完成 11,692 ms   中間 3.51 ms
loader 進來 11,656 ms   載入完成 11,659 ms   中間 3.34 ms
loader 進來 11,719 ms   載入完成 11,721 ms   中間 2.76 ms
```

慢路徑:18,104 → 18,108,中間 **4.35 ms**。

那 3.5 毫秒裡有:配 64 KiB、開檔、讀 32 KB、關檔、驗 VBIN、兩次整份快取、
放 10 個區段、呼叫 worker 的 entry(它自己再配一塊、複製 1.4 KB、建任務)、
判斷要不要寫 flash、arm abort。**全部。**

所以快路徑的帳是:

```
相機自己開機        ≈ 8,876 ms    完全不歸我們管
AutoRun 的 42 條    ≈ 2,813 ms    唯一能動的(用單價估)
loader + stage2     ≈     3.5 ms
```

### 三個推論

1. **`fpSup.BIN` 裡放什麼、放多少,對開機時間幾乎沒有影響。**
   og3k 塞 80 個區段 3,307 筆寫入,跟 shell 卡塞 10 個區段,差在毫秒等級。
   三張卡的載入階段一樣快,差別只在各自 AutoRun 的條數。
2. **「把東西從 AutoRun 搬進檔案」這個設計方向從頭到尾都對** ——
   stage2 從 loader 搬進檔案、drain/space 搬進池、worker 搬進池,
   每一次都是把 72 ms/字換成 0。
3. **剩下能做的只有兩件小的**:store_boot 從 26 個字瘦下來(5 個是字面池,
   理想 18~20 字,省 0.4~0.6 s);無畫面的卡不必寫那三條螢幕補丁 + monitor
   (實測全關省 869 ms)。再往下就撞到相機自己的 8.9 秒。

### 冷開機比熱重開慢

拔電冷開兩次是 11,701 / 11,712 ms,`reboot` 熱重開五次是 11,031~11,140。
差約 600 ms。樣本少,先記著。

## 5. 兩次凍結,都是我寫的,都在同一段七條指令裡

要在 loader 最前面讀時鐘,兩次都踩到 ARM 呼叫慣例:

**第一次:`bl` 排在 `push {…, lr}` 之前。**
`bl` 會寫 `lr`,而那時 `lr` 還是 echo handler 的返回位址。
loader 最後 `pop {…, pc}` 就回到垃圾。

**第二次:`mov r1, sp` … `bl` … `mov sp, r1`。**
r0-r3 和 ip 是 caller-saved,被呼叫者可以自由破壞 —— 還原的是垃圾 sp。
`recprobe.S` 用 r5 就是為了這個。

兩次的症狀都一樣:**每次開機都凍在同一個地方,而 loader 一壞就沒有 shell 能救,
卡只能拔出來放進 Mac 還原。** 一個下午拔兩次。

### 兩道機械守衛(`build_autorun.py`)

`verify_loader_saves_lr_first()` 從產出的機器碼解碼,兩件事任一中止建置:

- 任何 `bl` / `blx` 排在存 `lr` 的 push 之前
- 用 r0-r3 或 ip 跨呼叫保存 sp(`mov rN,sp` … `bl` … `mov sp,rN`)

兩個都做過 mutation:把程式碼改回錯的版本重組,守衛都抓得到。
跟 `verify_stage2_cache_publish` 同一個路數 —— **讀機器碼,不讀註解**。

### 程序規則:loader 的改動不准直接上開機路徑

先在**相機活著的時候**用 echo 借用跑一次:
`scratchpad/runprobe.py <source.S> <位址> <輸出字>` 會把候選程式碼寫進空洞區、
逐字回讀、借 echo 執行一次、把 handler 還回去,然後回答兩件事 ——
**shell 還活著嗎、它有沒有寫出東西**。

修好的那七條就是這樣驗過才寫進卡的:

```
探針 40 bytes -> 0xC072FE00
  10 個字寫入並逐字回讀相符
  借 echo 跑一次 …
  shell 還活著: True
  探針寫出的值: 0x06F51E1F = 116727 ms
```

今天兩次凍結,都是這一步沒做。

## 6. 上傳路徑不可靠 —— 還沒修

一個下午裡 `putfile` / `getfile` 出過:

- `status 3 — open returned 0`,**而退出碼是 0**
- 回報 `written`,實際卡上還是舊的(我因此誤判「探針已移除」一整輪)
- `echo handler is [None], not free to borrow`(讀 slot 的指令被丟掉)
- 一次在 putfile 期間凍結,原因未明

暫時的擋法是 `scratchpad/deploy.py`:**寫了不算數,逐位元組回讀相同才算**,
不對就重寫,五次不成就拒絕重開機。

真正要修的在工具裡:回讀驗證要內建、失敗要有非零退出碼、
echo handler 的借用要保證還原。還有一件結構性的 ——
**`putfile` 的暫存區 `0xC072F700..FC84` 正好壓在 `store_boot` 上**,
用一次檔案工具就把它蓋掉(開機時早跑完了所以目前無害,但那是巧合不是設計,
而且沒有任何地方寫著這兩個共用同一個位址)。
