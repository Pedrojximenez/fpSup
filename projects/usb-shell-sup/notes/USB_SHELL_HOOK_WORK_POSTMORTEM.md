# USB shell 做 hook 工作 —— 一輪五次凍結的檢討 (2026-08-25)

一個 session 裡把相機弄凍五次,#1/#2/#3 進度為零。這份記錄**為什麼**,
因為每一條都是可以避免的,而我一度把責任歸給環境。

## 一、我犯的錯(七項,環境無關)

| 錯誤 | 後果 |
|---|---|
| 把未驗證的 `stksz` 從 0x2000 跳到 0x8000 | 污染共用堆疊池 `0xC301EAE4`,下一次任務建立整台死 |
| 位址撞車 ×3:注入常式蓋 `PEEK_CODE`、`FILEOBJ` 放進 worker 程式碼區、`CTL` 蓋 `push_addr` | peek 回垃圾 / 開檔失敗誤導半小時 / **BATCHPUSH 執行垃圾 → 凍結** |
| 狀態沒初始化就讓 hook 跑 | 池裡殘留的 `OPENED != 0` → 拿垃圾當檔案物件去 close → 凍結 |
| `pushread` 的 bus 位址換算對 DRAM 用錯 | 讀 `0x44F6ADC0` 讀到 `0xC4F6ADC0`,拿假資料下結論 |
| 一次改兩件事(poke 的 cache 路徑 + 裝 hook) | 凍結後無法歸因 |
| 凍結後從不讀卡 | **明明有現成的診斷通道,五次都沒用** |
| 把「USB 被背景腳本佔住」讀成相機死掉 | 白白要使用者拔一次電池 |

**這七項在 AutoRun 下一項都不會少**,而且迴圈更慢,每一項代價更高。

## 二、我對環境的錯誤指控

一度主張退回 AutoRun,理由是「hook 掛掉時觀測手段一起死」。
**使用者直接指出這是錯的:hook 寫的是卡,相機死了卡還在,去讀就好。**

同一輪還說錯兩件:
- 「hook 點被 shell 佔用」—— 讀現場才發現 shell 只拿它當開機跳板,用完就還原原指令
- 「`mem set` 有位址閘門是天生的」—— 是**我們自己加的**護欄
  (`WR_LO/WR_HI`、`RD_LO/RD_HI`、`INJ_LO/INJ_HI`,原始碼註解:
  "Hardened: Bounded ranges cap blast radius"),`shl` 走韌體自己的 shell 就沒有

## 三、USB shell 真正的限制(逐條檢驗後只剩這些)

**結構性的:**
- **池 `0x44F6ADC0` 就是 shell 自己的傳輸緩衝**(讀出來是 ASCII `"FPSH"`)。
  執行期呼叫 `memmgr bufmem get` 三次全部 `bad-frame-header`,最後一次弄死相機 ——
  它動到的正是 shell 賴以通訊的那塊。**要緩衝就用池尾(`0x44F6BDC0` 之後)或不用緩衝。**
- **相機狀態跟真實錄影不同**。要量「CinemaDNG 錄影中 SD 寫入阻塞多久」,
  閒置狀態下的數字不能代表 —— 那時卡片被灌到 ~93 MB/s。必須真的在錄影中量。

**只是不方便的:**
- 注入的東西每次凍結都要重建(一個腳本,十秒)
- `0xC072Fxxx` 真正空著的只有 512 bytes(有地圖就可管理;池尾也能用)

## 四、USB shell 在這輪實際交付的

全部是**非 hook** 工作,而且都很有效率:
- 鏡頭程式端到端驗證(建資料夾 → 韌體 API 讀鏡頭 → 解析焦距 → 檔名消毒 → 覆寫寫入 → **讀回卡片確認**)
- 檔案 API `open` 模式語意(7 可覆寫 / `0x402` 已存在就失敗)—— 挖出潛伏 bug
- 錄影幾何 `0xC37CE210` = {1936, 1090, 3244544}
- 任務建立 ABI 實機驗證,順帶抓出 stage6 兩個會凍結的錯
- blk0a 焦距欄位(+4,BE u16,×10 mm)—— 靠兩次即時讀取交叉比對

**分界很清楚:「呼叫一個東西、看結果」極有效率;hook 那種自主持續執行的程式碼,
shell 的強項用不上、弱項正面撞上。但那不構成換環境的理由。**

## 四點五、讀卡讀出來的關鍵事實 —— 我的量測設計是錯的

使用者要求「用 shell 讀卡」之後(第一次真的去讀),結果:

```
\GYROSTRM.BIN   不存在   ← 但當時回報 open=1、write 成功、2016 bytes
\GYROD1.BIN     不存在
\GBLK.BIN       不存在
\AutoRun.txt    存在,讀得到   ← 對照組通過
```

**沒有 flush,卡上什麼都沒有。** `write`(`0xC03660E8`)只是進緩衝,
真正的 SD I/O 發生在 flush(`0xC0366020`)。串流任務卡住時還沒走到 close,
所以那 2016 bytes 從來沒離開記憶體。

**這直接推翻了原本的量測設計**:`timed_write` 只計時 `write` 呼叫,
量出來會是接近零的數字,然後我就會下「沒有延遲問題」的錯誤結論。
**必須計時 write + flush 合計。**

而「每個區塊寫完就 flush」同時解決兩件事:讓量測量到真實延遲,
並讓凍結後卡上真的有東西可解剖。

## 五、往後的做法

1. **hook 每寫完一個區塊就 flush**,不要等關檔 —— 凍結時資料才真的在卡上
2. 除了資料檔,另寫一個小**狀態檔**(階段標記、計數器、最後一次寫入耗時)
3. **凍結後第一件事是讀卡**,不是重建 shell
4. 新程式碼**先直接呼叫一次**確認能乾淨返回,再讓它掛上去每秒跑 50 次
5. 一次只改一件事
6. 位址先查 `SHELL_MEMORY_MAP.md`,用之前寫標記回讀確認
7. 未驗證的參數(`stksz` 等)不要在別的測試中途順手改
