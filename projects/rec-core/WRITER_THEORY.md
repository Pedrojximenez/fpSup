## 1. 模型

每個檔:傳輸 `t_x = 補齊後大小 / R`,CPU `c_f`(開檔/配置/關檔,SD 與 SSD 相同),中繼資料 I/O `m_f`(只有 SD;queue depth 1,不能與 DMA 重疊)。
原廠是串行:每檔 `c_f + m_f + t_x`。

用 rec log 擬合(假設 cluster 補齊有傳到媒體 —— **唯一未驗證的前提**):

| 參數 | 值 | 來源 |
|---|---|---|
| R(SD UHS-II,此卡) | 265 MB/s | 57 × 1,179,648 B / 254 ms |
| R(SSD) | 412 MB/s | 43 × 1,572,864 B / 164 ms(相機跑分 390 為 10 MB 單次寫入、含 ~6 ms 固定開銷,不矛盾) |
| c_f | 0.51 ms | SSD 批間空檔 22 ms / 43 檔 |
| m_f(SD) | 3.19 ms | SD 批間空檔 211 ms / 57 檔 − c_f |

**驗證**:模型原廠值 SD 134 MB/s(實測 ~135)、SSD 253 MB/s(實測 ~250)。

## 3. 結論

1. **SD 的槓桿是中繼資料合併**(134 → 216;加重疊 240)。只做重疊幾乎沒用(143),因為 SD 的中繼資料 I/O 不能和 DMA 同時。
2. **SSD 的槓桿是 cluster 補齊**:改 128 KiB 不改程式就 253 → 325;再加重疊 383。只做重疊是 287,勉強過 240p。
3. **SD 上 12-bit 240p 物理上做不到**:即使理想化,上限 ≈ R = 265 ≈ 需求 263,沒有餘量。SD 的 240p 只能 10-bit 以下。
4. **在途幀數**(一塊在填、一塊在寫、加 200 ms 尖峰):

| 格式 | 64 MiB 塊 | 32 MiB 塊 | 8 MiB 塊 |
|---|---|---|---|
| M12 239.76 | 155 | 102 | 62 |
| M12 119.88 | 131 | 78 | 38 |
| FHD 59.94 | 48 | 30 | 17 |

   原廠 64 MiB 在 240p 需要 155 > 94 —— 這正是 240p 在 94 幀停錄的理論解釋。
   ⚠ 更正:上表只算未壓縮檔;壓縮小檔下在途幀仍與 1/檔案大小成正比。原理上的解是塊同時以幀數 k 關閉(WRITER_SPEC §5.1b)。
   **塊縮到 8 MiB,所有未壓縮格式都在原廠 96 格內,不必擴充描述子池**(前提是塊縮小後每塊固定開銷仍可忽略;
   SSD 指令起點 2 MiB、上限 32 MiB,8 MiB 塊仍是 1 條 BOT 指令)。

## 4. 與 Magic Lantern 的對照

ML 的 MLV:一段錄影一個檔、專屬 writer、緩衝池、每次寫 ~32 MiB 連續區塊。
在這個模型裡,單檔容器等於 **c_f = m_f = 0、沒有補齊** —— 正好消掉我們量到的全部損失,所以 ML 那樣改是有道理的。

CinemaDNG 必須每幀一檔,但上面的設計能拿回大部分:
- 中繼資料合併 + 預配置連續 cluster ≈ 把 m_f 壓到接近 0;
- 寫入 task 重疊 ≈ 把 c_f 藏起來;
- cluster 補齊是 CinemaDNG 格式留下的唯一結構性損失(SD 128K 時 7.7%,SSD 依 cluster 大小)。

若之後要再往上,自製單檔容器(先前評估過,代價是 Resolve 不能直讀)就是剩下那 7–30% 的來源。

## 5. 對規格的修正

- SD:W3(中繼資料合併)優先於 W1。
- SSD:先處理 cluster 大小,再做 W1。
- 塊大小預設 8 MiB(SSD)/ 依 AU 的 RU 倍數(SD),逐塊歸還 ⇒ 不再需要擴充描述子池。
- 全部數字的前提「補齊有傳到媒體」仍需 M2 確認;若不成立,SSD 的 R 會降到 ~287,cluster 大小就沒有收益,改由重疊為主。
