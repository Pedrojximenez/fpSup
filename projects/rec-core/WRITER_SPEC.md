## 1. 目標與範圍

**目標**:CinemaDNG 錄影時,讓媒體在有資料可寫的時候一直在寫,並把每檔的固定成本壓到最低。

| 情境(現況 [L],WP §4) | 現況持續速率 | 目標 |
|---|---|---|
| SD UHS-II,1008×672,119.88p,積壓中 | ~135 MB/s(duty 0.55) | ≥ 220 MB/s |
| SSD,239.76p,積壓中 | ~250 MB/s(duty 0.86),需求 263 | ≥ 275 MB/s,能連續錄 240p |
| 所有情境 | 一批 64 MiB 寫完才放幀 | 一塊寫完就放該塊的幀 |

**範圍內**:幀的 DNG 檔交給檔案系統之後,一路到媒體完成、幀歸還。SD 與 SSD(Custom 模式)。音訊 WAV 的寫入排程。

**不在範圍**:檔案格式(仍是每幀一個 CinemaDNG)、MovRec 與 RAW 環、DNG 檔頭內容、LOSS 壓縮、gyro(已隨 DNG 寫入)、
相機設定區(一律不寫)。共用 loader 的位元組不動;本模組是一個獨立的 sup。

## 2. 現況的關鍵事實(全部引自 WP)

1. 送出是**同步的**:提交幀的 task 在 `C063F380` 攢滿門檻時直接呼叫 `C063F140`,寫完才返回;全程握著
   FS 全域鎖 `[0xC37D0644]`(`C063B898`)[C]。
2. 一個 volume 同時只有一批;SD 驅動全機一張 ADMA 表 `0x43818EC8`(忙碌旗標 `0xC3816E80`),**queue depth = 1** [C]。
3. 205 份 rec log 零重疊 [L]。~~SD ~4–6 ms/檔~~ **更正**:SD 那幾段沒有積壓,空檔是在等幀;SSD 240p 有輕微積壓,空檔 ~0.5 ms/檔。
4. **錄影中檔案系統是「關檔不寫回」**(vol+0x481C = 0,停錄才 flush)⇒ 每檔中繼資料寫卡 ≈ 0 筆 [C](EXFAT_PER_FILE_METADATA.md)。
   原廠本來就延後了中繼資料;§5.3 的大部分已由原廠完成。
5. 整批完成後才對批內每個 cookie 呼叫 `C03A55D0(frame, status)`,幀才歸還 [C]。
6. 任何一般寫入 `C063F898`(音訊 WAV)都會先強迫送出未滿的批 [C]。
7. 每檔補零到 cluster 邊界,補的部分計入門檻;SSD 512 KiB cluster 時 240p 每檔 +43.6% [C];是否真的傳到媒體 **未知**。
8. 卡的錄影協定:V60 卡有 VSC(AU 36 MB),原廠 VSC 配置器會啟動但「每檔一個 AU」;舊卡無 VSC [L](WP §12)。
   CMD20 在 FS 鎖內經 `0xC01EB941` 送出是安全的 [L],但卡不回報子指令是否生效。

## 2b. SSD 跑分對照(2026-10-14,使用者提供)

SSD 跑分寫入 **390 MB/s**。rec log 的 240p 每批 43 檔、164 ms:依檔案大小算 ~287 MB/s;
若 512 KiB cluster 補齊真的傳到媒體,實際傳輸 43 × 1,572,864 B ≈ 64.5 MiB ⇒ **~412 MB/s ≈ 跑分** [I]。
⇒ SSD 在寫入期間很可能已滿速,損失主要是補齊(43.6%),不是重疊。
最便宜的驗證:SSD 改格式化為 128 KiB cluster(浪費 7.7%,有效 ~362 MB/s > 需求 263),不改程式 [P]。
因此 SSD 的順序改為:**M2 驗證補齊 → 換 cluster 大小試錄 → 才做 W1 重疊**。

## 3. 不變式(每一項都要有測試)

- **I1 恰好一次**:每一幀恰好被送出一次、恰好收到一次完成、恰好歸還一次。
- **I2 順序**:同一檔的資料在媒體上的位置與檔案系統記錄一致;檔案逐位元等於送出時的內容。
- **I3 不重疊使用**:一份描述子清單在 DMA 期間不被修改;驅動的 ADMA 表只在寫入 task 送出的那一刻使用。
- **I4 有界**:在途資料 ≤ 預算(RAM、描述子數);超出時走原廠停錄路徑,不硬撐、不丟幀不報。
- **I5 停錄排空**:停錄時所有已接受的幀都寫完並歸還;沒有卡在中間狀態的孤兒。
- **I6 錯誤一致**:媒體錯誤時,所有受影響的幀以失敗狀態完成(交給原廠既有的錯誤處理),不靜默。
- **I7 優先權**:高優先權 task 永遠不等待較低優先權的寫入 task(記憶:凍結=優先權反轉,SRecFile(6) 等 writer(28))。

## 5. 架構 [P]

```
提交端(原廠 task,握 FS 鎖)                    寫入 task(新,單一)
─────────────────────────────                  ─────────────────────────────
C063F380 每幀:配置 cluster、記 {ptr,len,cookie}
   → 加進「目前的塊」(我們的清單,不是驅動表)
   塊滿(依 §5.4 的大小)或停錄
   → 塊交給寫入佇列,立刻開新塊,返回 ──────→  取一塊
                                                 (SD/SSD 各自的方式送出,§5.2)
                                                 完成後:逐 cookie 呼叫 C03A55D0
                                                 → 幀歸還
```

### 5.1 塊(取代 64 MiB 批次)

- 一塊 = 一份 {ptr, len} 清單 + cookie 清單 + 媒體起點 cluster + 長度。至少兩塊輪替(建議三塊,吸收抖動)。
- 塊的記憶體從配置器要(記憶:主機端也用配置器、別自己挑位址),錄影開始時配好,整段重用,停錄排空後釋放。
  ⚠ 跨錄影不保留配置(記憶:配置器不能跨錄影)。
- 塊滿的條件:長度達到塊大小、cluster 不連續、描述子數用完、或停錄。

### 5.1b 塊的關閉條件:位元組或幀數,先到先關(2026-10-14)

原廠的問題:歸還看位元組(64 MiB),耗盡看幀數(94 格)⇒ 扣住幀數 = 64 MiB ÷ 檔案大小,小檔(壓縮 0.5 MB:~134)必然撞上。
只縮小塊仍與檔案大小成反比(4 塊 × 8 MiB ÷ 0.25 MB = 128),**不是**原理上的解。
規則:**一塊在 `B` 位元組或 `k` 幀時關閉,先到者生效**;`k = floor((94 − R) / WQ_BLOCKS)`,R = 停錄與管線保留(初值 14 ⇒ k = 20)。
⇒ 在途幀 ≤ WQ_BLOCKS × k ≤ 80,與檔案大小無關。
實作(精確數幀,不估大小):每塊開始時 `vol+0x4828 = B`;本層的完成回呼指標(+0x4834)在「幀結束 / cookie 登記」時
把本塊幀數 +1;數到 k 時設 `vol+0x4828 = round_up(+0x4A58, RU)` —— 原廠下一次比較就送出本塊,結尾落在 RU 邊界。
⚠ 不可用「k × 壓縮前大小」當位元組門檻:壓縮後一個位元組門檻裝得下更多幀,會低估幀數(2026-10-14 討論)。
⚠ k 由在途塊數決定,不是 64 MiB ÷ 原始大小(原廠只有一批在途;本層最多 WQ_BLOCKS 塊)。
剩下會停錄的唯一情況是媒體頻寬不足(4 塊都在排隊),那是正確的停錄。

### 5.2 寫入 task 與媒體送出

- 開機時建立一次、永不刪除(記憶:任務刪不掉,缺 tk_ext_tsk)。優先權必須**數字小於等於**所有可能等它的 task,
  或保證沒有人等它(I7)。初值:與 SRecFile 同級,M3 後再定。
- **SSD**:寫入 task 呼叫原廠送出鏈(`C0646C60` 一族)送出整塊。要確認的前提:送出時哪些部分需要 FS 鎖。
  [P] 只在「準備」那一小段拿 FS 鎖(`C0646580` 的 kind3 cache writeback),裝置寫入本身(`C01EB790` 以下)不握 FS 鎖,
  讓提交端可以同時做下一塊的逐檔工作。**這是 SSD 主要收益的來源**(WP §4:22 ms/批可被藏住)。
- **SD**:驅動 queue depth 1,提交端的中繼資料 I/O 一定要等 DMA。SD 的收益主要來自 §5.3,重疊只藏得住 CPU 那部分。
- 驅動的 ADMA 表/SSD arena 只在寫入 task 送出時,由塊清單複製進去(≤ 1024 筆 × 8 B),送完即放(I3)。

### 5.3 中繼資料(**降級**:原廠錄影中已延後寫回,只保留一致性改善)

依 M1 的結果決定做哪幾項:
- **預配置**:一塊開始時一次在 bitmap 配好整塊需要的連續 cluster(對齊 AU,§5.4),之後每檔只切這段,
  不再逐檔走 bitmap。
- **連續檔**:每個 DNG 都是連續的 ⇒ 目錄項標 NoFatChain,**不寫 FAT 鏈**。
- **目錄項整批寫**:同一塊內的檔案,目錄項在 RAM 累積,塊完成時一次寫入目錄 cluster。
  ⚠ 斷電一致性:塊未完成前斷電,這些檔不出現在目錄裡(資料在卡上但沒有目錄項)。需與使用者確認可接受。
- 有 CMD20 時:目錄寫入用 CMD20 包住(原廠 `C0649DB8` 的模式),讓卡用另外的緩衝處理。

### 5.4 塊大小與 AU 串流

| 媒體 | 塊大小 | 對齊 |
|---|---|---|
| SD 有 VSC(V60) | VSC AU(36 MiB)或其整數分之一的 RU 倍數 | AU 邊界(第一個在 cluster 34) |
| SD 無 VSC | 一般 AU(舊卡 64 MiB);若太大,改用 RU 等級的較小塊、仍順序寫入同一 AU | 一般 AU 邊界 |
| SSD | 指令上限的整數倍(BOT 32 MiB、UAS 8 MiB×4) | cluster |

**整段錄影一條 AU 流**:錄影開始時取第一個 AU,檔案依序塞進去,寫滿才換下一個;錄影結束才放手。
有 CMD20 的卡:開始時 Start Recording 一次;每換 AU(VSC)送 Set Free AU;結束時 Release DIR。
**不**採用原廠「每檔一個 AU」(WP §12.4:FHD 30p 約 113 秒用光 free AU)。


### 5.4b 依卡片能力選擇流程(2026-10-14,依 SD Physical Layer Simplified Spec 6.00 核對)

**CMD20 參數格式**(Figure 4-62):`[31:28] SCC`、`[27] VSC`(0 = 舊式 Speed Class/UHS Speed Grade,1 = VSC)、
`[26:24] CNT/ID`、`[23:22] 00`、`[21:0] ADDR`(512 KB 單位)。SCC:0 Start Recording、1 Update DIR、4 Update CI、
5 Suspend、6 Resume、7 Set Free AU、8 Release DIR。
⇒ 韌體的 0x08000000 / 0x18000000 / 0x7…|ADDR / 0x88000000 全部是 VSC=1 的版本;`C0649DB8` 的「Update DIR 失敗 → Release DIR → 重試」
正是規格 §4.13.4.7.3.4 的錯誤處理。

| 卡片能力(SD Status) | AU 大小來源 | 流程 |
|---|---|---|
| VIDEO_SPEED_CLASS ≠ 0 且 VSC_AU_SIZE ≠ 0 | VSC_AU_SIZE(MB);SU 由表 4-56 決定(36 MB → SU 9 MB) | **VSC**:Update DIR(slot)→ Set Free AU → Start Recording(VSC=1);Suspend/Resume;結束 Release DIR |
| SCR CMD_SUPPORT bit32(CMD20)= 1、無 VSC | UHS 匯流排:**UHS_AU_SIZE**(§4.10.2.9,host shall use);否則 AU_SIZE | **舊式**:Update DIR → Start Recording(VSC=0);Update CI |
| 能力或 AU 資訊不足 | 不假定 | 一般寫入(原廠現況) |

**兩種流程共用**:寫入 task、塊佇列、連續空間配置、批次寫入、逐塊歸還。**分開處理**:目錄更新、換 AU、停錄收尾。
VSC 與舊式**不可混用**(§4.13.4.1.1:VSC 錄影中使用 Speed Class/UHS Speed Grade ⇒ 行為不確定)。

**規格對設計的硬性要求**:
1. **寫入要 RU 對齊、RU 倍數**:active AU 內的 CMD25 不是 RU 倍數或不從 RU 邊界開始 ⇒ 破壞 SU 時序;非連續位址 ⇒ 錄影終止(表 4-66)。
   ⇒ 塊 = 連續資料流上的 k × RU,**允許把一個檔切在兩塊之間**(原廠本來就會切),不能在塊尾為了檔案邊界補齊。
2. **Start Recording 最長 busy 1 秒** ⇒ 只能在錄影開始時送一次,不能每檔送。
3. **換 AU**:前一個 AU 完整寫滿 ⇒ 不必再送 Start Recording;沒寫滿 ⇒ 必須再送(§4.13.4.1.1 step 6)。
   ⇒ 原廠「每檔一個 AU」每檔都留下沒寫滿的 AU,等於每檔都要 Start Recording(最長 1 秒)。整段一條 AU 流才能避開。
4. **目錄**:VSC 有 8 個 DIR slot(512 B 區);舊式只有**一個**指定的 DIR 扇區,寫到別的扇區 = 非 Speed Class 寫入 ⇒ 錄影結束,
   需重新 Update DIR + Start Recording。原廠錄影中目錄只在 RAM(sync off),只在目錄 cluster 成長(約每 1024 檔)與停錄時寫,
   所以兩種流程都只在那幾個點需要處理目錄。
5. **舊式的順序**:Update DIR 必須在 Start Recording 之前;兩者之間只允許資料讀寫/抹除/secure/狀態讀取,
   其他指令 ⇒ 要重送 Update DIR(§4.13.2.9)。SDXC 卡要在 Start Recording 之後寫入才保證 Class 效能(§4.13.2.8)。
6. **FAT 更新預算**:VSC 單 slot 平均 ≤ 100 ms/次、最大 750 ms;主機緩衝要能吸收(規格例:8 次 × 100 ms = 800 ms)。
7. **錯誤回報在下一個指令的 R1**(CMD13);保留碼不算錯誤 —— 與 12.3 的實測一致。

**實測卡片對照**:V60 卡 VSC=60、VSC_AU_SIZE=36 ⇒ VSC 流程(SU 9 MB)。舊卡 VSC=0、UHS-II 下 CMD20 旗標=1 ⇒ 舊式流程;
UHS_AU_SIZE 依快取字 0xC2F2E8AC 的第二個 nibble 推為 0xA = 8 MB [I,欄位位置未證實;V60 卡為 7 = 1 MB]。

### 5.4c RU 對齊與兩種流程的狀態機

**RU = 512 KB**:VSC(§4.13.4.2.3)與 UHS Speed Grade(§4.13.3.1.3)相同。
規格範例(§4.13.4.2.3 圖)是「每檔檔尾補到 RU」;對每幀 1 MB 的 CinemaDNG,這等於把 1,095,168 B 補到 1.5 MiB(+43.6%),不採用。
**改為在塊的層級對齊 RU**:
- 整段錄影的檔案在 LBA 上是一條連續流(§5.3 預配置連續 cluster;檔與檔之間仍有 cluster 補齊,128 KiB 時 +7.7%)。
- 每塊 = 這條流上的 `[k × 512 KB, (k+n) × 512 KB)`,邊界只看 LBA,不看檔案;一個檔可以跨兩塊。
- 流的起點對齊 AU 邊界(AU 是 512 KB 的倍數 ⇒ 自動 RU 對齊)。
- 停錄時最後一塊不足 RU:照寫(只影響最後一筆的 SU 時序,不影響正確性),然後走收尾。

**VSC 狀態機**(V60 卡:AU 36 MiB = 72 RU,SU 9 MiB):

```
IDLE ──錄影開始──> Update DIR(slot0, VSC=1) + 寫該目錄扇區
     ──> Set Free AU(ADDR=第一個空 AU 的 512KB 位址, CNT=bundle)
     ──> Start Recording(VSC=1)  [busy ≤ 1 s,開錄時吸收]
RECORDING:  每塊 = n×RU 連續寫入 active AU
     AU 寫滿 ──> Set Free AU(下一個空 AU)  [前一個 AU 寫滿 ⇒ 不必 Start Recording]
     目錄 cluster 成長 / 必要的目錄寫入 ──> Update DIR(slot) 後寫該扇區(≤ 8 slot;換位址前先 Release DIR)
     錯誤/中斷需求 ──> Suspend AU ─(之後)─> Resume AU + Start Recording
停錄 ──> 寫完最後一塊 ──> 原廠 flush 目錄/bitmap(sync 回 1)──> Release DIR(slot0)──> IDLE
```

**舊式狀態機**(舊卡:UHS_AU_SIZE,推定 8 MiB = 16 RU):

```
IDLE ──錄影開始──> Update DIR(VSC=0) + 寫「唯一」指定的目錄扇區
     ──> Start Recording(VSC=0)   [兩者之間只允許資料讀寫/狀態讀取,否則重送 Update DIR]
RECORDING:  每塊 = n×RU,依序寫入「完全空的」AU;換 AU 不需要指令(舊式沒有 Set Free AU)
     允許的非資料寫入只有:FAT(≤16 KB)+ Bitmap(≤16 KB)+ 指定 DIR 扇區(512 B)、或 Update CI + 512 B
     需要寫「別的」目錄扇區(目錄 cluster 成長) ⇒ 錄影模式結束 ⇒ 寫完後重送 Update DIR + Start Recording(busy ≤ 1 s)
停錄 ──> 寫完最後一塊 ──> 原廠 flush ──> IDLE(舊式沒有 Release DIR)
```

**一般寫入**(能力不明):不送 CMD20;仍使用 §5.1–5.2 的塊與寫入 task,塊大小取 8 MiB、對齊 cluster。

**選擇時機**:錄影開始時讀 SD Status 快取(0xC2F2E8A8 / 8AC)與 vol+0x1FF0;SSD 一律一般寫入(USB MSC 無 CMD20)。

### 5.5 cluster 補齊(依 M2)

若補齊確實傳到媒體:同一塊內的檔案共用一條連續 cluster 流,只在檔尾補到 512 B(檔案系統仍需 cluster 對齊時,
改由下一檔接續使用剩餘 cluster —— 需確認 exFAT 是否允許,否則保留補齊)。若未傳到媒體,不處理。

### 5.6 音訊 WAV

一般寫入不再強迫送出影像塊:`C063F898` 的「先送出未滿批次」分支改為把該筆寫入排進寫入 task 的佇列,
與影像塊依序送出。音訊 writer 原本的時序不變。

### 5.7 停錄與錯誤

- 停錄(`C03A5190` ← `cDevt_stop`):提交端送出最後一塊,等寫入 task 排空,再讓原廠收尾(`C063F310`)。
- 媒體錯誤:該塊所有 cookie 以失敗完成;後續塊照原廠錯誤流程處理(停錄)。不重試同一塊(避免重複寫入)。
- 停錄期間不碰 USB(記憶:錄影/回放中不碰 USB)。

暫定一律接手(WRITER_PLAN §7):錄影初始化 C03A5050 內 C03A50F8 把 `settings+0x9C` 複製到 `mgr+0xD` 之後,

## 5.9 對檔案生產者的公開約定(與 LOSS 等 sup 解耦,2026-10-14)

本層只看檔案層的位元組與 cookie,不知道也不需要知道是誰產生檔案(原廠、LOSS、之後的 sup)。雙方只依賴下列約定:

1. **送出即定案**:生產者在 C069ADE0 送出前寫完檔案緩衝的全部內容;送出後不得再改。本層可能在很久之後才寫入媒體。
2. **大小可變**:每幀檔案大小可以不同;本層不得假設固定大小或由大小推算幀數(§5.1b 精確數幀)。
3. **只走原廠完成路徑**:幀只經 C03A55D0 → 原廠釋放;生產者不得提早釋放,也不得依賴完成回呼的 task、FS 鎖或時間點。
4. **背壓**:塊用完時本層讓提交端在 C063F140 等待(SRecFile 停住);生產者在同一 task 的工作會一起延後,不得假設固定時間餘量。

另:本層 hook 位置與 LOSS 不重疊(LOSS:C03A33C8、C038BFF0、C0398D88、C03A5490、回放;本層:C063F140、vol+0x4834..0x4848、mgr+0xD);
雙方不共用位址或狀態;寫入 task 優先權(≤ 6)高於 LOSS 壓縮 task(12)。兩者可各自建置、測試、發布。

## 8. 未解與風險

- SSD 送出時哪些步驟必須握 FS 鎖(§5.2 的前提)—— 要讀 `C0646580`/`C0646C60` 再定。
- 寫入 task 在 FS 鎖外呼叫裝置寫入,與提交端的中繼資料 I/O 在驅動層如何互斥(SD 忙碌旗標、SSD 鎖 `0xC3821468`)。
- 目錄項延後寫入的斷電一致性(§5.3)—— 需使用者決定可接受的行為。
- exFAT 能否讓多個檔共用 cluster 尾端(§5.5)—— 多半不行,屆時保留補齊。
- 寫入 task 的優先權與 MRecMgr(15)/CamSch(15)/SRecFile 的互動(I7)。
- 錄影中途卡滿、拔卡、低電量的路徑。
