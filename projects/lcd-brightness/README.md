# SIGMA fp LCD 亮度：離線開發

已製作獨立 **Loader v4 LCD Backlight sup**：來源與用法見 [fpSup/backlight](../../fpSup/backlight/README.md)，本機交付目錄為 [sup/20261025-v0.1.0test](sup/20261025-v0.1.0test/)。它在載入與選單操作時讀寫電流控制，不修改下列歷史實驗用初始化表。

**2026-10-25 更新：找到獨立的 LED 背光電流控制。** RT5035C 的 DIM7 有 0–31 共 32 檔，兩份正常初始化表均設定為 18；上方另有 13 檔。已用原廠 ARM 程式模擬確認。詳見 [背光電流研究](BACKLIGHT_CURRENT_2026-10-25.md)。這擴充了下面 2026-10-24 僅針對 LCD 命令表的結論；不能將一格 LCD 參數當成整機亮度能力的上限。

2026-10-24，對象為 fp Ver.5.02。**目前完成控制路徑、實驗補丁計畫與原廠機器碼模擬，尚未證實能提高實際尼特數。** 本目錄的工具沒有相機或 USB 存取路徑。

原廠手動最高檔的 LCD 命令，已經與原生細調 **99** 完全相同。沒有找到原廠允許範圍內尚未使用的最高亮度。細調表另含 **100** 的資料，但原廠驅動明確拒絕這個值。僅憑未使用表格資料，不能判定面板支援、安全範圍或實際發光量。

## 可重現的結果

| 路徑 | 六個命令資料位元組，依驅動寫入順序 | 模擬結果 |
|---|---|---|
| 原廠手動索引 6，最高檔 | `FF FF 48 59 77 FF` | 送出命令 |
| 原廠細調 99 | `FF FF 48 59 77 FF` | 送出相同命令 |
| 原廠細調 100 | 無 | 底層回傳 `FFFFFFFF`，不送出命令 |
| HAL 細調 100 | 無 | 上層回傳 `0`，底層仍拒絕，不能以成功碼認定生效 |
| 實驗候選：最高檔的 `77` 改為 `7A` | `FF FF 48 59 7A FF` | 模擬會送出；實際面板效果未知 |

`77 → 7A` 是十進位 **119 → 122**。這是命令資料，沒有證據可將其比例解讀為尼特數、PWM 占空比或 LED 電流。也未確認它只影響背光而不影響其他面板特性。

實驗計畫只修改手動表 `0xC2EFEDA6` 的一個 byte，對照的值來自細調表中被拒絕的第 100 格。它不移除驅動上限，也不產出可上機的 AutoRun、sup 或卡片包。套用與還原函式只接受完整、已知的 42-byte 表格前後影像；任何不同的內容都拒絕。

模擬另確認：如果最高檔已被快取，單改表格再要求相同檔位，不會重新送出命令。這個原型不包含相機上的快取失效或狀態切換方案。

## 工具與輸出

- `firmware.py`：分區讀取、韌體 SHA-256 核對、原廠數值表、實驗計畫及本機 byte 字串還原。
- `build_offline.py`：產出分析與補丁計畫 JSON。它不執行模擬，也不修改韌體原檔。
- `emulate.py`：依既有 `fpSup/fp_usb_shell/test_splash.py` 的嚴格執行範圍原則，執行真正的原廠 Thumb 機器碼；使用原廠資料段中的描述表與命令序列。
- `test_brightness.py`：11 項測試，含所有 7 檔、細調 1–99、非法邊界、HAL 假成功、冷／暖快取、完整還原、非預期程式執行與故意改壞的模擬變體。
- `validate_offline.py`：執行測試並保存韌體與程式雜湊、模擬邊界、命令樣本及測試紀錄。缺少 Unicorn 或執行失敗時不會報成通過。
- [`artifacts/20261024-offline/`](artifacts/20261024-offline/)：本輪分析、實驗補丁計畫、模擬證據與測試紀錄。

從儲存庫根目錄執行；Python 需可執行 Unicorn：

```sh
python3 -B projects/lcd-brightness/build_offline.py --out projects/lcd-brightness/artifacts/20261024-offline
python3 -B projects/lcd-brightness/validate_offline.py --out projects/lcd-brightness/artifacts/20261024-offline
```

受限 macOS 環境可能封鎖 Unicorn 的 JIT 執行記憶體；這是主機模擬環境限制，不能解讀成韌體測試通過或失敗的硬體結論。

## 韌體來源與控制路徑

必須分別讀兩個 DFI 區段。當前工作目錄的 `out/MAIN_c0000000.bin` 尾端仍含過長解壓資料，不能用它讀 `0xC2EF6E00` 以後的資料段。既有 `tools/unpack.py` 已註明這個陷阱；本輪不修改任何韌體來源檔。

| 區段 | 長度 | SHA-256 |
|---|---:|---|
| `out/seg0_c0000000.bin`，`C0000000` | 49,245,696 | `aaa5208a028d9c4aebb9cc8614add723d456e96b2a95914f433079954320e622` |
| `out/seg1_c2ef6e00.bin`，`C2EF6E00` | 236,032 | `0dcaca8f5441fe4ddc6ed801cb888e325df4e76006e4f53a1c3219809b22ce7b` |

| 位址 | 靜態與模擬支持的意義 |
|---|---|
| `C00AD338`，ARM | `MenuItemLcdBrightness::v3`：選單值 1–7 轉成手動索引 0–6；其他值設定自動旗標 |
| `C0308208`，ARM | `XC_DisplayLcdJDI_LPM032M366C_Brightness::v2`，組裝模式與數值後交給 HAL |
| `C0625F20`，Thumb | HAL：模式 1 接受 0–100，但忽略底層回傳碼；模式 0 的完整路徑未納入本輪模擬 |
| `C00FA4F0`，Thumb | 原廠手動表處理器，低 byte 索引必須小於 7 |
| `C00FA940`，Thumb | 原廠細調處理器，只接受 1–99；100 在讀表和命令更新前被拒絕 |
| `C2EFED84`，42 bytes | 6 欄 × 7 檔原廠手動表 |
| `C07CACA0`、`C07CACD4` | 細調低段／高段查表；高段第 `value - 50` 格才是實際索引 |
| `C2EFED48/4C/50` | 模式組、手動檔位與細調快取；互相失效會改變後續是否送命令 |
| `C31D715C` | 原廠狀態欄位；本輪明確建立 ready=2、非 ready=0、抑制=1 的測試場景 |
| `C2EFF150` | 由原廠初始化路徑選用的描述表根；本輪在模型中明確設定 |
| `C2EFF7E8`、`C2EFF8B0` | 原廠手動／細調命令序列，各 25 筆 |
| `C00F4560` | 原生命令分派器；模擬在此攔截，核對指標、長度、6 個資料字與未改動的其他命令欄位 |

反編譯交叉來源：`out/decomp/full/blk_c00.c`、`blk_c03.c`、`blk_c06.c`。最終數值來自具有上述雜湊的實際位元組，沒有把反編譯文字當作可執行韌體。

## 驗證邊界與後續缺口

測試證實的是模型內的控制流程、命令內容與還原邊界。它會檢查 `r4–r11`、SP 還原，拒絕執行任何未列入範圍的原廠程式，也拒絕命令資料與快取範圍以外的寫入。原廠函式本身不一定符合 8-byte 呼叫點堆疊對齊，因此這裡不把對新注入程式的 ABI 規定錯套成原廠保證。

故意改壞的測試只作用於獨立模擬記憶體：把候選改成 121 時，命令一致性檢查會失敗；移除細調上限分支時，100 拒絕檢查會失敗。原始檔案不受影響。

要判定是否真的增加尼特數，仍需釐清面板命令的電氣意義及允許範圍，再於獲授權的硬體試驗量測相同白場、設定與穩定時間下的亮度。自動亮度執行緒、完整開關顯示流程、原生匯流排傳輸、功耗、溫升與長時間穩定性均未由本輪證實。**目前不能宣稱大幅提亮，也不能把這份實驗計畫當成已驗證的上機版本。**
