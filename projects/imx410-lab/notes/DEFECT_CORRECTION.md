## 1. 什麼時候把表載進 DEFC

唯一的載入函式是 `FUN_c030e2a0(ctx=0xC343A66C, mode, enable, step, xlate)`;唯一寫 0x300F0D84 的是 `FUN_c0633778`,只經 `FUN_c0635d80` 從 `c030e2a0` 進來 [C,整份 decomp 內]。

| 呼叫點 | 路徑 | 參數 (enable, step, xlate) |
|---|---|---|
| `FUN_c0314708` +步驟 10(blk_c03:15316) | SetImgMode_s 與 FrameExpos_s 都會先跑 | (0,0,0) → **關閉 DEFC** |
| `FUN_c03149b0`(15395) | **SetImgMode_s 的後半 = LV/錄影換模式** | (1,0,0) |
| `FUN_c031b3a0`(19524) | LV 放大(只對放大表內的模式 10、3) | (1,step,1) |
| `FUN_c0317e58`(17369) | FrameExpos_s 0xC0315BD0 → 靜態拍照,每幀在 PreExpos_s 之後 | (1,0,**1** 只在 R68+08≠0 且 曝光 `+0x28` ≥ 0x7A121(>0.5 s)且 `+0xB`=0;否則 0);暗場等旗標時 (0,0,0) |
| `FUN_c0318e10`(17906) | 拍照結束,恢復 | (1,0,0) |
| `FUN_c030cd18` | shell `imager defect_collect_off` | (!flag,0,0) |

錄影沒有自己的呼叫點,用的就是 SetImgMode_s 那次 [C 無其他呼叫者;I 錄影=同一模式切換]。

`c030e2a0` 內部 [C]:
- `imager+0xCD`(defect_collect_off)≠0 → 當成 enable=0。
- **vtable +0x8c = v33 `0xC0324FD8`**:目前模式(imager+4)∈ {0x66,0x6C,0x7C,0x98} = {102,108,124,152} 就**強制 xlate=1**(不管誰呼叫)。v33 只有這裡用。
- 表 id = R68+04;若 R68+08≠0 且 xlate → 改用 R68+0C。
- xlate=0:**直接把目錄裡那張表的位址交給硬體,不做任何平移**。
- xlate=1,依序:
  1. 模式在放大表(desc+0x128,stride 0x5C)且 desc+0x11C(=1)→ `FUN_c030fd68`:用放大表 `+0x20+4·step` x0、`+0x2C` w、`+0x38` y0、`+0x44` h 平移(模式 10/3:y0 = 0/1010/2020)。
  2. 否則 v33=1 → **`FUN_c0310410`:只平移裁切**(R68 +10 x0、+14 y0、+18 w、+1C h),無縮放。
  3. 否則 R68+08≠0 → **`FUN_c0310740`:平移 + 座標換算 + 重排 + 重新編碼**。
- desc+0x94(ROM 0xC0B5F94C)= 0 → IMX410 走「單表」分支,只用 `FUN_c0635d80(2,…)`,第二表(0x300F0DC0/DC4)不用 [C]。

## 2. 平移在哪條路上跑

| 函式 | 何時 | 結論 |
|---|---|---|
| `FUN_c0310410` | xlate=1 且 v33 | **LV/錄影/拍照都會跑,但只限 102/108/124/152** [C] |
| `FUN_c0310740` | xlate=1、非 v33、R68+08≠0 | 只有 >0.5 s 靜態拍照(以及放大表外的放大,原廠不存在)[C] |
| `FUN_c030fd68` | LV 放大 | 只模式 10/3 [C] |

非 v33 模式的 LV/錄影 **完全不平移**;硬體也沒有原點暫存器:`FUN_c0633778` 只寫 0x300F0D84(表位址)、0x300F0D00(=1)、0x300F0D80(=0x101)、0x300F0380(=1)、0x300F0E00..0FFC(128 個點)、0x300020EC bit0;韌體內建 dump `FUN_c01597b8` 的 DEFC 區只有 0x300F0D00、0x300F0D20 兩組,沒人寫 0x300F0D20 [C]。所以**平移全靠軟體**。

座標系 [I,強]:表座標 = **校正模式的 receiver 窗格(TIM x0/y0 之後)上的像素座標**。證據:v33 模式 102 用表 7 裁切,R68 窗 = (944, 616) = (TIM102.x0 − TIM7.x0, TIM102.y0 − TIM7.y0) = (952−8, 970−354);模式 95 的 x = 184−8 = 176,y 另含感光元件窗起點差(412)。DEFC 比對的是進 CRCT 那條串流的行列計數,不是感光元件絕對座標。
所以原廠 mode 95(MONIT1_24_HD)在 LV/錄影用表 97 原樣 → 偏 (176, 412)[C 路徑;I 後果]。

## 3. 表的格式與位置

**位置** [C]:flash(NAND)分割區 **0xF**(`FUN_c0041f78(…,0xF)`,PromDriver)整塊 0x40000 B 讀進 heap(class 0),指標存 **`*0xC343A71C`**(+0x10 = dirty 旗標),第一次 `c030e2a0` 時 lazy 載入(`FUN_c051e488`)。`SensorAdjustSeparate` vtable(0xC0D00930)+0x14 回 0 → 用小格式(0x40000;大格式 0x200000 / 目錄 +0x60000 不用)。

**目錄**(buf+0x16000)[C,`c030e2a0` 讀、`FUN_c05211b0` @blk_c05:24868 建]:

| 偏移 | 內容 |
|---|---|
| +0x000 u32 | 1 = 有效 |
| +0x004 u32 | 表數 n(≤64) |
| +0x008 u16[64] | 表 id(= 校正模式 id,依 R68 列順序;建表條件 R68+00 == R68+04) |
| +0x088 u16[64] | 每張表大小(u32 字數) |
| +0x108 u32[64] | 第二表位移(雙表模式用,IMX410 不用) |
| +0x400 | 各表依序緊接(第 i 張起點 = +0x400 + 4·Σsize[<i]) |
| buf+0x40000 − 0x100·(i+1) | 第 i 張的**點清單**:64 個 u32 `x | y<<16`,0xFFFFFFFF 結尾 |

找 id:線性掃 ids[0..n),找不到 → `return 0`,**不寫硬體**(換模式時第 10 步已關閉,所以結果是乾淨的關閉)[C]。

**表格式**(u16 串流)[C,由 `FUN_c0310ce0` 產生、`c0310410` 解析]:
- `0x8000 | y`(bit15)= 行標頭,y 在低 13 位元。
- 其後 `x | flags`:x 低 13 位元;bit13(0x2000)= x+2 也是壞點、bit14(0x4000)= x−2 也是(同色相鄰,`FUN_c0310ac0` 設)。
- 結尾 **4 個 0xFFFF**。
- 依 y 再 x 升冪(`FUN_c0310e90` 基數排序)。
- 硬體限制:同一行內任 5 個連續點必須跨 ≥12 px(一個 receiver 字);超過的放進點清單(→ 0x300F0E00,最多 127 個)。
- 座標單位 = 該表校正模式的輸出像素:1x1 表(97/6/7/130)是 1x1 像素,2x2 表(98/27/88/131)是 2x2 輸出像素,3x3 / 3x6 同理 [I,因 LV 直接用]。

**座標換算型別**(R68 +0x20 = x 型別、+0x24 = y 型別、+0x28 = x 偏移、+0x2C = y 偏移;`FUN_c03111e8(type, off, c)` 對 (c+off))[C]:
0 = 不變;1 = /3,c%3==1 丟掉;2 = /3,c%3==1 進位;3 = 6 行一組(3x6 用)只留特定相位;7 = `(c&1) + (c>>2)*2`(2x2 同色合併);4/5/6 = 不變。
`c0310740` 先減 (x0,y0) 再換算,超出 META 寬高(`c032c860`)的丟掉。
**更正舊說法**:+0x2C 不是工廠參數,是 y 偏移;工廠參數從 +0x30 起。

**寫回 flash** [C]:`ImagerPowerOff_e` 0xC0315640 → `FUN_c051e720`:dirty 時先把 0x10000..0x40000 從 flash 讀回覆蓋 RAM,再寫回、釋放 buffer → RAM 裡改的目錄**不會**被這條寫進 flash,但 buffer 會被釋放、下次重載。Pixel Mapping(`c05211b0` 等,經 `FUN_c051e030` 寫整塊 0x40000)會把目錄 memset 0xFF 後依 R68 重建 → 注入項被清掉,但**此時若 R68 被生成表換掉,重建結果會寫進 flash**(危險)。

## 4. 結論:生成模式能不能拿到正確修正

**(a) 只填 R68 欄位、指向現有表:有限度可行。**
- 非 v33 的 host id(例如放大用的 10):LV/錄影/短曝拍照都**原樣**用 +04 那張表。只有當新模式的 raster 原點與該表校正模式相同(同 binning、同 TIM x0/y0、同感光元件窗起點,也就是「左上角對齊的裁切」)才對;+10..+2C 對 LV 沒作用 [C]。超出 raster 的表項原廠就會送(v33 的 w = 4716 打錯、mode 95)且照常運作 [I]。
- 若 host id 是 102/108/124/152(v33),LV 也會跑 `c0310410`:+08=1、+0C=來源表、+10..+1C = 新模式原點 − 來源表原點(偶數保持 Bayer 相位 [I])→ **任何同 binning 的裁切都正確**。不能換 binning。
- 換 binning(或沒有同 binning 的來源表)只有 >0.5 s 拍照會走 `c0310740`。

**(b) 一般解:自己準備表。** 兩種做法,都不改程式碼本體:
1. **讓韌體自己算**:callfn `FUN_c0310740(0xC343A66C, mode, size_words, out_tbl, out_list(0x200 B), src_tbl)`,R68 那列填 +10..+1C 裁切窗(1x1 座標,相對表 97 原點 x=8,y=40)與 +20..+2C 換算型別/偏移;回傳 1 即 out_tbl/out_list 是正確格式。注意它的暫存區用 **class 10**(錄影配置器)→ 只在非錄影時做。
2. **掛進目錄**(零 hook):在 `*0xC343A71C` 的目錄加一項:ids[n] = 不是任何模式 id 的新 id(**不可等於模式自己的 id**,SensorAdjustment 會誤當校正模式)、size[n] = 字數、表放在最後一張之後、點清單放在 buf+0x40000−0x100·(n+1)、n++;R68 +04 = 新 id、+08 = 0。之後 LV/錄影/拍照全部走原樣路徑。空間未知(要上機讀目錄);buffer 被釋放重載(`*0xC343A71C` 變了)要重新注入;做 Pixel Mapping 前要先卸下生成模式。
3. 不碰 flash buffer 的替代:hook `FUN_c0635d80`(0xC0635D80,只轉呼叫 `c0633778` 的包裝),目前模式 = 生成模式且 r0==2 時換成自己的 `{表位址, list[128]}`;或把 vtable 0xC0B5FCC0+0x8c 換成自己的 v33 讓 host id 也走 `c0310410`(只解同 binning 裁切)。

位址/快取 [I]:硬體位址 = (ptr − 0x40000000)>>2,ptr < 0x40000000 會被拒;韌體直接給 heap 指標、寫完不清快取 → 自己的表用與韌體 heap 相同的別名配置,寫完做快取清理(`FUN_c000e91c`)。
