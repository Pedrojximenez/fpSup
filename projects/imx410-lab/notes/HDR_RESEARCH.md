## 1. 結論一覽

| 方法 | 狀態 | 能多多少 | 代價 |
|---|---|---|---|
| 時域交替曝光（SHS 每幀交替） | [M] 可用 | 不限（常見 +2~+4 級），基準 ISO 也有效 | 移動物殘影，有效幀率減半 |

## 2. 空域棋盤的機制（已確認）

- 暫存器分工 [M]：`0738` = 第二條讀出路徑的**列位址錯開量 V**（也決定倍率 k）；`0242` bit0 = 哪幾組欄（每兩欄交替）用這條路徑 → 2×2 格棋盤；`023A` bit0 = 共用像素對中哪一列用這條路徑。
- 壓暗樣本**不是溢出、不是數位增益** [M]：跟快門成正比；全亮組飽和後仍繼續上升。
- 讀出時間 [M]：120 Hz 閃爍測試，壓暗樣本的閃爍相位對應第 y+V 列（0x20 → −36 列、0x40 → −59.5 列、0x00 → 0）→ 是那個像素在自己正常的時間、走低增益路徑讀出，再放到輸出第 y 列。
- 容量 [M]：電壓擺幅上限，約 0 dB 滿井的 1/5；隨類比增益放大，不隨 HCG 變 → 限制在電荷轉電壓之後、類比放大之前。
- 推測 [I]：原廠用來做快速預讀（測光/防閃爍/對焦）的路徑，不是設計給 HDR 的雙增益。

## 3. 能多幾級（多出的高光，相對全亮組飽和點）

| 條件 | 綠 | 紅藍 |
|---|---|---|
| 0 dB、HCG 關（≈ ISO 100） | 負（先飽和） | 負 |
| 0 dB、HCG 開 | +1.6 | −0.2 |
| +12 dB | −0.5 | −1.3 |
| **原廠 ISO 3200（26.4 dB、LCG）** | **≥ +3.8** | **+2.2** |
| +30 dB | +2.3（V=0x20） | +1.65 |

- V 越大，可救越多（ISO 3200：0x60/0x80 紅藍 ≥ +2.6，未到頂），但壓暗樣本 DN 越小、高光雜訊越重 → 預設 V=0x20。
- 以 **2×2 輸出**為比較基準（每 2×2 格每色 2 全亮 + 2 壓暗真實樣本，不補值）：暗部 −0.5 級（一半光被浪費）。
- 基準 ISO 無效：像素滿井 ≈ AD 範圍，上面沒有可救的。

## 4. 合成（PC 端，`hdr_ml.py`）

1. 壓暗組對位：位移 = V 列（固定公式）。
2. 換到同一亮度刻度：**用校正曲線（每個增益/HCG/V 一條，曝光掃描 `calib_att.py` 建立）**，不要每張現場擬合（V 大時會失敗）。
3. 熱點、欄相位（col%16=1/5/9 在強垂直梯度處讀錯）修補。
4. 可信度：全亮樣本接近飽和時（看 5×5 最大值）四色一起交出；壓暗樣本只用在全亮已飽和處。
5. 不可信像素用另一增益的同色鄰居補（G 方向加權，R/B 色差）→ 色度中值 → 一次 Hamilton–Adams 去馬賽克。
- 待做：高光區大範圍色度降噪（讓 V=0x40/0x80 可用）；頂部 V 列無壓暗資料要裁掉；快門不可短於 V 行。

## 5. 走過的彎路（避免重犯）

- 早期把 k 當成「+4/+5/+5.9 級」——那只是倍率，不是可用範圍；真正上限是壓暗路徑的容量。
- v1–v4 合成的暗帶、梳紋、彩環，根因是**沒做 V 列對位**，不是混合演算法。
- 「單幀紅色推估」版本（hdr_color.py）在發現棋盤之前做的，已被棋盤取代。
- 分析時要避開壓暗組接近自身上限（~455 DN @AE 增益）的像素，否則閃爍/線性量測會被壓縮扭曲。

## 6. 14-bit + 空域 HDR（2026-10-20，`l7.py t3`）

- 1×1、14-bit AD（mode 0 的 Family A + `0001=29`）、HMAX 911、14-bit 接收與 DMA，加 `0242=01`、`0738=0x20`：可用。
  合成：`hdr_ml.py` 已支援 14-bit（frame.json `bits=14`，飽和 16378）；此模式頂部只有約 7 列暗區（影像從第 8 列起）。
- 結果（ISO 3200 設定）：燈罩恢復、無色帶；暗部有零星冷像素未修（壞點門檻照 12-bit 設，待調）。
- 意義：高光同 12-bit（壓暗路徑容量決定），暗部 14-bit 讀出雜訊約減半，可能抵銷棋盤的 −0.5 級；代價 29 fps、捲簾約 26 ms。
- 未量：同場景 12 vs 14-bit 的暗部雜訊實測。

## 8. 感光元件垂直 2:1 + 棋盤 HDR（2026-10-20，`l7.py vhdr`，`captures/vhdr/`）

- 原理：垂直合併加的是同一欄、相隔兩列的同色像素 → 同一組（同全亮或同壓暗），棋盤不被破壞；水平合併會把 a、b 兩組混在一起（L6 失效的原因）。
- 設定：L3 的垂直 2:1 組合，但 `0242 = 0x2D`（= 2C 垂直合併 + bit0 棋盤）、`0738 = 0x20`。
- [M] 比例（對同樣垂直 2:1 不開 HDR）：R a 0.133 / b 0.997，Gr 0.107 / 1.000，Gb 1.019 / 0.107，B 0.860 / 0.116 → 與 1×1 一樣乾淨。
- [M] 壓暗組列位移在合併輸出中約 **17 列**（感光元件 32 列 ÷ 2 + 1）；`hdr_ml.py` 自動量得，合成無色帶（`hdr_v2.png`）。
- 意義 [I]：等同 2×2 HDR（水平 2:1 在後製）；垂直相加的訊噪比收益應能抵銷棋盤的暗部 −0.5 級；只讀一半的列 → 捲簾減半。未量：暗部雜訊實測。

## 9. 找「每四欄」分組（讓水平合併也能保留 HDR）——沒找到（`col8.py`，`captures/col8/`）

背景開棋盤（0242=01、0738=0x20），掃 0242 其他位元、0236–024F、0270–027F、08B0–08BF、05A8–05AF、0726、0790–079F，775 張。
- 0237/023A/023C/023D：仍是每兩欄週期（換組或破壞影像）；05A9/05AA–05AD：只改壓暗程度（例 ×0.7–0.8）。
- **0277 = 04**：每 8 欄出現「全亮、0.55、壓暗、0.54…」——一半像素 =（全亮 + 壓暗）/2，是相鄰兩欄讀出被平均，不是四欄分組，對 HDR 無用。
- 結論：感光元件只有每兩欄的切換；2×2 HDR = 感光元件垂直合併 + 後製水平處理（§8）。
- 螢幕預覽看到的是垂直條紋（每兩欄冷暖/亮暗交替），因為每格上下排的差異在去馬賽克縮圖時被平均掉，欄間的色彩組成差異留下來。

## 10. 水平交給 RWZM？——不行（2026-10-21）
RWZM 是線性縮放（同色相鄰加權平均），水平 2:1 會把全亮與壓暗平均在一起；HDR 合成是非線性選擇，必須在任何水平合併之前。
可行順序：感光元件垂直合併 → HDR 合成（依亮度選擇、換刻度）→ 縮放。機內做法：A 錄棋盤 RAW、電腦端合成（現在可做，對應需求的 PC 合成工具）；
B 機內先合成再給 RWZM（需 CPU 或 ISP 的查表/比較區塊 + 緩衝 V 列，待研究）。
