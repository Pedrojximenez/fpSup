# IMX410 模式表的消費者 —— 每個欄位最後去了哪裡

韌體 5.02,純靜態分析(MAIN_c0000000.bin + Ghidra 全反編譯 `out/decomp/full/`)。
[F] = 直接從程式碼讀到;[I] = 推論。位址都是函式入口或指令位址。
腳本在 scratchpad `mt/`(fn.py / foot.py / dumpt.py),不在 repo。

## 0. 結論先講

1. **readout-mode 值(R10)確實有自己的表**,而且有四張,都在 ROM 0xC07D1600 一帶,用 R10 的值(0..7)查。[F]
   但 **值 3(mode 10)和值 5(mode 8)之間只差一個欄位**:前端時脈除頻
   `0x30000A08[14:8]`(值 3 = 0x0B → ÷12,值 5 = 0x17 → ÷24)。SLVS-EC 實體層/通道表、
   `0x300F1080` 的 nibble 全部一樣。[F]
2. 這個時脈是前端「每時脈 12 像素」的處理時脈:f = 1152 MHz ÷ (欄位+1)。[F 公式,I 用途]
   用它算每一個原廠模式的「每行最少要多少 HMAX」= 每行字數(12px)÷ f × 72 MHz,
   70 個模式全部 HMAX ≥ 這個值(最緊 1.067 倍),沒有一個違反。[F 計算,I 結論]
   **mode 10 的下限正好是 506 字 ÷ 96 MHz × 72 = 379.5** —— 就是你們量到的「HMAX < ~380 就隔行掉線」。
   也就是說:掉線的那一級還在用 **mode 10 的 6072 像素寬窗(506 個 12px 字)** 在處理每一行,
   時脈本身(96 MHz)比 mode 8 原生的 48 MHz 還快,不是時脈不夠。[I,但數字吻合到 0.1%]
3. 為什麼「把不同的 CRCT/receiver/BUFA 暫存器抄過去」沒用 [F 機制,I 套用]:
   - CRCT(其實是 **DCLP**,見 §R38)的設定由 `FUN_c0320ab0(obj, 目前模式 id, 1, 0)` 依表重寫,
     而這個函式在每幀的 AE 回呼 `FUN_c0313658`(0xC0313658)裡會再被呼叫(條件見 §4)。
     目前模式 id 還是 10,所以它會把 mode 10 的 R38 列(水平字數 0x1FB=507)寫回去。
   - receiver 的窗(0x3010000C / 0x30100024 / 0x300F1084 / 0x300F021C)只有在真正的模式切換
     `FUN_c0320008` 裡寫一次。
   - readout 鏈 `FUN_c0128ad0` 有**快取**:值沒變 + `0x30100B08 != 0` 就整段跳過(0xC0128B18–B28)。
4. 「虛擬模式」最乾淨的作法:**不要事後補暫存器,讓韌體自己做一次完整的 SetImgMode_s**。
   七張表 + REG 表都是透過 RAM 裡的描述子 0xC2F1E654(和 0xC343B67C)取指標,
   描述子在 RAM、表在 ROM → 把表複製到 RAM、加一列新模式、改描述子指標與筆數即可。
   找不到模式 id 時六張表**默默回第 0 列(mode 0 = ACQ 全幅 HMAX 911)**,REG 表回 -1(讀到垃圾)。
   另外韌體已內建兩個除錯掛鉤(§6):`imager mode_reg_add` / `mode_reg_test`(切換時追加最多 10 個感光元件暫存器)、
   `imager hpixsiz_test`(覆寫 SoC 同步產生器的 HMAX/尾段/VMAX,只能**加大** HMAX)。

建議的單一驗證(不用改表):在 mode 10 + 合成 mode 8 的狀態下把 `0x30000A08[14:8]` 從 0x0B 改成 0x07(→144 MHz),
若掉線門檻從 ~380 移到 ~253(=506/144×72),就證實是「某一級仍以 506 字/行在跑」;改成 0x17(48 MHz)門檻應跳到 ~759。
韌體自己就是直接寫這個欄位(0xC0127CB4–CC6,PLL 字 0x30000034 不變時不重鎖),但它是在 receiver 停著的時候寫的(§5 步驟 5→15)。

## 3. readout-mode 值鏈(R10 值)完整解碼

`FUN_c0635ED8(&{值, x0|x1<<16, y0|y1<<16})`(0xC0635ED8,Thumb)依序 [F]:

1. `FUN_c0124F80(值)` → 存 0xC31D89AC(**只寫不讀**,整個映像沒有讀者)。
2. receiver 窗:0x3010000C、0x30100024、0x300F1084(見 TIM)。
3. `FUN_c0124F98(值)`:
   - `FUN_c01287C0`:**不看值**。0x30100000 = (舊值 & 0x600000) \| 0x201008;0x30100048/4C/54/58/5C/78/290 = 0;0x301001E4 = 0x100;0x30100080 = 0x11000;0x301001E0 = 0x1001010;0x300F10C8 = 0x10;0x30100184/204 = 0x3FFF;0x30100188/208 = 0x3FFFF。
   - `FUN_c0125010` → `FUN_c0128978`:**0x300F1080[3:0] = 表 A[值]**。
   - `FUN_c0128AD0(值)`:**快取**(0xC2F14A50 = 上次的值,0xC2F14A4C = 再上次)。
     若 `0x30100B08 != 0 && 值 == 上次 && 旗標 0xC31D8E7D == 0` 就整段跳過(0xC0128B18–B28)。否則:
     - `FUN_c01283E0` 查表 B → `FUN_c0127C80`:**PLL 0x30000034**(不同才重鎖,`FUN_c0127BE8` 等 0x30000000 bit8)、
       **0x30000A08[14:8]**、0x30000A0C[6:0]、0x30000A10(遮罩 0x03310006)、0x30000A20 = 0。
     - `FUN_c0128448` 查表 C(→ 沒人用的暫存區)與表 D → `FUN_c0128B68`:SLVS-EC 實體層 —
       0x30100800、0x30001290、0x300EA024..0x300EA3A4(8 通道)、0x300EA424..0x300EABA4 = 1、0x300EB004..284 = 2、
       0x30100B00、0x30100B28 = 0x22222222、0x300E1004..1020(通道對應 nibble,0x76543210 → 直通)、0x300E1030..10BC,最後 0x30000880 bit16。
   - 0x300F082C / 0x300F091C / 0x300F077C:[29:14] = 0x80(固定)。
4. 0x300F10C0[19:16] = x0 % 12;0x300F021C = 補白。
5. 寬度 = `FUN_c01250E8(0)`;**≥ 0x1CE1(7393)才設 0x300F0C4C bit4 與 0x300F0010 = 1**。IMX410 最寬 6064,所以永遠 0。
6. `FUN_c0630540/570/af8/b28/fc8/ff8(0)`。

第二路 `FUN_c0636048`:0x30100310/314、0x300F3084、0x300F30C0、0x300F221C,`FUN_c0124FF0` → 0x30100334/300/324/330 固定、**0x300F3080[3:0] = 表 A[值]**、0x300F3000 = 0x13300000。[F]

  (Julien 是把選擇器 108 → 100,見 `research/other/external/sigma-fp-supmod-R120/JULIEN_14BIT_AND_MODES.md`)。
- 兩條路與我們的放大路徑的差別只有:**(1) 放大會跑 v32 改感光元件窗;(2) 上層 base 尺寸固定為 mode 10 的 6064×2022,META 較大就裁切**。
  沒有任何 14-bit 專屬的額外步驟(接收端位元深度已由 R10 = 2 處理)。

### 7.5 建議

**A. 首選:虛擬模式期間把描述子 +0x11C 清 0(RAM 0xC2F1E770 一個 byte),離開放大後寫回 1。** [I,依 §7.1 的 F]
- 效果:`FUN_c031B3A0` 整個跳過 → 不呼叫 v32,donor REG 列自己的 0003/0022–0025 保留(mode 8 = 不開窗全高 1344、mode 6 = 993/1087、mode 0 = 不開窗 4042);
  缺陷表與 AF 換算改走 R68 / 非放大路徑(對 donor 反而正確)。
- 等同原廠 14-bit 錄影模式的進入方式(§7.4),接收窗與感光元件窗一致。
- 要在按 OK **之前**清,因為 v32 在 `FUN_c03149B0` 內呼叫;不改的話別的 donor 也都受 1069/2022 限制。

**B. 若要保留放大的 AF/段功能:複製放大表到 RAM、改描述子 +0x128 指標**,mode 10 列改成 donor 的窗,三段寫成一樣(讓選段無關):
`+0x1C = 0`、`+0x38[0..2] = donor 起始實體列`、`+0x44[0..2] = 2 × donor 列數暫存器`。
donor REG 有窗就抄(mode 6:993 / 1087×2 = 2174);沒窗的(0、8、98、139)用置中值 `(4160 − vbin×H)/2`、列數 = H(偶數向上)——
例:mode 8 起始 (4160−4032)/2 = 64、+0x44 = 1344;mode 0 起始 59、+0x44 = 4042(v32 仍會寫 0003=1,窗必須包住整個 donor 讀出)。[I]
**不要把 +0x12C 筆數改 0 或把 host id 換成表外的 id**:找不到時 `FUN_c031B3A0`(local −1)與 v32(0xFFFFFFFF)都會讀表前 0x5C 的垃圾當窗。[F]

**C. 14-bit donor 另外要注意** [I]:
- META 比 6064×2022 大的 donor(mode 0 的 4042 列、mode 6 的 2174 列)會被 ContSet_Adr1 置中裁切到 2022 列再進 BUF-A
  (mode 6 裁 76 列);若要整幀,donor 的 META +4/+8 要 ≤ 6064×2022,或另外改 BUF-A 窗。
- mode 0 = 19.1 fps(HMAX 911 × VMAX 4132),每幀 52 ms;等待時間由 `c032CA20` 算,不會出事。
- 上機前先只做 A(清 +0x11C)+ 12-bit donor 8,驗證「1344 列全有影像」= 證實 v32 是限制;再試 mode 6(窗自洽、2174 列裁 2022)、最後 mode 0。
- 卡死診斷:看 `imager mode_now` 的 frame_count(VD,同步產生器)是否在走、trans_count 是否停住;只走前者 = 接收端/BUF-A 等不到幀尾。
