# VMAX 到底去了哪裡(離線,2026-10-21)

純靜態:MAIN_c0000000.bin(Thumb-2 全域掃描,解出 movw/movt 與 ldr-literal 基底)+ Ghidra `out/decomp/full/` + 既有傾印
`captures/vmaxsrc2/dumps.json`、`captures/soc_m8_m10.json`。掃描腳本:scratchpad `vsrc/scanst.py`(不在 repo)。
[C] = 程式碼/資料證明;[I] = 推論。

## 0. 結論

1. **前提要修正 [C]**:mode 98 和 143 的 REG 列**不是完全相同**,差一個暫存器:`0016` = 0x14(98)/ 0x32(143)。
   但 `0016` 不隨 VMAX 走(例:104/111/113 同為 0x23,VMAX 3640/7280/9100;8 與 139、143 同為 0x32),所以它不是幀長。
   **韌體從不把 VMAX 寫給感光元件** —— 161 列表、v32、v16、v27、每幀 0005–0008/003D–0040/041F… 都沒有 VMAX 衍生值。[C]
2. **時序表 VMAX(+8)寫進硬體的地方全映像只有一個 [C]**:`FUN_c01265c0` 0xC012660E `str.w ip,[r4,#0x1c]` → **0x30100020 = (VMAX−1)<<16**。
   Thumb 掃描 0x30100000–0x30100FFF 共 309 個存取,0x30100020 只有這一個 store(另有 `c0126480` 初始化/關閉寫 0)。
   沒有第二個 VMAX 暫存器、沒有其他 SoC 區塊收到 VMAX。
3. **直接證據 [M+C]**:`vmaxsrc2` 用同一 donor 98 只改 TIM VMAX(2094 vs 4188)走完整模式切換後傾印 0x30100000/0x30000000/0x300E0000/0x30182000/0x30002000:
   設定類暫存器的差異**只有** 0x30100020(0x082D0000 / 0x105B0000)、0x30100048 [26:16](1 / 0,AE 的整幀數,見下)、
   0x30100054 與 0x30100120(0x3F / 0x7E,≈VMAX/33,管線側,見 §3)。其餘是計數器/狀態。行計數 0x30100590[29:16] 在 4188 時讀到 2550、2181(> 2094)→ 完整切換後 SoC 確實跑 4188 行。
4. **所以真正的 XVS 來源仍是 0x30100004/0x30100020 這個 SoC 同步產生器**;§46 的「改了 0x30100020 感光元件不跟」最可能是
   **寫法不對,不是位址不對** [I]:韌體從不在產生器運行中單獨改 0x30100020,一定伴隨「停 → 寫 → 啟動提交」(§2)。
   推測:幀計數/VD 中斷直接讀活的 0x30100020,而送往感光元件的 XVS 輸出用的是**在啟動/提交時鎖存的副本**。
5. 佐證 0x30100048 是 XVS 輸出控制 [C 機制 / I 名稱]:`FUN_c0321398` 把長曝光拆成「整幀數 + 餘數」,餘數 → SHS,整幀數 → `FUN_c0125f68` → **0x30100048[26:16]**;
   這正是 Sony slave 長曝光的作法(遮掉 N 個 XVS,感光元件看到 (N+1)·VMAX 的長幀)。`FUN_c01289d8` 每次寫完 HMAX/VMAX 都 `0x30100048 |= 0x60000000`(bit29/30,推測 XHS/XVS 輸出致能)。

`c0125a40(0)`(0x30100050 ^= 1;0x30100060 行欄 = 0、^0x10000)→ 等 12 行 → RAM 旗標 → `c0128a88` → **0x3010006C = 1** → `c0125740(1)` →

## 3. 其他與 VMAX 成比例的值 [C 寫入點 / I 意義]

- 0x30100054:LV 中 98/V=2094 → 0x3F、V=4188 → 0x7E、mode 10 → 81、mode 8 → 848(不是單純幀長)。寫入點只有 `c01287c0`(= 0)與 `FUN_c0179360` 0xC0179430/40(= 管線參數 +2,預設 2);同一函式寫 BUF-A 0x30182180..。屬影像管線側,**不是感光元件同步**。
- 0x30100120:`FUN_c0156300` 從結構寫入(0x30100110–0x3010013C 一組),同樣成比例,也是管線側。
- 0x300E1054..1E54(8 lane)在 4188 時 = 1:PHY 狀態位,非設定。

## 4. 建議的最小上機測試

前提同 §46(虛擬 V1 或 donor 98、增益鎖、SHS 用 IMXB 代換)。只改一件事:**寫 0x30100020 之後補做韌體的提交**。

- **測試 A(首選,不停產生器)**:`mem set 0x30100020 ((V−1)<<16)` 後,callfn **`FUN_c0125c48`**(= `c0127e58` 啟動,運行中分支只做 §2 的兩次提交 + 0x3010006C=1;callfn 前先讀首字確認 Thumb,位址 +1)。
  - 預期:SHS 歸零點移到 **新 VMAX/2**;V 加大時在固定 SHS 下亮度依 (V − 2·SHS) 線性增加。成立 → 「0x30100020 + 提交」就是感光元件真正的 XVS 週期。
  - 不成立 → 測試 B。
- **測試 B(照抄韌體完整順序)**:callfn `FUN_c0126560(1)`(停)→ callfn `FUN_c01265c0(H, V, 0)` → callfn `FUN_c0126560(0)`(啟動)→ `FUN_c0126560`… 再呼叫 vtable +0x5C(v21 連線重訓)。這就是 `FUN_c03149B0` 的 4.1/4.8/4.9 步,但不換模式。
- 便宜的旁證:改 VMAX 後讀 0x30100590[29:16] 的最大值(行計數是否超過舊 VMAX)與 0x30100048。
- 對照組:加大 VMAX(例 2700 → 5400,不要縮小到讀出時間以下),避免「XVS 早於讀出結束」這種 Sony slave 未定義行為混進來;§46 的 147 行案例本身就違反這個條件。
- 風險:B 的停/啟動在 LV 中執行過(模式切換就這樣做),但 shell 卡死時照 fp-firmware-call 流程冷開機。上機前廣播相機使用權。
