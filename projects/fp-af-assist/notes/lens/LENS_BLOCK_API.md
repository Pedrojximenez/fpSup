# 鏡頭資料存取 — 借用韌體自己的 API（含握手）

原程式／證據目錄：[research/lens/notes](../../../../research/lens/notes/)。筆記已集中至 fp-af-assist；下文歷史結果與限制保留。

> 2026-08-24。**推翻**「直接對鏡頭下位址請求」那條路。

## 一句話
之前讀鏡頭讀出全 FF ＋ 跳「鏡頭異常」，**不是缺神秘的 unlock 指令，是沒拿匯流排 mutex**。
韌體有現成的、自帶握手的區塊讀 API，直接借用即可。

## 缺的那一步：PreCommunicationSequence
```c
PreCommunicationSequence(ctx)   @0xC03554E0
  → FUN_c0016b0c()                     // 取 TID
  → FUN_c036dba0(ctx, 1, 3000)         // ★ 取匯流排 session lock，3s 逾時
  → 失敗印 "comm busy timeout TID %d"、走復原
  → _DAT_c347d194/198 記下擁有者 TID/lr
FUN_c03555a0(ctx)               @0xC03555A0
  → FUN_c036db68(ctx, 1)               // 釋放
```
所有 L-mount 命令都包在 Pre…/…Post 之間（例 `FUN_c0357f30` cmd6 區塊讀）。
我們 out-of-band 直接上匯流排 → 跟相機自己的週期輪詢對撞 → FF ＋ 異常提示。

## ★ 該借用的 API（自帶鎖，一行搞定）
```c
ctx = FUN_c03554a0();                    // @0xC03554A0，無參數，取鏡頭通訊 ctx
ok  = FUN_c0355de0(ctx, blockId, dst);   // @0xC0355DE0，完整鎖定讀，!=0 成功
// FUN_c0355de0 → FUN_c0355e10(ctx,id,dst,0) @0xC0355E10
```
韌體範本見 `FUN_c0347b90` @0xC0347B90（`blk_c03.c:47466` 讀 0x47 後解析）。
接收緩衝韌體用 2552 bytes（`local_a1c`），足夠最大區塊。

## 定址是「區塊 ID」不是原始位址
```c
FUN_c0355e10(ctx, id, dst, 0):
  if (*(u32*)(0xC0B9436C + id*0xC) == 1) return 0;     // flag==1 → 拒讀
  return CmdRead(ctx, *(u32*)(0xC0B94364 + id*0xC),     // addr
                      *(u32*)(0xC0B94368 + id*0xC), dst, 0);  // len
```
**ROM 表 `0xC0B94364`，stride 0x0C，`{addr, len, flag}`，ID 0x00–0x51**（0x52 起是字串 `"src/"`＝表尾）。

## DFD 相關落在哪
- **0x4b `0x011040` 2101 bytes** ★ 最大塊。解析成一連串 **8×8** 與 **8×8×3** 的 u16 表，
  落在鏡頭資料結構 +0x340 / +0x3C0 / +0x540 / +0x6C0 / +0x840…
  8×8 空間格點 × 3(center/horizontal/vertical) → 對應 `LENS_DATA_ACCESS.md` 的
  **distance correction(center/horizontal/vertical × H/L × stationary/af light)**。
- 0x4e `0x012023` 600 bytes、0x42 `0x010030` 126 bytes、0x47 `0x000520` 402(光學表)。
- 之前讀出 FF 的正是 0x42 / 0x4b / 0x4e —— **它們是合法區塊，不是空的**。

## 為什麼可能「fp 不會自主抓」
```c
lensInitImpl(ctx)  @0xC0351418
  if (isUpperLensFwNotExist(ctx) && isLensCompatible(ctx))
      DownloadLensData(*(ctx + 0x80));    // 整包下載只在這裡發生
```
而且 0x4b/0x4e 在下載鏈中是**巢狀條件**：0x49 → 0x48 → 0x4a → **0x4b** → 0x4c → 0x4d → **0x4e**，
前一個失敗後面全不讀。所以「相容性閘」或鏈中任一步失敗 → DFD 表根本沒被抓進 RAM。

## 待辦 / 未定
- 鏡頭資料結構的**執行期基底位址還沒找到**（`lens_mgr 0xC347CB14` / `mount 0xC347D098` 的 +0x80 都不是；
  掃前 0x100 也沒有指向 0xC2Fxxxxx 的欄位）。要從 `lensInitImpl` 的 ctx 往上追。
- `flag==2` 的語意未定。
- CmdWrite `0xC0355E88` 是寫入對應（未用）。

## 建議做法
注入一段常式：`ctx=FUN_c03554a0()` → 對 id 0x00..0x51 逐一 `FUN_c0355de0(ctx,id,buf)`，
結果連同 (id, ok, len) 寫進 worker RAM → **hook-push 一次帶回**。
韌體自己做鎖與握手，不撞匯流排、不會有「鏡頭異常」。
⚠️ 風險：在 worker task 內呼叫會取 mutex（最長阻塞 3s）並做序列 I/O；最壞情況同專案慣例＝凍結/拔電池。

# 實機驗證 2026-08-24 — 方法成立（鏡頭：LUMIX S 40mm F2）

## 決定性證據
`id 0x2d` 回傳 ASCII **`"LUMIX S 40/F2"`** —— 掛載鏡頭自己的名字，從鏡頭 ROM 即時讀出。
借用韌體 API 這條路確定通了，全程**沒有「鏡頭異常」提示、沒有 bus 衝突**。

## 注入常式（已驗證）
`/tmp/lensblk.S` v2，40 words，注入 `0xC072F200`：
```
r0=STATE, STATE+0x70 = block id
ctx = FUN_c03554a0();  ok = FUN_c0355de0(ctx, id, dst)
結果 @0xC072F700:  +0 id  +4 ok  +8 len  +0xC nzcount  +0x10 起 = 資料
nzcount = 非 0x00 且非 0xFF 的位元組數（一眼看出有沒有真內容）
```
- ⚠️ **不要注入 `0xC072F100`** —— 那是 `fpstate.py` 的 `PEEK_CODE`，蓋掉會讓之後所有 peek 傳回垃圾。
  `0xC072F200` 安全（push 常式在 `0xC072F600`）。
- ⚠️ 結果區**不要放 `0x50000000`** —— 關閉中的 DMA ring，寫入/讀取視圖不可靠（實測拿到矛盾值）。
  用 worker RAM `0xC072F700`（可放到 `0xC0730000`，容得下最大區塊 2101 B）。
- 每次呼叫阻塞約 **260–520 ms**，82 個全掃約 25 秒，**全程無 stall**。

## `ok` 的真義
`ok=1` **只代表交易完成，不代表有內容**。`CmdRead` 會先 `memset(dst, 0, len)` 再逐段填，
所以「回傳全 0」＝鏡頭沒這塊資料；「回傳 0xFF」＝那段根本超出 len、是舊殘值。

## 全 82 區塊掃描結果（LUMIX S 40mm F2）
**34 個區塊有真資料。** 完整落點：
- `0x08–0x10`（`0x0001fa`–`0x0002ff`）：有料，身分/基本參數區
- `0x12/0x13/0x26`：少量
- **`0x29–0x3c`（`0x000c00` 區）：整區有料** —— 含 `0x2d` = 鏡頭名字串
- `0x3e/0x3f/0x40/0x41`：少量（各 2–6 bytes 非空）
- **`0x42`（`0x010030`, 126 B, 非空 25）** ★ 之前 out-of-band 讀出全 FF 的那塊，現在有真資料
- `0x4a`：1 byte

**全空（此鏡頭沒有）**：
- **`0x47`（`0x000520`, 402 B）光學校正表 → 0**
- **`0x4b`（`0x011040`, 2101 B）距離校正 8×8×3 表 → 0**  ← DFD 最想要的那塊
- **`0x4e`（`0x012023`, 600 B）→ 0**
- 另有 0x11/0x14–0x25/0x27/0x28/0x32–0x36/0x3d/0x43/0x45/0x46/0x48/0x49/0x4c/0x4d/0x4f/0x50/0x51 → 0

> **結論：0x4b/0x4e/0x47 空，是「這顆 Panasonic 鏡頭沒有」，不是方法失敗。**
> 同一條路徑在 0x2d 讀出鏡頭名、在 0x42 讀出結構化資料。
> **要驗證 DFD 表是否真的存在，必須換一顆 SIGMA L-mount 鏡頭再掃一次。**

## 0x42 內容（`0x010030`, 126 B）
```
+000  03 a3 00 09 dc 00 00 00 04 8b 00 0a 2d 00 00 00
+010  03 1f ff ff ... (未使用槽 = FF)
+020  ... 00 0a 3d 00 00 00 00 38
+030  ...            00 0a 56 00 00 00 00 ac
+040  00 0a 5a 00 00 00 00 4c  00 0a 60 00 00 00 00 52
+078  00 5a 04 38
```
稀疏記錄，配對值（第一欄遞增 2524→2656，像 focus_pos/mpos）：
`(0x0009dc,0x00048b) (0x000a2d,0x00031f) (0x000a3d,0x38) (0x000a56,0xac) (0x000a5a,0x4c) (0x000a60,0x52)`

韌體解析在 `FUN_c03344b0` @0xC03344B0（`blk_c03.c:35310/35344/35350`）：
u16 → 結構 +0x223C，接著 `FUN_c06ae7b8`（24-bit 讀）→ +0x2240、+0x2244…
（同函式的另一分支讀 `0x3d`，填 +0x2234/+0x2236/+0x2238/+0x2274…+0x2288。）
→ **這區在鏡頭資料結構尾端 0x223C+，是 AF 標定相關；值的語意待解。**

## 其他讀到的內容

- `0x0a`（86 B）：`02 00 09 00 01 90 00 00 01 2c 00 00 01 2c 00 a8 …` — 0x190=400, 0x12c=300，像焦段/光圈參數
- `0x41`（122 B）：只有前 7 bytes `01 01 90 00 00 01 2c`
