# EP83 T0：單一 owner 的一次有界傳輸

2026-09-29。Track A 的第一步：**先隔離傳輸**，用主機自己寫進去的位元組證明 EP83 這條路能走一次，之後才談 hook 資料。純離線實作與模擬；**沒有相機 I/O、沒有替換 daemon、沒有安裝、沒有卡片變更**。使用者要求上機前先回報，本頁即為該回報的依據。

## 1. 關鍵發現：T0 不需要第二個 owner

核對 [fpshd.c](../../../fpSup/fp_usb_shell/host/fpshd.c) 的 `ep83_exchange()` 後確認，它要的 terminal **就是一般的 `shl` 回覆 frame**：64 bytes、magic `FPSH`、version 1、command `CMD_SHL`、sequence 相符、`flags==0`、`status==0`、CRC 正確、payload ≤ 44。

也就是說整個流程可以是：

```
主機 EP83 <bytes> echo
  → daemon 在 EP01 送出一個普通的 shl 命令
  → worker 執行 echo handler（= 我們的 sender），它 Start EP83 並等完成後返回
  → worker 照常在 EP82 送出自己的回覆 frame，那就是 terminal
```

**現行維護中的文字 worker 全程保有 EP01／EP82；我們只碰 EP83。** 因此 [af_ep83_control.c](../highrate/af_ep83_control.c) 的 mode-5 CMD4 adapter **不使用**——同時啟用它與 worker，正是 [transport gap](AF_STREAM_TRANSPORT_GAP_2026-09-27.md) 第 2 點禁止的雙 owner。這條決定寫進了 sender 的檔頭與測試。

## 2. 接點是 worker 自己就記載的

[camera/worker.S](../../../fpSup/fp_usb_shell/camera/worker.S) 的檔頭已經列出三個端點：

| 端點 | logical | physical | TRB 指標 |
|---|---:|---:|---|
| EP 0x01 OUT | 1 | 2 | `0xC31E3268` |
| EP 0x82 IN | 2 | 5 | `0xC31E326C` |
| **EP 0x83 IN** | **3** | **7** | **`0xC31E3270`** |

送出序列即 worker 的 `arm_in_block`：TRB `[0]`＝bus 位址（CPU − `0x40000000`）、`[4]`＝高位字、`[8]`＝長度、`[12]`＝control `0x813`，`dsb`，然後 `StartTransfer(physical)`；完成以 `Wait(logical, timeout)` 等待。`DALEPENA`（`0x2100C720`）bit 7 即此端點是否存在——EP 0x84 是 physical 9、未啟用，那正是 v1 白等五十秒的原因。

## 3. 新增的程式

| 檔案 | 內容 |
|---|---|
| [ep83_send.S](../highrate/ep83_send.S) | **332 bytes**。經借用的 echo 進入，驗 op／`DALEPENA` bit 7／緩衝區在 `0x40000000..0x80000000` 且四位元組對齊、長度 1..65536 不越界／TRB 槽非空，再依 worker 同一序列武裝並等待，把 StartTransfer 與 Wait 的回傳、以及事後讀回的 TRB control 寫進參數塊 |
| [ep83_t0.py](../highrate/ep83_t0.py) | 主機端：寫入 nonce 專屬 pattern、發布 D／I cache、指 echo 到 sender、`EP83 <bytes> echo`、比對回來的位元組、讀回執行回執。`--inspect` 唯讀；`--run-live` 目前由命令列直接拒絕 |
| [test_ep83_send.py](../highrate/test_ep83_send.py) | **16 tests**，Unicorn 跑真實機器碼 |
| [test_ep83_t0.py](../highrate/test_ep83_t0.py) | **11 tests**，假記憶體與假 socket |

一次性：op 字在碰端點**之前**就被清除，所以重入會被拒絕而不是重新武裝。任何失敗都保留 TRB 原狀、不重試、**不呼叫 EndTransfer**——那會是第二個 owner 對它看不到的控制器狀態動手。

## 4. 驗證與突變對照

sender 的 16 tests 涵蓋：武裝的四個 TRB 字與 worker 完全一致、control 字最後寫且其後有 barrier、第二次使用被拒且不碰端點、`DALEPENA` 沒有該端點時不碰 TRB、七種不合格緩衝區／長度、視窗兩端邊界可用、TRB 槽為空、Start 失敗不 Wait、Wait 失敗保留 TRB 為 `0x813`、未知 op、SP 差 4 仍正常返回、r4–r11 與 SP 保留。

**6 個突變全部被抓**：拿掉端點檢查、拿掉一次性 latch、拿掉視窗上界、允許零長度、允許空 TRB、忽略 Start 失敗。

`dsb` 沒有列入突變對照：Unicorn 不模擬 barrier，硬要說它「被測到」是假的。改以**真實位元組的指令順序檢查**——control 字的 store 必須在第一個 `blx` 之前，且兩者之間必須有 `dsb`。

主機端 11 tests：成功路徑、payload 在 op 字之前寫入、cache 發布在傳輸之前、sender 非零狀態保留位元組、損壞 payload 報出偏移、echo 已被借用時什麼都不claim、不確定傳輸保留全部資源且不重試（fault 後不再交換，所以 echo 也不還原）、pattern 邊界、sender image 隨參數塊位址改變、inspect 不建立傳輸。

highrate 168 tests、專案根 560 tests 通過（仍只有既有的 guarded-loader 來源身分錯誤）。

## 5. 配置器已接上（同日）

抽出 [user_alloc.py](../highrate/user_alloc.py)，讓 AF 探針與 T0 走**同一份**已測程式，不再各有一份：

- `claim()`：經維護中的 `cave.py` 取得 boot-scoped 區塊，注入嚴格 transport，唯一允許的寫入是 bump pointer 本身、且值必須落在 arena 內；同名 claim 已存在就拒絕。
- `allocate()`：一次 USER 配置嘗試（**絕不第二次**），核對 status／attempted／大小／mapping、`0x40000000..0x80000000` 視窗與 128-byte 對齊，並排除 worker 自己的 pool 與 body。被拒的 mapping 仍把 raw receipt 交給呼叫端保存——那是證據，不是使用許可。

`ep83_t0.boot_allocator()` 依此取四個 cave 區塊（sender 參數、sender、helper、helper 參數）與一塊 64 KiB USER 配置，回傳 128-byte 對齊的 base 當 payload 緩衝。echo 借用集中在一個 `Borrow` 物件，publish 一律 D→I。

抽出時發現並修掉一個自己造成的回歸：配置被拒時原本會保留的 raw receipt 消失了（驗證在記錄之前）。改為 `record` 回呼在任何判斷之前交出 receipt。

新增測試：T0 20 tests（含 boot allocator 的宣告名稱／大小、對齊 base、發布順序、拒絕的 mapping、落在 worker pool、DMA 視窗三個邊界、base 未對齊、未知 echo owner、cave bump 守衛的四種非法寫入）。共用配置器另做 **5 個突變對照全部被抓**：拿掉 mapping 檢查、拿掉 DMA 視窗檢查、允許 worker 重疊、允許同名 claim、bump 寫入不設限、以及「配置嘗試兩次」。

highrate 177 tests、專案根 569 tests 通過（仍只有既有的 guarded-loader 錯誤）。

## 6. 上機前還缺什麼

1. **daemon 要換。** 執行中的 binary 自 9/25 起沒有 EP83（`strings` 0 筆，STATUS 自報 `transport=EP01-EP82`）。要用已測候選重建並重啟——這本身就是一次 live 操作。
2. **原廠 PTP event sender 是否仍會寫同一個 TRB。** shell v3 拿掉了 PTP class handler，bulk 管線歸我們；但這只是文件敘述，**未在本 boot 實測**。這是目前最大的未知，也是唯一會動到原廠行為的部分。
4. USB 自 9/27 20:30 起回 `NO_DEVICE`。

## 7. 邊界

- T0 通過只代表**端點、TRB、DMA 與 daemon framing 合作成功一次**。不代表 AF、不代表連續 session、不代表速度（單批 4 KiB 量到的數字沒有意義）。
- Unicorn 裡 `StartTransfer` 與 `Wait` 是 stub；相機上它們是韌體。模擬不證明控制器真的搬了位元組，也不證明任何時序。
- 失敗後資源全部保留到本 boot 結束，`reclamation_proven` 固定 false。
