# mode 3 open gate — 6064×4042 原生讀出 → RWZM 2.0× → 3032×2020

跟 `mode98_autorun/` 是兩條不同的路：那邊靠換讀出設定降低雜訊地板，這邊**讓感光元件
把每一顆光電二極體都讀出來**，再由管線對半縮。

```
mode 3  MONIT1_30   6064×4042  1:1 全 3:2   類比「安靜組」
        hmax 445  tail 445→735  vmax 5398   →  29.97003 fps,0 ppm
        捲簾 24.982 ms
        RWZM 0x640 → 0x800 (2.0×)  →  輸出 3032×2020,active 3000×2000
```

這就是社群那位在跑的架構（他是 mode 151 開窗 + RWZM 2.0× 得到 3000×2000，24p），
差別是我們用 picker 直接選 mode 3——它出貨就是全高全寬，不必改讀出視窗，
也不必動那三份高度表。而且是 **29.97，不是 24**。

## ⚠ 為什麼 RWZM 一定要 2.0×,不能是 unity

上一次實測：**picker 填 mode 3、RWZM 留在 unity、畫布釘 3032×2012 → 相機當場凍住。**

```
感光元件送出   6064 × 4042
RWZM           1.0,不縮
緩衝區         3032 × 2012     ← 幾何 hook 把 base 釘在這裡
```

每一行送進來 6064 個像素，緩衝區只有 3032 個的空間，溢位。
`0x800` 在進緩衝區之前就把它對半縮掉，所以不會。

（社群那份從一開始就是 `0x800`。這個坑是我自己踩的，記在這裡免得再踩。）

## 刻意精簡

這份**沒有 dispfit、沒有選單標籤**。

上一版 `mode98_autorun` 的 fragment 是 199 行，實機驗證發現**資料補丁全中、兩個
payload 都完整載入、選單標籤也套上了，但最後兩行 arm 沒有生效**——幾何 hook 和
live hook 都讀回原廠值，命中次數 0。再往前的舊版是 151 行，完全正常。

懷疑 AutoRun 直譯器有指令數上限。這份只有 **71 行**，遠低於已知可用的 151。

在查清楚之前，`mode98_autorun` 每次冷開機都要用 USB 手動補一行：
```
mem set 0xC043A19C 0xEB0BD597
```

## 安裝

1. 確認機身是 **Ver.5.02**。
2. 完全關機、拔電池，用讀卡機操作 SD 卡。
3. 備份卡上現有的 `AutoRun.txt`（`codex/opengate/card_backups/` 已有一份舊的）。
4. 複製本資料夾的 `AutoRun.txt` 到卡片根目錄，`sync`，回讀確認
   32,768 bytes 且 sha256 與 `MANIFEST.txt` 相同。
5. USB 拔除，冷開機，等螢幕出現 **`fpOG3!`**。
6. CINE → CinemaDNG → **FHD** → **29.97p**。其他幀率沒有被改，不要用。

## 錄完要量什麼

跟 `A001_066`（mode 117）比：

```
python3 codex/opengate/measure_photodiodes.py <066 資料夾> <新資料夾>
```

還有完整的光子轉移擬合（斜率 a 與讀出雜訊 R）。三種結果：

| 結果 | 意思 |
|---|---|
| a 明顯低於 117、R 也低 | 全解析度讀出有賺到,值 2 EV 等級,捲簾代價值得 |
| R 低但 a 差不多 | 只賺到安靜讀出,跟 mode 98 同級,但捲簾差兩倍 → 不如用 98 |
| 兩者都差不多 | 2× 讀出本來就在合併,全解析度沒有額外好處 → 維持現狀 |

順帶要看的：**細節疊紋**。全解析度讀出沒有跳行，布料、磚牆、遠樹的爬行閃爍應該
明顯減少——這一項不管雜訊結果如何都是真的收穫。
