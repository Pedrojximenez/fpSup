# RAW14 ÷3 bounded probe —— 設計

2026-09-16。目標:回答**一個**二元問題 ——

> 把 `reg 0x0001 = 0x2E`(RAW14 + 3/3 的候選索引)寫進感測器之後,
> 感測器會不會送出畫格?

不回答畫質、不回答動態範圍、不產生任何檔案。

前置證據在 `../raw14_2x_experiment/README.md` 與
`../../notes/OG14_FEASIBILITY.md`;`reg 0x0001` 的完整分布見本文 §1。

---

## 1. 為什麼只剩這一個問題

70 個模式的 `reg 0x0001` 與 `(位深, 縮減)` 完美一對一:

| 值 | n | 位深 | 縮減 |
|---|---|---|---|
| `0x29` | 8 | RAW14 | 1/1 |
| `0x2A` | 15 | RAW12 | 1/1 |
| `0x2F` | 8 | RAW12 | **3/3** |
| `0x30` | 3 | RAW12 | 3/6 |
| `0x39` | 36 | RAW12 | 2/2 |

其餘 160 個 register 可由 M139 家族(8 個 3/3 模式)與 RAW14 深度區塊合成,
兩塊的交集只有 `reg 0x0001`。

`0x2E` 是唯一候選:未被 70 模式使用,且符合「RAW14 比同縮減的 RAW12 少 1」。
**該規則只有一個觀測對(0x29/0x2A)支撐,因此這是探測,不是計畫。**
數值本身不是算術的(1/1→2/2 是 +0x0F,1/1→3/3 是 +5,3/3→3/6 是 +1),
所以它是 Sony drive-mode 表的索引,不是可組合的位元欄位。

## 2. 安全封套

五道機制,任何一道失效就不得武裝。

### 2a. Writer hard gate
武裝期間攔截寫檔入列點,直接回報「已消化」,並累計被抑制的次數。
**探針永遠不產生檔案。** 這道閘在武裝之前就位,在解除之後才撤除。

### 2b. 不碰共享表
不得修改 M139 / M141 的 sensor / metadata / timing / receiver 共享列。
候選寫入 private scratch 列,並以精確的 caller guard 只在探測期間導向。
理由:改共享列會波及原廠靜態拍攝路徑。

### 2c. 雙重看門狗
原廠等待畫格的 timeout 是**無限**的,所以探針不得依賴它。

- **主**:主機端輪詢。`arm` 之後由主機以自己的時限輪詢狀態,逾時就下 `disarm`。
- **備**:相機端惰性期限。每次 hook 進入時比對 tick 與期限,逾期自行解除武裝。
  它只在 hook 有跑時才會觸發,但那正是「感測器有出東西卻不對」的情況。
- `arm` 一定帶最大武裝時間;**下一個 shell 指令無條件執行 cleanup**,
  不論它是什麼。

### 2d. Redzone
狀態區前後各一個哨兵字。cleanup 時比對;不符就把結果標記為不可信,
並且不得根據該次結果做任何結論。

### 2e. 可完成的 cleanup
cleanup 是狀態機,不是一串寫入:撤 hook → 還原 private 列 → 檢查 redzone →
清狀態 → 回報。每一步都可獨立重跑,重跑必須是冪等的。

## 3. 改變了的設計決定:描述子探針,不是 5 MB RAM sink

`raw14_2x_experiment/README.md` 原本要求「一格預配置的 RAM frame」。
本設計改成**只記錄畫格描述子加一段摘要**:

- 2016×1344 的 RAW14(16-bit 容器)是 5.42 MB,scratch 區放不下,
  勢必要動配置器 —— 那是一整類新的風險。
- 而 stage 1 的問題只是「有沒有畫格」。描述子的前 8 個字加上緩衝區
  前 256 bytes 的校驗和,已足以區分「沒有畫格」/「有畫格但幾何不對」/
  「有畫格且幾何符合預期」。
- 讓原廠管線照常配置,探針只讀不配,**嚴格比原設計更少侵入**。

真正需要整格資料時,那是另一個實驗,另外設計。

## 5. 閘門

產生器在這些項目全部綁定、且位移指令與韌體相符之前,**拒絕輸出任何可執行負載**。

| 閘門 | 狀態 |
|---|---|
| `F_WRITE` | **已解 = `0xC03660E8`**(2026-09-16) |
| `TICK_US` | **已解 = `0xC002B6E0`**(2026-09-16) |

**原本的 `HOOK_WRITER` 與 `HOOK_FRAME` 合併成一個。** 錄影的每一格 CinemaDNG
都是對 `F_WRITE` 的一次 ≥1 MB 寫入,而它的 `r1` 就是緩衝區指標 —— 閘門和
畫格偵測本來就是同一個事件,不需要第二個掛鉤。

```
FUN_c03660e8(file_object, buffer, length)     r0 / r1 / r2
回傳 0 = 失敗,非 0 = 成功   (blk_c03.c:21560 與 85823 兩個呼叫端都這樣判斷)
```

掛在**第一道指令**,所以進來時 prologue 還沒跑、堆疊未動、`lr` 還是呼叫端的 ——
要抑制寫入只需要 `bx lr`,不必拆別人的框架。被位移的指令是
`stmfd sp!, {r4,r5,r6,r7,lr}`(`0xE92D40F0`),位置無關;產生器會把它和韌體
逐位元比對,不符就拒絕產生負載。

`TICK_US` 是**函式**不是位址,回傳微秒。負載用 `blx` 呼叫,不是 `ldr` 讀值 ——
讀值會讀到函式的第一道指令,而那看起來像個合理的大數字,不會立刻出錯。

兩者的證據都來自 `fpSup/gyro/phase_probe.S`:它已經掛在 `F_WRITE` 的函式體上
觀察 DNG 寫入,並用同一個 1 MB 門檻分辨,也以 `TICK_US` 之名呼叫計時器。
**這兩個站點是已在出貨程式碼裡運作的,不是新找的。**

### 5a. 這個掛鉤的廣度 —— 已知限制

`F_WRITE` 是**通用**檔案寫入。shell 的 `getfile`/`putfile`、記錄檔、gyro CSV
全部走它。負載因此在查任何狀態**之前**就先比長度,`< 1 MB` 一律原樣放行。
有測試守著這個順序。

但武裝期間,**任何** ≥1 MB 的檔案寫入都會被抑制,包含靜態拍照。
所以:**武裝期間不要拍照。**

另一個未證實的風險:如果錄影器把 DNG 標頭用另一次**小**寫入送出,那次會通過
閘門,卡上可能留下一個只有標頭的檔案。stage 1 的驗收條件已經涵蓋這點 ——
它要求 `dir \CINEMA` 前後沒有新增,所以會被抓到,不會靜默發生。

## 6. 階梯

每一階必須先過,才准進下一階。

1. **`stock_nominal`** —— 用 stock M139(RAW12 3/3)武裝探針,錄一次。
   預期:writer gate 抑制 ≥1 次、`state=2`、`frames≥1`、redzone 完好、
   **卡上沒有新檔案**。
2. **`stock_timeout`** —— 同上,但刻意不觸發錄影。
   預期:主機輪詢逾時 → `disarm` → `abort_code=1`、`state=3`、redzone 完好。
3. **`candidate_dry`** —— 綁定候選列但**不寫 `reg 0x0001`**,其餘 160 個
   register 照合成值。這區分「合成的 160 個 register 有問題」與
   「`0x2E` 這個索引有問題」。
4. **`candidate_live`** —— 才寫 `0x2E`。需要另外的明確同意。

1 和 2 是**原廠模式**,不碰感測器未定義索引,風險等同一次普通錄影。
3 才開始寫合成 register。4 是真正的賭。
