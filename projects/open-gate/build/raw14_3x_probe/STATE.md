## 1. 這條路線在問什麼

> 把 `reg 0x0001 = 0x2E` 寫進感測器之後,它會不會送出畫格?

不問畫質、不問動態範圍。純二元。

背景與可行性論證在 `../../notes/OG14_FEASIBILITY.md` §6。

## 2. 已經確定的事

**時序模型已用實機驗到微秒。** `imager mode_list` 會報每個模式的有效讀出時間,
對上 `hmax × rows / 72 MHz`,三個 hmax 等級、兩種位深全部吻合(§6a)。
所以下面這個預測是硬的:

```
RAW14 ÷3 2016x1344 有效讀出 = 911 × 1344 / 72 MHz = 17.005 ms
  25p / 29.97p / 50p 放得下;60p 差 322 µs 放不下
```

**暫存器合成成立,而且乾淨。** `synthesize.py` 可重跑:

```
位深區塊 RAW12->RAW14 : 38 個暫存器,4 組配對的位址和值都一致
÷3 縮減核心 1/1->3/3  : 22 個暫存器,4 組配對一致
交集                  : 1 個 -> reg 0x0001
```

**唯一的未知就是那一個暫存器。** 它不是參數,是 Sony drive-mode 表的索引:

| 值 | n | 位深 | 縮減 |
|---|---|---|---|
| `0x29` | 8 | RAW14 | 1/1 |
| `0x2A` | 15 | RAW12 | 1/1 |
| `0x2F` | 8 | RAW12 | 3/3 |
| `0x30` | 3 | RAW12 | 3/6 |
| `0x39` | 36 | RAW12 | 2/2 |

70 個模式、5 個值、完美一對一、零例外。數值不是算術的(1/1→2/2 是 +0x0F,
1/1→3/3 是 **+5**,3/3→3/6 是 +1),所以**外插沒有根據**。
`0x2E` 只是「RAW14 比同縮減的 RAW12 少 1」的外插,而那條規則只有一個觀測對
(`0x29`/`0x2A`)支撐。

`imager mode_list` 的活體表已確認感測器自己回報的就是那 70 個模式、8 個 RAW14、
全部 1×1 —— **沒有隱藏的 RAW14 縮減模式可撿**。

## 3. 隨時可按的候選

`candidate_m139.json`,由 `synthesize.py --plan 139` 產生,可重跑驗證。

```
感測器列 M139 @ 0xC0B65B54   38 個寫入(含 reg 0x0001 0x2F -> 0x2E)
時序列   0xC0B599A4          1 個寫入(hmax 445 -> 911,vmax/tail 不動)

結果:讀出 17.005 ms / 一格 34.156 ms (29.277 fps),餘裕 17.151 ms
```

只改 hmax 就夠 —— vmax 維持 2700,畫格週期自然拉長到 34 ms,放得下。

## 4. 怎麼觀測(不需要注入任何程式碼)

這是這一輪最重要的簡化。`imager mode_now` 本來就會報 `frame_count`,
實測每秒跳 61(MONIT1_60 = 60 fps),所以:

```
1. 讀 imager mode_now 的 frame_count
2. 套用候選列
3. 讓相機進入該模式
4. 再讀 frame_count
      還在跳 → 感光元件吃了
      凍住   → 沒吃
5. 寫回原值
```

**不需要 writer gate、RAM sink、看門狗。** mode 139 是 MONIT class,
即時預覽層級就能測,不必進錄影。

`raw14_probe.S` / `raw14_probe.py` 那套是**錄影**測試的裝置(§5),
要等到真的想錄一格 RAW14 才用得上。先做出來是順序搞反了,但它是好的,留著。

## 6. 為什麼停在這裡 —— Super 16 是更好的路

同一輪算出來的:

```
IMX410 像素間距 5.920 µm
Super 16 (12.52 × 7.41 mm) → 2115 × 1252 px   ← 原生就是 2K,1:1,不需縮減
```

| | RAW14 ÷3 OG2K | S16 2K |
|---|---|---|
| 縮減 | ÷3 | **無,1:1** |
| Bayer 偽色 | 有(÷3 與週期 2 互質) | **不存在** |
| `reg 0x0001` | **未知,要賭 `0x2E`** | **`0x29` 已存在於 8 個原廠模式** |
| RAW14 60p | 放不下(差 322 µs) | **放得下**(15.84 ms) |
| 捲簾 (RAW12) | 8.31 ms | 5.74–7.74 ms |

原廠現成的 1:1 裁切捐贈者:`ACQ_CROP` / `ACQ_CONTINUOUS_CROP`(3968×2640
RAW14 1/1)、`ACQ_12BIT_CROP` 系列(RAW12 1/1)、`MONIT1_24_HD_LOWP`
(4176×2174 RAW14 1/1)。

要做的只是把視窗縮到 2115×1252 —— **那是 OG3K/OG2K 做過兩次的操作**
(改 `x_start/x_end/y_start/y_end`),不是合成新的感測器模式。

S16 的代價是少約 3.2 級總進光量(面積是全幅的 1/9)和 2.97× 裁切倍率,
那是物理,不是缺陷。未知的是「原廠沒用過的小視窗合不合法」——
比「這個 drive mode 存不存在」小得多。

## 7. 要恢復這條路線的話

```sh
cd projects/open-gate/build/raw14_3x_probe
python3 -m unittest test_raw14_probe        # 先確認 38/38
python3 synthesize.py --plan 139            # 重新產生候選,核對 json
```

然後需要使用者針對 `0xC0B65B58`(以及另外 37 個感測器位址與
`0xC0B599A4`)的**明確寫入同意** —— 那是寫入原廠資料。

分兩步比較有診斷價值:先寫 37 個、`reg 0x0001` 維持 `0x2F`,再寫 `0x2E`。
但要注意第一步是個內部矛盾的組合(RAW14 的類比設定配 RAW12 的 selector),
失敗不一定代表什麼。

回復:寫回原值,或拔電池(整張表都在 RAM)。
