# 畫布不是設定 block (2026-09-10, USB shell 實機驗證)

> 接續 `FRAME_RATE_IS_VMAX.md`。感光元件那一側已經做完(3032×2012 3:2 @29.97),
> 這一份是畫布那一側 —— **一個乾淨的排除,而且它移走的正是大家一直在打的目標。**

## 一句話

**設定 block 的第一份寬高被完整控制了整場錄影,DNG 尺寸完全沒變。**
所以 open-gate 文件那句「DNG 尺寸 = 設定 block 的 `+0x00`/`+0x04` 再加 16 與 10」
指錯了欄位。

> ⚠️ **§2 原本寫「整個設定 block 排除」,那是講太滿了,見 §7。**
> 每個 block 內部有**兩對**寬高,而它們在 record-start 走的是**兩個不同的重算**。
> 被排除的是第一對。第二對現在是最活的線索。

## 1. ★ 轉換表找到了:`MenuItemMovieRecSize` 的中繼資料

open-gate 文件把「找出 `0xC31AC530` 的 `+0x1A0` 屬性有誰在觀察」列為下一步。
**觀察者不用找 —— 轉換表就在屬性自己的中繼資料裡。**

```
0xC0742204   "MenuItemMovieRecSize"        字串
0xC0742218   0
0xC074221C   0xC0741DB8
0xC0742220   0
0xC0742224   22
0xC0742228   2        ← 列舉值
0xC074222C   1920     ←   對應寬
0xC0742230   1080     ←   對應高
0xC0742234   3        ← 列舉值
0xC0742238   3840     ←   對應寬
0xC074223C   2160     ←   對應高
0xC0742240   "Invalid MovSize"             錯誤字串
```

**只有列舉 2 與 3 合法。** 這解釋了先前量到卻誤讀的行為:掃 `SetMovRecSize` 0–13 時
「從 FHD 出發只有 3 會跳到 UHD、進了 UHD 之後其他值保持 UHD」——
真相更簡單:**其餘所有值都落到「Invalid MovSize」,什麼都不做。**
(`FRAME_RATE_IS_VMAX.md` §4 那段語義描述據此訂正。)

### 改它有效,而且效力貫穿 record-start

```
0xC074222C  1920 → 3032
0xC0742230  1080 → 2012
menu SetMovRecSize 2
  → 主設定 0xC3074BE8 = 3032 x 2012
```

**然後錄一段,主設定還是 3032×2012 —— 沒有被刷回去。**

這是關鍵差異。先前直接寫主設定,record-start 一重算就變回 1920×1080;
現在重算讀的是這張表,算出來的就是我們要的值。
**「設定是輸出不是輸入」這個死結解開了:設定確實是輸出,但產生它的函數在我們手上。**

## 2. ★★ 但畫布沒動 —— 所以設定 block 被排除

```
主設定       3032 x 2012      整場錄影都是
DNG          1936 x 1090      3,244,544 bytes × 82 幀
0xC37CE210   1936 1090 3244544
```

檔案是直接看的(`dir \CINEMA\A001_006`),82 個 DNG 全部 3,244,544 bytes。

**兩件事同時為真,所以那個 +16/+10 的關係不是因果。** 出貨組態下
1920+16=1936、1080+10=1090 剛好成立,但把設定改成 3032×2012 之後 DNG 沒有變成
3048×2022 —— 它根本沒在讀那裡。

> **原本這裡寫「這條路從頭到尾都不通往畫布」。訂正:只有第一對不通。**
> 見 §7 —— 同一個 block 裡的第二對是另一回事,而且它跟 DNG 對得上。

## 3. 怎麼走到轉換表的

屬性鏈是用探針一次走完的(手動分次 `mem get` 會抓到輪替中的值,見
`FRAME_RATE_IS_VMAX.md` §6):

```
FUN_c0057ae8()              → 0xC31AC530     (open-gate 文件點名的那個物件)
*(obj+0)                    → 0xC31AC59C
*(that+4)                   → 0xC07397D8     vtable
*(that+0x1A0)               → 0xC0084700     accessor thunk
```

thunk 全是「回傳 `r0 + 固定偏移`」,反組譯出來:

```
0xC0084700:  mov ip,r0 ; add r1,ip,#0x680 ; mov r0,r1 ; bx lr     → +0x680
0xC00846E8:  → +0x664     0xC0084710: → +0x69C
0xC0084740:  → +0x6D0     0xC0084768: → +0x704
```

所以屬性物件 = `0xC31AC59C + 0x680` = **`0xC31ACC1C`**(不是 `obj + 0x680`;
`r0` 傳的是 `*(obj+0)`)。判別方式:`+0x14` 存的值等於 `menu SetMovRecSize` 讀回的值。

```
0xC31ACC1C  +0x00  0x69       屬性 id
            +0x08  0xC31AC540 擁有者
            +0x0C  0xC07421BC vtable
            +0x14  2          ★ 目前值 = SetMovRecSize
```

vtable `0xC07421BC` 全是 `0xC00A8xxx` 的**通用**屬性類別
(`+0x2C` 寫值、`+0x30` 衍生值變了、`+0x34` 通知),所以轉換不在 vtable 裡。
`+0x3C` 指向 `0xC0742204` —— 中繼資料,轉換表就在那裡。

**通知那條路(`FUN_c00A8DE0 → FUN_c0091288 → FUN_c00912f8 → FUN_c0091050`,
清單掛在 `0xC31AC540`)沒有追下去,也不需要了。**

## 4. 為什麼不是用搜尋找到的

值得記,因為兩種搜尋都失敗了:

- `0xC3075230`(設定 block 的指標)在映像裡**沒有對齊的字面值,也沒有 MOVW/MOVT 對** ——
  它是用 `base + offset` 取的。
- `MOVW #1920` 全映像只有 1 處、`#3840` 3 處、`#2160` 1 處,而且互不相鄰。
  **常數不是內嵌的,所以一定在表裡。**

相鄰字對 `(1920,1080)` 有 48 處、`(3840,2160)` 有 32 處 —— 雜訊太多。
真正指出答案的是**位置**:`0xC074222C` 就在剛找到的屬性 vtable 後面 0x70 bytes,
而 vtable 的 `+0x3C` 正好指著那一區。**先走到物件,再看它旁邊有什麼。**

## 7. ★ 訂正並收窄:一個 block,兩對寬高,兩個重算

§2 只設了「第一對」(`+0x00`/`+0x04`)。第二輪把**六份全部**設成 3032×2012:

```
master     +0x00/+0x04  與  +0x1C/+0x20
CameraMgr  +0x40/+0x44  與  +0x5C/+0x60      FUN_c0206e98() = 0xC31F865C
鏡像       0xC3758B98   的同樣兩對
```

三個 block 完全同形,CameraMgr 只是整體偏移 0x40。錄影前六處都是 3032×2012、三次讀取穩定。

**錄完之後:**

```
             錄影前        錄影後
第一對       3032x2012  →  3032x2012    撐住
第二對       3032x2012  →  1920x1080    ★ 被改回去
```

DNG:159 幀,全部 3,244,544 bytes,1936×1090。

### 所以 record-start 跑的是兩個重算,不是一個

| | 來源 | 現況 |
|---|---|---|
| 第一對 | `MenuItemMovieRecSize` 轉換表(§1) | **在我們手上**,但不決定 DNG |
| 第二對 | **未知,且不讀那張轉換表** | 重算成 1920×1080 |

而 DNG 的 1936×1090 = 1920+16 / 1080+10 —— **跟第二對對得上,跟第一對對不上。**

### 新的目標

> **是什麼在 record-start 把 `+0x1C/+0x20` 重算成 1920×1080?**

已知它會在 record-start 執行、不讀 `MenuItemMovieRecSize`、也不接受直接寫入。

下一步:掃 RAM 裡所有**相鄰的 `(1920, 1080)` 字對**。掃 `3244544` 時 8 MB 只有兩個
單獨命中(其餘是畫格描述環),同樣的方法對這一對應該一樣乾淨,而第二對的來源必在其中。

### 掃描工具

`scratchpad/scan32.S` + `runscan.py` —— 在相機上掃,只有命中回主機。
主機端掃不動:`mem get` 一趟十六個字,一 MB 要數小時。自證方式是先掃已知答案
(`0xC37CE218` 的 `3244544`)。

掃 `3,244,544` 的結果本身也值得記:

```
0xC34B9F28 起 356 處   stride 0x80 的規律排列 = 寫入器的畫格描述環
0xC352028C            前一個字是 82 = 該次錄影的畫格數  → 統計,不是來源
0xC359BE6C            同上
```

## 10. ★ 屬性中繼資料註冊表,以及唯三帶尺寸的項目

`0xC0700000..0xC0760000` 是 `MenuItem*` 中繼資料的註冊表 —— **263 個項目**,
每個都是 `"MenuItemXxx\0"` 字串後面接參數。掃過全部,**只有三個帶尺寸**:

```
0xC0742204  MenuItemMovieRecSize      [1920, 1080, 3840, 2160]   ← 已改,餵第一對
0xC0742860  MenuItemStillImageSize    [3840, 2160, 1920, 1080]   ← 新發現
0xC074407C  MenuItemHdmiOutputFormat  [4096, 2160, 3840, 2160, 1920, 1080]
```

### `MenuItemStillImageSize` 為什麼可疑

```
0xC0742880  22            與 MovieRecSize 相同的標記
0xC0742884  3840          尺寸成對,但沒有交錯的列舉值 —— 位置索引,不是 {enum,w,h}
0xC0742888  2160
0xC074288C  1920   ← 改成 3032
0xC0742890  1080   ← 改成 2012
```

理由:`setting get cam_still_imagesize.h/v` 讀到 **1920/1080**。靜態照片不該是這個
數字(fp 的靜態是 6000×4000),**除非 CINE 模式下「靜態尺寸」就是影片畫格尺寸**。
若錄影器讀的是這一份而不是 MovieRecSize,一切都對得上。

**已改,未測。** 這是下一次錄影要驗的東西。

### 註冊表本身也值得記

263 個 `MenuItem*` 全部可定位,而且每個的參數就在字串後面。
**要找任何一個選單項的實際值域或對應表,不必追屬性框架 —— 找字串,讀它後面。**
這比從 `FUN_c00658e8` 的通知路徑往下追快得多(那條走到
`FUN_c0091050` 的觀察者清單就停了,而且不需要)。

## 12. 第四輪:三張表全握,什麼都沒被刷回,DNG 還是沒變

三對寬高各有各的來源表,全部找到並改掉:

```
第一對 ← MenuItemMovieRecSize     0xC074222C   {2,1920,1080,3,3840,2160} 的 enum2
第二對 ← MenuItemStillImageSize   0xC074288C   位置索引的第二對
第三對 ← MenuItemHdmiOutputFormat 0xC07440BC   4096x2160/3840x2160/1280x720/1920x1080 的第四筆
```

驗證方式跟 §1 相同:改表 → 跑對應的 `menu Set*` → 看複本有沒有跟著動。三條都成立。

錄影之後:**九對全部維持 3032×2012,一個都沒被刷回,而 DNG 一動也不動。**

### ★ 我前四輪的推論方式是錯的

我一直讀成「被刷回的那個就是來源」,因為每次被刷回的都是 1920×1080、DNG 正好是
1936×1090。**那是相關不是因果。** 實際上:每補一張表,刷回就移到下一個還沒補的地方;
全部補完,刷回消失,DNG 從頭到尾不受影響。

**那些刷回一直在追蹤「我還沒改到哪」,不是「誰餵 DNG」。**

同一類錯這個 session 犯了兩次(另一次是 raw_zoom,見 `FRAME_RATE_IS_VMAX.md` §5)。
共通點:**拿一個會跟著我的動作變化的東西,當成因果鏈上的一環。**

## 13. 重開機之後:位址穩定性,以及 `0xC37CE210` 也出局

重開機後只灌感光元件那組(vmax + picker),三張畫布表故意留原廠值。

**錄一次,`0xC343B590` 立刻讀到 117** —— 感光元件確實跑 3032×2012 3:2 @29.97。
(這次是錄完立刻讀的;`FRAME_RATE_IS_VMAX.md` §8 那條「事後讀不算數」的教訓已套用。)

**而 `0xC37CE210` 全程是 `{0, 0, 0}`,DNG 照樣 1936×1090。**

所以它也只是反映用的快取。文件用「第三個字精確等於卡上檔案大小」認定它是錄影幾何 ——
**那證明它反映幾何,不證明它決定幾何。** 跟設定 block 同一類。
(它會在某些條件下才被填;同一個開機週期裡第一次錄影沒填,第二次填了。條件不明,也不重要。)

### 位址穩定性:記位址時要標類別

```
穩定(靜態 BSS)   0xC352028C / 0xC359BE6C 的統計、0xC343B588 感光元件物件、
                   所有 0xC0xxxxxx 的表
不穩(堆積/緩衝)   寫入器描述環 0xC34B9F28 → 重開機後 0xC34BB028
```

## 14. ★ 最後一個排除,以及它推翻的搜尋方向

`(1936, 1090)` 這一對在**整份 49 MB 映像裡只出現一次**,`(3856, 2170)` 也是:

```
0xC096F580   3856 2170     ← 文件測過這一筆(2170→2570),當時錄的是 UHD
0xC096F588   1936 1090     ← 從沒人測過,而我們錄的是 FHD
0xC096F590   6064 4042
0xC096F598   3968 2640
```

把第 1 筆改成 968×546 再錄 —— **表沒被刷回(它是靜態表,沒人重寫),DNG 還是 1936×1090。**

> ⚠️ **2026-09-10 稍晚降級:這不算排除。** 這張表根本不在畫布的資料流上
> (真正的在 `FUN_c043a158` 的 geometry record,見 `CANVAS_MOVED_AT_C043A19C.md`),
> 所以改了沒反應是應該的 —— 那不是排除掉一個候選,只是打錯地方。
> 下面「尺寸是算出來的」這個結論仍然成立,而且現在知道算它的是誰了。

### 結論:錄下來的尺寸是算出來的,不是查表來的

**加過邊界的實際 DNG 尺寸,在整份韌體裡只存在一個地方,而改掉它沒有任何效果。**

所以 1936×1090 不是從任何表讀出來的 —— 它是在執行期算出來的。
**「找一張看起來對的表 → 改 → 錄」這個方法到此為止,它已經失敗六次。**

## 16. 下一步該換方法

值不值得繼續是另一回事,但如果要繼續,不該再猜表:

- **抓寫入者**,而不是找值。所有下游都在 record-start 被寫,所以在 record-start
  之前裝一個東西,把「誰寫了那個位址」記下來。shell 能注入、能建執行緒(`XT_CREATE`),
  這是唯一還沒用上的能力。
- 或**從輸出端往回**:DNG 檔頭裡的尺寸是誰填的。`putfile`/`getfile` 能把 DNG 拉回來,
  檔頭的 TIFF tag 位置固定,寫那個 tag 的程式碼比「畫布」好搜。
