# 借照片 profile 的代價:交給訊號處理引擎的三欄與原廠影片不符

2026-09-27。起因是回報「OG3K 錄影中 live view 閃爍,輸出的 CDNG 正常」,
使用者的判斷是「live view 管線沒有正確設定」。

**結論分兩半,不要混在一起讀:**

- **§1-§5 的三欄錯配是真缺陷**,反編確認、實機讀值確認生效、DNG 零回歸。
- **§7 的閃爍沒有被這個修正解掉**,而且量到的閃爍在我們的程式碼**完全失效**
  時照樣發生 —— 原廠 UHD 的事件率是 OG3K 的三倍多。**修正 ≠ 修好症狀。**

信心:**[C]** 實測/反編確認 · **[I]** 推論 · **[?]** 未解。

## 1. 為什麼檔案沒事而 live view 有事 [C]

OG3K 八個格率全部掛 **p83**,那是 S 尺寸 12-bit **照片**的拍攝 profile。
畫布 hook 只改記錄矩陣與平面格式碼,所以 RAW 那一半(DNG 的來源)是對的。

但畫布不只餵 RAW。`FUN_c0434ef8(holder, config)` 會把畫布**整份翻譯**成
訊號處理引擎的組態:

```
FUN_c043a158  → FUN_c0439d18(canvas, profile)      從 PARAM 列建畫布
              → [我們的 hook 0xC043A19C 在這裡改畫布]
              → FUN_c0434ec0(holder, canvas)        canvas 存進 holder+4
                 → FUN_c0435428(holder)             算各平面的尺寸與張數
FUN_c0429910  → FUN_c0434ef8(holder, cfg[0x1B0])   畫布 → 引擎組態
              → FUN_c01d1630(ch, cfg)               組態 → 引擎全域
```

`FUN_c01d1630` 把組態平鋪進 `0xC31DF564 + ch*0x1B0`。channel 0:

| 引擎組態 | 畫布 | 存取器 |
|---|---|---|
| `0xC31DF574` (+0x10) | `+0x030` 格率 | `FUN_c01d34f0` |
| `0xC31DF5D0` (+0x6C) | `+0x0C0` | `FUN_c01d3bc0` (`&0xf`)、`FUN_c01d3488` (`==0x10`) |
| `0xC31DF5E8` (+0x84) | `+0x090` | `FUN_c01d3558` |

## 2. 三欄的值:p83 與八個原廠影片 profile 逐項不同 [C]

原廠八個格率用八個 profile(就是 OG3K 各格率頂掉的那八格),
`picker table 3 = 0xC0BE5B50`,每筆 16 bytes 的 `+4` 是 profile:

```
slot 10 FHD23_98 → p176  +0x030 = 24   +0x090 = 1   +0x0C0 = 0
slot  9 FHD24    → p431  +0x030 = 24   +0x090 = 1   +0x0C0 = 0
slot  8 FHD25    → p180  +0x030 = 25   +0x090 = 1   +0x0C0 = 0
slot  7 FHD30    → p175  +0x030 = 30   +0x090 = 1   +0x0C0 = 0
slot  6 FHD48    → p430  +0x030 = 48   +0x090 = 1   +0x0C0 = 0
slot  5 FHD50    → p174  +0x030 = 50   +0x090 = 1   +0x0C0 = 0
slot  4 FHD60    → p173  +0x030 = 60   +0x090 = 1   +0x0C0 = 0
slot 12 FHD100   → p178  +0x030 = 50 ★ +0x090 = 1   +0x0C0 = 0
```

**p83:`+0x030 = 18.0`(0xC0BD47AC)、`+0x090 = 0`(0xC0BD6DEC)、
`+0x0C0 = 1`(0xC0BD513C)。三欄全錯,而且我們一欄都沒補。**

★ **FHD100 那一格原廠宣告的是 50.0,不是 100。** 自己算一定錯,
所以值一律從映像裡「同一個 slot 的原廠 profile 的 +0x030」讀出來
(`Plan.engine_fps(slot)`),不用 `NOMINAL_FPS`。

`+0x088`(p83 = 4、原廠影片 = 0)也不同,但它只進
`FUN_c04358d0` 的預覽平面高 `= (+0xE0 ?: +0x10) + [+0x88] + [+0x8C]`,
多配置 4 列,無害,**不動**。

## 3. `+0x0C0` = 管線延遲,差一格 [C]

```c
FUN_c0434ef8:  cfg+0x6C = canvas+0xC0;
               if (canvas+0xC0 && canvas+0xAC) cfg+0x6C = 2;   // p83 的 +0xAC = 0
FUN_c01d3bc0:  return cfg+0x6C & 0xf;                           // 我們 1、原廠 0
FUN_c01d7a88:  iVar2 = cfg+0x04 (= canvas+0xB4, 影片 = 1)
               if (iVar2 == 1) return (canvas+0xC0 == 0) ? 3 : 2;
```

消費端把回傳值當成**「往回退幾格」**用:

```c
FUN_c00ce770(&timestamp, -N)                    // blk_c00:155282
FUN_c00f7ed8:  iVar3 = -N (再依 DAT_c2efec64 +1/+2)
blk_c07:13970  for (i = 0; i < FUN_c01d7a88() + 1; i++) FUN_c07254a8();
```

原廠影片一律 **3**,我們拿到 **2**。另外 `FUN_c0176e98(a, b, N, ch)` 的
第三參數就是 `FUN_c01d3bc0` 的值,**非 0 時走另一條硬體路徑**
(發 message `0x30183110`,而不是直接寫 `iVar1+0x30220024`)。

## 4. `+0x030` = 引擎格率,永遠是 18 [C]

已追到的消費端(全部在引擎側,碰不到 DNG writer):

```c
FUN_c01caba0  fps < 30.0 ? clk/0x21 : clk/100   → 硬體欄位 cfg2+2
              ★ 29.97 就分岔:原廠 p175 宣告 30.0 走 ÷100,我們 18.0 走 ÷33
FUN_c01cec08  return fps > 99.0                 → HFR 閘門,OG3K100 永遠拿不到
FUN_c01c9e38  fps ≈ 15/30/60/-1 → 15/30/60/10,其餘 → 30  (cfg2+0x48)
FUN_c01cc868  cfg3 = (int)fps                   → 存 18
FUN_c01d11e8  timeout = (int)fps * 1000         → 18000
FUN_c01cef08  +0x090 && fps == 60.0 → FUN_c01d10d0(1)
```

**安全界線**:`FUN_c04357e0` 的 plane count 是
「`+0xA4 == 1` → 2;`+0xA4 ∈ {9,10}` 或 **`+0x030 == -1.0`** → 0;否則 3」。
所以寫進去的一定要是**正值**,`check()` 驗 `0 < fps <= 240`,
鎖存為 0 時 payload 不寫(留著 donor 原廠值,寫 0.0 比 18.0 更糟)。

## 5. 改法:兩個既有開關 + 一個新鎖存

`+0x090`/`+0x0C0` **不需要新程式碼** —— `og3kcanvas.S` 的
`TARGET_HIRATE_90`/`TARGET_HIRATE_C0` 寫的就是原廠影片的值(1 和 0),
先前只給 HSW 用。OG3K 只挑這兩欄,不要 HSW 那組 >60fps 專用的
`B0/DC/E4/FC/100`(`DC/E4` 會動生產者對,p83 原廠是 0)。

`+0x030` 走 `BITLATCH` 同一個模式:格式表每筆的 `+0x2C`(原本只是驗證用的
整數 nominal class)改放**引擎格率的 float bits**,`fmttable` 命中時鎖存進
`FPSLATCH = 0xC0731C40`,`og3kcanvas` 的錄影 case 再寫進畫布 `+0x030`。

```
fmttable.S    LDA r4,FPSLATCH / ldr r3,[ip,#0x2C] / str r3,[r4]      4 字
og3kcanvas.S  LDA r2,FPSLATCH / ldr r2,[r2] / cmp r2,#0 /
              strne r2,[r1,#0x30]                                     5 字
state()       FPSLATCH = 0                                            1 字
```

開關:`OG_HIRATE=90,C0`(目標預設)、`OG_ENGFPS=0/1`。
`OG_HIRATE=none OG_ENGFPS=0` **逐位元組回到 2026-09-26 的建置**(字數 960)。

錄影中 0xC31DF574      30.0   (原本 18.0)
錄影中 0xC31DF5D0      0      (原本 1)
錄影中 0xC31DF5E8      1      (原本 0)
畫布錄影命中 121 次,最後 profile 83
DNG A001_111  3024x2010 / 12-bit / strip 9,117,360 / crop 3008x2000 @(8,5)

## 7. ★ 閃爍沒有被解掉,而且它不是 OG3K 造成的 [C]

HDMI 擷取(AVerMedia ExtremeCap UVC,1920x1080 UYVY)。偵測器:6σ + MAD,
窗 20-30 秒。**只列訊號活性驗證過的擷取**(見 §11)。

| 組態 | 事件/20秒 | 陰影幅度 | 最大單幀跳動 |
|---|---|---|---|
| OG3K(FLAG=1,三欄修正已載入),USB 連著 | 3.0 | 7.90% | 126.6 mEV |
| FLAG=0 的某個 16:9 原廠模式 ⚠️,USB 連著 | 5.0 | 7.94% | 120.1 mEV |
| FLAG=0 的某個 16:9 原廠模式 ⚠️,USB 連著 | **10.0** | 7.84% | 120.5 mEV |
| **純原廠 + 原廠電池 + USB 拔掉 + 乾淨卡** | **1.3** | 7.95% | 120.9 mEV |

⚠️ **第 2、3 列原本標成「FHD」與「UHD 12-bit」,那兩個標籤不可信。**
使用者 2026-09-27 指出:「切換 og3k/fhd/uhd **有時候沒有真的切過去**」——
`menu SetMovRecSize` 讀回新值不等於模式真的換了,這正是
`FLAG_AND_PICKER_DISAGREE.md` 整份在講的事。我當時有印 `imager mode_now`
但輸出被截成只剩標題行,**從未真的看到感測器模式**。

**存活的與倒下的:**
- OG3K 那一列可信 —— HDMI 的畫面矩形量到 1626x1080(3:2),幾何獨立證實;
  `FLAG` 是讀我們自己的 cave 字,也可信。
- 另兩列的 `FLAG=0` 可信(同樣是自己的字),但「是 FHD 還是 UHD」不可信。
- **結論「hook 全失效時照樣發生,事件率不低於 OG3K」仍然成立**,而且使用者
  用乾淨卡冷開機(完全沒有 OG 程式碼)獨立證實。倒下的只有 FHD/UHD 的細分。

**2026-09-27 補救:HDMI 的畫面矩形事後救回了一半。** `lvflicker.py` 的
`rect()` 從擷取的中位數幀量非黑邊界:

```
og3k_20s   1626x1080  比例 1.5056  → 3:2,OG3K 確實生效
oem2       1920x1080  比例 1.7778  → 16:9,確實是原廠 16:9 模式
ssd        1619x1080  比例 1.4991  → 3:2,OG3K 確實生效
```

所以「3:2 對 16:9」這一層可信,倒下的只有「16:9 裡面是 FHD 還是 UHD」。

### ★ SSD 那一份:0 事件,但不能歸功於修正(2026-09-27)

| 擷取 | 模式(幾何驗證) | 事件/20秒 | 三欄修正 |
|---|---|---|---|
| OG3K + SD + USB 連著 | 3:2 ✓ | 3.0 | **已載入** |
| 原廠 + 原廠電池 + USB 拔掉 | 16:9 ✓ | 1.3 | 失效 |
| OG3K + SSD | 3:2 ✓ | **0.0** | **已載入** |

**修正在 3 次與 0 次兩邊都在**(前者走 USB 熱載入),所以差異不可能是它。
變掉的是:SD → SSD(**SSD 佔住 USB 口 = 把 USB 連線拿掉**,與 §7b 的
「拔 USB 少 8 倍」一致)、12-bit → 8-bit、29.97p → 約 24p,
以及場景暗很多(陰影位階 27.1 → 9.6、訊號雜訊 1.73 → 0.58)。

**要歸因給三欄修正,只能換 `fpSup.BIN` 一個檔、其餘全部固定**
(同場景、同燈、同格率、同位元深度、同媒體)。兩張 A/B 卡就是為此存在:
`projects/open-gate/cards/engfps-2026-09-27/{fast,fast-baseline}/`,
AutoRun 與 FPSUPUI 逐位元組相同,只差 BIN。
⚠️ 接了 SSD 就沒有 USB shell,所以換 BIN 要把 SD 卡拿到電腦上。

**下次要證明模式真的切了,要有獨立證據:**
`imager mode_now` 的**完整**輸出(模式 enum + size + aspect,不要只印第一行)、
HDMI 的畫面矩形(3:2 與 16:9 分得出來,但 FHD 與 UHD 分不出來)、
以及錄一段解 DNG 的 `ImageWidth`。**選單讀回值不算證據。**

簽名:**單獨一幀整幅均勻暗約 3%**,八條帶同步下降、沒有列邊界
(不是撕裂幀、不是半幀、不是部分更新的緩衝 —— 那會讓某一條帶掉 23%
而其他不動),下一幀就恢復。陰影的相對降幅是高光的兩倍
(−121 vs −20 mEV),所以看起來像「陰影在閃」。

**兩個獨立的結論:**

1. **不是 OG3K 造成的。** 在我們的程式碼完全失效(FLAG=0)時照樣發生,
   而全原廠 UHD 的事件率是 OG3K 的**三倍多**。使用者換乾淨 SD 卡冷開機
   (卡上沒有 VSHL.BIN,USB shell 一起消失 = 純原廠)後 FHD/UHD 仍然閃,
   **相機自己的 LCD 也閃** —— 也不是擷取卡的產物。

2. **幅度是不變量,只有頻率會變。** 四種組態的陰影幅度是
   7.84 / 7.94 / 7.90 / 7.95 %,最大單幀跳動 120-127 mEV ——
   **落在 0.1% 內**。而事件率從 1.3 跑到 10,差 8 倍。
   一個「幅度固定、頻率浮動」的單幀事件是**離散故障**,不是模擬電源下陷
   (下陷的幅度會隨負載變)。[C]

## 7b. 頻率隨電氣負載變 —— 這回頭解釋了 §6 的 SSD 觀察 [I]

使用者 2026-09-27 實測:**換原廠電池 + 拔掉 USB,閃爍變好但沒消失**。
量出來是 **10 → 1.3 次/20秒**(約 8 倍),幅度不變。

這讓三個先前互相矛盾的觀察一致了:

| 觀察 | 出處 |
|---|---|
| 換 SSD 閃爍的樣子會變 | `OG3K_WHAT_WAS_WRONG.md` §6,當時被否定 |
| 換原廠電池會變好 | 2026-09-27 |
| 拔掉 USB 會變好 | 2026-09-27 |

`OG3K_WHAT_WAS_WRONG.md` §6 當時的推論是「跟儲存媒體有關就不是幾何錯誤,
是頻寬」,後來因為幾何上的理由把頻寬假說整個否定掉。**那個否定否定得太多了**
—— 幾何確實不是原因,但「負載影響頻率」這一半是對的。

推論 [I]:這是原廠 live view 的離散故障,**頻率隨電氣/負載環境上升**。
OG3K 12-bit 是頻寬最高的模式(29.97p 要 273 MB/s),實拍時負載最重,
所以社群把它回報成「OG3K 的問題」是可以理解的 —— 但**同一個故障在原廠
UHD 上更頻繁**。

**尚未做的隔離實驗**:同電池同卡,只切 USB 連/不連(隔離 USB 單一變數);
待機 vs 錄影中(隔離寫入負載);不同 ISO(隔離模擬增益)。

## 7c. 社群的兩個候選原因,以及量測能區分哪一個 [C]/[I]

使用者 2026-09-27 提供:SIGMA fp 臉書社團與 Reddit 上有大量一模一樣的回報,
描述是「**戶外/自然光、純監看 Live View 時螢幕偶爾極輕微暗閃,
一按錄影或拍成照片,成品完全正常**」。社群歸納出兩個原因:

| # | 社群的說法 | 我的量測怎麼看 |
|---|---|---|
| 1 | 測光/光圈在未錄影狀態的即時補償:處理器不斷微幅控制光圈葉片與電子增益;**按下錄影就鎖定,閃爍立刻消失** | **支持。** 幅度是嚴格不變量(四種組態 7.84-7.95%、120-127 mEV,差在 0.1% 內),而且事件是**整幅八條帶同步的位階階躍**。「幅度量化、頻率浮動」正是**離散致動器/增益階**的指紋 |
| 2 | 特定 ISO 下的 Live View 降採樣,暗部雜訊看起來像在閃 | **不支持。** 我量到的是**整幅均勻**的位階變化,不是雜訊形狀。降採樣雜訊不會讓八條帶同步下降同一個比例 |

**所以量測把兩個候選原因分開了**:這個事件是真實的全域曝光/增益階躍,
不是「暗部雜訊看起來像閃」。

⚠️ **「按下錄影就消失」我還沒驗證,而我的錄影擷取窗太短。**
`fix_record.gray` 只有 57 幀 ≈ 1.9 秒,而事件每 6-15 秒一次 ——
那個窗不可能抓到,所以「錄影中 0 事件」**不是證據**。這一項與社群說法一致
但未測,是下一輪第一個該做的(§7b 的隔離實驗 2)。

⚠️ **幅度換算的界線**:§7 的 mEV 是**8-bit 顯示碼**的 log2,不是場景光的
EV。HDMI 是 gamma 編碼的,所以「120 mEV 碼」對應的光量變化取決於色調曲線
的局部斜率(冪次 1/2.2 的話約 0.26 檔)。**不要拿它直接去對「1/8 檔光圈階」**
—— 形狀(量化的階躍)對得上,絕對值對不上,需要用 RAW 或已知曲線才能定。

### 決定性的一刀:無電子接點的手動鏡 [?]

若原因 1 成立,換上**沒有電子接點的手動鏡**(或拿掉鏡頭)應該讓事件歸零,
因為沒有光圈葉片可以被即時補償。這一刀不需要程式碼、不需要 shell,
而且能一次判定「光圈致動」與「電子增益」哪一個是主因。**未做。**

另外,原因 1 對 §7b 的電氣依賴解釋較弱:為何拔 USB + 換原廠電池會讓
光圈補償少 8 倍?可能的連結是「供電邊際讓測光/AE 迴路更吵 → 重新平衡
更頻繁」[I],但這是推論,沒有量測支撐。

### 對本專案的意義

如果這是機身在**待機 live view** 的原廠行為,那它與 §1-§5 的三欄修正
**完全無關**(三欄有 FLAG + profile 83 雙守衛,只在錄影 case 生效,
見 §8)。三欄仍應保留,但理由只有「正確性」。

**同時要注意兩個回報指向不同條件**:本文的起因是「OG3K **錄影中**閃爍」,
而社群的描述是「**沒錄影時**閃、一按錄影就正常」。兩者若都真,就是兩件事,
不要用同一個假設去追。

## 7d. ★ OG3K + 119.88 -> 錄成 UHD 且畫面拉長。已修,A/B 閉合 [C]

2026-09-27 使用者回報:「og3k 120 禎舊版有問題,畫面會拉長,錄出來變成 UHD」。

### 機制(反編 + 實機確認)

`FMT_OG3K` 只有八個鍵,最高 `OG3K100`。選 119.88 時
`XC_LiveViewConfiguratorW71c1__v2`(0xC043CAF0)依 enum 10 給後綴 `"120"`,
`FUN_c043b828` 組出 **`OG3K120`** —— 我們的表與原廠三張 picker 表都查不到,
原廠的錯誤退回給出 `&DAT_c0be5b50` = TAB3[0] = **UHD30**
(同一條退回路徑見 `OG3K_8BIT_10BIT_FALLS_BACK_TO_UHD.md`)。

而 `og3kout` / `og3kaspect` / `og3kaspect2` **只看 FLAG**,於是:

```
picker 說 UHD30 (16:9)  +  顯示鏈被強制成 3:2  ->  畫面拉長
錄影幾何跟著 UHD profile                      ->  檔案是 UHD
```

`og3kcanvas` 有 profile 守衛(r5 == 83)所以完全不動作 —— 這就是為什麼
**檔案本身是乾淨的 UHD 檔、不凍結**。損害限於顯示與曝光。

`OG3K120` **物理上不可能**:全機最小 hmax 是 330,3032x2012 的上限
`72e6/(330*2012)` = 108.4 fps(`FORMAT_REGISTRY_DESIGN.md` §5 早就記了)。
當年寫「那一格只能留原廠 FHD120」,但那個意圖實現不了 —— 鍵帶著 OG3K 的
標籤,永遠碰不到原廠的 `FHD120` 那一筆。

### 為什麼只有接 SSD 才會中 [C]

SD 卡上 OG3K 可選的格率**恰好就是我們表裡的七個**(實機掃 enum 0..13,
用 donor 時序記錄的指紋反推):

```
選單 enum  1->23.98  2->25  3->29.97  4->50  5->59.94  12->24  13->48
           0、6~11 一律「寫不進去」= 設定層拒絕
```

100 與 119.88 的 enum 是 **6 與 7**(見下),在 SD 上被設定層拒絕。
接了 SSD 允許清單放寬,於是選得到 -> 才會踩到。

### 格率選單的內部結構 [C]

`MenuItemSelector<eXC_MenuFrameRate>::v1` @ **0xC00B20E8**(v0 0xC00B1540、
v2 0xC00B2880)。物件大小 0x1C:

```
+0x04 設定物件   +0x08 值陣列   +0x0C 游標   +0x14 最大索引   +0x18 環繞旗標
```

值陣列是**靜態**的,而且兄弟變體就排在旁邊 —— 那就是原廠的閘門機制:

```
0xC0CDACB8  [1,12,2,3,13,4,5,6]     8 項,最後是 100       <- 「只到 100」
0xC0CDACD8  [1,12,2,3,13,4,5,6,7]   9 項,最後是 119.88    <- OG3K 在用
            enum: 1=23.98 12=24 2=25 3=29.97 13=48 4=50 5=59.94 6=100 7=119.88
```

**清單在 SD 上也是九項**(最大索引 8),游標本來就到得了 119.88;擋它的是
設定層,不是清單。

### 兩條被否決的修法,以及為什麼

| 做法 | 否決理由 |
|---|---|
| `fmttable` 把 `OG3K120` 夾成 OG3K100 那一筆 | 感測器會跑 100 fps 而選單是 119.88。管線若照選單格率配置就等不到幀 —— `HSW_240FPS_MODE12.md` §20 的「22 格請求永遠不會完成,錄影結束不了(需斷電)」。HSW 的方向是感測器**比較快**(已驗證可行),我們這個方向是**比較慢**,未測 |
| 撤掉 FLAG(像 og3kfmt 對 MOV 那樣) | 撤 FLAG 要連帶跑 GTAB 交易(六個**共用**預覽 profile 的可見高 1125<->1334)。不跑就會讓原廠 16:9 的預覽停在 1334 -> 一樣變形。而那套交易只能在 setter 裡跑,**而 UI 的格率路徑不經過 `0xC005C0B8`**(掛探針實測:shell 的 `menu` 會經過,畫面選單一次都沒經過) |
| 把游標上界從 8 收到 7(真的選不到) | 技術上可行且最漂亮,但使用者選擇了「退化成 UHD」而不是「選不到」 |

### 採用的修法:顯示鏈聽 picker,不聽選單

```
MATCH = 0xC0731C44   開機值 1
fmttable  命中 OG3K 鍵 -> 1  ;  看到自家標籤但查不到 -> 0     +13 字
og3kaspect / og3kaspect2 / og3kout   條件收緊成 FLAG && PICKOK  各 +5 字
```

- `og3kout` **只收緊 FLAG 那一支,PBFLAG 不碰** —— 回放我們的片子時必須維持
  3:2(2026-09-13 的 `SS__0427`)。
- 刻意**不動** `og3ksel` / `og3kfmt` —— 那兩個是修硬凍結的關鍵 payload。
- 開機值 1 = 在看到壞鍵之前逐位元組等同改動前;`OG_MATCH=0` 回到舊行為。
- **自我修復**:格率回到合法值 -> picker 再被查 -> `MATCH` 回到 1。
- OG6K 受益最大(表裡只有四個格率,未支援的最多);HSW 表含 120/240,行為不變。

### 上機狀態(2026-09-27 收盤)

修正版在卡上(`fpSup.BIN 9bfb9c7fb668`),`--check` 通過、`MATCH` 開機值 1。

  mode 117(MONIT1_100)、時序 330/270/2182,而引擎格率是照抄原廠 FHD100
  宣告的 **50.0**(不是 100)。
- **60p** 是 `FUN_c01cef08` 的 `+0x090 != 0 && 引擎格率 == 60.0` 閘門在改完
  之後第一次為真 —— 那是唯一被標為「上機前該測」的風險。

### ★ A001_182:缺陷留下的實體證物(2026-09-27 09:11,SSD)

```
/Volumes/Untitled/CINEMA/A001_182   (使用者的 SSD,卡名 "Untitled")
3856x2170  12-bit  crop 3840x2160 @(8,5)  FrameRate 120000/1001
BaselineExposure 330/1024 = +0.322        只有 31 幀
```

三個指紋同時出現,正好是本節推導的那個狀態:

| 指紋 | 說明 |
|---|---|
| 幾何是 **UHD** 3856x2170 | picker 退回了 TAB3[0] = UHD30 |
| 幀率是 **119.88** | 容器跟著選單走,不是跟著 picker |
| 12-bit 卻是 **+0.322** | 該是 +3.000。`og3kgs`/`og3kfps` 因為 FLAG=1 還開著,用 OG3K 的假設算增益 —— 就是「損害限於顯示與曝光」的曝光那一半 |
| 只有 31 幀 | UHD 12-bit @119.88 = 1.5 GB/s,寫不動 |

⚠️ **當時選了什麼沒有被記錄**,所以這是很強的間接證據而不是證明。
但四個指紋同時對上、時間也吻合。**在它被覆蓋之前值得留著** ——
這是這個缺陷唯一的實體證物。

### 8-bit / 12-bit 的 BaselineExposure 是位深分派,不是缺陷 [C]

2026-09-27 在 OG2K 上做的差分(同格率同場景,只切位深):

```
OG2K 8-bit  23.98   strip 2,709,504 = x1.0   BE +0.322
OG2K 12-bit 23.98   strip 4,064,256 = x1.5   BE +3.000
```

`og3kgs` 讓 `FUN_c03a6dd8` 回 1,之後 `FUN_c039dde8` **依位元深度分派**;
12-bit 拿到 gain_state 7(門檻 3200、+3.000),8-bit 拿到另一個。
SSD 上六段素材全部符合這條規則(8-bit 一律 +0.322、12-bit 一律 +3.000),
**只有 A001_182 例外** —— 那正是它是壞掉那一段的第四個指紋。

**未追**:8-bit 的 +0.322 是否也少了高光餘裕。要判斷需要一段**原廠** UHD/FHD
8-bit 當對照,目前沒有。

### OG2K 上機驗證(2026-09-27)[C]

`og2k-fast/fpSup.BIN f1aec3c7486d`。不需要 SSD 的部分全部通過:

**OG2K 的錯是反方向的**(引擎被告知 60 而原廠說 24),所以 23.98 那一格才是

**OG2K 碰不到 120p 的缺陷** [C]:使用者實測「OG2K 接上 SSD 最高也只有 100」。
所以 `OG2K120` 的壞鍵路徑從選單到不了,`MATCH` 對 OG2K 只是用不到的安全網。

⚠️ **未解的不對稱**:兩個產品佔同一個解析度槽(enum 4)、共用同一列 CSV,

## 9. 永久性:這套工具沒有寫非揮發性位置的路徑 [C]

使用者擔心 OG3K/OG2K 造成永久影響。程式碼層面:

- 計畫裡每一筆都是 `mem set` 到 RAM(cave `0xC0730000..0xC0740000`
  加韌體 RAM 複本的 hook 點),`check()` 驗每個位址都在允許範圍內。
- `og3k_load.py` 對要碰的每個位址先抓原廠快照,**拒絕**在「不是全原廠、
  也不是同一份計畫已完整安裝」的狀態上動作;錯誤路徑 `_rollback` 寫回原廠。
- 專案規則禁止 `menu save` / `setting save` / `setting write`(FlashValue),
  載入器一次都沒呼叫。
- **唯一刻意跨電源存活的是一個字**:`OGSAVE = 0xC30754CC`
  (XC_CommonSaveData +0x290)。挑它正因為原廠沒有任何程式碼讀它,
  而且不在快速啟動佔用的 +0x028..+0x200 內。

要實際稽核而非推論:卡上放回 `VSHL.BIN` + AutoRun,跑
`og3k_load.py --check`(996 個位址、零寫入、逐位址分類),再讀 `0xC30754CC`。
**尚未執行。**

## 11. 儀器的教訓

HDMI 擷取可以把「看起來有沒有閃」變成數字,但兩個陷阱各踩一次:

1. **avfoundation 回報假時基**(`1000k tbr`),`-t` 會讓 ffmpeg 瘋狂複製幀 ——
   寫出 202 GB 把磁碟塞滿。一律用 `-framerate N` 在 `-i` 之前、
   `-fps_mode passthrough`、`-frames:v N` 計數、`-fs` 當硬上限。
2. **擷取卡的第一幀是殘幀**(只填了部分畫面)。不丟掉開頭 3 幀,
   它一個人就製造 556 mEV 的假峰對峰,把真訊號(3 mEV)完全蓋掉。
   我第一輪的「357/650 mEV 閃爍」全部是這個。

3. **★ 沒有訊號時擷取卡送的是它自己的 "No Signal" 靜止卡。** 逐幀差恆為 0,
   偵測器報「0 事件」—— 看起來像「閃爍消失了」。我因此一度**錯誤地收回**
   §7 的簽名(說它「不穩定」),而那份「400 幀 0 事件」的擷取根本沒接 HDMI。
   **每一份擷取都要先驗訊號活性**:活的相機畫面光是雜訊就有 ~1.7 位階的
   逐幀差。`build/lvflicker.py` 的 `assert_live()` 擋這個,門檻 0.20。
   同樣的錯在這個專案裡已經是第三次:`RECORDING_REGRESSION` 的
   「S_ACTIVE = 0 讀成從未啟動」、`LIVE_VIEW_DISPLAY_CHAIN` §7 的
   「擷取器只抓第一次」,都是**沒有驗證儀器本身的狀態**。

第三個:**偶發事件要用事件偵測(6σ + MAD),不是變異數**,而且窗要夠長。
2 秒的窗量不到每 6-10 秒一次的事件,而 p2p/std 會把它稀釋掉。
