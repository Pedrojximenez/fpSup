**檔頭沒有一項是錯的。** `DefaultCropOrigin (12,6)` 正是 active 3008×2000 置中的結果。

## 2. ★ Hook 點與 record 佈局

```
C043A18C  ldr r1, [ip, r5, lsl #2]   選擇器 → geometry index
C043A198  bl  FUN_c0439d18           把 record 組進 r4+0x5C
C043A19C  mov r0, r4                 ★ hook 在這;被位移的就是這一條
C043A1A0  bl  FUN_c043a1c8
C043A1B4  bl  FUN_c0434ec0           推導
```

當下:**`r4` = FieldAngle 物件,record 在 `r4+0x5C`,`r5` = 選擇器。**
Hook 返回前必須補回 `r0 = r4`。

### record 欄位(實機量測確認)

```
+0x00  base W        +0x04  base H        ← allocator 用它算 RAW buffer
+0x24  active W      +0x2C  active H      ← DefaultCropSize 的來源
+0xDC  override W    +0xE4  override H    ← 尺寸 getter 用它,決定 DNG 檔頭
+0xF4  input W       +0xF8  input H       ← 感光元件送進來的形狀
```

**兩層都要改。** 只改 override 會讓檔頭和後面的位元組長度對不起來;
只改 base 會讓檔頭沿用舊尺寸。

3032×2012 的值:

```
base 3032×2012   active 3008×2000   override 3032×2012   input 3032×2012
```

`3008×2000` 是原廠 3K geometry 既有的 active-area 慣例,拿到置中的
`DefaultCropOrigin=(12,6)`。要全畫布 active 就填 3032×2012。

### ⚠️ 我用賦值順序推偏移,推錯了

`FUN_c0439d18` 是欄式 gather,我照 `param_1[N] = ...` 的順序把 N 當成 word index,
推出 base 在 `+0x0C`、active 在 `+0x20`、override 在 `+0xD8` —— **全部差 4,而且是錯的。**
(只有 `+0xF4/+0xF8` 湊巧對上。)

證據是記錄器同時抓兩組偏移:同一個 profile,正確偏移讀到 `1936/1090/1920/1080`,
我的偏移讀到 `3048/2022/3032/3048` —— **那是我自己稍早寫進去的值**,
也就是我把數字寫進了完全不相干的欄位。

**教訓:反編譯的賦值順序不保證等於結構偏移。** 要偏移就去量,不要從 C 推。

## 3. ★ 我漏掉的一整層:選擇器 → index → 列

```
r5  ──DAT_c0bd05d4[r5]──▶  geometry index  ──▶  SoA 的欄陣列
```

我先前用 sensor 幾何去猜「第幾列」,連 `DAT_c0bd05d4` 這層轉換都跳過了 ——
所以那 39 列的 patch 是三重錯誤:錯的層、錯的列、錯的偏移。

實測經過 record-start 的四個 profile(去重記錄,覆寫前的值):

```
r5=  5  index=  2   base 0x0        input 2016x1344     即時取景
r5=210  index=153   base 0x0        input 2016x1344
r5=175  index=122   base 1936x1090  input 3032x1708     ★ CinemaDNG 畫布
r5= 73  index= 39   base 0x0        input 3032x2012     另一個消費者
```

### 順帶解掉 open-gate 文件一個懸著的觀察

文件說「`*(0xC375D840 + 8)` 讀到 175 和 3,不是有效的模式 id」。
**175 就是這裡的 `r5`**,不是模式編號 —— 它是 FieldAngle 的選擇器。

### 條件寫在值上,不要寫在 r5 上

`if base == 1936×1090` 才覆寫。這樣不管走哪一條 selector 都會命中
(CinemaDNG 可能另有 kind3 路徑,靜態證不出每次都選到同一個),而其他 profile 不受影響。

## 4. 未解:檔頭對了,像素資料是花的

機身預覽花屏。檔頭宣告 3032 寬、每列 4548 bytes 緊排 12-bit,
但 producer 寫進去的位元組不是那個形狀 —— 典型的行距沒跟上造成的斜切。

**你給的八個欄位裡沒有 pitch/stride。** 下一步就是找那一格 ——
record 裡還握著舊形狀的欄位,候選值是 `1936`、`1708`、`2904`(1936 緊排)、
`4548`(3032 緊排)。

一條佐證:profile 2 覆寫前的 `input` 讀到 **3032×1708**(不是 2012),
所以那一格在錄影當下確實還是舊值,而 ISP 可能在更早的路徑就照它程式化好了。

## 5. ⚠️ 我把相機弄凍結了 —— 讀過界

倒整份 record 的版本用 `SPAN = 0x140`(320 bytes),但:

```
record 只有 65 個欄位 = 0x104 bytes   (FUN_c0439d18 的賦值數量)
你給的偏移最高只到 +0xF8
建構函式已知寫到 +0x168
0x5C + 0x140 = +0x19C                 ← 越過全部
```

讀到未映射頁 = data abort,而它跑在韌體活路徑上、shell task 握著 dispatcher,
整台從 USB 消失(`LIBUSB_ERROR_NO_DEVICE`)。拔電池。

**`0x110` 就夠。** 我挑 `0x140` 是想「一次拿全」,沒有拿已知欄位數去核對 ——
`fp-usb-shell` 技能檔那五條凍結原因裡沒有這一條,但它同屬一類:
**payload 讀寫的範圍要有依據,不能取一個「應該夠大」的數字。**

> 卡上的資料沒事。A001_008 是在凍結前就寫完的,9,229,824 bytes、81 幀,檔頭驗過。

## 6. 訂正:`0xC096F588` 那次不算排除

`CANVAS_IS_NOT_THE_SETTINGS_BLOCK.md` §14 把 CinemaDNG 畫格尺寸表列為「已排除」。
**降級:它根本不在這條資料流上**,所以改了沒反應是應該的,那不是排除掉一個候選,
只是打錯地方。同一節「尺寸是算出來的不是查表來的」這個結論仍然成立 ——
而且現在知道算它的是誰了。

## 7. 工具:record 記錄器

`scratchpad/rowlog.S` + `rowlogctl.py`(`arm` / `read` / `off`)。

```
借 0xC043A19C,置換 mov r0, r4      → bl 0xC072F800
payload 只碰 r0-r3 與 ip,全部保存    → 六個暫存器,偶數
以 r5 去重                          → 這條路徑被走幾千次,要的是集合不是最後一筆
返回前補 mov r0, r4
```

`off` 把 `0xE1A00004` 寫回去。武裝前會檢查現場是不是原指令,不是就拒絕。

**這是這個專案第一次在韌體活路徑上掛自己的 hook 並成功取得資料**,
不是借 shell 指令、也不是借陀螺回呼。

## 8. ★ Producer 的 cap:`sl+0x64/+0x68`

畫布是對的、檔頭是對的,但 producer 只填左上角一塊。用 `C01BE5E4` 的純紀錄 hook
(Thumb,見第 9 節)抓到錄影路徑那一次呼叫:

```
src 3032 × 2012        sl+0x58 / sl+0x60      ← 已經是新畫布
tgt 3032 × 2012        sl+0x74 / sl+0x78      ← 也對(即時取景時是 0,錄影才填)
★   1936 × 1090        sl+0x64 / sl+0x68      ← 沒跟上,就是 cap
producer 1922 × 1088   r4+0x08 / r4+0x0C
         1920 × 1080   r4+0x18 / r4+0x1C
```

**source 與 target 兩端都已經是 3032×2012,中間這一對還釘在舊畫布。**
producer 從它推出輸出:`1936×1090` → 去 padding 得 `1920×1080` → 重新對齊成 `1922×1088`。

同一次呼叫裡 `sl+0x7C/+0x80` = `0x8000015E` / `0x80000216` —— 最高位被設起來,
是旗標不是單純座標。

### 對 `+0xD8/+0xE0` 的判定

先前把 `record+0xD8/+0xE0`(1936/1090)改成 3032/2012 —— 927~1204 次命中、
覆寫前的值確認過 —— **producer 完全沒動。** 所以那一對不是 producer 的輸入,
或至少不是唯一的。

### 修的位置

在 `C01BE5E4` 寫 `sl+0x64` 來不及:那時 `FUN_c01becd8` 已經回來、`r4+0x08` 已算完。
要攔在呼叫之前,也就是 `C01BE5DE` 那條 `bl #0xc01becd8`。

## 9. Thumb hook

`C01BE5E2` 是 **2 bytes** 的 `ldr r0, [sp, #0xc]`,而 Thumb `bl` 是 4 bytes ——
掛上去會吃掉後面 `movw` 的前半、留後半當垃圾。

改掛 `C01BE5E4`(4-byte `movw r1, #0xd844`),精確置換:

```
r0 已由未被動的 ldr 載好;r4 與 sl 都還活著;lr 回來是 C01BE5E8,不用調整
兩條指令之間沒有東西碰 r4 或 sl
```

BL 編碼不要照公式硬寫 —— **組出來之後用 capstone 反組譯回去對**,
`71f10cf1` → `bl #0xc072f800` 這樣才算數。

Thumb payload 放 `0xC072F900`(`C043A19C` 的 ARM hook 佔著 `0xC072F800` 起 232 bytes)。

### 兩個教訓

**去重要真的去重。** 第一版只抓「第一次」,結果抓到開機後最早的即時取景呼叫
(`src 2016×1344`),不是錄影路徑。第二版改成以 `(src W, src H)` 去重記多筆才對。

**而第二版的去重迴圈有 bug**:`add r5, r5, #0x80` 之後忘了加 `i*128`,所以永遠只跟
entry[0] 比,四筆 `src 3032` 全被當成新的追加進去。無害(四筆內容一致,反而是旁證),
但要修。

## 10. 判讀花屏不要用「非零」

未填區是**雜訊,不是零** —— 逐 byte 數非零會判成「整張都有資料」。

可靠的判別是**梯度平台**:雜訊區的水平梯度極度平坦(703±76),影像區起伏很大
(581~1968)。以「偏離平台超過 6σ 的最後一行/列」定位,量到 1937×1289,
與肉眼判讀的 1936×1288 一致。

## 11. ✅ 驗收:怎麼證明「填滿了」

三種判別法,只有第三種在成功之後仍然有效:

| 方法 | 結果 | 問題 |
|---|---|---|
| 逐 byte 數非零 | 「整張都有資料」 | **錯** —— 未填區是雜訊不是零 |
| 梯度平台 6σ | 1937×1289(未填時正確) | 成功後失效:沒有雜訊平台可當基準,量到 2485×2012 這種假數字 |
| **相鄰列相關性** | 見下 | 不需要基準區,成功與否都成立 |

```python
a, b = block[:-2:2].ravel(), block[2::2].ravel()      # 同一 Bayer 相位的相鄰列
corr = ((a-a.mean())*(b-b.mean())).sum() / sqrt(...)
```

影像的相鄰列高度相關,隨機雜訊接近 0。取畫面四邊各 400 列/行:

```
A001_015   左 +0.837  右 +0.048  上 +0.846  下 +0.053   → 右下是雜訊
A001_016   左 +0.933  右 +0.879  上 +0.907  下 +0.876   → 整張填滿
```

**教訓:一個依賴「壞的部分」當基準的量測方法,會在事情做對的那一刻失效。**
我用梯度平台量到「2485×2012」並差點當成部分成功回報 —— 實際上那張是完整的。
驗收方法要在成功與失敗兩端都成立才能用。
