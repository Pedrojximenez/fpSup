# OG3K 回放:profile 的「類別」才是關鍵(2026-09-13,讀源碼)

一整天在回放上換過三種做法(改原廠名稱表、hook 換指標、換 profile 43),
三次都黑屏或花屏,我也給過三個不同的原因,**其中兩個是錯的**。
這一篇把源碼讀出來的結構寫下來,並且把錯的結論明確收回。

用到的函式(反編譯,`out/decomp/full/blk_c04.c`):

| 函式 | 作用 |
|---|---|
| `FUN_c043a158(obj, profile_id, dims)` | 載入一個 profile 成為「畫布」 |
| `FUN_c0439d18(dest, row)` | **權威的欄位對照表**:畫布第 i 個字 ← 第 i 欄[row] |
| `FUN_c0434e08(obj, pid, dims)` | `obj[0]=pid, obj[2]=dims[0], obj[3]=dims[1]` |
| `FUN_c0434ec0(obj, canvas)` | `obj[1]=canvas`;兩個維度都 >0 才算尺寸 |
| `FUN_c0435428(obj)` | 算出九個平面的「元素數 × 位元組數」 |
| `FUN_c0435588(obj)` | 把九項加總 = 這個組態要的緩衝總量 |
| `FUN_c0436300(obj)` | `return canvas+0x30 < 0.0` |
| `FUN_c04357e0(obj)` | **平面張數**:1→2,9/10/`+0x30==-1.0`→**0**,否則 3 |

## 1. `PARAM+0x30` 是「要不要配置 RAW 緩衝」的開關

`+0x30` 一直被我當成「畫格率浮點,-1.0 = 無效」。不是。它被兩個地方讀:

```c
FUN_c0436300:  return canvas+0x30 < 0.0;          // 第一項直接歸零
FUN_c04357e0:  if (ABS(canvas+0x30 + 1.0) < eps)  // 張數 = 0
                   return 0;
```

而 `FUN_c0435588` 的第一項與最後一項都是
`一個平面的位元組數 × FUN_c04357e0()`。所以 **`+0x30 = -1.0` 會把預覽平面
與 RAW 平面兩項同時歸零** —— 這是韌體自己表達「這個 profile 不配置擷取緩衝」
的方式,不是一個無效值。

實測全部 506 個 profile:`+0x30` 為負的只有 18 個,而且這 18 個的張數全部是 0。
其餘 488 個張數全部是 3。這條界線沒有例外。

`fmttable.S` 為了解決「錄影最後一禎花屏」把 30.0 寫進 p43 的 `+0x30`。
現在知道那一禎花屏的成因是**張數 0 = 沒有 RAW 緩衝**,寫 30.0 讓張數變成 3,
所以它有效。這個修法是對的,但它同時把 p43 從「純預覽類」翻成「擷取類」。

## 2. 收回:黑屏不是緩衝池爆掉

昨天的結論是「p43 的 RAW 半部被算進總和,要求的池遠大於回放保留量 → 黑屏」。
把 `FUN_c0435588` 照著反編譯重寫一遍(`codex/opengate/sizesim.py`)實際算:

| profile | 用途 | `+0x30` | 張數 | 總量 |
|---|---|---|---|---|
| p43 | S 尺寸照片 | -1.0(原廠) | 0 | **8.2 MB** |
| p43 | 被我們寫成 30.0 | 30.0 | 3 | **15.7 MB** |
| p51 | UHD 影片回放(**正常工作**) | -1.0 | 0 | **22.0 MB** |
| p102 | UHD30 錄影 | 30.0 | 3 | 52.4 MB |

**回放路徑本來就在服務 22 MB 的 p51,15.7 MB 的 p43 遠在其下。**
尺寸從來不是問題,那個解釋是錯的。同樣收回更早的「p43 有完整 RAW 半部所以
配置器多了不預期的欄位」—— `+0x3C == 0`,RAW 那一對維度在尺寸計算裡根本沒被讀。

## 3. 真正的差別:profile 有「類別」

用 `(+0x44, +0x80, +0x1C, 張數)` 把 506 個 profile 分類,只有九類:

| +0x44 | +0x80 | +0x1C | 張數 | 個數 | 是什麼 |
|---|---|---|---|---|---|
| 0 | 0xA | 2 | 3 | 238 | 3:2 擷取 |
| 0 | 0xA | 1 | 3 | 96 | 16:9 擷取 |
| 1 | 0x9 | 1 | 3 | 72 | |
| 0 | 0x7 | 1 | 3 | 54 | |
| 2 | 0x9 | 1 | 3 | 28 | |
| **0** | **0xA** | **2** | **0** | **6** | **3:2 純預覽 = 照片檢視**(p41-46) |
| **1** | **0x1000A** | **1** | **0** | **4** | **影片回放,8-bit** |
| **1** | **0x10009** | **1** | **0** | **4** | **影片回放,10-bit** |
| **1** | **0x10007** | **1** | **0** | **4** | **影片回放,12-bit** |

十八個「張數 0」的 profile 分成兩群,而且**兩群的類別欄位不同**:

* `+0x44`:影片回放 = 1,照片檢視 = 0。`FUN_c0435af8` 開頭就是
  `if (canvas+0x44 == 0) return 0;`,而 `+0x44` 為 1/2/3 時走的是
  `*0xb9` / `*0xb1` / `*0xa1` 三組公式 —— 那是**壓縮位元流的解碼緩衝**估算。
* `+0x80`:影片回放多了 `0x10000` 這個位元(0x1000A / 0x10009 / 0x10007),
  照片檢視是裸的 0xA。低位是位元深度(7=12bit, 9=10bit, A=8bit)。

**這就是 p43 不能當影片回放 profile 的原因,而且跟大小無關:**
它是照片檢視類,`+0x44 = 0` 宣告「不需要解碼緩衝」,`+0x80` 沒有壓縮位元。
把它交給影片回放的消費端,壓縮禎沒有地方解碼 → 黑屏。

## 4. 名稱表 `0xC0BE4508` = 位元深度 × 解析度

一直記成「三組 × 四筆」但不知道三組是什麼。三組就是 `+0x80` 的位元深度:

```
group 0  (8-bit,  0x1000A):  UHD p51   FHD p53   UHDCROP p371  FHDCROP p373
group 1  (10-bit, 0x10009):  UHD p61   FHD p63   UHDCROP p381  FHDCROP p383
group 2  (12-bit, 0x10007):  UHD p71   FHD p73   UHDCROP p391  FHDCROP p393
```

十二個影片回放 profile **正好填滿十二個格子,沒有備用的**,而且十二個
全部是 `+0x1C = 1` 的 16:9。「有沒有現成的 3K 回放流程可以選用」的答案是:
**照片那邊有(p41/p42/p43 就是 3:2 純預覽),影片這邊沒有。**

OG3K 錄 12-bit,所以走 group 2;3032x2000 不匹配四個解析度中的任何一個,
落到 FHD 的 **p73**(預覽柵格 1936x1090)→ 用 16:9 幾何顯示 3:2 的片子 → 花屏。

## 5. 依原有設計的延伸點

p73 的**感測器視窗原廠就是 3032x1708** —— 寬度已經對了,錯的是高度與柵格。

畫布是「每次載入時複製到 RAM 的一份」,韌體自己就用 `+0xD8/+0xE0` 覆寫
`+0x0C/+0x10`。所以在載入之後、算尺寸之前改那份 RAM 複本,是這個設計原本
就有的動作,不是改原廠資料。

`0xC043A19C` 這個位置剛好:

```
C043A198  bl  c0439d18      ; 畫布剛填好
C043A19C  mov r0, r4        ; <= hook。r4=obj, r5=profile_id, r6=dims
C043A1B4  bl  c0434ec0      ; 之後才算平面尺寸
```

`r5` 還是 profile id,`r4+8 / r4+0xC` 是**呼叫端給的真實片子尺寸**,
所以守衛可以是「profile 是 p73 **而且** 來源寬度是 3008/3032」,
不需要任何旗標 —— 這是一個自我判斷的 case,不是一個開關。

覆寫的值**全部從 p43 抄**,因為 p43 是韌體自己給 3032x2012 視窗用的 profile
(柵格四捨五入的方式各模式不同,算出來的一定錯,這是 2026-09-12 學到的)。
`+0x44` 與 `+0x80` **不動**,類別必須留著:

| 畫布 | p73 原廠 | 抄自 p43 |
|---|---|---|
| +0x1C | 1 | **2** |
| +0x0C / +0x10 | 1936x1090 | **2024x1341** |
| +0xD8 / +0xE0 | 1936x1090 | **2024x1341** |
| +0x20 / +0x28 | 1920x1080 | **2000x1334** |
| +0x60 / +0xD0 | 1600 | **1536** |
| +0xF4 / +0xF8 | 3032x1708 | **3032x2012** |
| +0x44 | 1 | 1(不動) |
| +0x80 | 0x10007 | 0x10007(不動) |

模擬總量 **9.8 MB**,而回放池已經在服務 p71 的 18.6 MB / p51 的 22.0 MB,
餘裕充足。

## 這一篇收回的結論

1. ~~回放黑屏是緩衝池爆掉~~ → p43 要 15.7 MB,回放正在服務的 p51 要 22.0 MB。
2. ~~p43 的 RAW 半部讓配置器多了不預期的欄位~~ → `+0x3C == 0`,RAW 維度沒被讀。
3. ~~`+0x30 = -1.0` 是「無效值」~~ → 是「不配置擷取緩衝」的開關,兩處讀它。
4. ~~沒有現成的 3:2 純預覽 profile~~ → p41/p42/p43/p44/p45/p46 就是,六個。
   真正缺的是**影片回放類**的 3:2 成員,那一類十二格全滿。

## 6. 上機實測:PARAM 幾何不是回放顯示幾何的來源(2026-09-13)

第 5 節那個延伸點**上機測了,是否定的**,而且中間兩個守衛都寫錯,值得記下來。

### 第一次:守衛全錯,一次都沒命中

守衛寫成「畫布 +0x44 == 1 且 +0x80 == 0x10007 且 `obj+8` 的寬是 3008/3032」。
結果 hook 被叫 4906 次、**全部退回**,最後退回的寬度是 **1620**。

用一個純觀測的 payload(`pbobs.S`,只記不改,過濾條件是畫布 +0x80 的
bit16 = 壓縮位元流,依 profile id 去重)重測,回放期間只出現一筆:

```
profile 51   +0x44=1  +0x80=0x1000A  柵格 3856x2170  +0x1C=1  呼叫端尺寸 1620x1080
```

兩個錯:

1. **回放載入的是 p51,不是 p73。** 位元深度不影響選哪個 profile。
   原因在 `XC_LiveViewConfiguratorW71c1__v3`(mode 5)→ `FUN_c043bc68`:
   它組一個 15 字元的**字串鍵**,再用 `FUN_c043cf38(obj, 表, 鍵)` 比對。
   查表的筆數是**寫死在函式裡**的(`+0x40` = 影片表 4 筆,
   `FUN_c043ced8` 的 `+0x80` = 照片表 8 筆)。查不到就記錯誤(行號 0x41B)
   並**退回表的第一筆** —— 表 `0xC0BE4508` 的第一筆正是 `{6, p51, 222, "UHD"}`。
   所以 p51 是「鍵比對失敗的退回值」。
   HUD 上的 `FHD` 是另一條依尺寸比對的退路(`0xC0BCFE70` 的常數池),
   兩條退路本來就不一致,所以「HUD 說 FHD 但載入 p51」不矛盾。

2. **`obj+8 / obj+0xC` 不是片源尺寸,是顯示畫布 1620x1080。**
   片源尺寸在 `FUN_c043a158` 這個呼叫裡拿不到。唯一看得到 3008x2000 的是
   名稱發射器 hook(`0xC0437B48`,HUD 的 "3008x2000" 就是它畫的)。

### 第二次:守衛改對了,命中 33 次,畫面完全沒變

守衛改成「畫布 +0x80 的 bit16 有設」且「PBFLAG == 1」(PBFLAG 由 og3kname
從真實片源尺寸設定,實測確實是 1)。計數器:

```
命中(有改)          33
最後改到的 profile   51
退回:不是影片回放類 2256
退回:PBFLAG = 0     0
```

p51 的畫布被改成 p43 的 3:2 那一套(柵格 2024x1341、視窗 3032x2012、
比例 1536、+0x1C = 2)共 33 次,**畫面一模一樣,沒有任何變化**。

### 結論(以及要收回的第三個推論)

`FUN_c043a158` 載入的 PARAM 列只餵 `FUN_c0434ec0` → `FUN_c0435428` →
`FUN_c0435588` 的**緩衝尺寸計算**。它**不是**回放顯示幾何的來源。

所以第 5 節裡「p51 柵格 3856 ≠ 片子 3032 → stride 不符 → 雜訊」這個推論
**沒有證據支持,收回**。花屏的來源在別的地方,還沒找到。

`WITH_PBROW = False`,payload 與計數器留著。
下一步是對照實驗:**原廠 UHD/FHD 的片子在現在這個狀態下回放正不正常** ——
正常就表示問題只在 3032 寬的檔案,不正常就是我們裝的東西破壞了回放路徑。

## 7. p83 才是該借的 profile,不是 p43(2026-09-13)

使用者提示「可以參考一下照片 S 的回放設定」,照著看照片表,結果順手解掉了
一個一直存在的缺陷,而且讓整個方案變成**零原廠欄位修改**。

### 照片表是成對的:檢視 / 拍攝

```
檢視表 0xC0BE5CF0(FUN_c043bb20:*param_2 != 4)  span 0x80 = 8 筆,張數 0
  [3] {1, 43, 98,  "12BLOW"}   raw 3032x2012  柵格 2024x1341  視窗 3032x2012  +1C=2
拍攝表 0xC0BE5D70(*param_2 == 4)               span 0x80 = 8 筆,張數 3
  [3] {1, 83, 143, "12BLOW"}   raw 3032x2012  柵格 2024x1341  視窗 3032x2012  +1C=2
```

**p43 與 p83 的 65 個字裡只有 `+0x030` 不同**:p43 = −1.0(張數 0,檢視),
p83 = 18.0(張數 3,拍攝)。其餘完全一致。

而且鍵是組合出來的,`FUN_c043bb20` 逐段接:

```
param_2[8] == 0       → 接 "12B"
FUN_c043bdb0() != 0   → 接 "LOW"     ← 它比的就是 3008 / 2000
*(param_2+0x17) != 0  → 接 "CROP"
```

所以 **`"12BLOW"` 字面意思就是「12-bit + 3008x2000」**,而 `FUN_c043bdb0`
裡寫死的 `0xbc0`(3008)與 `2000` 是韌體自己認得這個尺寸的地方。

### 借 p43 的代價:拍 S 尺寸照片會凍結

p43 是**檢視** profile,張數原廠 0。錄影需要張數 3,所以 fmttable 把畫格率
寫進它的 `+0x030` —— 那一寫就讓 S 尺寸 12-bit 照片的檢視要求三張原本不配置的
3032x2012 RAW 緩衝(+8.2 MB)。2026-09-13 使用者拍一張 S 尺寸照片,**相機當場凍結**。

這個風險其實早就寫在 `RATE_OFF` 的註解裡(「p43 是 S 尺寸 12-bit 照片實際在用的
profile,所以畫格率必須跟著旗標還原」),但還原只綁在「OG3K 未被選中」,
而使用者是**在 OG3K 選中的狀態下**去拍照的,所以還原沒有發生。
旗標式的還原對「模式切換」這種事本來就不夠。

### 改用 p83:一個原廠欄位都不用改

* 張數原廠就是 3 → 「錄影最後一禎花屏」本來就不存在,**不需要寫畫格率**
* 幾何與 p43 完全相同 → 錄影幾何不變
* **p43 保持原封不動** → 照片檢視不受影響
* 沒有東西需要「跟著旗標還原」→ 畫格率群組整個拿掉

計畫從 429 筆降到 425 筆。組建時加了守衛:p83 的 `+0x030` 必須是正值,
且 `RATE` 必須全部是 0 —— 這兩個是整個方案的前提,寫成檢查才不會哪天悄悄失效。

### 順帶收回第四個推論

第 6 節猜「原廠寬度都是 16 的倍數(1936, 3840),3032 只有 8 對齊,
所以 12-bit 每列 4548 bytes 的 stride 讓回放解錯」。**收回** ——
S 尺寸 12-bit 照片就是 3032x2012 的未壓縮 12-bit DNG,照片檢視顯示它完全正常。
3032 這個寬度本身沒有問題。

### 回放還沒解決,但嫌疑換了

`FUN_c043bc68` 用 `param_2+0x20` 選表:`4` → 0xC0BE4508(+0x80 = 0x1000A,8-bit)、
`3` → 0x4548(10-bit)、否則 → 0x4588(12-bit)。
實測回放拿到 **p51 = 0x4508 的第 0 筆,也就是 8-bit 表**,而檔案是 12-bit。
把 12-bit 封裝當 8-bit 解,出來正好是細條紋雜訊。
下一步是用 `cfgobs.S`(hook 0xC043BE68)量 `param_2+0x20` 到底是多少,
並和照片檢視的請求對照。

## 8. 花屏是我們自己的 hook 改掉了查表鍵(2026-09-13,純讀源碼)

### 影片回放的鍵就是解析度名

`FUN_c043bc68`(配置器 mode 5)組鍵的方式:

```
C043BC7C  鍵基底 ← 0xC0BE477C 的 16 bytes(**空字串**),放在 sp+0x10
C043BCA4  ldr r2,[r5,#8]      ; param_1 的 vtable
C043BCA8  add r1,sp,#0x10     ; 鍵緩衝
C043BCAC  ldr r3,[r2,#0xc]    ; vtable+0xC = 解析度名發射器
C043BCB8  blx r3              ; 回來時 lr = 0xC043BCBC
C043BCBC  ldrb r2,[r6,#0x17]  ; 要的話再接 "CROP"(0xC0BE4774)
```

那個發射器就是 **`FUN_c0437b48`** —— og3kname 掛的地方。它是一張尺寸對照表:

```
比 [r5+8]/[r5+0xC] 對 0xC0BCFE70 = 4096x2160 → "DCI4"  (0xC0BCFE90)
                      0xC0BCFE78 = 3840x2160 → "UHD"   (0xC0BCFE8C)
                      0xC0BCFE80 = 1280x720  → "HD"    (0xC0BCFE98)
都不中                                        → "FHD"   (0xC0BCFE88,退回值)
```

那四個「名稱指標」其實是**內嵌的 4-byte 字串**,而且 `"UHD"` / `"FHD"`
**正好就是影片回放表的鍵**。所以影片表的鍵字面上是
`<解析度 token>` + 可選的 `"CROP"`。

### 我們的指紋:p51 而不是 p53

og3kname 只要看到 3008x2000 就**無條件**發射 `"OG3K"`(那一段在 FLAG 檢查之前,
`ours` 是從尺寸分支直接掉進去的)。於是:

* 鍵變成 `"OG3K"` → `FUN_c043cf38` 掃不到 → `FUN_c043bc68` 記錯誤(行號 0x41B)
  並退回**表的第 0 筆** = `{6, p51, 222, "UHD"}`
* 原廠行為應該是:3008x2000 三組都不中 → 退回值 `"FHD"` → 命中第 1 筆 = **p53**

第 6 節實測到的就是 **p51**。「p51 而不是 p53」這個落差沒有別的解釋 ——
**花屏有一部分是我們自己造成的。** 截圖 HUD 上的 `FHD` 是另一次呼叫
(帶的尺寸不是 3008x2000)走了原廠退回值,所以兩者並不矛盾。

### 修法:用 lr 分辨兩種用途

同一個發射器的輸出有兩種用途:給人看的名字,以及查表鍵。只有前者該被我們改。
`ours` 開頭加一個比較:

```asm
LDA ip, 0xC043BCBC      @ 鍵組建者的返回位址
cmp lr, ip
beq pass                @ 一律放行,交回原廠
```

PBFLAG 在這之前就維護好了,所以放行不影響旗標。照片那邊的 `FUN_c043bb20`
**不呼叫**發射器(只接固定 token `"12B"/"LOW"/"CROP"`),不受影響。
一個原廠欄位都不用改。og3kname 152B → 168B,計畫 429 筆。

### 但這還不會讓回放正確

修好之後鍵會是 `"FHD"` → p53(柵格 1936x1090、視窗 3032x1708、`+1C = 1`)。
視窗的寬度 3032 本來就對了,但仍然是 16:9。牆在這裡:

* 影片回放類只有 **12 個成員**(3 張表 × 4 筆),**全部 `+1C = 1`**,一格都沒空
* `FUN_c043cf38` 的掃描跨距 **寫死 `0x40`**(4 筆),加第 5 筆要改原廠函式
* PARAM 列是「每欄一個陣列」,無法新增

所以要讓回放正確,缺的是一個 **3:2 的影片回放類 profile**,而韌體裡沒有。
照片檢視類有六個 3:2 的(p41-46),但 `+0x44 = 0`,沒有壓縮位元流的解碼緩衝。

### 這一輪的兩個自我修正

1. 我先說「`0xC0BE44DC` 就是 `FUN_c043bc68` 呼叫的 vtable+0xC」—— **算錯了**。
   `0xC0BE44D0 = 0`(offset-to-top)、`44D4` = typeinfo,所以 vtable 基底是
   `0xC0BE44D8`,`0xC0437B48` 在 **+0x04**,而 bc68 取的是 `param_1+8` 指向的
   vtable 的 +0xC,是另一個類別的表。結論(就是這個發射器)最後靠的是
   **字串證據**:它的內嵌字串正好是影片表的鍵,而退回值 `"FHD"` 對上截圖。
2. 相機在裝了 `cfgobs` 之後一進回放就凍結,原因**還沒確定**。
   `cfgobs` 已改成 v2:不解參考 `param_1`(配置器在 mode 3/4/5 短路下原廠
   不會讀它),`r1` 加 4 對齊與位址範圍檢查。

## 9. 回放幾何住在配置器的內嵌管線,不在 PARAM 列(2026-09-13)

用 C++ 的類別結構去查關聯(`fpxref.py name Configurator`)才看懂整條鏈。

### vtable 的約定

`fpxref` 說 `XC_LiveViewConfigurator__v1 @ c0437b48` —— 我們掛的發射器就是
**基底類別的 v1**。對照 vtable:

```
0xC0BE44D0  0            offset-to-top
0xC0BE44D4  0xC0BE639C   typeinfo
0xC0BE44D8  0xC043AE48   v0
0xC0BE44DC  0xC0437B48   v1   ← base + 0xC
0xC0BE44E0  0xC043CAF0   v2   ← base + 0x10
0xC0BE44E4  0xC043BE68   v3   ← base + 0x14
```

**vptr 指向 vtable 開頭(含兩個 RTTI 字),vN 在 base + 8 + 4N。**
所以 `FUN_c043bc68` 的 `*(param_1+8) + 0xc` 就是 **v1**,和 vN 命名完全吻合。
第 8 節說「我算錯了」其實是這個約定沒看懂,結論是對的。

### v5 才是消費端,而它選的是「管線子物件」

`XC_LiveViewConfiguratorW71c1__v5`(0xC043C090):

```c
entry = (**(param_1+8) + 0x14)(param_1, param_2);      // v3:選一筆表項
// 然後用純範圍檢查判斷它來自哪張表
//   FUN_c043d058/d098/d0d8/d118/d158/d198/d1d8/d218/d258
//   全部都是 `表 <= 指標 < 表 + 跨距`,沒有別的邏輯
```

映射結果是**配置器內部的一個偏移**:

| 表 | 型別 | 幾何 | → 管線 |
|---|---|---|---|
| 0xC0BE4870 / 4BD0 / 5CF0 / 5D70 | 1(照片) | **3:2** | **`param_1 + 0x268`** |
| 0xC0BE4D50 / 5150 / 5450 | 3 / 4 | 16:9 | +0x340 / +0x3D0 / +0x3F4 / +0x43C … |
| 0xC0BE5810 / 59B0 / 5B50 | 5(錄影) | 16:9 | +0x460 |
| 0xC0BE4508 / 4548 / 4588 | 6(回放) | 16:9 | 鍵是 `"UHD"` → +0x4CC / +0x4F0<br>否則 → +0x514 |
| 全部不中 | — | — | +0x268(並記錯誤 0x511) |

**回放的顯示幾何住在這些子物件裡,不在 PARAM 列。** 這就是第 6 節那個
「改 p51 的 PARAM 畫布命中 33 次卻毫無變化」的原因,也讓那個否定結果
從「不明所以」變成「本來就不可能有用」。

還有一個副產品:我們的鍵污染不只把 profile 從 p53 換成 p51,**它把管線從
FHD(+0x514)換成了 UHD(+0x4CC/+0x4F0)** —— 用 3840x2160 的管線去顯示
3008x2000,那就是截圖裡那片雜訊。

### 出路:照片管線已經是我們要的那一條

`param_1 + 0x268` 是所有照片表共用的管線,而 **S 尺寸 12-bit 照片本身就是
3032x2012 / 3008x2000 的未壓縮 12-bit DNG,檢視時顯示完全正常**。
也就是說韌體裡已經有一條能正確顯示 OG3K 這個幾何的管線,每天都在用。

而 v5 認表的方式**只是範圍檢查**,不看內容。所以不需要新增 profile、
表項或 PARAM 列 —— 只要在 mode 5 遇到 3008x2000 時,讓 v3 回傳
**照片檢視表現成的那一筆**:

```
0xC0BE5D20 = 0xC0BE5CF0 + 3*16 = {1, 43, 98, "12BLOW"}
```

它落在 `0xC0BE5CF0 .. +0x80` 之內,`FUN_c043d0d8` 回 1 → `+0x268`,
而且**不會**觸發錯誤記錄。用 p43(檢視,張數 0)而不是 p83(拍攝,張數 3):
我們要顯示一個檔案,不需要擷取緩衝。

`og3kpbsel.S`(116 B,hook 0xC043BE68 = v3):守衛是「mode == 5 且
`param_2+0x08/+0x0C` == 3008x2000」,完全自我判斷不靠旗標(那一對就是
v1 比對的同一對欄位,PBFLAG 實測為 1 已證明回放時它確實是 3008x2000)。
唯讀引用原廠表項,**一個原廠位元都不動**。計畫 461 筆。

### 為什麼 og3kpb.S 當初會失敗

它掛在 `FUN_c0437af8` —— 那是**緩衝尺寸查詢**(建物件、算 `FUN_c0435588`、
銷毀),不是管線選擇器。替換那裡的表項只會改變算出來的尺寸,
管線還是照 v5 選的走。掛錯層。

### 尚未確認

* 裝了 `cfgobs` 之後一進回放就凍結的原因還沒確定。**注意 og3kpbsel 與
  cfgobs 掛在同一個位址(0xC043BE68)**,所以如果 og3kpbsel 也凍結,
  那就是這個 hook 點本身的問題,而不是 payload 的邏輯 —— 這正好是一個

## 10. 回放鏈讀到底:三條死路各自被證據關掉(2026-09-13)

`fpxref name Cinema` 找出整條回放鏈,全部在 `src/library/CinemaDngPlay/`:

```
CinemaDngFileReader  →  CinemaDngTagReader  →  CinemaDngRawMemInterface
                                            →  CinemaDngYuvCopier  →  顯示
DngBufferInfo(緩衝配置)   DposPreReader   XC_CinemaDngPlay(外殼)
```

### 影格緩衝:實測正確,不是問題

`FUN_c05c2d10(obj, nbytes)`(DngBufferInfo.cpp)把 `nbytes` 向上對齊 4K 再多一頁,
配置 `0x6F090` 的描述子陣列(每筆 `0x5EC`,最多 300 筆),然後**不斷配置那個大小
的緩衝直到失敗**。`nbytes` 來自 `XC_CinemaDngPlay+0xA0`,而整個 library 裡
**只有建構子 `CPlayM` 把它歸零**,找不到寫入非零值的地方 —— 所以直接上機量
(`bufobs.S`,hook 0xC05C2D10,純觀測):

```
FUN_c05c2d10 被呼叫 19 次
  nbytes =  9,229,824  → 實配  9,236,480    ← 正好是 OG3K 影格檔的大小
  nbytes =  3,244,544  → 實配  3,252,224    ← FHD 影格檔的大小
  nbytes =  8,447,488  → 實配  8,454,144
```

**回放把整個 DNG 檔讀進一個大小正確的緩衝。** 緩衝假設被乾淨否定。

### 這一輪關掉的三條死路

| 路線 | 怎麼被關掉的 |
|---|---|
| 改 profile 的 PARAM 畫布 | 命中 33 次,畫面零變化。後來才知道回放幾何在配置器的內嵌 DispParam,不在 PARAM 列(第 9 節) |
| 借照片管線(`+0x268`) | 機制正確(40 命中 / 36 放行,原廠 FHD 完全沒被碰到),但 S 尺寸照片的 DNG **另帶一張 3008x2000 的 RGB JPEG 全尺寸預覽**,照片檢視顯示的是那張 JPEG,根本不解 RAW。CinemaDNG 沒有內嵌預覽 → 粉綠斑點(SS__0422) |
| 影格緩衝太小 | 實測 9,229,824,正好等於檔案大小 |

改描述子(og3kout 那套)也不該走:它動的是 **1620x1080 這種面板端幾何**,
而截圖裡畫面**已經是 3:2 且填滿螢幕** —— 顯示尺寸本來就對,壞的是內容解讀。

### 靜態分析的終點

影格交給顯示的最後一步是

```c
FUN_c05c2708:  (**(code **)(param_1 + 0x180))(frame - 1, param_3,
                                              *(undefined4 *)(param_1 + 0x17c));
```

—— 一個**執行期註冊的 callback**(函式指標在 `obj+0x180`,context 在 `+0x17c`)。
靜態追不下去,下一步只能上機 hook 那個呼叫點,把三個參數記下來,
看它把什麼幾何交給顯示。

### 這一輪確定下來的東西

* 錄影改用 **p83**:張數原廠就是 3,不需要寫畫格率,**一個原廠欄位都不用改**,
  而且解掉了「拍 S 尺寸照片會凍結」。解檔驗證通過(A001_035,整幅完整)。
* og3kname 的**查表鍵污染**已修(`lr == 0xC043BCBC` 時放行)。
* 回放的選擇層完全畫出來了:v3 組鍵查表 → v5 用純位址範圍檢查認表 →
  選出配置器內嵌的 DispParam 管線。

## 11. 管線旋鈕:可選的值只有三個,而且都試過了(2026-09-13)

使用者指出「已經找到會讓解析產生變化的點了,就在那邊調」—— 對的。
v3 回傳哪一筆表項 = 選哪一條管線,而 v5 **只用位址範圍認表**,
所以這是一個可以列舉的旋鈕。把它做成從 RAM 讀(`PBSEL_ENT = 0xC0732390`),
換候選只要一個 `mem set`,不用重載(`pbsel_try.py`)。

v5 的檢查順序與對應管線(表有重疊,先中先贏):

```
0xC0BE4870/4990/4BD0   → +0x268  照片
0xC0BE4C50/5050        → +0x340/3D0/3F4/43C
0xC0BE4D50/5150        → 同上(type 3)
0xC0BE5450 跨距 0x300  → 鍵=="DCI4K" ? +0x560 : +0x538   ← WithRaw
0xC0BE5610 跨距 0x200  → 鍵前3=="UHD" ? +0x4A8 : +0x484   (與上表重疊)
0xC0BE5810/59B0/5B50   → +0x460  錄影
0xC0BE4508/4548/4588   → +0x4CC/4F0/514  回放(原廠)
```

### 實測結果

| 表項 | 管線 | 結果 |
|---|---|---|
| 0(不介入) | +0x4CC/4F0/514 回放 | 均勻水平條紋雜訊 |
| `0xC0BE5D20` `{1, p43, 98, "12BLOW"}` | +0x268 照片 | **有低頻結構 + 粉綠斑點**,相鄰列剪切僅 2 螢幕像素 |
| `0xC0BE5690` `{4, p331, 106, "FHD30"}` 柵格 3032x1708 | +0x538 WithRaw | **黑屏凍結** |

### 從這三個結果推出來的

+0x538 凍結的原因應該是:**那條管線屬於錄影路徑,回放模式下根本沒被填值**,
消費端拿到空描述子。同樣的理由會套用到 +0x460(錄影)與多半也套用到
+0x340 家族 —— 也就是說**在回放模式下真正「活著」的管線只有
+0x268(照片)與 +0x4CC/4F0/514(回放)**。兩個都試過了。

所以這個旋鈕的可用範圍已經走完,它不會給出正確的畫面。

但 +0x268 那一次的性質很有價值:**剪切只有 2 個螢幕像素,代表列距(幾何)
基本正確,錯的是像素解讀**。合理的解釋是照片管線預期的是
**tile 256x256 的 lossless JPEG**(S 尺寸照片就是那樣),
拿到未壓縮的封裝 12-bit,於是把原始位元組當成壓縮流去解 →
低頻結構還在(位元組本身有結構)但顏色完全錯 = 粉綠斑點。

換句話說:
* **+0x268 = 幾何對、codec 錯**
* **+0x514 = codec 對、幾何錯**

下一步應該是找出回放管線(+0x514 那一族)的幾何是從哪裡設定的 ——
它的 codec 已經是對的,只差幾何。而且影格緩衝已經證明是照檔案大小配置的,
所以幾何錯的地方在更下游。

### 一條操作規則

`PBSEL_ENT` 的**預設值必須是 0(不介入)**。這一輪把 0xC0BE5690 設成預設,
結果一進回放就凍結,而重開機後一載入又是同一個值 —— 差點變成「一開機就凍」。
要換管線用 `pbsel_try.py` 當場轉,凍結最多損失一次重播。

## 12. 檔案結構完全相同,只有尺寸不同(2026-09-13)

`FUN_c05c1a58` 是回放真正的幾何/格式讀取點,它只讀六個 tag:

```
0xC620 DefaultCropSize  → param_3[0..1]
0x0100 ImageWidth       → param_4[0]
0x0101 ImageLength      → param_4[1]
0x0102 BitsPerSample    → param_4+0x10   (12 → 0,10 → 3,其他 → 4)
0x010A FillOrder        → param_4+0x14   ((b & 0x7f) >> 6)
0xC764 FrameRate        → param_3[6]     (沒有就填 4)
```

(上一句我曾說「回放不讀位元深度」—— **錯的,收回**。那是只 grep 了兩個
helper 就下的結論,`FUN_c05c1ed0` 才是讀 0x102 的那個。)

把 OG3K 的影格和原廠 FHD 的影格逐 tag 比對:

| tag | OG3K | 原廠 FHD |
|---|---|---|
| ImageWidth / Length | 3032 x 2012 | 1936 x 1090 |
| DefaultCropSize | 3008 x 2000 | 1920 x 1080 |
| BitsPerSample | 12 | 12 |
| Compression | 1(未壓縮) | 1(未壓縮) |
| StripOffsets | 78848 | 78848 |
| FrameRate | 30000/1001 | 30000/1001 |
| FillOrder | 沒有 | 沒有 |

**兩邊的 tag 集合完全一樣,一個多的都沒有。**

所以檔案本身沒有問題,回放引擎裡存在一個**只跟尺寸有關**的限制或固定假設。
到目前為止已經排除的:

* 影格緩衝大小(實測 9,229,824 = 檔案大小,正確)
* profile 的 PARAM 幾何(改了沒反應)
* 管線選擇(可用範圍只有照片與回放兩條,都試過)
* 檔案結構(與能正常播放的檔案完全同構)

剩下最可能的是 **YUV 轉換的目的端幾何**:來源列距對(所以 +0x268 那次
只有 2 像素剪切、看得到低頻結構),但寫進去的緩衝 stride 不對就會產生
這種「有結構的雜訊」。要確認需要 hook 轉換呼叫點把來源/目的幾何記下來,
就像量影格緩衝那次一樣。

## 13. 回放交給顯像引擎的東西每一項都正確(2026-09-13)

`FUN_c05bb4a0(engine, prev, cur)` 是回放把一格 raw 送去顯像的地方,而且
**回放不是自己做像素轉換 —— 它把每一格交給 RAW 顯像引擎**(和照片顯像同一套):

```c
piVar3 = FUN_c0055ab8();                         // 顯像引擎
(**(*piVar3 + 0x1c))(local_24, piVar3);          // 取得參數區塊
FUN_c0014dac(param_3 + 0x24, uStack_20, 0x264);  // 612 bytes 複製進影格描述子
FUN_c02b8e38(0xc, 6, piVar3, uVar1);             // 送出
```

### 提交當下的快照(devobs.S,hook 0xC05BB4A0)

第一版只記描述子指標、回放結束後才讀 —— 讀到的是**拆除後的殘留**
(解析器 0、StripOffsets 0、其餘描述子幾何全 0),據此推論「引擎從檔案標頭
當像素讀」。**那個推論是錯的,收回。** 改成在 hook 當下就抄欄位之後:

```
呼叫 46 次   cur = prev = 0xCD900480   引擎 0xC37CE364
  +0x010 StripOffsets = 78,848      ✓ 與檔案一致
  +0x014 緩衝指標     = 0xD1B00780
  +0x018 緩衝大小     = 9,236,480   ✓ 檔案大小向上對齊
  +0x020 解析器       = 0xC363543C  ✓ 有效
  +0x260 寬 = 3032   +0x264 高 = 2012   +0x268 = 12   ✓ 全部正確
```

描述子陣列本身也正常:至少五個 9,236,480 的緩衝
(0xD1B00780 / 0xD23CF7C0 / 0xD2C9E800 / 0xD356D840 / 0xD3E3C880),
以 0x5EC 串接。**緩衝數量不是問題。**

### 這一輪的結論

**`CinemaDngPlay` 交給顯像引擎的每一項都是對的**:像素位址、strip 位移、
緩衝大小、解析器、3032x2012、12-bit。所以花屏發生在**顯像/縮放那一段之後**,
不在檔案讀取或影格管理。

而顯像期間顯示路徑取用的描述子(og3kout 的 FLAG=0 記錄)是
**1920x1080 / 1620x911 / 320x180 —— 和待機時完全一樣的面板端描述子**,
沒有任何回放專屬的。

所以下一個該查的是**顯像的目的端幾何**:來源 3032x2012 要被寫進一個
目的緩衝,而那個目的的寬度/stride 是誰決定的。顯像引擎是一個大子系統
(`FUN_c02b8e38`、`Daylight`、`FUN_c0055ab8`),而且照片路徑用同一套
卻能正確處理 3032x2012(S 尺寸照片)——差別在照片是 tile 256x256 的
lossless JPEG、我們是單一 strip 的未壓縮封裝 12-bit。

### 順帶記一個操作上的根因

USB shell 每次在回放操作之後就死掉,不是隨機的:
`notes/projects/usb-shell-sup/../../usb-shell-sup/notes/RECORD_SHELL_COEXIST_RESOLVED.md` 早就記過
**USB worker 武裝後,它的 IRQ 處理會與卡片 I/O 的 IRQ 互鎖(DWC3 livelock)**,
任何讀卡/寫卡的擷取動作都會踩到。已驗證的做法是**操作相機前拔線、操作完插回**
—— hook 跑在相機端,不需要主機在場。改用這個流程之後就不必再抽電池。

## 14. ★ 回放解決了(2026-09-13)

根因是兩件事疊加,而且**都不在我追了一整天的顯像/解碼鏈裡** ——
兩個都在幾何的「慣例」層。

### (一)記錄尺寸沒有遵守 fp 自己的邊界慣例

統計原廠**所有**影片錄影 profile:

| profile | 記錄 | 裁切 | 邊界 | 寬 16 對齊 |
|---|---|---|---|---|
| p171 (UHD) | 3856x2170 | 3840x2160 | **+16 / +10** | ✓ |
| p173 (FHD) | 1936x1090 | 1920x1080 | **+16 / +10** | ✓ |
| **p83(我們借的)** | **3032x2012** | 3008x2000 | **+24 / +12** | **✗** |

p83 是**照片** profile,它的記錄尺寸就是感測器視窗 3032x2012。
影片那邊的慣例是「裁切 +16 寬 / +10 高」,而且那個 +16 正好讓
16 對齊的裁切寬(1920 / 3840 / 3008)保持 16 對齊。
3032 = 8 x 379,只有 8 對齊。

依慣例,3008x2000 應該記錄成 **3024x2010**,裁切原點 (8,5)。

### (二)回放 profile 的柵格就是「來源列距」

原廠回放 profile 的柵格**正好等於該格式片子的記錄尺寸**:

```
p53 (FHD 回放)  柵格 1936x1090  = FHD 片子的記錄尺寸
p51 (UHD 回放)  柵格 3856x2170  = UHD 片子的記錄尺寸
```

我們的片子沒有對應的 profile,鍵查表失敗退回 p51(3856)或命中 "FHD" 得到
p53(1936)—— 兩者都與實際寬度不符,於是整幅被以錯誤的列距讀出 → 花屏。

### 修法:一個 hook,兩個 case,原廠 PARAM 列一個位元都不動

`og3kcanvas.S`(284 B,hook `0xC043A19C`,改畫布的 RAM 複本):

* **錄影**(`r5 == 83`):`+0x00/+0x04` → 3024 x 2010
* **回放**(畫布 `+0x80` 的 bit16 = 壓縮位元流類,且 `PBFLAG == 1`):
  柵格 `+0x0C/+0x10`、覆寫 `+0xD8/+0xE0`、視窗 `+0xF4/+0xF8` 全設 3024x2010,
  可見 `+0x20/+0x28` 設 3008x2000,`+0x1C` 設 2,
  縮放比 `+0x60/+0x64/+0xD0/+0xD4` 設 unity 1024

### 驗證

* **錄影**:A001_036 解檔 —— 標頭 3024x2010、裁切 3008x2000 @ (8,5)、
  `StripByteCounts` 9,117,360 = 3024x2010x1.5(完全吻合)、
  整幅影像清晰、邊到邊、無剪切。
* **回放**:A001_037 機內回放截圖 **SS__0426 完全正常**,
  計數器顯示錄影 case 命中 196 次、回放 case 命中 21 次。

### 我在這條路上犯的錯

**同一個 hook 我早就試過,並且結論「沒反應」。** 那次填的柵格是 **2024x1341**
(照 p43 抄的,遵守我自己訂的「柵格只能抄不能算」規則),
**而不是片子的實際記錄寬度**。規則本身沒錯 —— 錯在我沒看出這裡的約束
不是「柵格要和視窗一致」,而是「柵格必須等於檔案的列寬」。
因為值填錯,我把一個**會成功的做法判定成死路**,然後又花了好幾輪去追
YUV 轉換、顯像引擎、影格緩衝、管線選擇。

教訓:當一個實驗得到否定結果時,要先確認**填進去的值本身是不是對的**,
再把整條路線判死。

### 14b. 播放中的比例(同日稍後)

暫停那一格正確之後,**播放中**的畫面被垂直壓扁(截圖 SS__0427:內容清晰、
3:2 被塞進約 2.09:1 的視窗)。原因是輸出描述子還是 16:9 ——
`og3kout` 本來就會把它改成 3:2(高 911 → 1080、180 → 213),
但它的守衛只看 `FLAG`(OG3K 被選中),而回放時 FLAG 是 0。

守衛擴成 **`FLAG` 或 `PBFLAG`** 之後正常。實測:

```
og3kout 命中 82 次

  TPL2 idx2 已建置 → 320 x 213     (原 320x180)
拒絕環只剩 1920x1080(本來就不該動)
og3kcanvas:錄影命中 14   回放命中 39
```

計畫 554 筆。AutoRun:release 135 條 / 開發版 195 條,兩者建置器回讀自檢通過。

## 15. UI 的三個外觀問題:追到牆(2026-09-13)

症狀(截圖 SS__0428 / 0429 / 0430):

1. `MENU → 記錄設定 → 解析度` 顯示 `3` 而不是名稱
2. QS 的 RES. 格子畫出疊在一起的亂圖
3. QS 底部選項條裡我們那一格是空白的

功能不受影響 —— OG3K 可以從 MENU 正常選取、錄影與回放都對,只是不能從 QS 切。

### 排除掉的

**`MenuItemMovieRecSize::v3`(0xC00A81E8)不是來源。** 它是「解析度 enum → 寬高」
的查表,表在 0xC0742228 只有兩筆({2, 1920, 1080}、{3, 3840, 2160}),
後面緊接著終止用的字串 `"Invalid MovSize"`,無法就地擴充;OG3K 用 enum 4
查不到會走錯誤路徑,看起來非常像根因。加了一個 case 讓它在 OG3K 時回
3008x2000,**計數器確認命中 5 次、FLAG=1、enum=4,但三個症狀完全沒變**。已拆掉。

`0xC0BE4460` 那一段看似 QS 表,實際是重複五次的 `{1920,1080,3840,2160,"UHD"}`
常數池 —— 各個鍵組建函式的初始值。

### CSV 這條路走不通

選單那一行的標籤來自 CSV 的 `TEXT` 欄,而那一欄放的是**字串資源 ID**
(原廠 `0313` / `0314`)。我們塞字面字串,解析不到就退回顯示 `NO` 欄的 `3`。

空間:那塊 CSV 區塊只有 **92 bytes**(原廠內容就佔 89)。
用原廠的 6 欄格式再加第三列需要 **111 bytes**,放不下。

試過把**標頭名稱縮短**(欄位數與順序維持 6 欄)擠到 91 bytes ——
**那一列直接消失**,所以**解析器是按名稱對欄的**,標頭不能動。

搬到別處也不行:
* 整個映像裡**沒有任何字面值**指向那 108 個 CSV 區塊中的任何一個
* 也**沒有任何 movw/movt 組出 `0xC0F8xxxx`**

也就是說 CSV 區塊完全靠計算出來的位址存取,要改得先把選單資源的載入機制
整個逆出來 —— 那是一個還沒碰過的子系統。

### 目前的取捨

退回 5 欄版的 CSV:格式不完全合(少 `Popup` 欄、用 `\n`),但**那一列存在而且可選**,
只是標籤顯示 `3`。功能完整,外觀不好看。

要修這三項,得先逆出「選單字串資源 ID → 字串」以及 QS 的選項清單來源。
那是獨立的一塊工作,對錄影/回放沒有任何影響。
