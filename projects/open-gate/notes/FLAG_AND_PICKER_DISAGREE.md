## 1. 兩個真相來源 [C]

| | 誰寫 | 意思 |
|---|---|---|
| `FLAG` `0xC0731C08` | **只有** `og3ksel`(解析度 setter hook) | 「選單選了 OG3K」 |
| `HITS` `0xC0730700` | **只有** `fmttable` 的 `hit` | 「picker 真的把鍵解析成 OG3K」 |

全部 13 個引用 `0xC0731C08` 的 `.S` 裡,只有 `og3ksel.S` 對它 `str`。
`og3kname.S` 看起來也寫,但那兩筆是 `PBFLAG`(`+0x0C`)。

消費端分成兩派,**沒有一派同時看兩個**:

```
og3kcanvas  錄影 case    r5 == PROF  且  FLAG == 1      ← 幾何
og3kout / og3kaspect / og3kaspect2 / og3kfps / og3kgs   ← 只看 FLAG
fmttable    hit          只比對鍵,不看 FLAG            ← 感測器模式 + 時序
```

而 `fmttable` 的 `hit` **命中當下就把 donor 的時序記錄覆寫下去**
(`str r4, [r3, #4]` / `[r3, #8]`)。也就是說:**改感測器的條件,比改幾何的
條件寬。** 兩者不一致時,感測器已經換了模式,畫布卻還是原廠的。

## 2. 三個不一致狀態,正好對上三則回報 [I]

### 2a. `FLAG = 0`、picker 命中 → **凍結**

感測器被程式化成 donor 模式(OG3K = mode 98、OG2K = mode 139)加上該格率的
hmax/vmax,但 `og3kcanvas` 的 `FLAG` 守衛不成立 → 記錄矩陣、active、平面格式
碼、感測器視窗 `+0x0F4/+0x0F8` 全部維持 donor profile 的原廠值。

`HSW_240FPS_MODE12.md` 已經把這條規律寫死了:**`fin_cnt < req_cnt ⇒ 凍結`**,
而 §「1141 -> 1147」那段正是同一個機制 ——「p13 宣告 2016x1344,而 mode 12 只讀
672 行,不補的話 22 格請求永遠不會完成,錄影結束不了」。

**這解釋「開機沒等 AutoRun 載入直接錄影必發凍結」。** `og3k_plan.state()` 開機
把 `FLAG` 寫 0(「開機時未選」),但解析度設定是相機**自己存在設定裡**的 ——
上次關機前選的是 OG3K,開機就還是 OG3K。於是:

```
開機 → 相機還原解析度設定(enum 4) → picker 查 "OG3K30" → 命中 → 換感測器
     → FLAG 仍是 0(使用者沒進選單,og3ksel 沒跑過)
     → 按錄影 → 幾何是原廠的 → 凍結
```

⚠️ **「有沒有等 AutoRun 載完」很可能是假線索。** 真正讓它好起來的是「進選單
重選一次解析度」,那會跑 `og3ksel` 把 `FLAG` 立起來。§4 的實驗就是要分開這兩件事。

### 2b. `FLAG = 1`、picker 沒命中 → **突然跳回其他格式**

`FUN_c043b828` 查不到鍵就 `e = &DAT_c0be5b50`,也就是表 3 第 0 筆 = **UHD30 /
p171 / mode 7**。`og3kcanvas` 的 `r5 == 83` 不成立 → 錄出來是乾淨完整的 UHD30,
而選單、QS、HUD 因為只看 `FLAG` 仍然寫 OG3K。

8/10-bit 那一條路已經在 v0.2.2bd 修掉了(`OG3K_8BIT_10BIT_FALLS_BACK_TO_UHD.md`
§7),但**退回路徑本身還在**,任何讓鍵對不上的原因都會走到同一個地方,而且
不論選了哪個格率退回的永遠是 30p。

### 2c. `FLAG = 1`,但人已經不在錄影模式 → **未知原因凍結** [I]

`og3kcanvas.S` 檔頭自己寫了這個缺口:

> p83 是 S 尺寸 12-bit 照片的拍攝 profile(照片拍攝表 `0xC0BE5D70` 引用),
> 所以借它必須靠 FLAG 守衛,而 **FLAG 只是選單狀態 —— 選了 OG3K 再去拍照
> 旗標仍然立著**。

沒有任何東西在離開 CINE 時清 `FLAG`。所以「選 OG3K → 轉到 STILL → 拍一張
S 尺寸 12-bit」會讓畫布 hook 去改照片的幾何。而 `og3k_plan.check()` 旁邊那段
註解點名了後果:「plane count 一旦變 0 ——『拍一張 S 尺寸照片就凍結』就是這條」。

`build_og3k_ui_candidate.py` 的 manifest 早就把這件事掛在待辦上:
`"cine_still_transition": "hardware pending; select FHD or UHD before leaving CINE until tested"`。
**那句話現在應該升級成使用者看得到的警告,而不是 manifest 裡的一行。**

OG2K 的 donor 是 **p13**,全映像掃過沒有任何表引用它,所以 2c 只影響 OG3K;
2a 與 2b 兩個目標都會。

## 3. 為什麼「未知原因」 [I]

因為觸發條件不是「做了什麼」,而是「**有沒有再跑一次 `og3ksel`**」。任何讓
相機重新解析格式、卻不經過解析度 setter 的路徑都會造成 2a:開機還原設定、
CINE/STILL 來回、設定重置、熱重啟。使用者沒有辦法把這些關聯到自己的動作,
所以回報只會寫「突然」「不知道為什麼」。

## 4. ★ 決定性實驗 —— 兩次 `mem get`,不用錄影,零風險

`build/ogstate.py` 就是為這個寫的。

```
A(對照組) 冷開機,讓 AutoRun 跑完出 banner,**完全不要碰選單**,
          接 USB 跑  OG_TARGET=og3k ./ogstate.py
B(處理組) 同一次開機,進 MENU 重選一次解析度,再跑一次 ogstate.py
```

預測:

```
A  FLAG = 0    HITS > 0    donor 時序 = 非原廠     -> 半武裝,此時錄影會凍
B  FLAG = 1    HITS > 0    donor 時序 = 非原廠     -> 一致
```

**A 若真的是 `FLAG=0` 而 `HITS>0`,§2a 就成立,而且「等 AutoRun」是假線索。**
A 若 `FLAG=1`,表示相機開機時確實跑過解析度 setter,那 2a 要改由載入期競態
解釋(AutoRun 武裝 hook 的那幾秒),修法不同,見 §5c。

第二個實驗,針對 2c:選 OG3K → 轉 STILL → `ogstate.py` 看 `FLAG` 是不是還是 1。
是 1 就不要按快門,直接把結論寫下來 —— 這一步**不需要真的把相機弄凍結**。

## 5. 修法,按「先讓不一致不可能發生」排序

### 5a. 止血,今天就能做:`fmttable` 的 `hit` 順便立 `FLAG` [I]

`hit` 已經在寫 donor 時序了。**改感測器和改幾何本來就該是同一個條件**,
現在一個寬一個窄,這就是全部的病。在 `hit` 裡 `str #1 → FLAG`(接在現有的
`dmb ish` 之前),2a 整類直接消失,而且是自癒的:任何路徑只要真的解析到
OG3K,畫布就一定跟著武裝。

代價:要配一條清除規則,否則 2c 變嚴重。掃完我們的表沒命中就落到 `pass`,
但 `pass` 也接非 CinemaDNG 的查詢。精確的位置是 `loop` 走到表尾那一次
(`ldr r3, [ip, #0x14]; cmp r3, #0; beq pass`)—— 那代表「這是一次 CinemaDNG
查詢,而且不是我們」,在那裡清 `FLAG` 才對。**清除規則會不會在選單瀏覽時
把 `FLAG` 洗掉,是這個修法唯一的風險,要先量 picker 的呼叫頻率。**

### 5b. 同樣便宜,而且沒有風險:開機不要留在 OG3K

`state()` 現在寫 `FLAG = 0`。與其讓設定與旗標對不上,不如讓載入器在最後把
解析度設定推回 FHD/UHD —— 開機永遠是原廠格式,要用 OG3K 就得進選單選一次,
那一次自然會跑 `og3ksel`。誠實、不可能半武裝,代價是每次開機多按幾下。

**在 §4 的 A 組確認之前,這是唯一可以直接出貨的修法。**

### 5c. 若 A 組顯示 `FLAG=1`(也就是載入期競態才是主因)

把所有 hook 的 payload 開頭加一個共用的 `ARMED` 字閘門,payload 與 hook 全部
寫完之後才用**一個字**把 `ARMED` 翻成 1。武裝窗口從「十幾個 hook、好幾秒」
縮成一次寫入。`HOOKS` 現在只保證 payload 在 hook 之前、picker 最後 arm,
**沒有保證 hook 彼此之間是原子的**。

### 5d. 2c 的正解

`og3kcanvas` 的錄影 case 不能只靠 `FLAG`,要再加一個「現在是錄影不是拍照」的
條件。最省的可能是查畫布 `+0x80` 的類別位元(回放 case 已經在用同一個欄位),
但**要先找出照片路徑在那一欄放什麼** [?]。在那之前,README 應該明講:
**離開 CINE 之前先把解析度切回 FHD 或 UHD。**

## 6. 待驗

- §4 A/B 兩組,以及 CINE→STILL 的 `FLAG` 殘留 [?]。
- picker 在選單瀏覽時的呼叫頻率(決定 5a 的清除規則可不可行) [?]。
- 相機開機時到底有沒有呼叫解析度 setter `C005C020` [?] —— 這一題也可以
  直接看 `ogstate.py` 的 `og3ksel 次數`:開機後不碰選單,那個數字是不是 0。

## 7. §2a 對 OG3K **是錯的**,收回

強制 `FLAG=0` 而 `SetMovRecSize` 保持 4,然後錄影:

```
rec log-out ->  file-size=3244544   req_cnt=48, fin_cnt=48
                = 1936x1090 x 1.5 + 79,184  = **FHD 12-bit**
```

**乾淨完成,沒有凍結。** 而且 picker 命中數在整段錄影期間一動也沒動
(4361 -> 4361),也就是說「OG3K30」這個鍵**根本沒有被查詢過**。

原因:`og3kname` 是 FLAG 守衛的,FLAG=0 時它不發射 OG3K 的解析度名,
於是組出來的鍵是原廠的 -> picker 正常命中 FHD -> 整條路乾淨退回。
不存在「感測器換了、幾何沒換」的半武裝狀態,因為感測器也沒換。

截圖 SS__0879:live view 是 16:9、HUD 29.97 —— 預覽也一起退回去了。

## 8. 開機不會落在 OG3K

兩次開機都量到:

```
og3ksel 次數 = 0        解析度 setter C005C020 開機時一次都沒被呼叫
FLAG = 0                HITS = 0        donor 時序 = 原廠
SetMovRecSize = 2       (先前用 shell 設成 4,重開機後自己回到 2)
```

所以「開機落在半武裝的 OG3K」這條路不成立。**`og3ksel` 開機不跑是事實**
(§6 第三個待驗項,已答),但因為解析度設定也沒有停在 4,兩者不會湊在一起。

⚠️ 只證明了**用 shell 設的值**不持久。實體選單選 OG3K 再正常關機開機,
是否持久成 enum 4 **尚未測** —— 那需要使用者的手。

## 10. ★★ 找到的凍結路徑:OG3K 選著 + 錄影格式切成 MOV + 按錄影

```
menu SetMovRecSize 4        -> OK
menu SetMovRecFormat 1      -> OK        (MOV)
menu SetMovRecSize          -> **4**     選單仍然說 OG3K
FLAG                        -> **1**     我們的 hook 仍然全開
picker 命中增量             -> **0**     MOV 不走 CinemaDNG picker
key MOVON                   -> shell 當場死,相機**硬凍結**
                               (使用者確認:畫面不動、按鍵沒反應)
```

相機仍在 USB 上列舉(ioreg node 沒變 = 沒有重開),但 worker 不回應。
使用者回報螢幕凍結 —— 所以不是單純的 USB endpoint 重建。

### 10a. 為什麼

MOV 不經過 CinemaDNG picker,所以 `fmttable` 與 `og3kcanvas` 兩個
**有 profile 守衛**的 hook 完全不動作。但只看 `FLAG` 的那一組全部還開著:

```
og3kaspect  / og3kaspect2   把長寬比壓成 3:2
og3kout                     主輸出描述子換成 3024x2010 的私有模板
og3kfps     x4              快門角度用 OG3K 的 nominal fps
og3kgs                      增益分派當成 raw movie
og3kname                    解析度名
```

H.264 編碼器拿到的是給 3024x2010 CinemaDNG 準備的輸出描述子與 3:2 長寬比。
最可疑的是 `og3kout`(它換掉整個主輸出描述子),其次是 `og3kgs`
(把 H.264 片子當成 raw movie 分派增益)。**尚未逐一隔離是哪一個** [?]。

### 10b. 這一條為什麼會變成「未知原因」的現場回報

切 MOV 拍個 proxy 再切回來是日常操作,而**中間沒有任何一個畫面告訴使用者
解析度已經不合法了** —— `SetMovRecSize` 讀回仍是 4。使用者只會記得
「我什麼都沒改,它就凍了」。

### 10c. 修法

`FLAG` 的意思必須從「選單選了 OG3K」收緊成
**「選了 OG3K **而且** 錄影格式是 CinemaDNG」**。

最小做法與現有設計完全同型:照 `og3ksel` 的樣子再掛一個
`SetMovRecFormat` 的 setter hook,格式 != CinemaDNG 就把 `FLAG` 撤掉
(連同 donor 時序還原,`og3ksel` 的離開路徑已經寫好那段程式),
格式回到 CinemaDNG 且 `SetMovRecSize == 4` 時再發布回去。

找 setter 位址的方法與當初找 `C005C020` 相同。**待做**。

## 12. §10 的修法方向已驗證(差分,不是單次觀察)

同一個 MOV + `SetMovRecSize=4` 狀態,只差一個字:

```
FLAG = 1   按錄影 -> **硬凍結**,shell 一起死,使用者確認畫面不動按鍵無效
FLAG = 0   按錄影 -> 乾淨錄完 3 秒,is_recording 正常回到 0
```

所以凍結確定來自「只看 FLAG 的那一組 hook 在 MOV 錄影時還開著」,
§10c 的修法(錄影格式不是 CinemaDNG 就撤旗標)方向成立。

**沒有再往下隔離是哪一顆 hook** —— 使用者判斷 MOV 的實際使用者極少,
不值得為此再燒一次抽電池。待辦保留在 §11。

## 14. shell 的 `menu Set` 不寫持久儲存 —— §8 的結論**不能推廣**

用原廠合法的 UHD(enum 3)當對照組:

```
menu SetMovRecSize 3  -> 讀回 3  -> reboot -> 讀回 **2**
menu SetMovFramerate 5 ->        -> reboot -> 讀回 **3**
```

合法值也一樣不持久,所以 §8 那句「重開機後 SetMovRecSize 自己回到 2」
**只證明了 shell 設的值不持久,沒有證明 enum 4 會被開機還原拒絕**。

「實體選單選 OG3K -> 正常關機 -> 開機,設定是不是還在 4」仍然未答,
而這一題決定了 §7 那個「安靜錄成 FHD」的狀態在使用者手上到底到不到得了。
**需要使用者的手,shell 做不到。**

## 18. ★ resident 沒有被日常操作蓋掉 —— H2 排除

原始分析的 H2 是「0xC0730000..0xC0740000 其實有人住」,而歷史上真的踩過
(舊位址 0xC072F800 是 USB shell 的檔案傳輸工作區)。

`mem save` 把 `0xC0730000..0xC0733000` 完整 dump 兩次,中間跑:錄一段 OG3K、
截圖 x3 並 getfile 取回、進回放播放再回來、進出選單、改 ISO x3、
解析度 2/3/4 各切一次、再錄一段。12 KB 逐字比對:

```
會動的:  0xC0730700 fmttable 命中   808799 -> 811830
         0xC0731C00 og3ksel 次數        15 -> 19
         0xC0732060 og3kout 命中       211 -> 241
         0xC07328C0 og3kgs 介入          8 -> 12
         0xC0732A00 畫布錄影          2007 -> 2635
         0xC073270C (這張卡的畫布 log)  102844 -> 108255
非預期:  **零個**
```

`0xC073270C` 一開始被判為非預期,追下去是這張自訂卡把畫布 log 放在 0x2700
(目前 plan 放 0x2A00)。決定性驗證:切到 FHD 之後 15 秒內
`0xC0730700` 與 `0xC073270C` **兩個都完全不動**,所以它跟著我們的路徑走,
不是外來寫入者。同段還讀了 0x2700/2704/2708/2710/2800/2880/28B0,全部靜止。

**結論:resident 的程式碼與資料在日常操作下一個字都沒被動過。H2 排除。**

量測方法的坑:`mem save` 寫到**已存在的路徑時不會覆蓋**,getfile 取回的是
上一份,兩次 dump 會假性「完全相同」(sha256 一致)。每次要用新檔名。

## 19. 觀察:picker 是一條很熱的路徑,而每次命中都遮蔽中斷

OG3K 待機時 `HITS` 約 **60 次/秒**(10 秒 151 -> 751),一次 session 累積到
八十萬次以上。而 `fmttable` 的 `hit` 每一次都:

```
mrs r2, cpsr / orr #0xC0 / msr cpsr_c     <- 遮蔽 IRQ+FIQ
str hmax|tail / str vmax|x / dmb ish       <- 即使值和上次完全一樣也照寫
msr cpsr_c                                 <- 還原
```

**值沒變也照寫、照遮中斷。** 遮蔽窗口只有幾條指令,60 Hz 的占空比極低,
本輪沒有觀察到任何由此引起的問題 —— 但這是一條「每秒六十次關中斷」的路徑,
值得在它上面加一個「和上次相同就跳過」的比較。**未驗證這能改善什麼**,
列為觀察,不是結論。

### 38a. 為什麼這件事重要

## 39. ★ 修法需要的 setter 位址已經找到:`0xC005BE58`

§10c 說「照 og3ksel 的樣子再掛一個 SetMovRecFormat 的 setter hook」,
當時寫「找 setter 位址的方法與當初找 C005C020 相同。**待做**」。做完了。

### 39a. 方法

shell 的 `menu` 指令表在 `0xC0BBB5C0` 起,**12 bytes 一筆**:

```
+0x00  名稱字串    +0x04  用法字串    +0x08  處理函式
```

```
0xC0BBB5DC  "SetMovRecFormat"   -> 處理函式 0xC03FD960
0xC0BBB600  "SetMovRecSize"     -> 處理函式 0xC03FDAB0
```

兩個處理函式**結構逐條相同**,差別只在它們呼叫的 setter/getter:

```
SetMovRecSize    bl 0xC005C020 (set)   bl 0xC005C058 (get)   <- 已知,og3ksel 掛這裡
SetMovRecFormat  bl 0xC005BE58 (set)   bl 0xC005BE90 (get)   <- 要的就是這個
```

用 `SetMovRecSize` 當驗證:這個方法確實推導出 `og3ksel` 已經在用的
`0xC005C020`,所以對 `SetMovRecFormat` 的結果可信。

### 39b. 兩個 setter 的進入點完全一樣

```
c005c020  push {r4, r5, r6, lr}    <- 解析度,SEL_STOCK = 0xE92D4070
c005be58  push {r4, r5, r6, lr}    <- 錄影格式,同一個字
```

`r0 = obj  r1 = 新值  r2 = flag`,連暫存器約定都相同。
**所以新 hook 可以用與 og3ksel 逐字相同的掛法**,只是回跳位址換成
`0xC005BE5C`。

```
   重開機後 OGSAVE 仍是 1,而 RecSize 回到 2 —— 正是還原要處理的情境
```

#### 踩到的坑(留給下一個人)

- `og3ksel` 加了程式碼之後從 260 長到 **304 bytes**,撞到原本規劃的
  `FMT_CODE`。它的 `OWNED` 上界也從 `0xC07318A0` 放大到 `0xC0731940`。
  **動 payload 之前先掃一次私有 RAM 的占用**,不要照舊註解假設。
- `EXPECTED_PLAN_WORDS` 原本是一個跨行三元運算式,
  `a - b if c else d - e + f` 會把 `+ f` **只掛在 else 那一支**。
  新增的調整項照原樣接在尾巴,對 `_ANGLE_FIX_TARGETS` 不會生效。已拆開寫。
- `check()` 裡 payload 的界線是一張寫死的 dict,新增 payload 一定要補進去,
  否則是 `KeyError` 而不是有意義的錯誤訊息。

### 39c-2. 原本的建議形狀(保留,已被 39c-0 取代)

`og3ksel` 的整段交易(FLAG / donor 時序 / GTAB 分組)**完全由一個
布林 `r5` 驅動**。所以新 payload 可以重用同一段本體,只換算 `r5`:

```
新增一個字 FMTLATCH:0 = CinemaDNG,其餘 = 非 CinemaDNG,只由新 hook 寫
兩個 hook 都算同一個述詞:   sel = (最後的解析度 enum == 4) && (FMTLATCH == 0)
og3ksel     先更新 LOG+4,再算 sel        回跳 0xC005C024
og3kfmt     先更新 FMTLATCH,再算 sel     回跳 0xC005BE5C
```

開機值 `FMTLATCH = 0`、`LOG+4 = 0` → `sel = 0`,是故障安全值。

**殘留缺口**:若相機上次關機時存的是 MOV,開機後 `FMTLATCH` 會是
陳舊的 0(因為開機不呼叫 setter,§8 已證實解析度 setter 開機不跑)。
這時若使用者直接選 OG3K,`sel` 會錯算成 1。要補這個缺口就得在
`og3ksel` 裡改呼叫原廠 getter `0xC005BE90` 取得真實格式
(`og3kfps` 已經在用「先呼叫原 getter」這個模式),代價是每次切解析度
多兩次韌體呼叫。**這個取捨還沒有決定。**
