# OG3K:這次調查的答案,以及我錯在哪裡

2026-09-12。這份筆記的重點是**被推翻的結論**。對的結論散在其他筆記裡,
錯的如果不寫下來,下一個人(或下一次的我)會再走一遍。

---

## 一、最後成立的模型

`profile 43`(列 30)是**韌體本來就有的原生 3:2 profile**,沒有被任何 movie
picker 引用:

```
+000/+004  3032x2012     RAW 幾何
+024/+02C  3008x2000     active
+0F4/+0F8  3032x2012     感測器視窗
+064/+0D4  0x3FF         RAW RWZM 原廠就是 unity
+00C/+010  2024x1341     預覽柵格
+020/+028  2000x1334     預覽可見
+01C       2             3:2 標記
+030       -1.0          畫格率 —— 唯一缺的東西
```

`+0x030` 是**畫格率浮點**(p102/p175 = 30.0、p221 = 50.0、p1/p5 = 60.0)。
p43 是 −1.0(無效),所以直接引用它會在**錄影結束時產生一禎花屏**。
在格式表命中時把該格率的浮點寫進去就解決了 —— 機制跟 fmttable 本來就在做的
「寫時序」完全一樣,只是多寫一個字。

唯讀重用:**不改那個 profile,只在格式表裡引用它**,所以就算拍照路徑用到
也不受影響。

## 一之二、最終架構(A001_017/018 驗收通過)

格式表指向 p43,並在鍵值命中時把該格率的浮點寫進 p43 的 `PARAM+0x030`
(`0xC0BD477C`)。其餘元件逐項測試開關:

| 開關 | | 理由 |
|---|---|---|
| `WITH_ROWPATCH` | **關** | p43 本身就是 3032x2012,畫布 hook 命中 0 次 |
| `WITH_RWZM` | **關** | p43 的 RAW 那對(`+0x64/+0xD4`)原廠就是 unity `0x3FF` |
| `WITH_PREV` | 開 | 待機走 profile 5,可見高仍需 1125 → 1334 |
| `WITH_ASPECT` | 開 | 全韌體兩處寫死的 16:9 enum,`C0306EA0` 與 `C0306EEC` |
| `WITH_OUT` | 開 | 輸出描述子 1620x911 → 1620x1080 |

拆掉前兩項換來的:畫布 hook 的 14 個 PUT、`row == 1936x1090` 的旗標守衛、
那個與 USB shell 暫存區衝突的位址,以及 32 個與 FHD 共用、必須跟旗標切換的
RWZM 欄位 —— 全部消失。

**逐項測試比一次全開重要**:如果直接把所有元件都留著,就永遠不會知道
RWZM 那 32 欄其實是多餘的。方法是先全拆,再一次開一個。

## 二、我錯的地方(依代價排序)

### 1. `+0xD8/+0xE0` 是 producer 的那一對,不是「預覽覆寫」

外部交接包寫「preview width from PARAM+0C, **overridden by nonzero +D8**」,
我讀成「+D8/+E0 是預覽柵格的覆寫,設 0 表示不覆寫」,就把它關掉了。

**而 `rowpatch_og3k.S` 自己的註解就寫著 `+0xD8` 是 producer-side 的寬高對。**
兩者衝突時我採信外部文件,本地註解才是在這台機器上驗證過的。

代價:A001_015 起只有左上約 1936 寬有畫面,A001_047 起連 strip 都縮成
3032x1341 —— **毀掉數十段素材**。

正確的角色劃分(後來量出來的):

| 欄位 | 角色 |
|---|---|
| `+0x0C/+0x10` | **producer 實際產出** |
| `+0xD8/+0xE0` | **消費端讀取** |

兩邊都必須是 3032x2012。關掉 `+D8/+E0` 會讓 producer 改讀 `+0x0C/+0x10`。

### 2. 用 live view 當驗收標準

每一輪我都只問「畫面對不對」,**從來沒有要求錄一段然後解 DNG**。
標頭一直是正確的 3032x2012,肉眼看 live view 也「修好了」,所以壞了三小時
沒人發現。

現在的規則:**動錄影路徑必須解 DNG**,檢查檔案大小、strip 長度、
以及右側 1936 之外的區域相鄰行是否仍相關(正常 0.7–0.98,壞掉 −0.12–0.03)。

### 3. 「柵格對齊」是死巷

我花了好幾輪讓錄影期的預覽柵格去對齊待機的柵格,理由是「顯示層 latch 的
縮放不會重算」。**反證**:原廠 FHD 錄影時柵格也會從 2016 變成 1936,
卻不會有任何異常 —— 顯示層本來就會重算。

那幾輪的「反比補償」(可見 2000 → 1992 → 1920 → 1878)全部建立在錯的模型上。

### 4. `S_ACTIVE = 0` 不代表「從未啟動」

gyro logger 的 `S_ACTIVE` 在**錄影中才是 1**,錄完回到 0。我在錄完之後讀到 0,
就宣稱「logger 從來沒被觸發」,往錯的方向找了一輪。

### 5. 擷取器「只抓第一次」

在有 latch 的系統上,第一次呼叫抓到的是**短暫的正確狀態**。所以連續好幾輪
量到「待機與錄影完全相同」,是儀器造成的假象。改成「最後一次覆寫」才看到差異。

### 6. 「上下閃爍是頻寬競爭」

使用者觀察到「換 SSD 閃爍的樣子會變」,我推論是預覽 producer 與 RAW writer
搶頻寬,於是只讓 RAW 那一對 RWZM unity。**結果錄影變花屏,相機隨後凍結。**
RWZM 四個欄位不能拆。

### 7. gyro 抄了預設路徑

`build_card.py` 的**預設**是 `logger.S`(寫 GYR + PGEN 後處理),但實測可用的
v1.11b 走的是 `--gcsv-stream` / `logger_stream.S`(錄製當下直接寫 gcsv,
不需要 PGEN.BIN 也不需要 GYRO 資料夾)。我補 PGEN.BIN、建 GYRO/ 全是白做。

### 8. 三次凍結,同一條規則的三個面

| 次 | 動作 |
|---|---|
| 1 | 邊執行邊覆寫 payload |
| 2 | 函式指標排在它指向的 payload **之前** |
| 3 | 在 picker hook 武裝時改寫它讀的**格式表** |

同一條抽象規則:**改動任何 hook 正在使用的東西之前必須先解除它** ——
無論那是程式碼還是資料。前兩次我寫成註解,註解會被下一次重構繞過。
現在寫成 `Plan.check()` 的程式檢查加上載入器的 `OWNED` 區域表。

### 9. 我自己的工具踩自己的程式碼

rowpatch 原本在 `0xC072F800`,那是 **USB shell 檔案傳輸的工作暫存區**
(`putfile.CODE .. CODE_END`)。`gyro/build_card.py` 說那裡「at boot 沒人用」
是真的,但**執行期每次 getfile/putfile 都會覆寫它**。抓截圖時就踩到過
(`still short after 6 passes` 那次凍結)。前幾天只用 `mem_set/mem_get`
所以從沒顯現。

## 三、真正的轉折點不是任何一個推理

是**使用者提到相機有截圖功能,而且會拍到影像**。

加上 `fp_usb_shell/getfile.py --size N` 可以直接把檔案從 USB 抓回來,
於是「放大幾倍」從口頭描述變成 0.4% 精度的量測:

```
水平 量測 1.560   預測 3032/1936 = 1.566   差 0.4%
垂直 量測 1.820   預測 2012/1080 = 1.863   差 2.3%
```

有了這個之後,錄影期 live view 從「三帶花屏」到「1.000x 完全一致」
只花了**兩輪**。前面純靠口頭描述的十幾輪,差別不是努力程度,是有沒有數字。

第二個儀器:LV Bayer 環形緩衝 `0x50000000 + idx*0x100000`,1 MB/frame,
`mem save` 已驗證可倒出 —— 可直接量 producer 實際的行距與有效行數。
這次沒用到,但下次該先用。

## 四、還沒解決的

- **回放花屏。** HUD 顯示 `FHD` 是 `LiveViewModeMgr` 常數池
  (`0xC0BCFE70`:4096x2160 / 3840x2160 / 1280x720)的**回退值**,
  對不上就顯示 FHD。改標籤不會讓畫面不花 —— 花屏在解碼/顯示路徑,是另一個
  子系統。p43 沒有改變這件事。
- **gyro 不產出 sidecar。** 區段表驗證正確,原因未明。
- `+0x030` 之外 p43 與 p83 完全相同(p83 = 18.0,也不是我們要的格率)。

## 五、回放花屏:量到的事實與下一步(2026-09-12 續)

### 量到的

1. **回放把 OG3K 片子當 FHD 組態引擎。** `cfgring` 記到四組幾何,回放那一組是
   `可見 1920x1080 / 柵格 1936x1090 / 視窗 3032x1708`,fps 30 —— 那是
   profile 175(FHD)的值。檔案是 3032 寬,行距差 `(3032-1936)*1.5 = 1644`
   bytes,正是截圖裡的水平條紋雜訊。

2. **picker 在回放時收到的鍵是 `FHD30`。** `keyring` 掛在 `C043CCF8`,
   回放整段只出現這一個鍵。

3. **解析度名發射器 `C0437B48` 不是回放標籤的來源。** `dimlog` 掛在它的
   進入點,量到它確實收到 `3008x2000`(與我們 patch 的比對對相同),
   所以它會回傳 `"OG3K"` —— 但回放 HUD 仍顯示 `FHD`。

   該函式的結構(反組譯確認):`[r5+8]`/`[r5+0xC]` 依序比對
   `0xC0BCFE70`(4096x2160)→ DCI4K、`0xC0BCFE78`(3840x2160)→ UHD、
   `0xC0BCFE80`(原廠 1280x720,我們改成 3008x2000)→ 走 `"HD"` 分支
   (字串指標在 `0xC0437C34`,我們改指向自己的 `"OG3K"`),
   都不中則回退 `"FHD"`(`0xC0437C40`)。

4. **回放用的是另一張名稱表。** `0xC0BE4510` 起,每筆 16 bytes
   `{222, 字串指標, 6, id}`,內容是 UHD / FHD / UHDCROP / FHDCROP 重複,
   id 為 53、371、373、61、63、381、383、71、73、391、393。
   跟 picker 表 `{5, profile, sensor_mode, key_ptr}` 同樣的形狀。
   字串池在 `0xC0BE45E4`(另一組,不是 `C0BCFE88` 那組)。

### 還不知道的

**是什麼把一段 OG3K 片子映射到那張表的某一筆。** 找到那個選擇器,才知道要
加一筆還是改一筆。可能的下一步:掛在 `0xC043A308` / `0xC043B0A0` 那一帶
(載入該字串池的程式碼)記錄它收到的 id。

### 又排除的兩條(2026-09-12 續)

**(a) 解析度名發射器不是回放標籤的來源。**
`C0437B48` 的結構是三段比對後回退 `"FHD"`:

```
[r5+8]/[r5+0xC] 比 0xC0BCFE70 (4096x2160) → "DCI4K"
                比 0xC0BCFE78 (3840x2160) → "UHD"
                比 0xC0BCFE80 (我們改成 3008x2000) → "HD" 分支
                                (字串指標 0xC0437C34,我們改指向 "OG3K")
                都不中 → "FHD" (0xC0437C40)
```

`dimlog` 掛在它進入點,量到它**確實收到 3008x2000** —— 也就是會走 OG3K 分支。
但回放 HUD 仍是 FHD。**結論:回放的標籤來自別處。**

回放用的是另一張表 `0xC0BE4508`(基底不是 0xC0BE4510,這個偏移我踩過兩次),
三組各四筆,每筆 16 bytes `{6, id, 222, 名稱指標}`:

```
0xC0BE4508  id 51, 53, 371, 373   → UHD, FHD, UHDCROP, FHDCROP
0xC0BE4548  id 61, 63, 381, 383   → 同上
0xC0BE4588  id 71, 73, 391, 393   → 同上
```

**(b) 「分派器認不得我們的表」不是原因。**
`0xC043C5F0` 起是一個分派器,用範圍檢查判斷一個表項指標屬於哪張表:

| 檢查函式 | 範圍大小 | 用於 |
|---|---|---|
| `C043D258` | 0x1A0 | picker 表(26 x 16) |
| `C043D218` | 0x200 | |
| `C043D0D8` | 0x80 | |
| `C043D1D8` | 0x40 | 名稱表的每一組 |

我們的 fmttable 回傳的是指向 `0xC0731000`(自己的表)的指標,不在任何已知
範圍內。加了一個 hook 讓 `C043D258` 在「查表 3 且指標在我們範圍內」時回 1
—— **回放完全沒有改變**,所以這不是原因。已退回。

### 下次的正確起點(不要再跳過這一步)

名稱表 `0xC0BE4508` 的 id(51/53/61/63/71/73、371/373/381/383/391/393)
**只出現在那張表裡**,鄰近沒有尺寸欄位 —— 所以「尺寸 → id」不是一張相鄰的
對照表,要往上追產生表項指標的程式碼。

三個讀取點:`0xC043ADC4`、`0xC043BD9C`、`0xC043C678`。
`0xC043C5F0` 起的分派器拿到的 `r5` **已經是選好的表項指標**,
所以選擇發生在更上游。

**下一步就一件事:掛在那三個讀取點,記錄回放時的 `r5` 指向哪一筆。**
知道是哪一筆(是 group 3 的 FHD=73 嗎?),再往上追誰算出那個指標。

不要再從「改哪個常數」開始猜 —— 這條線上我猜了三次(比對尺寸兩次、
分派器一次),三次都落空,每次都花掉一輪相機測試。

### 決定性結果:回放根本不查 picker(2026-09-13)

用「引擎組態的畫格率浮點 `C31DF564+0x10 == -1.0f`」當回放的判別條件
(實測待機 60.0、錄影是實際格率、回放一律 -1,UHD 與 OG3K 都是),
只在該條件成立時記錄 picker 看到的鍵 —— **零筆**。

**所以整條「picker 鍵 / 格式識別」的線都是追錯對象。**
先前量到的 `FHD30` 與 `OG3K30` 都來自模式切換,不是回放:

| 量測 | 錯在哪 |
|---|---|
| `keyring v1` → `FHD30` | 在改比對尺寸**之前**量的,結論早已過期 |
| `keyring v2` → `OG3K30` | 沒有綁定時刻,來自「回到拍攝模式」的查詢 |
| `cfgring` → 回放用 FHD 幾何 | 同樣在改動前量的;但**重量後結論不變**(見下) |

唯一站得住的量測是幾何,而且改動後重量過:

```
#1  可見 1920x1080  柵格 1936x1090  視窗 3032x1708  fps -1.00   ← OG3K 回放
```

`3032x1708` 是 **profile 175 的視窗**、`1936x1090` 是它的 RAW 幾何 ——
**回放是用 p175 組態引擎的**,而且與 picker 無關。

### 下一步

找出回放如何選到 profile 175。它不經 picker,所以是另一條路:
可能從 DNG 的中繼資料、或某個「尺寸 → profile」的對照。

具體做法:**掛在描述子建構器 `C0438018`**(交接包:「0xC0 descriptor,
RAW half then preview half at +58」),在 `fps == -1` 時記錄它拿到的**列索引**。
那會直接指出回放選了哪一列(p175 = 列 122),再往上追誰選的。

**教訓:每個量測都要先找一個把它綁定到目標狀態的判別條件**,
而不是靠操作順序去推。`fps == -1` 是這條線上第一個真正的判別條件,
它一上線就推翻了前面三輪的結論。

### 兩個獨立的事實

- **錄下來的檔案完全正常。** 同一批 DNG 在主機上解出來是完整的 3032x2012。
  這純粹是相機內回放的顯示路徑。
- profile 43 沒有改變這件事 —— 回放不讀錄影 profile。
