# LCD 顯示鏈:OG3K 的 3:2 取景是怎麼修好的

2026-09-12。3000×2000 open gate 專案紀錄。

錄影路徑（3032×2012、裁切 3008×2000）早就驗證過，實拍檔案為證。這份筆記只講
**LCD 顯示鏈** —— 它跟錄影路徑幾乎完全獨立，而且原廠是四層一路 16:9 自洽。

---

## 1. 這條鏈有四層,每層都量到了實際數字

在活著的相機上讀出來的（`codex/opengate/dispchain.py` 可重複取樣）：

| 層 | 位置 | 原廠值 | 比例 |
|---|---|---|---|
| ① 預覽來源 | profile 5 PARAM `+0x0C/+0x10` | 2016×1344 | **3:2** |
| ② 可見視窗 | profile 5 PARAM `+0x20/+0x28` | 2000×1125 | 16:9 |
| ③ 主輸出模板 | `C0437E98` idx 0 回傳的描述子 | 1620×911 | 16:9 |
| ④ 原生 fit | `C0306EA0` 的長寬比 enum | 3 = 16:9 | 16:9 |

**關鍵事實:① 本來就是 3:2 全高。** LCD 預覽拿得到的來源從來就是整片
2016×1344，是 ② 這一步把它中央裁成 16:9，之後三層一路維持 16:9。

所以要的不是「把來源變大」，而是**把中間那一刀拿掉**。

執行期可觀測點：引擎匯出組態 `C31DF564 + 0x30` 依序是
`可見W, 可見H, 來源W, 來源H`，通道跨距 `0x1B0`。引擎輸出維度在
`C31E0DD4 + 0x324/+0x328`。主管理器 `C375D840`，`+0x14` 是 owner。

## 2. 三個 hook

全部在 RAM，抽電池即還原。

### ④ 長寬比 `C0306EA0`（`og3kaspect.S`，9 字）
原指令 `mov r0,#3`。旗標立起時給 enum 2（3:2），否則照原廠給 3。
長寬比表在 `C0B4CAB8`，8 位元組一筆：1=4:3、2=3:2、3=16:9、4=1:1。

### ③ 主輸出模板 `C0437E98`（`og3kout.S`，53 字）
該函式就是 `return *(obj + idx*8)`，原指令 `push {r4,r5,lr}`。

實測 owner `0xC375EB68` → 描述子 `0xC375E934`，11 個字：

```
1620  911  0  0  1620  911  0  4  0x3FC000  1  1
```

3:2 版本**只有兩個高度欄位不同**，其餘九個字（格式 4、配置上限 0x3FC000、
視訊旗標 1,1）完全一樣。0x3FC000 = 4177920 容得下 1620×1080×2 = 3499200，
所以不必動配置。

不改原廠描述子（它是共用的活緩衝）。第一次命中時整份複製到私有緩衝
`0xC0731E00+4`，只改 `+0x04` 與 `+0x14` 兩個高度為 1080，之後恆回傳同一份
不可變副本。守衛：idx 必須 0、旗標必須立起、描述子必須確為 1620×911。

### ② 預覽可見高 `0xC0BDB9CC`（在 `og3ksel.S` 裡跟著旗標切換）
profile 5 PARAM `+0x28`，1125 → **1334**。
邊距 2016−2000=16、1344−1334=10，與原廠邊距同構。

**profile 5 是所有模式共用的顯示 profile**，靜態改死會讓 UHD/FHD 的預覽
一起變形，所以必須在解析度 setter 裡跟著旗標還原。

欄位位址算法：`raw-profiles.json` 的 `columns[offset].table + rows[profile].index*4`。
profile 5 的 row index = 2，`+0x28` 的欄基底 `0xC0BDB9C4` → `0xC0BDB9CC`。

## 3. 我走過的兩條死路,以及為什麼

### 死路一:照抄對方的 profile 429 做法
對方改 `profile 429 PARAM+0x10/+0xE0: 1135→1344`、`+0x28: 1125→1334`。
我直接類比到我們的 profile 上 —— **錯的**。

原因：**OG3K 沿用的就是 FHD 的 profile ID**（173、174、175、176、178、180、
430、431，全是 raw 1936×1090 / crop 1920×1080）。改它們的靜態表會把真正的
FHD 一起弄壞。而且 LCD 預覽根本不走這些 profile，它走 profile 5。

順帶釐清這個 65 字 PARAM 塊是 **RAW 與預覽交錯**的，不是前後分半：

| RAW | `+0x00/+0x04` | `+0x24/+0x2C` | `+0xDC/+0xE4` | 比例 `+0x64/+0xD4` |
|---|---|---|---|---|
| **預覽** | `+0x0C/+0x10` | `+0x20/+0x28` | `+0xD8/+0xE0` | 比例 `+0x60/+0xD0` |

依據是把對方列出的 8 個幾何位址反查欄位偏移，全部落在 RAW 那一列。
`rowpatch_og3k.S` 目前把 `+0xD8/+0xE0` 當成 RAW 寫了 3032×2012 —— 語意上
是錯的，但錄影實測正常，暫不動它（已驗證的路徑不做沒有證據的更動）。

### 死路二:以為問題在「原生 fit」的參數塊
交接包寫「Native fit C02F43A8→C02F4410，目的可見 W/H/X/Y 半字在
`+7C/+7E/+80/+82`，來源在 `+60/+62`」。我在 `C02F43A8` 進入點抓 `r0/r1/r2`
去套這些偏移，讀到 `r0=100, r1=133, r2=7` —— 全是小整數，那裡根本沒有結構
指標。這些偏移（若成立）是函式內部後段才建立的，不能在進入點套。

## 4. 半按會被拉長:預覽 profile 有六個兄弟

長寬比與模板都修好後,半按快門仍然會拉長。把引擎組態的每一次變化記下來
(`cfglog.S` 掛在原生 fit),軌跡是這樣:

```
#   可見        來源        profile5 表值
0   2000x1334   2016x1344   1334   ← 對
1   2000x1125   2016x1344   1125
3   2000x1125   2016x1344   1334   ← 表是 1334,引擎卻拿到 1125
5   2000x1125   2016x1344   1334
```

表值是 1334 而引擎拿到 1125,所以 1125 只能來自**別的 profile**。
全表搜索「來源 2016x1344」共 16 列,其中 `+1C == 1` 的六列可見都是
2000x1125,`+1C == 2` 的都是 2000x1334:

| +1C | profile | 可見 |
|---|---|---|
| 1 | **5、210、227、257、258、259** | 2000x1125 |
| 2 | 1、41、42、81、82、202、225、251、252、253 | 2000x1334 |

待機用 profile 5,半按與錄影會切到其他兄弟。六個 PARAM+0x28 位址
(`0xC0BDB9CC`、`0xC0BDBC28`、`0xC0BDBC60`、`0xC0BDBC8C`、`0xC0BDBC90`、
`0xC0BDBC94`)全部跟著旗標切換後,半按就正常了。

## 5. 錄影期預覽:柵格必須照韌體自己的數字

錄影期預覽走的是**錄影 profile 自己的預覽半部**,不是 profile 5。
這裡踩了三次,每次的失敗模式都不同:

| 設定 | 宣告 vs 產出 | 宣告 vs 待機 | 症狀 |
|---|---|---|---|
| 柵格 3032x2012(原始) | 差很多 | 差很多 | 整個花屏 |
| 比例 2048 → 1516x1006 | **相符** | 差很多 | 乾淨,但等比例放大往右下推擠 |
| 手算 1536 → 2016x1344 | 差 5 px | 相符 | 重影、交錯、顏色迷幻 |
| **韌體的 2024x1341** | **相符** | 差 <1% | 正常 |

兩種失敗模式是獨立的:

- **宣告柵格 ≠ 生產端實際產出** → 行距(stride)不匹配,每行累積位移,
  變成斜向重影與色彩錯亂。
- **宣告柵格 ≠ 待機柵格** → 顯示層的縮放與位移是在待機時 latch 的,
  不會重算,於是等比例放大並位移。

**預覽柵格 = 感測器視窗 ÷ (比例/1024)**,原廠各模式都精準對得上:

```
FHD  3032x1708 / 1.5625 = 1940x1093  → 宣告 1936x1090
UHD  6064x3412 / 1.5625 = 3890x2183  → 宣告 3888x2184
```

但進位規則不一致(一個往下、一個往上),**不能自己算**。正確做法是查韌體
自己對同一個視窗宣告了什麼 —— 表裡本來就有視窗 3032x2012 的 profile:

```
視窗 3032x2012  →  柵格 2024x1341  可見 2000x1334  比例 1536  覆寫 +D8/+E0 = 0
                   (profile 43、83、221)
```

`+D8/+E0` 要是 **0**(關閉覆寫),柵格取自 `+0C/+10`。這點手算時想不到。

可見尺寸最後設成 **2002x1334**,對齊的是實際錄下來的 DNG 裁切
(3000x2000 @ 原點 16,6 → 換算 2002.6x1333.0,置中偏移 (11,3)),
而不是對齊待機。

殘留:錄影與待機之間 <1% 的取景差,這是結構性的 —— 待機視窗
2016x1344 = 1.5000,錄影視窗 3032x2012 = 1.5070,兩條路徑的長寬比
本來就不同,無法同時對齊。

## 7. 未解:錄影時右邊一條細空隙

### 症狀
錄影時畫面等比例縮小約 2–5%,以左上角為原點,**只有右邊**露出一條空隙,
空隙裡是前一幀的殘影。下面不會露出空隙。待機、半按都正常。

使用者的關鍵觀察:**按下錄影的瞬間會「從中心放大一點」,然後馬上「鎖小」**
回到左上角對齊的縮小狀態。也就是說我們的 canvas 值確實生效了,之後被另一個
動作覆蓋。交接包那句「Layout applied bit is latched, not continuous rendering」
對得上。

### 已排除(都在錄影當下量過,待機/錄影完全相同)
| 量測項 | 值 |
|---|---|
| 目的矩形 `+0x60` | 1620x1080 |
| 目的偏移 `+0x74` | (43,5) |
| 引擎輸出維度 `C31E0DD4+0x324/+0x328` | 1620x1080 |
| 主輸出模板 | 1620x1080 |
| 面板長寬比對 `sp+0x4C` | 最後一次呼叫時兩邊都是 (3,2) |
| 預覽可見 | 2000x1334 |
| 四個輔助欄位 `+80/+84/+90/+C0` | 已對齊 |

也試過並否定的假設:
- 讓柵格與待機一致(視窗寬改 3024 → 柵格 2016x1344):組態驗證確實變成
  2016x1344,畫面完全沒改善。
- 第二個寫死 16:9 的長寬比點 `C0306EEC`(全韌體只有它和 `C0306EA0` 兩處):
  hook 之後沒有改善,該分支可能根本沒執行。
- 消費端直接讀靜態 profile 表:把八個 FHD profile 的預覽欄位全部改成與
  canvas 一致(不帶守衛),沒有改善。已還原。
- 反比補償(可見 2000 → 1992 / 1920):1992 看不出差別;1920 會在按下錄影
  的瞬間「從中心放大」然後被鎖回去 —— 這正是發現 latch 的線索。

### 儀器上的教訓
擷取器原本是「只抓第一次」,抓到的是按下錄影瞬間那個**短暫正確**的狀態,
所以前幾輪量到的「待機與錄影完全相同」是假象。改成「最後一次覆寫」之後才
看到差異。**在有 latch 的系統上量測,一定要抓最後一次。**

### 下一步的方向
最後一次呼叫抓到的目的物件,差異只剩 `+0xCC..+0xD8` 從全 0 變成
`(2, 5, 1, 指標)`,像是一筆待處理的版面操作。另外要注意這是**多層合成器**:
同一個函式不同次呼叫的「實體矩形」會是 1920x1080 或 1024x682(OSD 畫布),
在不知道層次結構前分別取樣會互相混淆。應先建立層次圖,再找那個在錄影開始
後重新套用版面、且以 (0,0) 對齊的動作。

## 8. 方法論的教訓

把別人韌體上的位址與 profile 編號直接類比過來,代價很高。真正有用的是
**在活著的相機上把每一層的實際數字讀出來**:`C31DF564+0x30` 那一行
`2000 / 1125 / 2016 / 1344` 一出現,四層模型就立刻閉合了。

第二個教訓是**不要自己算幾何**。柵格的進位規則各模式不一致,手算出來的
2016x1344 造成了最難看的一次(重影加色彩錯亂)。韌體自己的表裡就有同一個
感測器視窗的答案,查表比推導可靠。

第三個是**症狀要分型**。「花屏」「放大推擠」「重影迷幻」看起來都是壞掉,
其實對應三個不同的不匹配,分清楚之後每一個都只需要一次測試。
