2026-09-15。承 OG3K(`fpsup-og3k-v0.2.1a`)與
`research/imaging-hw/notes/REDUCTION_INVENTORY.md`。

> 2026-09-15 校正:第一基底改為 **M139 quiet**,不再以 M8 fast 為畫質版起點;
> metadata 只能證明 3x3 有效 geometry scale,不能稱為已確認的 charge binning。
>
> **2026-09-22 已解 —— 見 `REDUCTION_KERNEL_MEASURED.md`。** 不是 3x3:
> 垂直只併 **2 列**(每三條同色列丟一條),水平是 3 抽頭 `[1,2,1]/4`。
> firmware 自己的 merge tuple 就寫著 `(3,2,3,3)`,那個孤零零的 2 就是垂直抽頭數。

> **第 0 節的基底決策尚未改動** —— 替代路線 M98+RWZM1.5 在模擬裡明顯較優
> (疊紋 6.5% vs 31.4%、N_eff 10.24 vs 5.33),但它依賴一個還沒跨比例驗證的外推,
> 先看該文 §9 待驗第 1 項。
> 三階畫質路線與完整理由見 `OG_2K_3K_4K_QUALITY_OPTIONS.md`。

## 0. 目標與理由

**用感測器原生的 ÷3 geometry-reduction 模式(2016×1344)錄 open gate。**

相對現行的 OG3K:

| | OG3K | **OG2K** |
|---|---|---|
| 感測器光柵 | 3032×2012(÷2) | **2016×1344(÷3)** |
| 比例 | 3:2 | **3:2(2016/1344 = 1.5000,更精確)** |
| 捲簾 | 12.44 ms | **8.31 ms(M139)** / 6.16 ms(M8) |
| 29.97p 資料率 | 273 MB/s | **122 MB/s** |
| 縮減方式 | sensor 2x geometry reduction,RWZM unity | sensor 3x geometry reduction —— **一樣不碰 RWZM / hbin** |

**它不需要任何未證實的機制。** 三層縮減手段裡,這條只用最底下那一層
(換感測器模式),而那正是 OG3K 已經在用的手法。

⚠ **不要和 1984×1320 搞混。** 那個是 `3968×2640`(÷1.53 裁切)再 ÷2,
**視角只有 65%**,不是 open gate。全寬的 ÷3 只有 2016×1344。

## 6. 建議的第一步

**先只做 M139 原生 59.925p,確認 quiet 2K 幾何與錄影鏈;再套精確
59.94p timing。**

理由:M139 是唯一 full 2016x1344 Q12 mode。先保留整個原廠 mode 與原生時序,
把變數降到最少;跑通後才移植格率。

順序:

```
1. 離線/USB readback —— 確認 M139 被選中、幾何2016×1344
2. 決定借哪一個 PARAM profile
3. 改 og3k_plan 的 FMT / CANVAS 值,產生 OG2K 的 USB 載入版
4. 上機:取景 → 錄一秒 → 解 DNG 驗幾何
5. 才做 UI 與其他格率
```

USB shell 只用來做 runtime readback,不再用來查 mode 名稱。

## ★ 2026-09-15 決策:獨立版本 + 單一程式碼庫,donor 用 LV 3:2 profile

### A. 為什麼要出成獨立的卡 —— 選單只放得下三個選項 [C]

這不是偏好問題,是已經證明過的硬限制:

- 解析度選單的 CSV block **只有 92 bytes,原廠就佔 89**。
- 2026-09-13 實驗證明解析器**按欄位名稱對欄**,標頭不能縮短(縮了整列消失)。
- 加第三列已經被迫拿掉 `Popup` 欄才塞得下。**第四列放不進去。**
- QS 的底列同樣是三格。

所以「UHD / FHD / OG3K / OG2K 四選一」在現有 UI 做不到,除非把整個 CSV block
搬到別的地方重新安置 —— 那是新的工程與新的風險。**出兩張卡最省。**

### B. 但程式碼要同一份 [I]

`og3ksel` / `og3kfps` / `og3kgs` / `og3kaspect` / `og3kout` / `fmttable` 幾乎
全部與幾何無關。兩個目標實際不同的只有:

```
FMT             格式鍵 + donor mode + 時序
CANVAS_REC      錄影矩陣 / active / 平面格式碼
OG_PROFILE      借用的 profile id
名稱字串        "OG3K" / "OG2K"
UI 資產         QS 圖塊、CSV 那一列
```

→ `og3k_plan.py` 加一個 build-time target,產出兩張卡。不要分叉兩份原始碼。

### C. M139 八個格率零誤差,而且全部 quiet 指紋 [C]

stock:`hmax=445 tail=445 vmax=2700 x=6` → 1,201,500 cycles = 59.92509 fps,
捲簾 8.31 ms。用同一個 hmax 重算:

```
key          目標 fps      vmax  tail    實際 fps       誤差   vmax-1344
OG2K23_98    23.97602     6748   585    23.97602   0.000ppm      5404
OG2K24       24.00000     6741   700    24.00000   0.000ppm      5397
OG2K25       25.00000     6471   850    25.00000   0.000ppm      5127
OG2K30       29.97003     5398   735    29.97003   0.000ppm      4054
OG2K48       48.00000     3370   795    48.00000   0.000ppm      2026
OG2K50       50.00000     3235   870    50.00000   0.000ppm      1891
OG2K60       59.94006     2699   590    59.94006   0.000ppm      1355
OG2K100     100.00000     1617   880   100.00000   0.000ppm       273
```

**這是 OG2K 勝過 OG3K 的地方**:OG3K 的 100p 只能用 M117(fast 指紋,
使用者實測噪點明顯較差),而 OG2K 八個格率全部跑在 M139 的 quiet 指紋上。
100p 仍留 273 行空白 > 它的 vblank code 100。
119.88p 不行(`445×1344 = 598,080` of 600,600,只剩約 5.7 行),但不在八格率內。

### D. donor:沒有 2016×1344 的錄影 profile,但有更好的東西 [C]

全 306 row 掃過:**沒有任何 profile 以 2016×1344 當錄影矩陣。**
2016×1344 在 PARAM 表裡只以「感測器視窗」與「預覽柵格」的身分出現 ——
合理,因為 2016×1344 是 MONIT 類,相機從來不把它寫成檔案。
所以 **OG3K 借 p83 那一招在 OG2K 沒有對應物。**

但有六個「LV 3:2」profile 反而更適合:**p1、p202、p225、p251、p252、p253**

```
            rec      預覽柵格      active   預覽可見     視窗        +1C  RWZM×4   +80/+84
p202/225/   0x0    2016x1344      0x0    2000x1334  2016x1344    2    1023 全部   10/10
251/252/253
p1          同上

對照
p83        3032x2012 2024x1341  3008x2000 2000x1334  3032x2012    2    1536/1023  10/7
p175       1936x1090 1936x1090  1920x1080 1920x1080  3032x1708    1    1600 全部   7/7
```

逐項比 OG3K 的處境**更乾淨**:

| | OG3K(借 p83) | OG2K(借 LV 3:2) |
|---|---|---|
| 預覽可見高 | 1125 → 1334,要 GTAB 群組 0 補六個 profile | **原廠就是 2000x1334,不用補** |
| RWZM | p83 的 lv 對是 1536,FHD donor 是 1600 → 要 GTAB 群組 1 補 32 欄 | **四欄原廠就是 1023 unity,不用補** |
| 感測器視窗 | 3032x2012 ✔ | **2016x1344 ✔** |
| 與原廠功能衝突 | p83 是 S 尺寸照片拍攝 profile,**共用**,要 FLAG 守衛 | **rec = 0x0,沒有任何東西用它錄影** |
| 3:2 標記 +1C | 2 ✔ | 2 ✔ |

→ **`og3ksel` 的 GTAB 兩個群組在 OG2K 都可以拿掉。**
畫布 RAM 複本只要寫:錄影矩陣 `2016x1344`、active `2000x1334`、
以及依位元深度的平面格式碼 `+0x080`/`+0x084`(v0.2.2a 的機制直接沿用)。

`+0x030` 是**該 profile 的標稱 fps 浮點數**,不是張數
(p202/p1 = 60.0、p225 = 50.0、p251/252/253 = 70/80/90、p83 = 18.0、
p175 = 30.0、p43 = −1.0)。舊筆記寫「張數」不精確,緩衝張數是**由它導出的**。
OG3K 的做法是完全不寫它,OG2K 照做;選哪一個候選要看緩衝配置,待實測。

## ★ 2026-09-15(第二輪):離線尺寸模擬通過,donor 改推 p13

### F. 平面尺寸模擬乾淨通過 [C]

`og2k_sizesim.py`(在 `build/`)照 `FUN_c04356b0` / `FUN_c0435588` 的反編
逐條重算。RAW 平面大小三個位元深度全部正確(資料 + 24 bytes 標頭,
與 p83 同一個 pattern):

```
12-bit  4,064,280   資料 4,064,256 = 2016x1344x1.5
10-bit  3,386,904   資料 3,386,880
 8-bit  2,709,528   資料 2,709,504
```

plane count 一律 3,與 p83、p175 相同。總配置也都低於 OG3K 目前的
15,067,664 —— OG3K 既然跑得動,OG2K 的記憶體壓力只會更小。

順帶解掉一條舊誤解:`c04357e0` 的 plane count 是
`+0xA4 == 1 → 2;+0xA4 ∈ {9,10} 或 +0x30 == −1.0 → 0;否則 3`。
p43 的 `+0x30 = −1.0` 所以是 **0 張**,把畫格率寫進去就變 3 張 ——
「拍一張 S 尺寸照片就凍結」的機制到此完全對上。

### G. AF 表:六個 LV 3:2 profile 其實有人用 [C]

`0xC0BE48A0`–`0xC0BE4900` 是一張 AF 表,鍵是 `AF60/AF70/AF80/AF90/AF100/AF120`:

```
p1 = AF60(mode 8)    p251 = AF70(148)   p252 = AF80(149)
p253 = AF90(150)     p225 = AF100(147)  p202 = AF120(56)
```

所以 §D 說它們「沒有任何東西用」是**錯的,收回** —— 它們是 AF / 高速
live view 的 profile。借它們就會跟 p83 一樣需要 FLAG 守衛,而且撞的是
半按對焦這種隨時可能發生的事,比 p83 撞拍照更難避開。

(附帶:AF 表的 60fps 用的是 **mode 8(fast 指紋)**,不是 M139。)

### H. 真正沒人引用的 row:全映像掃描 [C]

掃全映像所有 `{1|5|6, profile, mode, key_ptr}` 形式的表項,
306 個有效 profile 裡 **132 個沒有被任何表項引用**。其中 `+0x1C == 2`(3:2)的只有四個:

```
prof row  rec   預覽柵格    可見        視窗        +0x30  RWZM
 13    6  0x0   1920x1280  1904x1270  2016x1344     60   全 1023 unity
 14    7  0x0   1236x824   1220x814   2016x1344     60   全 1023 unity
221  161  0x0   2024x1341  2000x1334  3032x2012     50   1536/1023/1536/1023
222  162  0x0   1296x864   1280x854   3032x2012     50   1536/1023/1536/1023
```

**OG2K 用 p13。** 視窗已經是 2016×1344、RWZM 已經 unity、3:2 標記已經對,
而且沒有任何表引用它。畫布 RAM 複本要寫四組:

```
+0x00/+0x04  2016x1344    錄影矩陣

+0xD8/+0xE0  2016x1344    生產者對 —— p13 原廠是 1920x1280,不補就會重演
```

模擬結果:RAW 平面 4,064,280 / 3,386,904 / 2,709,528,總配置
14,364,808(12-bit),全部合理。

### I. ★ 順帶:OG3K 應該把 p83 換成 p221

p221 與 p83 在**每一個會影響分支的欄位上逐格相同**
(`+0x1C/+0x3C/+0x44/+0x7C/+0xA4/+0xB4/+0xCC/+0xD8/+0xE0/+0xF0/+0xF4/+0xF8`),
畫布只要寫同樣的兩組 PUT,總配置還少 52,960 bytes。

差別只有一個:**p221 沒有被任何表引用,p83 是照片拍攝表的 profile。**

換過去可以直接消掉現在 `og3kcanvas.S` 檔頭寫的那個已知缺口:

> ⚠️ 這仍然不是完全隔離 —— FLAG 是選單狀態,選了 OG3K 再去拍照時仍然會立著。

也就是 v0.2.2a README 列的「選著 OG3K 拍照未驗證」那一條,換 p221 之後
**不必驗證,因為衝突不存在了**。

風險:p221 沒被引用代表也沒被原廠走過,可能有沒初始化好的欄位。
但分支欄位既然與 p83 逐格相同,而幾何欄位我們本來就要覆寫,面積很小。
建議當成 OG2K 的第一個實機測項一起驗(同一套 donor 機制,兩個目標各一個)。

## ★ 2026-09-15(第三輪):兩個目標共用一份程式碼,OG2K 卡已產出

### J. 參數化機制:clang 前處理器

`armasm.assemble(src, defines)` 本來就會把 defines 當 `-D` 傳給 clang,
而 payload 檔名都是 **`.S`(大寫)所以前處理器有跑** —— 不需要模板算繪、
不需要分叉原始碼,也不需要新檔案。

```
OG_TARGET=og3k  ./og3k_plan.py      (預設)
OG_TARGET=og2k  ./og3k_plan.py
```

`TARGETS` 表提供 label / donor profile / 記錄與裁切幾何 / FMT / 時序 /
donor 感測器模式與它的 timing record / CSV 標籤;`_defines()` 把它們變成
`TARGET_*` 巨集,`Plan.__init__` 再補上角度 wrapper 的白名單 tuple
(那些要讀韌體的時序表,所以不能在模組層算)。

三個檔用 `#ifdef` 分歧,其餘八個 payload 兩個目標**逐位元組共用**:

```
og3kcanvas.S   幾何、donor profile id、OG2K 才需要的 active / 生產者對
og3ksel.S      donor 模式的 timing record 與它的原廠 W0/W1
og3kfps.S      donor 模式編號、timing record、白名單 tuple(OG3K 七組 / OG2K 八組)
```

靜態檢查也跟著改成目標相依:新增 `_active()`(照 `#ifdef` 剝掉不會組進去的行,
讓檢查看見與 clang 相同的程式)與 `_symbols()`(把 `-D` 巨集與 `.equ` 串起來解值)。

**重構是中性的**:改完之後重建 OG3K 的 `VSHL.BIN` 與重構前**逐位元組相同**。

## ★ 2026-09-15(第六輪):+0x088 / +0x0B0 / +0x0C0 追完,而且改掉一個我自己加的錯

### U. `+0x088` / `+0x08C` = 預覽平面高度的加項 [C]

`FUN_c04358d0(obj)` 讀的是**畫布**(畫布在 obj+4):

```c
int FUN_c04358d0(int obj) {
  int h = *(int *)(*(int *)(obj + 4) + 0x10);
  if (*(int *)(*(int *)(obj + 4) + 0xe0) != 0)
      h = *(int *)(*(int *)(obj + 4) + 0xe0);
  return h + *(int *)(*(int *)(obj + 4) + 0x88)
           + *(int *)(*(int *)(obj + 4) + 0x8c);
}
```

它是 `FUN_c04356b0(c, 0)` 的高度來源,也就是**預覽平面**的高;
錄影平面(which=1)走 `+0x00/+0x04`,完全不碰這條。

```
prof  預覽柵格      生產者對 D8/E0    +0x88  +0x8C   預覽平面高
  83  2024x1341     0x0                  4      0   1341+4 = 1345
 175  1936x1090     1936x1090            0      0   1090
  13  1920x1280     1920x1280            0      0   1280
 221  2024x1341     0x0                  0      0   1341
```

**只有 p83 的 `+0x088` 是 4**,其餘全 0 —— 看起來是它那個 1341 柵格自己的
對齊餘裕,不是什麼要跨 profile 帶著走的東西。**p13 不需要補,§P 的擔心解除。**

### V. `+0x0B0` / `+0x0C0`:對 OG2K 不是問題 [C]

- `+0x0B0` 只在 `FUN_c0435e38` 用,而那個函式開頭就是
  `if (+0xA4 < 0x18) return 0;` —— p83/p13/p221 的 `+0xA4` 都是 0,
  所以這條路走不到,`+0x0B0` 是死欄位。
- `+0x0C0` 根本不在 p83 vs p13 的 19 欄差異裡(兩者都是 1)。

這兩欄是 p221 專屬的問題,p221 已經作廢(§S)。

### W. ★ 訂正我自己加的錯:OG2K 不該寫生產者對

§H 我要求 OG2K 補 `+0xD8/+0xE0 = 2016x1344`,理由是「p13 原廠是 1920x1280,

```

p13  生產者對 1920x1280  → 正好等於自己的柵格   自洽
```

高 +0xE0 = 1344」的錯配 —— 正是我想避免的那個失敗模式,是我自己造出來的。

### AW. 機制 [C]

相機用 `font_S_imageSize_<數字>` 這個資源族畫解析度標籤,**寬高各查一次**。

我們的私有 NBR 由 `og3k_ui.S` 的 `ui_load` 註冊進**相機自己的資源 context**,
所以只要 pack 裡有同名資源,原廠的名稱查詢就找得到 —— 不必動原廠資源表。

builder 現在會自動檢查目標的裁切寬高在韌體裡有沒有對應資源,**缺哪個補哪個**:

```
OG3K  3008 / 2000  兩個都在  → 不補,pack 3732 bytes,資產 3 個
OG2K  2000 / 1334  缺 1334   → 補一個,pack 4704 bytes,資產 4 個
```

### AX. ★★ XCI 有第二種像素格式:ARGB4444 [C]

`research/ui/tools/xci.py` 的模型是「低位元組 = 亮度,高位元組 = alpha,
原廠圖示 L == A」。**那對 QS 那類圖塊是對的,對 HUD 字型資源是錯的。**

解兩張原廠的 88x38 資源(`0xC13BA6E4` / `0xC13D5AFC`),31 個獨特值
全部長成 `A<<12 | g<<8 | g<<4 | g`:

```
0xFFFF  A=15 白      筆畫內部
0xF333  A=15 深灰    筆畫抗鋸齒(不透明)
0xF000  A=15 黑      黑邊
0x8000  A=8  黑      黑邊的抗鋸齒
0x0000  全透明
```

也就是 **ARGB4444**:alpha 取膨脹後的覆蓋率,RGB 取原覆蓋率。

**我猜錯兩次,兩次都是實機畫面指出來的:**

| 版本 | 假設 | 實機結果 |
|---|---|---|
| v0.1.5 | (亮度, alpha):黑邊 = L 0 / A 255 | u16 = `0xFF00`,畫出**橘紅邊** |
| v0.1.6 | RGB565 | 顏色仍然怪 |
| v0.1.8 | **解原廠資源** → ARGB4444 | 白字黑邊 |

`0xFF00` 在 RGB565 正好是 R=31/G=56/B=0 = 橘紅 —— 那個顏色本身就是線索,
但我當時拿它去推 RGB565,又猜了一次。**第三次才改成直接解原廠資源。**

**教訓:格式要解,不要猜。** 手上就有 2006 張原廠 XCI 可以對照,
第一次就該去解,而不是從既有筆記的模型外推。
