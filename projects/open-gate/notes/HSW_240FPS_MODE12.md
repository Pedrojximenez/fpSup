## 1. mode 12 出廠就是我們要的東西

`MONIT1_240`,metadata 索引 42。全部數字直接從 `out/MAIN_c0000000.bin` 讀出:

```
光柵            2016 x 672        3x6 非對稱縮減的**全片幅 3:2**(crop = 0)
hmax / tail     330 / 330
vmax            910
frame_cycles    330 x 909 + 330 = 300,300 @ 72 MHz
實際格率        239.760240 fps    ← 0 ppm,不是近似值
捲簾            330 x 672 / 72 MHz = 3.080 ms
timing record   0xC0B59A40        原廠字 0x014A014A / 0x0006038E
metadata +0x3C  0  = RAW12
metadata +0x40  240                標稱 fps,**就是真實格率**
metadata +0x54  2  = 3:2
metadata +0x58  0  = full(不是裁切)
metadata +0x5C  50 = vblank
metadata +0x60  23 = 「330 快」類比指紋、MONIT 類
```

沒有被任何 picker 表引用 —— 三張 CinemaDNG 表 26 筆全部掃過,沒有 mode 12。

**同光柵的另外兩個模式**(`G11` 家族):M140 = 59.925p 慢指紋、M9 = 59.940p 快指紋。
兩個都只有 60p,只有 M12 是 240。

## 2. ★ 這是四個目標裡唯一「感測器一個位元都不改」的一個

其他三個目標都要把 donor 的時序改掉才能拿到想要的格率,於是牽出兩件事:
donor 的 `metadata +0x40` 變成謊報值(mode 98 寫 78 而實際在錄 29.97),
以及離開時要把時序還原。HSW 兩件都不存在:

```
HSW 寫回 mode 12 timing record 的  (330, 330, 910, 6)
  = 0x014A014A / 0x0006038E
  = mode 12 的原廠字,逐位元相同
```

所以

- `fmttable` 的 timing transaction 是 **no-op**;
- `og3ksel` 的「離開 HSW 時還原原廠時序」是 **no-op**;
- 快門角度修正 **整組不武裝**(`_ANGLE_FIX_TARGETS` 不含 `hsw`)。
  角度修正存在的唯一前提是「`+0x40` 不等於實際格率」,而 mode 12 的
  `+0x40` 原廠就是 240 = 真實擷取率。stock getter 回傳的已經是對的,
  武裝那四顆 BL 只會多四個風險點換零收益。
  `SHUTTER_ANGLE_EXPOSURE_2026-09-15.md` 整篇講的那個 -1.38 EV 缺陷,
  在 HSW 上**結構上不存在**。

計畫字數 789,比 OG3K 多 40,差額幾乎全在格式表(9 列 x 48B vs 8 列)與
少掉的四顆角度 hook。

## 3. 非方形像素 —— 這一點不能忘

3x6 是**非對稱**縮減:水平 3x、垂直 6x。所以

```
視野      完整 3:2 全片幅(和 OG3K/OG6K 一樣,不是裁切)
像素      2:1 垂直壓縮
後製      垂直拉伸 2x 才是正確比例:2000x662 -> 2000x1324
```

`research/imx410/notes/SENSOR_MODE_METADATA.md` §4 尾註對這件事有明文警告
(「M140/M9/M12 是 3x6 不對稱縮減;光柵 2016x672 不能當成方形像素的正常 OG」)。
DNG 標頭寫的是 2016x662 的實際像素,沒有任何欄位告訴後製要拉伸 —— 這是使用者
要自己知道的事,必須寫進 README。

Live view 方面,`og3kaspect` 已經把長寬比 enum 設成 2(3:2),如果顯示鏈照著
長寬比把 2016x672 撐滿 3:2 的框,畫面就自動是對的比例。**這是推論,要上機看。**

## 4. ★ 選單格率 ≠ 感測器格率 —— 兩種結果都有價值

九個格率鍵全部指向同一組時序,感測器**恆為 239.76 fps**:

```
鍵          容器格率    若 writer 走 VSYNC
HSW23_98     23.976      9.99x 慢動作
HSW24        24.000      9.99x
HSW25        25.000      9.59x
HSW30        29.970      8.00x
HSW48        48.000      5.00x
HSW50        50.000      4.80x
HSW60        59.940      4.00x
HSW100      100.000      2.40x
HSW120      119.880      2.00x
```

原廠**從來沒有**讓錄影格率與感測器格率不同(`OPEN_GATE_EXPLORATION_ARCHIVE.md`:
「The recording frame rate matches the sensor mode's exactly」)。所以 writer 的
驅動來源是這件事唯一的未知數,而兩種答案都是有用的功能:

- **(a) writer 由 VSYNC 驅動** → 每一格都寫 → 上表的慢動作倍率成立,
  這是一個 240 fps 高速攝影模式。
- **(b) writer 由格率計時器驅動** → 抽格 → 正常速度播放,但
  **快門上限 1/240、捲簾 3.08 ms** —— 名副其實的「高速快門模式」,
  適合甩鏡、頻閃、螺旋槳一類的場合。

**同一份 build 兩種都涵蓋。錄一秒數格數就知道是哪一個。**

九個鍵全列的第二個理由是可達性保險:新的解析度 enum 4 到底能選到哪幾個格率
沒有離線證據(舊紀錄裡使用者回報過「100 fps 在 SD 卡路徑選不到」),
全列上去就不必賭哪一格能選。每一列都是純資料,不增加新的失效模式。

## 5. 資料率 —— 這是真正的天花板

```
                每格           239.76 fps
12-bit  2000x662x1.5 = 1.986 MB   476.2 MB/s
10-bit  2000x662x1.25= 1.655 MB   396.8 MB/s
 8-bit  2000x662x1.0 = 1.324 MB   317.4 MB/s
```

對照:原廠 UHD 3856x2170 RAW12/29.97 是 **376.2 MB/s**,那是相機每天在寫的量
(外接 SSD 路徑)。所以

- **8-bit 317 MB/s 低於原廠最高值** —— 這是唯一有把握的組合,先測它。
- 10-bit 397 MB/s 略高於原廠最高值。
- 12-bit 476 MB/s 比原廠最高值高 27%,**預期寫不動**,掉格或直接停錄。

位元深度是既有機制(三張 picker table + `BITLATCH`,見
`OG3K_8BIT_10BIT_FALLS_BACK_TO_UHD.md`),HSW 三張表都註冊了,不必另外做事。

若結果是 §4 的 (b)(抽格),資料率就退回容器格率那一格,全部位元深度都輕鬆。

## 6. 目標定義

```python
"hsw": dict(
    label="HSW", profile=13, rec=(2016, 672), act=(2000, 662),
    write_active=True, write_producer=True, write_preview=True,
    fmt=FMT_HSW, timing=HSW_TIMING,
    mode=12, mode_timing=0xC0B59A40, mode_stock=(0x014A014A, 0x0006038E),
    stock_nominal_fps=240,
    nominal_fps_addr=0xC0B5AE68, buffer_count_addr=0xC0BD471C,
    csv=b"3,HSW 2000x662,,1,2",
    angle_exclude=set(), nominal_fps_fixed=240,
)
```

- **profile p13**,和 OG2K 同一個(不同卡,不會同時存在)。沒有被任何表引用、
  `+0x1C = 2`(3:2)、`+0x030` 是正值(張數 3),幾何欄位全部由
  `write_active` / `write_producer` / `write_preview` 覆寫 ——
  這正是 OG2K 已實機驗證過的用法,`check()` 的 donor 白名單也已含 p13。
- **`nominal_fps_fixed=240`**:角度 AE 要的是真實擷取率,不是選單上那個數字。
  `check()` 用 `round(實際 fps) == nominal class` 驗這一點,九個鍵全部 240。
- **`og3kgs` 仍然武裝**。mode 12 是 MONIT 類,消掉的是 mode 98 那個跨類別賭注;
  但增益分派讀的是 **profile id 的數值範圍**(`FUN_c043a1c8`),不是感測器模式,
  而 p13 和 p83 一樣落在 raw movie 的 131..190 之外。與 OG2K 相同。
- CSV 第三列 `3,HSW 2000x662,,1,2`,整塊 87 bytes(上限 92)。

### 已知不符:感測器視窗 +0x0F4/+0x0F8

畫布的錄影路徑不寫感測器視窗,所以會留著 p13 原廠的 **2016x1344**,
而 mode 12 實際只讀 **672** 行。

**這不是 HSW 獨有的**:OG6K 拿同族的 p14(視窗一樣 2016x1344)去錄 6064x4042,
差得更多;OG3K 只是剛好 p83 的視窗就等於它的光柵。四個目標裡三個不符,
既有設計選擇是一個位元都不寫,HSW 照辦。

**若第一段素材的幾何是錯的(上下半幅垃圾、或影像被垂直拉開),這是第一個該翻的
開關** —— 做法是加一個 `write_window` 旗標,在 `og3kcanvas.S` 的錄影路徑補
`PUT 0xF4, W` / `PUT 0xF8, H`,並在 `CANVAS_REC` 加對應兩筆。一次只動這一個變數。

## 8. 上機測試矩陣(尚未執行)

抽電池冷開機是唯一接受的起始狀態。靜態場景,固定光圈 / ISO / WB。

1. **先數格數。** 8-bit、選單 119.88、錄約 1 秒,`rec log-out` 讀回幀數與 MB/s。
   - 幀數 ≈ 240 → §4 的 (a),真的是 240 fps 高速攝影。
   - 幀數 ≈ 120 → §4 的 (b),是高速快門 / 低捲簾模式。
   這一步決定後面所有測試怎麼讀。
2. 解 DNG:尺寸必須是 2016x662 光柵、2000x662 裁切,整幅清晰、上下沒有
   未初始化記憶體(比照 OG3K 的 A001_036 驗收方式)。垂直拉伸 2x 後比例要對。
3. 快門:180° 應該給 1/480 s(240 fps 的一半),不是 1/240 或 1/60。
   這是「角度修正整組不武裝」是否成立的直接證據。
4. 位元深度:8-bit 過了再試 10-bit(397 MB/s),12-bit(476 MB/s)預期會掉格,
   測它是為了知道極限在哪,不是為了用它。
5. Live view:2016x672 在取景時是不是被撐成 3:2(§3 的推論)。
6. 捲簾:甩鏡或拍轉動的東西,對比 OG3K 的 12.435 ms。3.08 ms 應該肉眼可辨。
7. 最後才測 CINE → STILL → CINE。與 OG3K 同樣的邊界:離開 CINE 前先選
   FHD 或 UHD(`SHUTTER_ANGLE_EXPOSURE_2026-09-15.md` 末段的 pending boundary)。

錄影中不要查詢相機。start/stop 是兩次各自完整的 `MOVON` → 短延遲 → `MOVOFF`,
`MOVON` 逾時不要盲目重試。

## 9. ★ 選單裡沒有 239.76 這一格 —— 機制與代價(2026-09-20 追加)

使用者提問:「239.76 是原廠沒有的 fps,你有加上去嗎?不然選不到。」
**沒有,而且韌體裡不存在。** 以下是查到的東西。

### 9.1 CINE 格率清單是 9 列,六個閘門變體

```
0xC0F8E848   全開:23.98 24 25 29.97 48 50 59.94 100 119.88
0xC0F8E94C   只開到 29.97          (48 以上 Enabled=0,0)
0xC0F8EA50   只開到 24
0xC0F8EB54   只開到 25
0xC0F8EC58   只開到 59.94
0xC0F8ED5C   只開到 100
```

列的 TEXT 是字串資源 ID:

```
0316 "23.98 fps"   1916 "24 fps"    0317 "25 fps"    0318 "29.97 fps"
2115 "48 fps"      0319 "50 fps"    0320 "59.94 fps" 0321 "100 fps"
0322 "119.88 fps"
```

六個變體就是「哪個解析度/格式能選哪幾格」的閘門 —— 這也解釋了舊紀錄裡
「100 fps 在 SD 卡路徑選不到」。**沒有 239.76 的列,也沒有對應的字串 ID。**

每塊 257B 用掉、到下一塊 260B,**只剩 3 bytes** —— 與解析度那塊
(89B / 92B)同樣的處境。

### 9.2 這不影響感測器,只影響「有沒有東西可以按」

HSW 的格率來自格式表(`fmttable` 把 mode 12 的時序寫進 timing record),
**不是來自選單**。所以現行 build 的感測器確實在跑 239.76,選單那個數字只進到
容器 metadata。少的是一個標著 239.76 的可選項,不是感測器能力。

**要不要補這一格,完全取決於 §4 的 writer 問題:**

- writer 走 VSYNC(§4a)→ 現行 build 已經是 240 fps 高速模式,補這一列只是
  讓 metadata 誠實(容器 239.76,後製自己 conform),是加分。
- writer 跟著選單格率抽格(§4b)→ **補這一列是必要條件**,否則永遠只錄到
  ≤119.88,240 只剩「快門變短」。

§8 的第 1 步(錄一秒數幀數)就是這個分岔的判別式,所以它必須先做。

### 9.3 四件事,三件已完成,一件未解

| 件 | 狀態 |
|---|---|
| picker 鍵發射器 | **不用改**。`FUN_c043caf0` 的界線原廠就是 `cmp r3,#12`(0xC043CB04),跳表十三筆(0xC043CB18),**enum 11 -> `"240"`、enum 12 -> `"400"`**,字串在 `0xC0BE4800`:`'400\0240\0120\0100\023_98\0...'`。列舉空間原廠就留了 240/400 兩格,只是沒有有理數也沒有選單列。所以鍵自然就是 `HSW240` |
| CSV 第十列 | **完成**。六個 `B2_5_5*.cvm` 變體全部重排成「拿掉 Popup 欄、資料列裸 `\n`」:257B -> **211B**,第十列 `10,239.76 fps,blank,1,2`。描述子的長度欄(大端序)一併改成 211,否則解析器會多讀 46B 舊殘留 |
| 有理數 | **完成**。`FUN_c00c9bd0` 被 `cmp r2,#10`(0xC00C9BF8)夾住,enum 11 會落到 default(29.97)。`hswrate.S` 掛在那顆 cmp:命中 11 就寫 240000/1001 再跳原廠收尾 0xC00C9CEC;不命中就原地重做 `cmp r2,#10` 跳回 0xC00C9BFC(movw/movt 不動旗標,後面那顆 `bhi` 讀到的條件碼與原廠相同) |
| **清單控制器上限** | **完成**。`0xC1A74B44`,BE float 8.0 -> 9.0(寫 `0x00001041`) |

### 9.4 ★ 上限那一顆是怎麼定出來的

社群交接文件只給了**解析度**那顆(`0xC1A709BC`)。格率的對應物盲掃找不到
(BE float 8.0 全映像 8257 個命中)。解法是用 handoff 自己的 UI 記錄解析法
(`inspect_uic_resources.load()` + `audit_fp3k_ui_layout` 的祖先鏈)跑在我們的
映像上 —— NBU 在 `0xC18C0460`,記錄鏈 `0xC18EB48C`..`0xC2D8CEF8` 共 303,599 筆,
與 handoff 的常數完全吻合。

先用 controlValue 的記錄簽章(`len==40`、`+0x10 == 0xFFFFFFFF`、
tag `0x0001000E`、pool `0x24FE0`、mask `0x0A`)掃出 77 筆 List 控制,其中
max-value == 8.0(= 九列)的只有兩筆,再各自解回祖先鏈:

```
0xC1A7099C obj 0x10A3 max 1.0  List / MenuItem_Select / B2_5_4 / Menu / Root   解析度(與 handoff 相符)
0xC1A74B24 obj 0x1157 max 8.0  List / MenuItem_Select / B2_5_5 / Menu / Root   ★ 格率,同一個畫面
0xC2B53E14 obj 0x00D7 max 8.0  List / ... / 2_01 / Menu / Root                 別的畫面,無關
```

max-value 在記錄的 `+0x20`,所以 `0xC1A74B24 + 0x20 = 0xC1A74B44`。

### 9.5 資源描述子

## 10. ★ 還沒解決的兩件事

### 10.1 enum <-> 列 的配對表沒有預留空位

```
解析度 @0xC2E4020C   {3,0} {2,1} {4,2}                     原廠只有兩列,卻**預留了第三筆**
格率   @0xC2E44EE4   {1,0} {2,1} {3,2} {4,3} {6,4}
                     {7,5} {8,6} {9,7} {10,8}              剛好九筆,後面緊接別的表
```

**OG3K 第三列當年之所以那麼順,是因為原廠替解析度留了一格。格率沒有。**
而且這兩張表都**沒有任何字面引用**(掃全映像 0 個 LE 參照),表示它們是由
某個索引結構定位的,不能靠改一個指標搬走。筆記 §24 說它是
`FUN_c06bd988 -> vtable+0x5C -> (table, count) -> FUN_c06ccd10` 這條路拿到的。

缺它的後果**未知**:可能只影響收合摘要的顯示,也可能影響選取本身。
要解就照當年追解析度的做法上機追:掛格率 setter `C005C0B8` 記錄選第十列時
送進來的 enum,再掛 `vtable+0x5C` 的取得點記下 (table, count)。

**整條路是 fail-open:** 送進來的 enum 不是 11,`hswrate` 不動作、鍵也不會是

## 12. 400 fps:沒有模式,也做不出來

enum 12 原廠印 `"400"`,但**沒有任何感測器模式撐得起來**:

- mode 12 的 239.760 fps 是全機 70 個模式的最高值,第二名直接掉到 119.88。
- 400 fps 一格 = 180,000 cycles;mode 12 光是有效讀出就要
  `330 x 672 = 221,760` cycles,**已經超過**。
- 所以 2016x672 這個光柵的上限是 `72e6 / 221,760` = **324.7 fps**(消隱歸零的
  理論值;照它 vblank code 50 算約 302 fps)。
- 要 400 fps 得要一個約 500 行的光柵(hmax 330 -> vmax 546),韌體 70 個模式裡
  **沒有這種光柵**,最矮的就是 2016x672。

那需要自己合成一組新的感測器暫存器組,不是「沿用出貨暫存器組、只改
hmax/tail/vmax」這一類工作。**`"400"` 是個沒有模式撐腰的空字串。**

## 16. ★ 但管線扛不住 —— 這是硬阻斷,不是調參問題

`rec log-out`(那一段約 1.2 秒的 take):

```

```

**8-bit 也還差三倍。** 所以 239.76 fps 錄到這張 SD 卡,任何位元深度都不可能。
原廠 12-bit UHD 的 376 MB/s 是走**外接 SSD**的,不是卡。

### 16.1 因此設計層面有三條路,不是調參

1. **外接 SSD**:8-bit 的 317 MB/s 低於原廠 UHD 12-bit 已經在做的 376 MB/s,
   這是唯一有機會跑滿 239.76 的路。**尚未測。**
2. **把 mode 12 降速**:2016x672 配上媒體能吃的格率。實測的 48 fps 正好是
   `104 MB/s / 2.11 MB`。2016x672 @ 48p、捲簾 3.08 ms,本身就是個有用的
   低捲簾模式 —— 只是它不叫 240。
3. **維持 239.76 但抽格**:做不到。writer 是 VSYNC 驅動的(req_cnt 跟著感測器
   跑),它不會抽格,只會餓死。**所以 §4 的 (b)「高速快門」路線在這個
   實作下不存在。**

### 16.2 安全項:必須加護欄

現在的 HSW 只要按下錄影就會把錄影器卡死,需要斷電。**在找到可行的媒體/格率
組合之前,這張卡不能交給任何人**,而且應該在計畫層加一個拒絕條件
(例如 donor 格率 x 每格位元組 > 已知媒體上限就不註冊)。

## 30. ★ 凍結的分界線落在 60 fps —— 指向 donor 的 `+0x030`

### 30.1 使用者的兩次更正,再次成立

- **「儲存卡住頂多斷開錄影,不會卡住」** —— 由使用者自己的 SSD 素材證實:
  `A001_107` 容器標 119.88、**實際只有 31.0 fps**(392 MB/s 天花板),
  `A001_106` 容器標 100、實際 87.4 fps,**兩段都正常完成**。
  **媒體飽和在這台機器上的行為是掉格 + 正常結束,不會凍結。** 吞吐徹底出局。
- **「一定是緩存的關係」** —— 目前所有資料都指向這個方向,見下。

### 30.2 實測的分界

```
HSW  23.976   vmax 9100   正常
HSW  29.97    vmax 7280   正常(SD 41/15/9 格;SSD 177 格 x 2 段,6 秒)
HSW  59.94    vmax 3640   **未測**
HSW 119.88    vmax 1820   錄超過約 1 秒就凍結(A001_115 0 格、A001_116 5 格)
HSW 239.76    vmax  910   凍結(A001_114 0 格,目錄配置 105M 但一格未寫)
```

**分界線在 29.97 與 119.88 之間。**

### 30.3 為什麼不是消隱不足

```
HSW 119.88   hmax 330 vmax 1820,有效 672 行 -> 消隱 1148 行 = 5.26 ms
原廠 mode 58 hmax 330 vmax 1820,有效 1708 行 -> 消隱  112 行 = 0.51 ms
```

**原廠在完全相同的 330/1820 下、消隱只有我們的十分之一,照樣跑滿 119.88。**
所以消隱時間不是原因,差別在 profile 這一側。

### 30.4 候選:`p13` 的 `+0x030` = 60.0

```
p13  (OG2K / HSW donor)  +0x030 @0xC0BD471C = 60.0
p83  (OG3K donor)        +0x030 @0xC0BD47AC = 18.0
```

`og3k_plan` 對這個欄位的既有規則是「**一個位元都不寫**」,因為 `FUN_c04357e0`
只用它的正負號決定 plane count。但它的**數值**是標稱 fps,若管線據此配置緩衝,
那麼 60.0 正好解釋分界線在 60。

這也解釋了前三個目標為什麼從沒踩到:

```
OG2K  用 p13,最高只到 60      從未超過那個值
OG3K  用 p83,100p 走 mode 117  不是同一條
HSW   用 p13,要跑到 119.88/239.76   ← 第一個超過的
```

### 30.5 兩個實驗,按資訊量排序

**實驗 A(直接驗機制,不用改 build):** 用 shell 把 `0xC0BD471C` 從 60.0 改成
240.0,錄 HSW 119.88 超過 2 秒。

```
正常錄完  -> 緩衝配置就是原因。修法是讓 og3kcanvas 把 +0x030 寫成當前格率
           (畫布是 RAM 複本,和其他欄位同一個機制,不碰 PARAM 本體)
仍然凍結  -> 這個欄位不是原因,假設推翻,回到 wedge_probe 找別的
```

**實驗 B(便宜的夾擠):** 錄 HSW **59.94** 超過 2 秒。

```
正常  -> 分界確實在 60,強化實驗 A 的假設;而且 59.94 本身就是可用的模式
       (2016x672、捲簾 3.08 ms、8-bit 只要 81 MB/s,SD 卡就夠)
凍結  -> 分界比 60 低,+0x030 的解釋變弱
```

A 是直接測機制,B 是夾出邊界。兩個都只要一次錄影。

65 欄裡 26 欄不同,其中**我們從不寫的有 10 欄**。最顯眼的三個:

```

FHD120  8b     1        1        2.0f
FHD120 12b     1        1        2.0f
FHD60  12b     1        0        2.0f     <- 60p 與 120p 只差 +0x0B0
p83 (OG3K)     0        0        2.0f
p13 (HSW)      0        0        3.0f     <- 只有它是 3.0
```

### 31.3 `+0x0B0` 的語意:確實是張數,但不在我們這條路上

反組譯確認 profile 欄位是**同位移**複製到畫布(`0xC0439FE8`:
`movw/movt r6,#0xC0BD7B9C` -> `ldr r3,[r6,r4,lsl#2]` -> `str r3,[ip,#0xb0]`)。

`FUN_c0435e38`:

```c
r1 = canvas[0xA4];
if (r1 <  0x18) return 0;
if (r1 == 0x18 || r1 == 0x2B) return canvas[0xB0] == 1 ? 8 : 6;   // ★ 張數
if (r1 == 0x19) return 2;
if (r1 == 0x1A) return 3;
```

**但五個 profile 的 `+0xA4` 靜態值都是 0**,所以這支對它們一律回 0 ——
`+0xB0` 根本走不到。這一點我在提出實驗時就標成但書了。

**實測(2026-09-20):把 p13 的 `+0x0B0`(`0xC0BD7BB4`)從 0 改成 1,
錄 HSW 119.88 —— 仍然凍結。** 與但書的預測一致,`+0x0B0` 排除。

### 31.4 方法換掉:不再從靜態表推論

靜態的 profile 欄位表無法告訴我們**執行期畫布真正長什麼樣**(`+0xA4` 就是例子:
表說 0,但那支函式明顯期待 0x18/0x2B,所以它一定在別處被設)。

所以在 `og3kcanvas` 的錄影分支加一個字:

```asm
#ifdef TARGET_CANVAS_PTR_LOG
    str     r1, [ip, #0x14]             @ LOG+0x14 = 執行期的畫布位址
#endif
```

只有 HSW 開(`canvas_ptr_log=True`),OG3K/OG2K/OG6K 的字數與位元組不變。
計畫字數 1147 -> 1148(per-rate 模式下 807 -> 808)。

有了位址就能用 shell 直接讀整份畫布,然後把**已知能跑的 29.97** 與
**已知會凍的 119.88** 兩種狀態逐欄 diff(`build/canvas_dump.py`)。
差在哪一欄就是哪一欄,不必再猜。

## 35. 破解「接 SSD 就沒有 shell」的死結:把錄影 log 導到檔案

接 SSD 錄影時相機的 USB-C 被佔用,`rec log-out`(走 UART)讀不到。
但韌體的 `rec` 指令有檔案輸出模式:

```
rec log-on     錄完把 log 寫成檔案
rec log-file   直接寫檔
rec log-sim    檔案與 UART 同時        ← ★ 錯了,見 §46:它不寫檔
rec log-out    只走 UART(先前一直用這個)
```

> ★ **這張表的 `log-sim` 那一列是錯的,已由 §46 更正**(反組譯)。
> `log-sim` 是「與錄影同時逐筆吐 UART」,一個位元組都不會寫進媒體。

而 **AutoRun 本身就是一串韌體 shell 指令**,所以把 `rec log-sim` 寫進 AutoRun,
開機就生效,錄影 log 會落在媒體上,事後插回電腦即可讀 `req_cnt` / `fin_cnt`。

★ **必須插在 `# --- store bootstrap` 之前。** 快載入命中之後 loader 會
**停掉腳本**,所以任何加在結尾的指令在快卡上永遠不會執行。
`build/add_reclog.py` 做這件事並檢查那個標記存在。

### 44.1 `FUN_c0435e38` 是死路 —— `+0xB0` 從頭到尾不相干

### 44.5 ★ 未測的強假設:固定快門速度與 240 不相容(使用者提出)

```

240 fps 的格週期     =  4.17 ms            差 4 倍,物理上不可能
```

### 44.6 角度模式證實感測器與曝光系統都在 239.76

`A001_018`(SD、HSW、12-bit、格率槽 29.97 = 感測器 239.76、快門模式 1 = 角度、
角度 1800 = 180.0 度):

```

容器 29.970                  ISO 6400(自動補償)
req_cnt = fin_cnt = 94       零掉格,環用完乾淨停(ui factor: Nothing)
```

**角度模式按 239.76 算快門,不是按容器標的 29.97**(那會是 1/60)。
所以感測器真的在 239.76,而且**曝光系統讀得到真實格率**。整條上游鏈正確。

## 46. ★ 收回 §42:`rec log-sim` 不會寫檔,而且它在每一格的關鍵路徑上

§42 說「把 `rec log-sim` 寫進 AutoRun,錄影 log 就會以檔案形式落在媒體上」。
**那是錯的。** 反組譯 `rec` 那六個子指令(0xC04073C8 起,旗標區 0xC3757F08)
之後,語意是這樣:

```
子指令      做的事(旗標區 0xC3757F08)                      會寫檔?
log-on      strb #1,[+0x00]                                  ★ 會(結束時)
log-uart    [+0x0C] = 0xC0407368   [+0x04] = r0              不會
log-sim     [+0x08] = 0xC0407368   [+0x04] = r0              不會
log-off     清掉 +0x00 / +0x08 / +0x0C                       不會
log-out     當場把緩衝吐到 r0,不設旗標                       不會
log-file    當場把緩衝寫成檔案,不設旗標                      會(當場)
```

四個字會被 `FUN_c06B05D8` 複製到 0xC38D05BC..0xC8。錄影結束的處理在
`FUN_c06B03A0`:

```c
Normal();            // 媒體參數那一行
FUN_c06B00B0();      // 時間、rec factor、ui factor、電池、四個溫度
if (byte 0xC38D05BC) FUN_c06B05C8();                    // ← 寫檔,只有 log-on 會設
if (0xC38D05C8)      FUN_c06B0480(ctx, 0xC38D05C8);     // ← 吐 UART,log-uart 設的
```

**只有 `log-on` 會讓那個 byte 變成 1,所以只有它會產生檔案。**
「sim」不是「file + uart 同時」,是「**與錄影同時**」—— 它設的
`+0x08` 被 `FUN_c06B0318`(錄影開始,印表頭)與 `FUN_c06B03E8`(每一筆)
拿去**即時**輸出。help 字串 `simultaneous output` 指的是這個。

### 46.1 ★ 更糟的是:它掛在每一格 DNG 建檔的路徑上

逐格的 log 進入點是 `FUN_c03A59E8`,而它的呼叫者是:

```
XC_StillCreateFile::v4 (0xC037E0F8) → FUN_c03A5348 → FUN_c03A55D0
                                                        ├─ FUN_c03A59E8()   ← log,**排在最前面**
                                                        └─ FUN_c03A52D0()   ← 真正的建檔工作
```

`FUN_c03A59E8` 只在 `req_cnt` 前進時才送一筆,也就是**每一格一筆**。
筆的格式是 `FUN_c03A5750` 的 `%9u %9u %4u %4u %6u %6u %4u %3u …`,
約 60 個字元。所以 AutoRun 裡掛著 `log-sim` 時:

```
119.88 fps   約  7.2 KB/s 的 UART 輸出,而且在每一格建檔之前
239.76 fps   約 14.4 KB/s              ← 剛好是會凍結的那一檔
```

而且 `log-sim` / `log-uart` / `log-out` 都會把**下指令當下的 shell 輸出
控制代碼**(r0)存進 `+0x04`,之後每一筆 log 都 `ldr r2,[r0]; blx r2`
(`LAB_c0407368` 的尾巴)。從 AutoRun 下這些指令,存的是**開機腳本的**
控制代碼 —— 錄影時那個物件是否還活著,沒有驗證過。

**★ 2026-09-20 20:14 上機更正:卡上實際寫的是 `rec log-out`,不是 `log-sim`。**
所以上面那個「每格 60 字元 UART」的混淆因子 **從來沒有被武裝過** ——
§43 的那些 SSD 測試不帶這個成本。上面的分析仍然成立(那是一個真的陷阱,
`add_reclog.py` 的預設值曾經是 `log-sim`),但**它不是 240 凍結的原因**。

而 `log-out` 從 AutoRun 下也是白做工:它是「當場把緩衝吐到 r0」,開機時
緩衝是空的,而且它**不設任何旗標**。所以那些 SSD 測試其實是
**完全沒有錄影 log** 的狀態在跑。

`build/add_reclog.py` 已改成預設 `log-on`,並且會擋下另外三個;
**卡上的 AutoRun 也已經改成 `rec log-on` 並逐位元組驗證過**(2026-09-20 20:16)。

### 46.3 媒體參數那一行的來源(§45.2 步驟 3 已備好)

```c
if (slot == 5) { printf(" : %dMbps", vtbl+0x28(dev)); return; }   // ← 外接走這條
else            printf(" : %s", {Normal|UHS-I|UHS-II|unknown});   // ← SD 走這條
```

### 46.4 順手解出來的:每一格配置多少(§45.2 步驟 4 的一半)

`FUN_c03A4B00` = 每一格要佔多少位元組:

```
per_frame = round_up( round512(frame_bytes) + 0x15400 , cluster ) + 128
            + (音訊開著時) 192000 / fps
```

`0x15400` = 87,040 是 DNG 標頭/中繼資料的保留量,`192000` = 48 kHz x 2ch x 16bit。
8-bit 的 1,354,752 + 87,040 = 1,441,792 = **剛好 11 個 128 KB 叢集**,一格不浪費。

`FUN_c03A48E8` = 這張媒體還能錄幾格 = `剩餘空間 / per_frame`,再被
`7200 x fps`(0xC0BA0354 = 7200 秒)夾一次。結果存進錄影脈絡 `+0x9C`。

而 `FUN_c03A4D00`(`src/framework/recMgr/src/CinemaD…`)就是**建 WAV** 的地方:

```c
wav = local_314->vtbl[0xC]("WAV");          // 這一段的 WAV 路徑
FUN_c03A5858(slot, wav, 0x4000000);         // 註冊錄影 log,bulk-size = 64 MB(字面常數)
…
FUN_c03662D0(mediafile, wav, {frame_cap, 0x18, buf, 0x40000});   // 建檔,vtbl+0x44
return 0;   // ← 任何一個建檔步驟失敗就回 0,呼叫端 FUN_c0378A50 直接放棄開始錄影
```

★ **「240 + SSD 沒有 WAV」= `FUN_c03A4D00` 回了 0 或根本沒走完。**
`FUN_c03662D0` 的 `vtbl+0x44` 解出來是 `XC_MediaFileSdCard::v15`(0xC0369178)——
**SD 與 SSD 共用同一顆**(整個映像只有 `XC_MediaFileSdCard` 一個實作類別),
再往下是 `FUN_c0367708`(遞迴建父目錄)→ `FUN_c0367D10` → `FUN_c063C4D0`。
所以差別不在檔案層,而在它背後的 driver —— 見 §50。

`0xC359BE68` 那組計數器的欄位也一併確認了:

```
+0x00 req_cnt(FUN_c03A5858 開頭清 0)   +0x30 bulk-size(= 0x4000000,呼叫端給的)
+0x38 fin_cnt(FUN_c03A59E8 每次 +1)    +0x40 上一筆已記錄的 req_cnt
```

## 50. ★ SD 與外接 SSD 在 driver 層只差四顆虛擬函式

`XC_MediaDriverHost : XC_MediaDriverSdcard`(vtable @0xC2E3CF7C vs @0xC0B97A08)。
逐格比對兩張表,**Host 只覆寫了 [0]、[8]、[15]、[16] 四格**,其餘十五格逐字相同:

```
slot   Sdcard        Host          是什麼
[ 0]   c036c5e0      c036d598      解構/型別
[ 8]   c036bd88      c06afc40      Host = 問連線速率(FUN_c063D1A8(dev,0x1001))-> Mbps
                                   Sdcard = `return 0`
[15]   c036a2e8      c06afbf8      掛載
[16]   c036b200      c06afc20      ★ 裝置參數 / 速度等級初始化
```

`Normal()` 印媒體參數那一行時 `if (slot == 5) 走 +0x28`,而物件的表基底是
`&DAT_c0B97A04`(建構子 `FUN_c0369F28` 設的,比 slot0 少 4),所以 +0x28 正好是
**[8]** —— 這就是「外接會印 Mbps、SD 印 UHS 模式」的來源,也確認 **slot 5 = 外接**。

### 50.1 ★ Host 的 v16 是空實作,裝置參數結構停在建構子預設值

```c
XC_MediaDriverHost::v16(void)        { return 1; }                  // 0xC06AFC20
XC_MediaDriverSdcard::v16(this, go)  {                              // 0xC036B200
    type = vtbl+0x14(this);                     // 0xb 或 0xe
    … 從 SD 的暫存器讀速度等級 / AU 大小,填進 this+0x6C/0x70/0x74/0x78/0x7C
      (type 0xe 走 +0x84..+0x94,並設 +0x100 = 0x10)
    … 再填 +0xFC / +0xE4 / +0xF8
    FUN_c01F0820(devid, this + 0x50);           // ★ 把那個參數結構交給檔案系統層
}
```

而且 `Sdcard::v15`(掛載)裡有一行 `vtbl+0x48(this, 1)` = **呼叫 v16**;
`Host::v15` 沒有那一行。所以外接這條路 **從頭到尾不會執行 v16,也不會呼叫
`FUN_c01F0820`** —— `+0x50` 起那 0xB8 個位元組停在 `FUN_c0369F28` 的預設值:

```
+0x6C = 0        +0x70 = 0x10003   +0x74 = 0      +0x78 = 0xC    +0x7C = 0x80
+0x80 = 0x80     +0xE4/+0xF8/+0xFC = 0x10003      +0x100 = 0     +0x104 = -1
```

`FUN_c01F0820(devid, params)` 依 devid 分派:`'P'(0x50) -> FUN_c01F07F0(0xb, params)`、
`'S'(0x53) -> FUN_c01F07F0(0xe, params)`、`'c'(99) -> FUN_c01F10D8()`。

**這是目前找到的、SD 與 SSD 之間唯一具體的行為差異,而且它正好是
「這張媒體的配置單位與寫入特性」那一類參數。** 它能不能解釋 240 的
「配置階段就死」還不知道 —— 但它是第一個不必猜的比對點:

- 240 + SSD 若死在配置,那組預設參數(特別是 `+0x78 = 0xC`、`+0x7C = 0x80`)
  就是第一個要量的東西
- 而 120 + SSD 能過,代表這組預設在 120 的節奏下夠用

**注意**:這條線索**不會**因為 §46.1 的 `log-sim` 混淆因子而失效,
但在確認 240 + SSD 仍然凍結之前,不值得投入 —— 先做 §49 的第 1、2 步。

## 53. ★ `req_cnt = 94` 的真正意思:描述子池被抽乾,而且那是**正常停止**

`vbuf` @ 0xC0379E08(`__func__` 字串就叫 vbuf,出自
`src/framework/recMgr/src/StillCreateFile`)是**每一格**的進入點。
它第一件事是跟池子要一個描述子:

```c
iVar4 = FUN_c0374268(pool, *(param_1 + 0xa0) /* = 1, CinemaDNG */, 0);
```

而 `FUN_c0374268` 的閘門是:

```c
if (param_2 == 1) { iVar7 = 0x60; iVar8 = 1; }     // CinemaDNG
else              { iVar7 = 0x3f; iVar8 = 6; }     // 其他
if ((uint)(iVar8 + (0x60 - iVar7)) < FUN_c03739c0())   // 剩餘數
        ... 配置 FUN_c0380480(0x111c) 的描述子 ...
```

CinemaDNG 那條的門檻是 `1 < 剩餘`,池子總數 0x60 = **96**。
所以最多配到剩 2 個 ⇒ **94**。`req_cnt = 94` 每次都剛好 94 就是這個常數,
與「環大小」無關 —— 描述子在每一格**寫完之後歸還**,所以 120 fps 寫得完的時候
池子永遠不會見底(A001_120 寫了 1177 格)。

★ **240 + SD 的 94/94 因此完全解釋了**:感測器 239.76、寫入端只跟得上約 42 fps,
池子在 94 格之內抽乾,`FUN_c0374268` 回 -1,錄影**正常停止**。
這在源碼層面證實了使用者 §25.2 的更正:**吞吐不足是乾淨停止,不是卡住。**

### 53.1 停止原因是一個字串,而且 `rec log-out` 會印出來

`vbuf` 的每一條失敗路徑都呼叫 `FUN_c03A5938(<字串>)`,寫進 `0xC359BE70`,
就是 log 裡 `req_cnt=.., fin_cnt=.., <這裡>` 的那一段:

```
", %s/%d/%d"  其中 %s 取自 0xC0B9A804 的五位元組字串表,索引由兩個條件組出來:
    idx = (ret == -2) + (frame_cap <= frames_done) * 2
    0 "vbuf"   ret=-1  還沒到上限   描述子池抽乾      ← 我們每次看到的
    1 "vmed"   ret=-2  還沒到上限   媒體側拒絕
    2 "vidx"   ret=-1  已到上限
    3 "vcnt"   ret=-2  已到上限
", cnt/%d/%d"   frame_cap <= frames_done        錄滿了
", data"        取不到 descriptor
", mem"         descriptor 的 +0x68 是 0,記憶體沒拿到
```

`vbuf/94/83783` 的兩個數字是 `frames_done` 與 **`frame_cap`**(§46.4 的
`FUN_c03A48E8` 算出來的上限),不是池子大小。SD 上是 83,783,受剩餘空間夾住。

★★ **這七種停止原因全部是乾淨停止。所以「凍結」照定義就不是其中任何一種 ——
凍結發生在 `vbuf` 的控制流之外。** 這把搜尋範圍砍掉了一大半。

## 54. ★ `FUN_c03A4D00` 不是「建 WAV」,是建 clip 目錄,而且它會寫 26 MB 的零

`FUN_c03662D0` -> `XC_MediaFileSdCard::v15`(0xC0369178)-> `FUN_c0367708`,
而 `FUN_c0367708(dev, path, 1, opts, 0)` 的 `param_3 == 1` 表示
**取 dirname**,然後遞迴建立 —— 也就是 `mkdir -p`。

所以 `FUN_c03662D0(mediafile, <WAV 路徑>, opts)` 建的是
**`\CINEMA\A001_nnn` 這個目錄**,不是 WAV 檔。§46.4 的敘述錯了,收回。

目錄要多大由 `FUN_c064E560` 算,參數就是 `FUN_c03A4D00` 傳的
`{frame_cap, 0x18, buf, 0x40000}`:

```c
if (opts[0] == 0) return 1 叢集;
if (opts[1] == 0) bytes = opts[0] * 0x60;
else              bytes = ((opts[1] + 14) / 15 + 2) * opts[0] * 0x20;
if (bytes >= 0x10000001) return 0;              // 超過 256 MB 直接失敗
clusters = ceil(bytes / (fs[0x1460] * fs[0x146c]));
```

`opts[1] = 0x18 = 24` 是**檔名長度提示**:`(24+14)/15 + 2 = 4` 個 exFAT 目錄項,
每項 0x20 = 32 B ⇒ **每格 128 B**。這正是 §52.1 從實測反推出來的常數,
現在有源碼了。(24 字元 / 每個 name 項 15 個 UTF-16 字元 ⇒ 2 個 name 項,
加 file + stream 兩項 = 4 項。)

而且 `FUN_c064E688` 配完鏈之後,`FUN_c064E5D0` 會**把整段寫成零** ——
用 `opts[3] = 0x40000`(256 KB)的緩衝一塊一塊寫:

```
容器 29.97   26.5 MB 的零     容器 119.88   105 MB 的零
```

**錄影開始時有一筆幾十到上百 MB 的同步寫入,發生在第一格之前。**

# 第七部分:破案與新缺陷(2026-09-21 上午)

## 66. ★★★ `OG_BUFCLASS=29` 是病因 —— §62 收回

§60 為了「自己做一個 240 用的緩衝類別」,在 `og3kcanvas` 的錄影路徑加了一筆
`PUT +0x0A4, 0x29`。§62 上機兩段後判定它「沒有用」。**那個判定是錯的:
那兩段本身就不正常,所以它只被判成「沒幫助」,從來沒有被懷疑是害處。**

在 RAM 裡把那一筆的 `str` 換成 `nop`(位址由掃描決定,見 `build/bufclass.py`),
其他一個位元都不動,同一次 SSD 連線前後對照:

```
              BUFCLASS 開                      BUFCLASS 關
A001_140/141/142  req_cnt = 1, 1, 1        A001_144..149  79 / 180 / 340 / 1317 / 4232 / 2137
                  sdb 恆為 95(只有一格在途)                六段全部 req_cnt == fin_cnt,零掉格
                  每格 182 / 185 / 215 ms                  全部按鈕停止,沒有一段凍結
                  第一筆請求都在 0.8-1.0 秒
```

`A001_148` 的細節:

```
req_cnt=4232, fin_cnt=4232, key
第一筆 694 ms   最後一筆 24205 ms  ->  23.511 秒
4232 / 23.511 = 180.0 fps          ->  完全跟上感測器,零掉格
4232 x 1,434,624 = 6.07 GB / 23.5 s = 258 MB/s 持續
sdb 全程 20-22   diff(req−fin) 穩定 42-43   ->  約 43 格同時在途,96 格的池子從未見底
```

**`+0xA4` 是畫布的緩衝類別碼。寫 0x29 把整條影像路徑歸到輸出/HDMI 那一類,
結果是外接寫入被串列化成每秒約 5 格。** 這也解釋了 `A001_120` 為什麼能跑
1177 格 —— 它是這個選項出現**之前**錄的,以及 01:28 之後每一段都不正常
(那正是 BUFCLASS 進卡的時間)。

註:A001_134/135 在 00:53-01:04 就凍了,那時 BUFCLASS 還不存在,所以更早的
那幾段仍然另有原因。這裡確立的是「BUFCLASS 開 = 必壞」,不是「所有歷史凍結都是它」。

## 67. ★★ 新缺陷:只有 8-bit 的 DNG 會被整塊往後推

`A001_144..149` 雖然零掉格,但在達芬奇裡會看到位移與變色。逐檔掃 `II*\0` 的位置:

```
位移 0       檔案正常
位移 7168    = 0x15400(每格保留的標頭量) − 0x13800(實際標頭)
位移 65536   = 64 KB
```

**DNG 是整塊被推的**(拿位移檔的資料和相鄰好格逐位元組比,推算後平均差 0.6-0.7,
不推是 42-73)。而檔案總長固定 1,434,624,所以**推出去多少就從尾巴截掉多少**:

```
位移 7168    少 3.55 行 / 672
位移 65536   少 32.5 行 / 672    ← 不是整數行,半行讓 Bayer 相位翻轉 -> 底部變色
```

`A001_148` 的分布 `{0:1236, 7168:1417, 65536:1579}`,而且是**週期性**的:
`好16 / 零27 / 好5 / 零32 / 好16 / 零32`,週期 128 格、29.2% 正確。

### 67.5 ★★ 機制追到了:每格檔案分兩段寫,而標頭區塊長度會變(2026-09-21)

`XC_StillCreateFile::v4` 的 CinemaDNG 分支走 `FUN_c03A5348`,那裡是**兩段**寫入:

```c
(**(vtbl+0x54))(file, ctx, *(desc + 0x14C), 0x200);   // 第一段:標頭區塊,512 對齊
iVar3 = *(desc + 0x14C);                               // 區塊長度
uVar4 = iVar3 + round512(影像位元組);                  // 檔案總長
FUN_c069ADE0(ctx, desc);                               // 第二段
```

**TIFF 標頭靠右對齊在那個區塊裡**,所以區塊比實際標頭大多少,檔案開頭就多幾個零。
實測的三種位移正好是 `desc+0x14C` 的三個值:

```
0x13800 = 79,872    -> 位移 0        實際標頭長度,正確
0x15400 = 87,040    -> 位移 7,168    ★ 每格的**保留量**,用錯了
0x23800 = 145,408   -> 位移 65,536   實際標頭 + 64 KB
```

`desc+0x14C` 在**錄影開始**時算一次(`FUN_c0378A50`,虛擬呼叫 `vtbl+0x2C`),
鏡射到 `FUN_c038A0F8()+0x0C`(= `0xC358DB98+0x0C`),再由 `FUN_c0373DD0` 逐格複製。
照理說整段是同一個值 —— 但實測位移在同一段裡週期性變動(週期 128 格),所以
**不是這裡算錯**。那個物件錄完會被清成全零,事後讀不到(§44.1 同型的坑)。

### 67.6 ★★★ 每格的開檔模式會依「段是不是 512 對齊」而跳

`FUN_c069ADE0` 其實是每格檔案的**完整寫入器**(它自己開檔):

```c
uVar4 = 0x806;
if (FUN_c069AD80(param_1[0x23]) != 0) uVar4 = 0x1806;   // 多 0x1000
FUN_c0365FB0(file, path, uVar4);
```

```c
FUN_c069AD80(串列):  走遍每個節點,只要有一個 (節點[2] & 0x1FF) != 0 就回 0
                     全部 512 對齊才回 1
```

**這是一條「全部 512 對齊才走」的對齊/直接 I/O 快速路徑。**
`XC_MediaFileSdCard::v1`(0xC0368178)把它翻成檔案系統的開檔型別:

```
0x806  (未全對齊) -> 型別 4
0x1806 (全對齊)   -> 型別 10
```

兩種型別在 `FUN_c063B180` 的開檔 switch 裡走同一條路(都落到 -4 = 要建新檔),
**所以差別是被帶到寫入端的**,下一步要追的就是那裡。

這條同時解釋了兩件事:

```
週期性        段的對齊取決於緩衝位址,配置器發出的位址循環 -> 位移呈週期出現
位元深度差異  影像位元組 8-bit 1,354,752/512 = 2646 整除(走快速路徑,壞)
                        10-bit 1,693,440/512 = 3307.5 不整除(走另一條,乾淨)
              12-bit 2,032,128/512 = 3969 也整除卻乾淨 -> `& 0x1FF` 測的
              多半是**位址**不是長度,這一點還要確認
```

### 67.7 ★ 把快速路徑關掉 —— 不可行(2026-09-21 實測)

`FUN_c069AD80` 改成無條件回 0(`mov r0,#0 / bx lr` @0xC069AD80,`build/fastpath.py`),
讓 8-bit 走 10-bit / 12-bit 那條已知乾淨的路。**實機:按下錄影幾乎立刻凍結,
來不及按停。**

所以那條「全 512 對齊」的快速路徑對這個組態是**必要的**,不是效能選項。
**修法不能是繞開它,只能是讓它把資料擺對位置。**

下一個該追的點是快速路徑專屬的那一步本身:

```
FUN_c0646BF8(fs, 4, dirent+0x5C8, 2)   把該檔的寫入快取模式設成 2
  -> FUN_c0646050(fs, 4, ptr, 1)       對那組緩衝排序/沖刷
     (DAT_c2e34818 + 4*4 是那組的數量,ptr[1]/ptr[2]/ptr+3 是項目陣列)
```

要找的是:模式 2 下,第一段(標頭區塊,`vtbl+0x54`,長度 `desc+0x14C`、對齊 0x200)
在什麼條件下會把標頭靠右對齊到區塊尾端 —— 那就是那 7,168 / 65,536 的來源。

### 67.8 ★★★ 上機量到了:區塊長度**沒有變**,零是寫入端補的(2026-09-21)

§67.5 留下兩個候選:(a) `desc+0x14C` 逐格變,(b) 長度不變、寫入端補零。
做了一顆 hook 當場量(`build/dngblk.S` + `dngblk.py`):

```
掛點   0xC03A53D0  `ldr r6, [r4, #0x14c]`(r4 = 描述子,r6 = 標頭區塊長度)
payload 68 bytes @0xC0730600,只讀不寫、不動旗標,做完原指令跳回 0xC03A53D4
環     0xC0730000  +0x00 索引 / +0x04 累計 / +0x10 起 128 筆 x 4 bytes
```

```
SD  對照(A001_040,64 格)      環:64 格全部 0x13800    素材:26/26 無位移
SSD 實測(A001_166,534 格)     環:128 格全部 0x13800   素材:65% 有位移
                                                      {0:187, 7168:122, 65536:225}
```

★ **`desc+0x14C` 一格都沒動過,而同一段素材 65% 被推位。所以候選 (a) 排除,
(b) 成立:那 7,168 / 65,536 個零是寫入端自己補的。**

補零發生在快速路徑(FS 開檔型別 10)那套寫入快取模式 2 裡,也就是
`FUN_c0646BF8(fs, 4, dirent+0x5C8, 2)` 換上去的那一套。下一步要追的是
第一段寫入(`vtbl+0x54`,長度 0x13800、對齊 0x200)在模式 2 下為什麼會把資料
往後推 7,168 或 65,536 —— 這兩個值必須從那裡長出來。

(hook 數到 580 格、磁碟上 534 個檔,差的 46 格正是 §69 停止路徑漏掉的在途格子,
兩邊互相佐證。)

### 67.9 補零發生在「寫入快取模式 2」,而那一層是 Thumb(2026-09-21)

順著 §67.8 往下:

```
FUN_c0646BF8(fs, 4, dirent+0x5C8, 2)   建檔時把該檔換成寫入快取模式 2
  -> FUN_c0646050(fs, 4, ptr, 1)       磁區快取的回寫:
        uVar7 = ptr[2]                 ★ 快取區塊大小
        uVar8 = *(&DAT_c2e34818 + 4*4) ★ 型別 4 的快取項數 = **1**(實機讀出)
        位移  = 項[1] x uVar7 + ...
        FUN_c0645D80(fs, 4, lo, hi, uVar7, 緩衝)   真正對裝置寫一個區塊
```

**模式 2 = 單一區塊的寫入快取**,每次對裝置寫的長度就是 `ptr[2]`。標頭那一段是
0x13800 = 79,872,不是 64 KB 的倍數 —— 補零的粒度(65,536 與 7,168)要從
`ptr[2]` 與磁區號的算術裡長出來。

**下一顆 hook 要掛在 `FUN_c0645D80`,記每次寫的(位移, 長度)。**
但那一層是 **Thumb** 編碼(`FUN_c0645D80` 與 `FUN_c0646050` 的首指令都是
Thumb-2 的 `push.w`),而 `ogdev.py arm` 寫的是 ARM 的 `B`,所以要先做一顆
Thumb trampoline。它又在熱路徑上(每個磁區寫都會經過),風險高於今天做過的
任何一顆 hook —— 下次動它之前先想清楚回復手段。

相對地,recMgr(`blk_c03`,`vbuf` / `FUN_c03A5348` / `og3kcanvas` 掛的那些)
是 ARM,今天的 hook 都掛在那一側,所以沒踩到這件事。

## 69. ★ 描述子在停止路徑上會漏 —— 每段 44 格 + 63 MB

240 + SD 的一段(`vbuf` 乾淨停,req 86 / fin 46)結束後:

```

不在自由串列上的 44 個節點,guard 全是 BEBEBABA(= 已配置)
```

```c

```

`FUN_c0381008` 只把在途的請求**從串列上摘掉**,沒有呼叫 `FUN_c0375030` 歸還
描述子,也沒有釋放它的 RAW 緩衝。原廠碰不到這條,因為 <=120 fps 時寫入端跟得上,
停下來時沒有在途的請求。

## 70. ★ 停止是一則會被丟掉的訊息(已實作、已測、**不是**凍結的原因)

```

  -> 組一則 0x168 的訊息 id 0x2B -> FUN_c03A9580 @0xC03A9580

c03a95b8  mov r5, #1          其他訊息要剩 >1 塊才送
c03a95d8  cmp r0, r5          r0 = MPoolFixed<360U,384U> 的剩餘塊數
c03a95dc  bhi post            否則丟掉,計數 +1 於 0xC35A8F38
```

原廠**刻意替 `0x2B` / `0x30` 保留最後一塊**。池子 384 塊,vptr 0xC0B9F0D0,

`vbuf` 開頭還有一行決定性的:

```c
if (*(char *)(param_1 + 0x78) != '\0') { ... return; }   // 旗標設了就丟棄每一格
```

所以「凍結後完全不再寫入」是設計行為,不是壞掉。
