# RWZM 是 open gate 的關鍵,以及建置流程的四個教訓

2026-09-12。承 `RECORDING_REGRESSION_2026-09-12.md` 與 `LIVE_VIEW_DISPLAY_CHAIN.md`。

## 1. RWZM:八個 profile,不是四個欄位

```
PARAM +0x60 / +0x64 / +0xD0 / +0xD4     0x640 (1600 = 1.5625x)  →  0x400 (unity)
```

1600 的實質縮小會把 **producer 的有效區釘在 1936 寬**,錄出來只有左上一塊有畫面,
其餘是未初始化記憶體。unity 才填滿 3032x2012。

舊 AutoRun 的註解寫「profile 122」,那其實是**列號**;查表對應的是 **profile 175**,
也就是八個格率裡的 OG3K30(29.97)一個而已。

**其他七個格率的 RWZM 從來沒被補過** —— 先前測試大多用 29.97,所以沒暴露。
八個 profile 各四欄 = 32 個位址,由 `og3ksel` 跟著選單旗標切換
(這些 profile 與 FHD 共用,寫死會壞掉 FHD)。

profile → 列號:173→120, 174→121, 175→122, 176→123, 178→125, 180→127, 430→287, 431→288

## 2. RWZM 同時決定 live view

unity 之後 producer 連預覽也產出 3032x2012,但預覽描述子還宣告 1936x1090,
消費端就從 3032 寬的緩衝按 1:1 取 1920x1080 —— **從中心放大 3032/1920 ≈ 1.58 倍,
而 1090 行之外沒人消費,上下兩條閃爍**。

**這件事把 2026-09-11 整晚的 live view 工作重新定位了**:那些「修好」是在
RWZM 意外變回 0x640(producer 縮回 1936、錄影已經壞掉)的狀態下取得的。
在壞掉的前提上調出來的結論不成立。

未解。候選修法在 `og3k_plan.TRIAL`:預覽柵格 `+0x0C/+0x10 = 3032/2012`、
可見 `+0x20/+0x28 = 3000/2000`。**`+0xD8/+0xE0` 絕對不能碰**(producer 那一對)。

## 3. 隱含依賴會在冷開機時炸掉

RWZM 原本由**卡上的 AutoRun** 套,`og3k_load.py` 沒有。一次意外冷開機之後
卡上是純 USB shell 版,RWZM 回到 1600,錄影全壞 —— 而選單、live view、DNG 標頭
全部看起來正常,從外面完全看不出來。

規則:**載入器必須自給自足。** 卡上只要有單純的 USB shell,一條
`./og3k_load.py` 就是完整的 OG3K。`og3k_plan.py` 是單一寫入計畫,
USB 載入器與 AutoRun 產生器共用,不會分歧。

## 4. 順序:指向 payload 的寫入必須排在 payload 之後

重構成共用計畫時,我把 `0xC0BE44DC`(解析度名的函式指標)放進 `misc()`,
排在 `payloads()` 之前:

```
第 7 筆    0xC0BE44DC = 0xC0731A00    ← 指向 og3kname
第 193 筆  og3kname 的 payload 才寫完
```

那個指標實質上就是 hook,一寫進去相機下次畫解析度名就跳進未初始化記憶體 ——
**載入中途凍結**。

`Plan.check()` 現在自動擋:任何「值等於某個 payload 起始位址」或「是跳到
payload 的分支」的寫入,若排在該 payload 寫完之前就拒絕。有回歸測試。

## 5. AutoRun 改走 .BIN,指令數不再隨內容成長

| 版本 | 指令數 |
|---|---|
| 純 `mem set` | 501(上限 648,加模式就會撞牆) |
| `.BIN` + loader,含 USB shell | **195** |
| `.BIN` + loader,無 shell | **135** |

AutoRun 只寫那個 loader,471 筆 OG3K 寫入全部進 `VSHL.BIN` 的區段。
`build_og3k_gyro.py` 會把產生的 BIN 重新解析、確認 471 筆逐字重現才寫出檔案。

## 6. gyro:兩條路線不能混

| 路線 | payload | 卡上需要 | 產出 |
|---|---|---|---|
| GYR + 後處理 | `logger.S` | AutoRun + VSHL + **PGEN.BIN** + **GYRO/** | `.GYR` → 後處理成 `.gcsv` |
| **gcsv-stream(v1.11b,實測可用)** | `logger_stream.S` | AutoRun + VSHL,**別無他物** | 錄製當下直接寫片段資料夾裡的 `.gcsv` + `.json` |

我照 `build_card.py` 的**預設**抄,拿到 `logger.S`,所以補 `PGEN.BIN` 和建
`GYRO/` 都沒用 —— 那是舊路線的需求。要走 stream 就用 `--gcsv-stream`,
而且**不要自己重算 orient_stub 的位址**(`build_card.py` 的註解警告過:
那個位置要由 payload 實際大小決定,算錯會讓相機在第一幀凍結)。

改成直接呼叫 `gyro/build_card.py --gcsv-stream` 並把 `--also-bin` 轉發過去,
區段表驗證正確,但**仍然沒有 sidecar 產出**。未解,已依使用者要求暫停。

## 6b. 截圖量測:錄影時 producer 只寫 1090 行

相機內建截圖會含影像,存成 `\DCIM\100SIGMA\SS__nnnn.JPG`(1024x682),
可用 `fp_usb_shell/getfile.py --size N` 直接從 USB 抓回來,不必讀卡。

`SS__0411`(錄影中)分三帶:

```
上   紅灰雜訊        未初始化記憶體
中   影像            但水平也被拉開
下   洋紅/青塗抹     同一批資料用錯格式解讀
```

量測:影像帶 y 182..517,高 335;非 HUD 區 595 px;**佔 0.5630**。
對上 `1090/2012 = 0.5417`(其他候選:1334/2012 = 0.663、1/1.5625 = 0.640,都不符)。

結論:**錄影時 producer 只寫 1090 行,消費端顯示 2012 行**。RAW 路徑拿到完整
2012 行(DNG 已驗證),預覽路徑沒有。兩個欄位的角色因此是:

| 欄位 | 角色 | 現值 |
|---|---|---|
| `+0x0C/+0x10` | **producer 實際產出** | 原廠 1936x1090 |
| `+0xD8/+0xE0` | 消費端讀取(覆寫) | rowpatch 設 3032x2012 |

下一個試驗在 `og3k_plan.TRIAL`:**只改 producer 那一對**成 3032x2012,
可見尺寸先不動。上次同時改可見又把 `+0xD8/+0xE0` 關成 0,毀掉數十段素材 ——
一次只動一個變數,而且改完解 DNG。

## 6c. RWZM 四個欄位不能拆

試過只讓 RAW 那一對(`+0x64/+0xD4`)unity、預覽那一對留 1600:
**錄影變花屏,相機隨後凍結**。所以預覽那一對也影響 producer,
舊筆記說的「四個都要 unity」是對的。

這也否定了「上下閃爍是頻寬競爭」的假設(雖然使用者觀察到換 SSD 樣子會變,
所以它確實跟時序有關,只是不能靠降低預覽解析度解決)。

## 6d. 解法:producer 與消費端的兩對欄位都要對齊(已驗證)

兩步,各自量測、各自解 DNG:

| 步 | 改動 | 量測結果 |
|---|---|---|
| 1 | `+0x00C/+0x010` = 3032/2012(producer 產出) | 上下壞帶消失;DNG A001_008 完整 |
| 2 | `+0x020/+0x028` = 3000/2000(可見窗口) | 放大 1.560x → **1.000x**;DNG A001_009/010 完整 |

第 1 步之後仍然放大,量測 水平 1.560(預測 3032/1920 = 1.579,差 1.2%)、
垂直 1.820(預測 2012/1080 = 1.863,差 2.3%)、異向比 1.167(預測 1.180)
—— 剩下的放大**完全就是可見窗口還是原廠 1920x1080,從 3032x2012 柵格中央裁出**。

第 2 步之後:截圖 `SS__0413` 對比待機 `SS__0408`,**水平 1.000x、垂直 1.000x、
異向比 1.0000、相關 0.9787**。錄影期 live view 與待機完全一致。

可見取 3000x2000 而非 3032x2012,是為了正好等於錄下來的 DNG 裁切
(3000x2000 @ 原點 16,6)—— 所見即所錄。

**這四個欄位已升級進 `og3k_plan.VERIFIED`。** canvas 的完整清單(14 個 PUT):

```
RAW      +000/+004 3032/2012   +024/+02C 3008/2000   +0DC/+0E4 3032/2012
預覽     +00C/+010 3032/2012   +020/+028 3000/2000   +0D8/+0E0 3032/2012
輸入     +0F4/+0F8 3032/2012
```

`+0x0C/+0x10` 是 **producer 實際產出**,`+0xD8/+0xE0` 是**消費端讀取**。
兩者都必須是 3032x2012;把 `+0xD8/+0xE0` 關成 0 會讓 producer 改讀
`+0x0C/+0x10`,那是 2026-09-12 毀掉數十段素材的原因。

## 7. 缺的是儀器,不是推理

整晚最貴的不是任何一個錯誤假設,而是**沒有量測工具**:我只能問「看起來對不對」,
然後在口頭描述上疊推論。三個具體代價:

- 「放大 1.3 倍」vs「1.58 倍」無法區分,所以無法驗證預測
- 把 `S_ACTIVE = 0` 讀成「從未啟動」—— 其實錄影結束後本來就是 0
- 擷取器寫成「只抓第一次」,抓到的是短暫的正確狀態,於是連續幾輪量到「完全相同」

兩個現成的儀器,下次先用:

1. **使用者截圖**(相機內建,會含影像):可直接量放大倍率、閃爍條的高度與位置、
   是裁切還是拉伸。
2. **LV Bayer 環形緩衝** `0x50000000 + idx*0x100000`,1 MB/frame,
   `mem save` 已驗證可倒出:可直接量 producer 實際的行距與有效行數。

這兩個儀器上線之後,錄影期 live view 從「三帶花屏」到「1.000x 完全一致」
只花了兩輪,每一輪都是先量測、再依量測值算出該填什麼、改完解 DNG 確認。
對比之前純靠口頭描述的十幾輪,差別不是努力程度而是有沒有數字。

而且**任何錄影路徑的改動都必須解 DNG 驗證**,不能看 live view。檢查項:
檔案大小、strip 長度、右側 1936 之外的區域相鄰行是否仍相關(正常 0.7–0.98,
壞掉 −0.12–0.03)。
