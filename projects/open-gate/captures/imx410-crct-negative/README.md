# CRCT hbin/vbin 在錄影路徑上**什麼都沒做** —— 否定結果的證物

2026-09-29。§6.1 的兩階驗證梯,階段 ① 的答案是**否定**。
機制與推導見 `notes/IMX410_FULL_DESIGN.md` §6.1。

## 判定

同一場景、相隔約 10 秒錄的兩段,只差 `hbin`/`vbin`:

```
A001_167  bin x3/x3   rec  672x448     530,432 B/格
A001_168  bin x1/x1   rec 2016x1344  4,143,104 B/格
```

兩段的 DNG 尺寸都符合各自宣告,所以**錄影路徑確實套用了新配方**。
取單一 CFA 平面比對:

```
假說 A  F ≈ F0 的 3x3 平均(bin 有效)    相關 -0.039
假說 B  F ≈ F0 的等尺寸裁切(bin 無效)   相關 +0.987   最佳位置 (0, 0)
```

★ **0.987 對上「左上角的純裁切」。** 列舉值有寫進 profile、`RECIPE` 27 字
逐字相符、相機不鎖死 —— 但沒有任何 binning 發生,只是把幾何宣告改小,
於是拿到左上角一塊。

## 連帶解釋了花屏

`A001_166_stride_garble.jpg` 是同一天稍早、光柵 6064x3412 配 bin x3/x3 的
錄影畫面:紫紅偏色 + 細棋盤 + 約 75% 寬處一條垂直接縫。

原本以為是「6064 / 3 = 2021.33 除不盡」。**那個解釋是錯的** ——
既然根本沒有 binning,就沒有除法。真正的原因是**裁切的 stride 對不上**:
從 6064 寬的讀出裡取 2016 欄,列間距仍是 6064,而封裝暫存器
(`0x30182214`,`FUN_c0630e90`)按 2016 設 → 每列起點偏掉 → 逐列累積。

(A001_167 同樣是裁切卻乾淨,因為 2016x1344 的光柵取 672 欄時
剛好沒踩到同一個條件 —— 為什麼,沒解。)

## 這不代表 CRCT 硬體不能 bin

**只代表寫這四個 profile 欄位不會啟動它。**
原廠 306 列裡 CRCT 只出現在**預覽**路徑(17 列 x3/x3,且 zoom 全 unity),
錄影路徑 306/306 全是 x1 —— 現在知道那不是「原廠沒用」,
比較像「錄影路徑上它根本沒接」。

要再往下追,入口是 CRCT 的啟用位元在哪(不是這四個列舉欄),
以及預覽路徑的那 17 列是怎麼讓它生效的。

## 對選單的影響

§8.0 的第 ⑤ 步(hbin/vbin)現在是個**裁切**軸,不是 bin 軸 —— 而且會
默默把視野砍成 1/3。在查清楚之前**不能**當成縮減手段給使用者。
