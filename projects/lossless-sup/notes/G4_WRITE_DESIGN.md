## 1. 注入機制(已由 G3 實測確定)

writer 每幀只登記**一個**節點:

```
FUN_c069ac88(writer, seg, kind)     seg = {buffer, length},  kind = 2
    node.buffer = 0x53B13C00        node.length = 0x318200 = 整份 DNG
```

而我們的探針在 hook 收到的 `r1` **就是那個 `seg` 指標**。所以注入是
「tail-call 之前改兩個字」——不需要拆成多節點,也不需要碰 writer 的其他部分。

## 2. 為什麼要拆成兩步

一次寫卡同時引入兩個未知:**重導向/快取可見性**,與**壓縮格式正確性**。
兩者失敗的徵狀相似(卡上檔案壞掉),混在一起無法歸因。§12.3 要求每次只加一個變因。

### G4a「鏡像」— 重導向,零格式風險

把**整份原始 DNG 原樣複製**到 arena,把節點指向副本,**長度完全不變**:

```
arena 用量   3,244,544  (= stock DNG)
node.buffer  handle           node.length  0x318200  ← 與原本相同
餘裕         949,760
```

預期結果:**卡上的片子和平常一模一樣**。

- 成功 → 重導向可行,且我們的緩衝區**對 SD DMA 可見**。快取問題就此解決。
- 檔案壞掉或全零 → 正是快取可見性問題,而且是乾淨的歸因,因為格式沒有任何變數。

這一步**沒有格式風險**:寫出去的位元組和相機本來要寫的完全相同。

### G4b「壓縮」— 只有在 G4a 通過後

```
segment0   @ +0x00000   79,872 bytes
codec 輸出 @ +0x13800   1 KiB 對齊 ✓
最壞情況總長            4,037,704
尺寸表                  0x3DA000 / 0x3DA400
版面結束 0x3DA434 / 0x400000     餘裕 154,572

實測一幀 node.length = 1,363,968,比 stock 小 58.0%
```

## 3. 每幀的裝置端工作量

| 工作 | 量 | 誰做 |
|---|---|---|
| 複製原標頭 → arena | 78,848 bytes | 探針 memcpy |
| IFD 樣板 | 714 bytes | **主機預建**,探針複製 |
| 修補 tile offsets + counts | 24 words | 探針 |
| root pointer | 1 word,**最後才寫** | 探針 |
| 改 `seg[0]`/`seg[1]` | 2 words | 探針,tail-call 前 |

主機預建 IFD 是關鍵簡化:整個標頭裡**只有 25 個字是每幀會變的**。
`canonical_header.build()` 已經能產生那 714 bytes,而且與主機 builder 逐位元組一致、
解碼驗證過。

標頭來源必須是**當幀的**原標頭(內含 timecode 等每幀 metadata),所以是探針複製,
不是主機預載整份。

## 4. 寫入順序(不可調換)

1. 編碼到 `handle + 0x13800`
2. 讀尺寸表、加總
3. 複製原標頭到 `handle + 0`
4. 複製 IFD 樣板、修補 24 個表字
5. **快取發佈**(見下)
6. 寫 root pointer
7. 改 `seg[0]`/`seg[1]`
8. tail-call

§4.4 明言 root pointer 最後才提交。第 5 步在第 6 步之前,理由與探針安裝相同:
半可見的標頭是唯一沒有安全復原路徑的狀態。

## 5. 快取:目前的最佳猜測與如何驗證

2026-09-23 量到同一塊 DRAM 有三個別名,全都顯示 codec 的輸出:

| 視窗 | 角色 |
|---|---|
| `0x4xxxxxxx` | 配置器 handle |
| `0x8xxxxxxx` | shell worker 稱為 uncached,寫入後**只 `dsb`** 就交給 USB DMA |
| `0xCxxxxxxx` | cached alias |

worker 那條路每一次 shell 指令都在運作,但那是 **USB DMA,不是 SD DMA**。
韌體自己的 `FUN_c062f510` 則是「在 `0xC` 操作 → `FUN_c000e91c` 全清 → 交出 `0x4`」。

**計畫:G4a 先用 `0x8` 視窗寫(worker 慣用法),只加 `dsb`。**
若卡上檔案正確,問題解決且不必每幀清快取。若不正確,再退回全清
(`FUN_c000e91c`,成本未量測,但我們有 28 ms 餘裕)。

G4a 的價值正在於它能**區分**這兩種答案,而且不混入格式風險。

## 6. 風險與復原

| 風險 | 後果 | 復原 |
|---|---|---|
| 緩衝區對 DMA 不可見 | 該幀資料錯誤或全零 | 刪片段。**這正是要測的** |
| 長度不被接受 | writer 錯誤或片段截斷 | 刪片段 |
| 探針在 tail-call 前故障 | 該幀寫入失敗 | hook 已自行還原,下一幀正常 |
| arena 版面算錯 | 守衛被踩,探針拒絕 | 不會寫出去 |

**所有後果都限於「那一段測試片」。** 卡上其他檔案、韌體、設定都不受影響,
因為我們只改 writer 這一次呼叫的兩個字。

## 7. 明確不做的事

- 不改 writer 本身、不改檔名、不改 timecode。
- 不連續多幀:G4a 與 G4b 都是**單幀**,`count == 1` 的一次性探針。
- 不碰回放(tiled `Compression=7` 本來就放不出來,export-only)。
- 不在 G4a 通過前做 G4b。
