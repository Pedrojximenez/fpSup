## 1. 一句話進度

**相機已經能用自己的硬體 codec 壓自己的實拍畫面、自己寫出可解碼的 DNG 到卡上。**
FHD 12-bit 實拍有 8 個壓縮檔，各 1,426,432 B，對 stock 3,244,544 B（44.0%）。ledger
明列 LibRaw 解碼第 1 幀的 min/max/mean 與同 clip 的 stock 第 9 幀相同；不是 8/8 解碼清單，
也不是同一來源幀的逐像素無損證明。[L] 2026-09-29，clip `\CINEMA\A001_219`

這筆可解碼證據屬於**同步版**；非同步 encode 另有獨立實驗，不能合併成 9/30 新整合版的 live pass。

目前阻擋項是**跨幀完整性與來源壽命**、**穩定度**（間歇性的引擎拒絕）及
**大尺寸的記憶體**（見 §5、§7）；單次能壓不代表整合版已可交付。

因此暫不走「維持原聚合政策、自有完整批次 buffer pool」：當時可配置量不足以承接整批；
這不是全機所有 allocator 的永久硬上限。3,244,544 B × 21 = 68,135,424 B，批次可跨過門檻，
不能把 64 MiB 當作 pool 的精確容量。
**寫回相機自己的 buffer** 沿用 writer 的持有期，避免把自有 codec 輸出區直接借給 SD。
這個作法是操作者提的；跨幀 codec 來源的持有期仍須另證，不能從「最多累積 21 幀」推出每幀保證。

## 3. 此前非同步探針的鏈條（現已停用 arm，見 §10）

hook 在 `0xC03A5490`（最後的 flush，原字 `0xEB0BD652`，真正的 flush 是 `0xC069ADE0`）。

```
每一幀：
  入口先暫時還原 hook
  檢查 writer 的 node 形狀 → 檢查這一幀是不是植入的格式（五個 tag）
  有在飛的工作？→ 收（poll 1 tick）→ F_SIZE → 加總 → 容量檢查
                 → 把壓縮 tile 寫回相機自己的 buffer（header 之後）
                 → 補 trailing IFD → 縮短 node
  沒有？→ 用「這一幀自己的 buffer」當來源 submit 下一個工作
  末端依 give_up／次數上限決定是否重掛（可恢復錯誤／not_ready 仍可重掛）
```

**零輸入拷貝**：引擎直接讀原生 frame，不再先複製 raster；輸出仍先到 block B，再由 CPU
copy-back。這不是 PHASE 8 的 codec 原地覆寫，也不表示解析度不影響 encode／輸出複製成本。
主機植入 geometry 移除了固定 4 MiB 來源副本的限制，不代表 UHD／6K 完整路徑已驗證。

**跨幀身分尚未正確對齊 [C]：** 現行程式 submit 幀 N，collect 時把 N 的壓縮畫面寫到當前
較晚的幀 M（逾時時不一定 N+1），不是回寫 N。collect／submit 交替；N 可先作 stock 寫卡，
M 的原畫面則被取代，metadata／時間戳也未證屬於 N。這不能當成「每個來源幀保留一次」或
已完成動態抽幀；來源生命週期與來源→檔案對應是整合驗收門檻（§7、§8）。

**來源格式可配置**：主機從一張參考幀算出寬高位深、header 位置、raster、宣告長度、tile 數、
目的地容量，植入 state；tile 512×368 與 tag 偏移仍編在探針中，並非通用格式解析器。
探針每幀比對 tag 256 的 ID 當 canary 再
比四個值，不符就整幀原樣送卡。這五個 tag 的偏移在 FHD 與 UHD 實測相同（entries 依 tag 排序，
會變的都在後面）。[H] + [L]

## 5. 6K 的真正阻塞點：不是 tile 數，是目的地容量 [I]

> **訂正（2026-09-30，同一作者）：本節結論不成立，保留原文供追溯。**
> 16 MiB 是 `C001CF78(0)`，也就是 **USER/class 0** 的量測；本節把它當成「我們能拿到的
> 任何一塊記憶體」的上限，這是錯的。錄影時的 `MOVIE_REC_DNG` 對應表裡 RAW/class 10 名義上約
> 708 MiB（§13.1），而 §14 已改由 REC 前預留 RAW 工作區。所以 6K 的阻塞點**不是**「輸出放不下」；
> 仍未成立的是 codec 的輸出上界與 DMA 寫界（§14「容量的精確含義」）。分帶編碼降為備案，
> 不是主路線（§13.1：不因 USER 16 MiB 結果直接轉向分帶）。

**此節保留 USER 探針時期的容量推估；當前優先順序改為 §13 的 RAW 池 REC 前預留。**
16 MiB 不是全機上限，不能據此認定必須分帶；但更大的配置仍不能代替 codec 輸出界限證明。

以最大尺寸 6064×4042 14-bit 計：

```
raster       6064 × 4042 × 14/8 = 42,893,704 B  ≈ 40.9 MiB
tile 數      ceil(6064/512) × ceil(4042/368) = 12 × 11 = 132   （TILE_MAX 160，夠）
已取得總量   16,777,216 B（還須留控制／表格空間） ≈ 39.1% 的 raster
FHD 實拍量到 42.4%                               [L] 2026-09-29
```

**不能保證 6K 14-bit 整幀輸出裝得下。** 沿用 FHD 的 42.4% 僅作估算，約為 17.34 MiB，
已超過上述 16 MiB，且無損壓縮不能保證 39.1%。尚未量得 6K 真實壓縮率；132 tiles 只說
state 的 160-entry 表夠放，不證明引擎、geometry、來源壽命與寫卡全都通過。

可能的出路，都未驗證：

1. **分帶編碼** [P]。先研究沿完整 tile-row 分帶，例如 11 列分為 6+5 列（72+60 tiles），
   不是上下各 66 tiles。第二帶來源偏移為 `6064×2208×14/8 = 23,431,296 B`。
   需驗證引擎能獨立提交該 geometry、size table／DNG tile 對應、每帶最壞輸出容量，以及
   實際寫入範圍不碰未讀來源；平均壓縮率不能證明安全。不承諾任意解析度成立。
   **未實作、未上機，不作當前 FHD 收尾前置。**
2. 降低聚合門檻（`vol[0x4828]`，量測值 `0x04000000`）不會增加單幀目的地容量，
   暫不以此解決 6K 輸出容量；它可能改變原生來源持有期，需另案驗證，不是安全捷徑。
3. 另一個 allocator。是否存在給得更多的來源，未知。

### 6.1 引擎為什麼拒絕一幀 —— 先把裝置讀懂了 [C]

實機出現間歇性的引擎錯誤位元。原本的解釋是「這一幀太細所以壓不進宣告容量」，但操作者說
**畫面完全靜止** —— 不支持「畫面內容突然變複雜」的推測，故收回根因判定；但靜止畫面仍有
感測雜訊，尚不能排除容量邊界或其他引擎原因。

於是去讀了裝置本身。整個 `C062F800..C0630700` 只碰六個暫存器：

| 暫存器 | 意義 | 出處 |
|---|---|---|
| `0x300D0000` | 控制；bit 1 是 GO | `C0630210`, `C0630418` |
| `0x300D0004` | **中斷狀態**。IRQ handler 讀它、立刻寫回清除、把讀到的**整個字**交給 callback | `C0630444`–`C0630462` |
| `0x300D0040` | 請求區塊的基底 | `C063024C` |
| `0x300D0074` | open 時設 bit 0 | `C06304AC` |
| `0x300D00F8` | **串流結束位置**。`C062F6C0` 清掉低十位、把其餘當成目的地內的位元組偏移去補被截斷的 EOI | `C062F91C` |
| `0x300D03FC` | soft reset 脈衝（bit 0 設再清） | `C062FFC8` |

關鍵事實與待驗推論：

* **狀態字只存在一瞬間。** IRQ handler 讀完就清掉，而 firmware 自己的 callback
  （`C062FCB0`）只看 bit 2、其餘全部丟掉。所以這個專案從頭到尾只看得到一個位元。
* **`0x300D00F8` 只在成功時被讀。** firmware 從來沒看過「被拒絕的工作」在這個暫存器留下
  什麼。錯誤時該值是否有效、會否殘留或被 reset 清除，尚未證明；0 不等於容量不足或完全沒產出。
* 另外：錯誤時**同步**路徑（`C062F90A → C062FE80`）直接 **close 裝置**，而**非同步**
  callback（`C062FCC2 → C062FE90 → C062FFC0`）只打一個 soft reset。我們走非同步而且錯誤後
  不 re-open，這一點未證。需觀察首次拒絕後的成功／拒絕序列，不能先假定恢復行為；
  現行 `frames_compressed` 名稱也不準確（§7.9）。

### 6.2 會說話的 callback

在請求的 `+0x2C` 裝我們自己的 callback，取代 firmware 的 `C062FCB1`：它記下狀態字和
`0x300D00F8`，然後**尾呼**進 firmware 原本那一個 —— 事件旗標仍然由一直在設它的那段程式設，
pattern 不變。**這版尚未上機**；IRQ callback 出錯可能遺失完成通知、留下資源或卡住，
不能保證只是「沒有幀完成」或不會產生壞檔案。

它跑在 IRQ context，儀器部分讀暫存器、寫 state，再尾呼原 callback；寄存器保存仍須按 AAPCS 驗證。
位址由主機從符號表算出
再植入（探針組譯在 0，不知道自己被放在哪），主機斷言它字對齊、bit 0 為 0、落在 claim 內；
探針在開 codec 之前拒絕 0 值。

新增的回報欄位：`callback_ran`、`engine_refusals`、`first_refusal_at_hook_entry`、
`refused_status`、`refused_end_position`、`good_status`、`good_end_position`，外加一段
`reading` 產生文字摘要；其對錯誤時 end-position 的確定性解讀仍待訂正，須保留 raw 值（§7.9）。

### 6.3 塞回 1,792 B 的 claim

加了儀器之後 1,888 B，超出借用的 claim，而 arena 只剩 72 B，**不能自己挑地址**。縮減內容：

* `r11` 全幀持有相機 buffer 的未快取別名 —— 原本重算六次，每次 4 B。把 r11 加進 push list
  不多花任何位元組（寄存器清單是同一條指令的一個欄位），而 r11 是 callee-saved，所以下面每
  一個 firmware 呼叫都會保留它。
* `DST_OFF` 是 0，卻繞了 `LDA`+`add`（12 B）。改成直接傳 block B，並加 `.if DST_OFF != 0`
  的組譯期錯誤，把安全性留在原地。
* `TILE_W`(512)、`TILE_H`(368)、`TEMPLATE_MAX`(4096)、`TEMPLATE_OFF`(0x310000) 都是 ARM
  可編碼的立即數，不需要 `LDA` 的兩個字。
* 第二道天花板改成「把第一道已經載好的寄存器乘三」—— 省 4 B，而且兩道界限再也不會走散。
* 結束位置改在 callback 當下讀，移除主路徑上兩處較晚讀取；錯誤時有效性仍待驗。

結果 **1,780 / 1,792 B**。

### 6.4 目的地容量改成「我們真正擁有的」

原本傳 `min(F_INIT 自己算的, 我們的 block)`。`F_INIT` 的數字是 raster 的 53.6%（約每樣本
6.4 bit，以該 FHD 配置計），部分輸入可能超過它。該 FHD 的 block B 約為 raster 的 132%，
所以改成傳自有目的地容量；這些比例不外推其他解析度。容量欄是否為硬體強制邊界仍須獨立驗證。
[C] + [I]，**尚未上機驗證是否消除了拒絕**。

本日先前開發紀錄：`test_inline_compress.py` 104 項、整個 `lossless_codec/` 目錄 **447 項全過**。
**本次文件收尾未重跑；以下是既有 [H] 紀錄，不是新測試，也不替代 ARM 執行或實機證明。**

### 10.2 最小緩衝區／交接核心

新增 [`frame_pipeline.h`](../../../fpSup/lossless/frame_pipeline.h)／
[`frame_pipeline.c`](../../../fpSup/lossless/frame_pipeline.c)，沿用现有 control 和 UI，不另造一套選單狀態。

1. 單一 lease 保存 `session/take/frame`、來源 buffer、metadata、writer identity、原生容量、
   **完整 stock DNG bytes**。不是 raster bytes；不使用可重用原廠 ID 冒充單調序號。
2. OFF／忙／停錄 drain 期間：後續幀 RAW 通過，不排隊、不丟棄、不先取 hold。
   空閒 ON 才接收已由 adapter 證明可持有、可延後寫檔的來源；拒絕時不接管 caller 的 hold。
3. Codec 完成通知不等於 DMA 已停。只有靜止、tile／尾端／容量／同幀 metadata 及原來源未被改動
   均由 adapter 證明後，才準備 handoff。IRQ 只通知；重工與狀態轉移必須在序列化 task context。
4. 完整壓縮 DNG 比 stock 小：callback 收到保存的 output，只能 copy-back 到保存的來源。
   等長／更大：進 `READY_RAW`，callback 收到 `NULL output`，交回**同一未改動來源**，不是 fault。
   這個判斷在 encode 之後，不能用來縮小 DMA 目的地或當壓縮前預測。
5. 兩種 handoff 都必須證明原生 writer 已接手來源，且 codec output 不再被 writer／DMA／callback
   借用。之後就能接下一個到來的幀，不等 SD 完成整批；工作槽不持有 SD 的資料副本。
   `COMMITTING` 擋住 inline completion 重入與 double handoff。
6. 停止不再選新幀，但可完成／交回最後一幀，不等下一張畫面。未知 DMA／partial handoff 或
   真正錯誤保留 lease，清理證據完成才可收尾；lossless fault 不靠 reset 活的 state 清掉。
   完整清理後仍可 OFF／RAW 拍攝。`handed_off` 包含 no-benefit RAW，壓縮計數僅加非 NULL output。

獨立檢查抓到初版把「壓完不更小」當 sticky fault，本輪已補成上述 RAW handoff 並加回歸測試。
這些程式只實作 policy，不把呼叫者傳入的 `held=1` 或 `validated=1` 當成原生證據。

### 10.4 下一個原生整合門檻：不是在最後 flush 直接跳過

詳細原廠機制集中在 [`NATIVE_BUFFER_PATTERNS.md`](NATIVE_BUFFER_PATTERNS.md)。

## 13. 原生錄影開始前預留 RAW 工作區

### 13.1 開發定案與容量證據

使用者指定順序：**先拿到壓縮需要的工作區，再讓原廠錄影配置其餘 RAW 緩衝。**
採一個持續整段 take 的工作區，沿用單一待壓幀 policy；不因先前 USER 16 MiB 結果直接轉向
分帶、多池或複雜搬移。以下配置表／呼叫鏈是離線事實 [C]，預留接線是待實作契約 [P]。

- 舊 `alloc_capacity_probe.S` 明確以 `C001CF78(0)` 測 USER，未測 RAW/class 10 或 RAW_SUB/class 14。
  原 ledger 保留不改，不把其歷史「ceiling」字樣當作全機硬上限。
- `C001EE58` 的 mode 3 是 `MOVIE_REC_DNG`：USER 30 MiB、RAW 約 708 MiB、RAW_SUB 82 MiB。
  RAW 不足會沿 link 到 RAW_SUB；YUV／JPEG 自身 payload 為零，也回到 RAW。
  這是名義分區，不是當前空閒量；兩池不能相加當作一塊連續配置。
- 原廠 still lossless 的目的區由 `C03989D8` 以 RAW/class 10 配置，`C037E0F8` 把它交給 codec。
  參考其 API，不挪用原廠全局 `C358E178`。自有 descriptor 走
  `C001CF78(10) → C001CFD8`，1 KiB 對齊，保存 `{handle, actual_capacity, requested_class}`；
  以 `C001D3D0` 正式歸還，linked fallback 不授權改寫 descriptor class。
- 普通 CDNG source 的 `C037A990` 申請 `align512(raster) + frame[0x128]`；kind 1 的
  header reserve 為 `0x15400`。6064×4042 packed14 對應 42,980,864 B，另有 allocator overhead。
  這不是 codec 輸出上界，也不解除現行 control 對 14-bit 的拒絕。

主要證據：[`blk_c00.c`](../../../out/decomp/full/blk_c00.c) 的 `C001CFD8 / C001D038 / C001D3D0 / C001EE58`；
[`blk_c03.c`](../../../out/decomp/full/blk_c03.c) 的 `C037A990 / C03989D8`。名稱表使用
`seg1_c2ef6e00.bin` 的 `C2EF7248 / C2EF727C`，不是 MAIN 的解壓 overrun 範圍。

### 13.2 每次 REC 的預留及釋放順序

1. 確認前一 take 的 worker／來源與輸出已排空，擷取本次實際格式；尚未啟動 producer。
2. 讓原廠完成需要的 map 切換，確認當前為 mode 3，再以自有 descriptor 正式預留工作區。
   若原本已是 mode 3，仍執行本次 reserve；不在 boot 的 STILL map 配置後跨 map 持有。
3. 預留後確認錄影來源所需餘裕及其他既有 readiness 成立，再經 `fpl_begin_direct` 放行原生 REC。
   預留成功本身不等於 `FPL_READY_CODEC / FPL_READY_REC_GATE` 全部成立。
4. 整段錄影持有配置，只在幀間重用；原廠繼續從剩餘池配置來源。空閒接下一幀、忙時 RAW 通過，
   不逐幀 alloc/free，也不在已開始錄影後嘗試擴大工作區。
5. 啟動失敗或取消時回滾自有預留；停錄先停止選幀，處理末幀，待 worker／codec DMA／所有輸出
   使用者退出才歸還。模式切換前必須完成這個過程；未知 DMA 狀態不得當作可立即 free。

大小由該格式的有界輸出、metadata／tile tables、對齊計算；只有 source 尾端不能安全直讀時，
才另列一塊 padded input，且同在 REC 前預留。不要預設「拿 43 MB」或「拿池子固定百分比」。
預留失敗／原生餘裕不足時撤銷可安全撤銷的自有配置，回報未就緒，保留既有 gate 的拒絕語意；
不可用靜默 RAW 錄影冒充 Lossless 已啟動，也不可搶回已屬於原生 frame 的記憶體。

本節建立時只更新設計與離線程式證據；後續程式實作與測試見 §14。沒有操作相機、寫卡或
發布。後續建置仍依 §12.4 與共用 build 規範，上機前先通知使用者。

## §18 Zero copy by buffer swap (方案 C) — static proof, card l built (2026-09-30)

Experiment A (in place, card k) is rejected: the engine writes ahead of what it
has read, and the top tile row is corrupt (§17). The copy-back is avoided a
different way instead: we do not copy the result into the frame; we hand the
frame the buffer that already holds the result.

Static facts (Ver.5.02, blk_c03.c):
- Allocation: C037A990 → `C001CFD8(C001CF78(10), &frame[0x68], bytes, 0x400, 0)`;
  the record at frame+0x68 is {handle, capacity, class}. It is the same allocator
  and class our raw_workspace uses.
- Free: C03777B8. If frame+0x1118 == -1 (the frame owns its allocation) and
  frame+0x1114 == 0 (no clones), each record is freed with C0374180 → C001D3D0.
  A clone (Dup2 path, 0x1118 = owner id) frees its owner's records when the
  last clone goes.
- Before the enqueue (C038BD98, before our C038BFF0 hook):
  - frame+0x14C = header bytes (0x13400).
  - C038C5F8 DMA-copies the header template to `raster − 0x13400` = A+0x2000
    (C00FBB90).
  - It passes the raster to an ImagCtrl lookup (C031AB40, read-only).
- Dispatch after release (XC_StillCreateFile C037E0F8, kind 1):
  - frame+0x4C −= frame+0x14C.
  - The file is written from there (C03A5348 → C069ADE0).
  - So the file buffer is taken from frame+0x4C at dispatch, after our release.

Swap (frame_hold.c):
- The engine reads A+0x15400 and writes the result to spare S+0x15400.
- At release, if the frame still owns its allocation with no clones, is class
  10, has raster == handle+0x15400 and header == 0x13400, and S ≥ its capacity:
  1. Copy the 0x15400 prefix (the DMA'd header) A → S.
  2. Write S into frame+0x68/0x6C/0x70 and 0x4C.
  3. The frame is released and the firmware writes and frees S.
  4. A becomes the next spare.
- If the check fails at hold time, the result is copied back as before (swap_declined).
- If it fails at release (for example a clone appeared), it is copied back
  (swap_undone).
- Card: one spare per take, from the same allocator, sized to the firmware's
  request (0x15400 + align512(raster)). It is freed with C001D3D0 when the take
  finishes. If the allocation fails, the take falls back to copy-back.

  - The fixture allocator never hands out a buffer that has a live owner.
  - Swap-specific tests.
  - 11 swap mutations are all caught.

- The private page comes from menu/build_menu_candidate.py (pure-fixed-gated): 179,725 B, with the fourth row bound to MV_fpLossless.
- It travels on the card as FPLMENU.BIN (menu/pack_menu_file.py, FNV-checked). This is because BIN MAXLEN 61440 cannot hold it: a copy/literal diff against firmware bytes still needed ~28 KB.
- At init the card reads the file with the loader's own file API into the rest of its USER block. BLOCK_BYTES grows to 0x80000; the memory is never freed.
- It builds the pool as the stock pool copied from firmware plus the page's 88 private bytes.
- It registers MV_fpLossless: an integer, default 0, name borrowed from the resident card state (C05DB309).
- Then it switches reader+14/+10 to the new pool and MainB2's entry+08 to page − NBU base.
- All-or-nothing checks against the stock structures come first. On any mismatch nothing is written and every take stays stock.
- REC start (card.c): if the row is not ON, the take goes straight to the original C03A2438 (rec_menu_off).
