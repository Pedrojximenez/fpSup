# fpLossless 2026-10-04：停錄缺幀複核、最小修正與診斷候選版

## 1. 本輪結論與界線

使用者已確認 Lossless 完成並出貨；[10/03 筆記](PROGRESS_20261003.md) 留有發布與後續本機修改歷史。本輪不是重做壓縮架構，也不是宣稱所有格式重新驗收，而是針對 OG3K 48/50p 自動停錄後檔號缺口，複核並開始最小修改。

- **已修正 [C/H]**：未啟動的 HELD 幀退回 RAW 後，pipeline 仍卡在 HELD；共用 codec 狀態不明時，另一 lane 仍可能被啟動；REC shim 進入新 C 函式前的堆疊對齊。
- **已新增 [C/H]**：原生錯誤事件、FIFO 丟棄、writer 完整返回值的有界診斷。不改原廠停止決策、不跳過 cleanup、不新增 RAW buffer。
- **已完成 [H]**：主機／ARM 回歸測試、普通／debug／Fast 三種本機測試包、實際封裝 bytes 的冷啟動／安裝／還原驗證。
- **尚未證明 [P]**：網友這一次 SD 停錄的最初觸發原因，以及本輪修正能否消除其缺幀。本輪沒有操作相機、USB、寫卡、部署、改發布品、commit 或 push。

本輪遵守 [SUP_BUILD_RULES.md](../../../fpSup/SUP_BUILD_RULES.md)。既有 shared loader／stage2／Fast Start 3 修改不是本輪所做，保留而不順便重構。**下次上機前先通知使用者。**

## 2. 重新核對的資料流與缺口形成位置

現行流程保留：

```text
C038BFF0：原生 ready frame
  → 兩個 lane、共用一個 codec（忙時新到幀 RAW 通過）
  → C037DD50：交回原生 creator enqueue
  → 原生 FIFO
  → C03A5490：壓縮結果的 metadata／length 套用
  → C069ADE0：原生檔案 writer
```

### 原生異常停錄不是普通 stop 的同一條排空路徑 [C]

1. `C038BD98` 處理 RAW completion event 5：非零且非 4 的結果走錯誤路徑，回收當前 frame，再由 `C038BF08 → C037DEE0` 清除 pending FIFO，之後才進入 `cDevt_stop / C038C3C0 → C0398D88`。
2. `C038C058` 的 event 8/9 completion 錯誤或 frame lookup 失敗，也可先在 `C038C0A4 → C037DEE0` 清 FIFO，再 stop。
3. `C037DEE0` 逐項 pop，呼叫 `C037E008` cleanup 與 `C0375030` registry reclaim；這個清除迴圈**沒有呼叫 writer**。進入我們既有 stop hook 時，被清掉的幀已來不及補寫。
4. 正常按鍵 stop（`C038B790` 的 key 路徑）原本有非同步排空：B/C/D 等 pending state 會延後最終關閉，後續 completion 推進 FIFO。不要在處理這些訊息的 Movie task 裡同步等待整個原生 FIFO，否則可能擋住它自己需要的 completion。

因此，原生系統本身存在「已取得檔名、尚未寫出就被異常清除」的機制。但本輪還不能判定網友那一 take 是哪個 error、由何處觸發，更不能把 result 1 一概解讀為記憶體不足：它也涵蓋 quota、registry、imager 等失敗；writer 的零返回同樣不是單一失敗原因。

### 原生 ARM 機制驗證 [H，不是網友錄影重播]

新增 [`test_native_abort_fifo.py`](../../../fpSup/raw/lossless_codec/test_native_abort_fifo.py)，執行韌體實際 enqueue、FIFO pop、clear 與 cleanup 指令；mailbox、allocator/reclaim 邊界由 fixture 代替。

- 人工設置 active 檔號 60、FIFO 59／61–106／108（48 幀）、另有尚未進 FIFO 的 107。
- 執行原生 abort：48 個 pending frame 到達 reclaim 邊界，writer 呼叫為 0；稍晚抵達的 107 仍可被 dispatch。
- 不 abort 的對照可正常逐項 dispatch；故意刪除 reclaim call 的 mutation 會被測試抓到。
- slot 是重用的 0–95 registry 編號，**不是 DNG 檔號**。檔名配置、真實釋放、codec 排程、SD 寫入均未模擬。

這證明缺口形狀可由原廠 FIFO 清除機制產生，不證明同一時序確實發生於使用者的卡片。

### 吞吐量判讀 [I]

網友報告 3K 50p 的 U/J 約 9.2／2.8 MB，若各半，資料需求約 `50 × (9.2 + 2.8) / 2 = 300 MB/s`；48p 約 288 MB/s。24p 實測平均 74 MB/s 不是卡的極限測速，256 GB 也不代表持續寫入速度。

[10/01](PROGRESS_20261001.md) 的 SD 自動停錄紀錄曾有 13 個 compressed promise 未到 flush；[10/02](PROGRESS_20261002.md) 的 SSD 48p 則有 44,208 幀、約 15.3 分鐘成功紀錄。這些支持調查媒體／積壓壓力，不能取代此次事件與 error code 的量測。

## 3. 本輪實際修正

### A. 取消未啟動 HELD lease，避免假性無法收尾

[`frame_pipeline.c/.h`](../../../fpSup/lossless/frame_pipeline.c) 新增窄範圍的 `fpl_pipeline_cancel_held`：只接受同一 token、HELD 階段及已解決 ownership 的情況；不處理 ENCODING／RETAINED，不清掉既有 fault。

[`frame_hold.c`](../../../fpSup/lossless/native/frame_hold.c) 的 `fpl_hold_abandon`：

1. 在原有 IRQ 保護下把 lane 從 HELD 暫時領成 COLLECTING，避免 worker 同時 kick。
2. 核對 registry 仍指向同一 frame、queueable flag 非零、kind=1、state=B；只呼叫一次原生 enqueue，且要求返回 1。
3. 轉交成立後才清除 HELD lease，回到 IDLE。之前誤用只接受 RETAINED 的 `reap`，會留下 lane 已 IDLE、pipeline 仍 HELD，造成 finish BUSY。
4. 身分或轉交結果不明時保留 FAULT；不重試 enqueue，因為失敗返回前也可能已改原生狀態。

enqueue 返回 1 只代表此邊界的接受／入隊，不代表實體檔案寫入成功。這項修正不是直接挽回已被原廠 FIFO 丟棄的幀。

### B. codec FAILED 不得被另一 lane 當成硬體空閒

兩個 lane 共用一個硬體 encoder。worker 現在在 poll **之後**檢查任一 job 是否 FAILED；若是，就不啟動另一個 HELD job。arrival／stop 在原本的呼叫情境中退回尚未啟動的那一幀 RAW；不把 native enqueue 移到 worker。

失敗 lane 的未知 output 仍保留，不假設 DMA 已停、不提前 free。已確認安全的 codec refusal／stall-abort 仍可讓下一個 job 繼續。stop 也不再為「已知 FAILED＋永遠不能 kick 的 HELD」白等完整 1,000 次 polling。

### C. REC／新 observer 的 ARM ABI

[`card.S`](../../../fpSup/lossless/native/card.S) 的 REC shim 會在進入 C 前對齊 SP 至 8 bytes，返回恢復原始 SP／LR。原生內部 call site 可能是 `SP % 8 = 4`，不能假設每個 firmware 邊界都符合新 C 函式的對齊需求。

event／discard／writer observer 同樣驗證 SP=0、4 mod 8。event 重播被取代的 load 並保留 flags／LR；discard 保留輸入、原生 cleanup 恰好一次；writer 保留原生全部輸入暫存器、64-bit `r0:r1` 返回及 flags。原 writer 是兩參數呼叫，不新增 stack argument 假設。

## 4. 最小診斷：記錄原因，不改原生處置

新增 [`record_diag.c/.h`](../../../fpSup/lossless/native/record_diag.h)：固定 **1,068 bytes**，內含最後 16 個被 FIFO 丟棄 frame 的記錄；每筆保存 slot、generation、clear caller、48-byte inline filename 複本。不配置記憶體、不 I/O、不 sleep、不保留會失效的 frame pointer，不遍歷整個 FIFO。

| 觀察位置 | 保存內容／限制 |
| --- | --- |
| 新 site `C038BD08`，原字 `E594300C` | event 5/8/9 的結果、最後非零或 lookup missing 的狀態；event 5 的 result 4 另列 capture limit，不當一般 RAW error |
| 新 site `C037DEF8`，原字 `EB000042` | 原生 FIFO 實際 pop 出來、即將 cleanup 的 frame；原始 clear caller 由進入 shim 前的 SP+12 取得 |
| 既有 `C03A5490` writer wrapper | native writer 返回後記錄完整 `r0:r1`，區分零／非零；不在返回後解參考 frame |

已分類的 clear caller 是 RAW error `C038BF0C`、completion error `C038C0A8`、global teardown `C0398D48`；其他位址另列，不猜測原因。

[`card.c`](../../../fpSup/lossless/native/card.c) 每次 REC start attempt 清診斷，Lossless OFF 也觀察；短暫 IRQ 保護 reset／更新。`take_frames` 改成實際經過 CinemaDNG arrival hook 的幀數（含 OFF／第一幀 RAW），仍不是所有已分配檔名的總數。

[`card_status.py`](../../../fpSup/lossless/card_status.py) 支援新欄位與舊 layout，列印最近 16 筆檔名及 overwritten 數；固定長度解碼，不假定 NUL。要在下一次 REC／關機之前讀取，且在錄影完全停止、狀態穩定後讀，避免多次記憶體讀取混到更新中的快照。

必須保持以下語意：

- `flush.applied` 是 header／length 套用次數，不是寫檔成功數。
- event 8 可能在真正 writer 之前，不是寫入成功。
- writer 非零 byte count 是 API 結果，不證明資料已持久化到 SD／SSD。
- `drop_overwritten` 超過 0 時，16 筆只剩尾段，不宣稱保存全部缺幀清單；與真實 DNG 檔名清單比對。
- hook 總數由 8 增至 10；cave 預留由 80 增至 96 bytes，host record 仍在 +32。所有 site 保留 stock-word guard、由共享 loader journal 並於關機還原。

## 7. 下一步：先量到觸發原因，再決定是否提前正常停錄

目前不搬動壓縮接入點。只把壓縮搬到 writer 同步執行會阻塞 writer；只把結果套用再往後搬，也救不回此前已被 FIFO 清除的 frame。若要改接入點，必須另外證明 writer 前可 defer、frame ownership／有界延遲及停止排空，不能把地址替換視為已完成。

取得使用者確認並通知上機後，按以下順序做小範圍測試：

1. **先做啟停安全。** 冷開機、暖開機、開機不錄影即關機再插卡開機約十次；舊版／另一張卡先開機後換候選的暖啟動另驗。Fast 候選還須獨立完成 retained/settings 路徑驗收，不因冷路徑通過便優先用 Fast 查錄影問題。
2. **先 plain 基線，再 debug 診斷。** 同一 SD／模式／場景，OG3K 12-bit 24p、48p、50p，比較 Lossless ON/OFF，另以 SSD 作參照。OFF 寫入量更大，不能要求 ON/OFF 同時長；比較的是 error、FIFO discard、檔號形狀。plain 沒有常駐 USB shell，不能直接讀這組記憶體計數；debug 可讀，但 shell 本身是變因，兩者的檔案結果分開保存。
3. **一次一 take 留證據。** 保存模式、模組／AutoRun／BIN hash、停止方式、完整 DNG 檔名／大小清單、解碼檢查及 debug 的 counters／最後 16 個被丟棄檔名。先在低負荷測試確認正常 stop 與下一次 REC 能收尾，再提高負荷；不要在有未知 DMA／ownership fault 時繼續重用 buffer。
4. **分辨三件事。** writer 返回零？event RAW/completion error 或 lookup missing？原生 FIFO 哪個 caller 丟了多少？與 lane fault／finish BUSY 及實際缺檔對齊，而非只看壓縮百分比。
5. **有證據後才做預防。** 若確認是可預測的 FIFO／buffer 壓力，在異常清 FIFO 前透過原廠正常 stop 請求提早收尾，保留排空餘裕，目標是「較短但連續的片段」。先辨識可靠壓力指標與原廠訊息介面，再決定最小門檻；本輪未實作猜測門檻、強制補號或跳過 cleanup。

網友的 shell＋Mass Storage 無法掛載另列相容性問題；本輪沒有嘗試修 USB。plain 無 shell 是控制變因，也符合既有發行版本不放 USB worker 的方向，不把 debug 包當發行包。
