## 240p 為什麼以前穩、現在卡（2026-10-13 補記，未上機）

使用者：240p 曾穩定運行，當時沒有使用 LOSS。對照現行來源，載入擴充位置版 LOSS 即使 OFF 也不是原廠路徑：

- `--expand-slots` 建置（含目前相機上的 `fe35400b`）在載入時由 `fpl_slots_init()`（`fpSup/lossless/native/card.c:343`、
  `native/slot_runtime.c:29`）把原廠 `MPoolFixed<4380,96>` 描述子池與 registry 換成 LOSS 常駐區內的副本，與 ON／OFF 無關。
- 常駐區由 loader 以 `C001CF78(0)` 取自 USER／NonCacheBuffer（[MEMORY_AUDIT](../validation/20261012-m12240-slot-capacity/MEMORY_AUDIT.md)）。
- HSW 已有實機紀錄：描述子池改放 NonCache 後，240 下把 USB worker 一起拖死（`fpSup/opengate/HSW_DEVELOPMENT_STATUS.md` §8.4／§9，
  `projects/open-gate/notes/HSW_240FPS_MODE12.md`）。10/12 M12240 119.88p／239.76p 的症狀（USB 逾時、實體停錄鍵無反應）與之相同。

**這是最強的假設，尚未量測證明。** 59.94p 的 OFF（同樣是擴充池）83.2% 也沒有「無 LOSS 卡」的基線可比。

驗證方法（需授權，119.88p，不碰 240p）：同一模式依序比較「只有 STOPFX」、「預設 96 位置 LOSS OFF」、「擴充版 OFF」、「擴充版 ON」，
用 10/12 的保護優先序 profiler 看 CPU 與 MRecMgr。若擴充版 OFF 已明顯高於前兩者，就證實是池的位置。

修正候選（離線先做）：

1. 延後擴充：開機保留原廠池，只有 LOSS ON 且當段計畫需要超過 96 位置時才換池，OFF 完全走原廠。
2. 池放到 cached 記憶體：在韌體自己的任務脈絡中從原廠 C++ heap 配置（HSW 記錄過 callfn 直接 new 會死鎖 shell），
   或在開機、池尚無引用時改用同一塊的 cached alias；後者須先確認 alias 對應與 DMA／cache 一致性。

## 補記 2：CPU 飆升的機制候選——擴充後原廠 registry 全表掃描（靜態，未上機）

使用者判斷：LOSS 的工作主要在壓縮晶片，CPU 不該大幅上升。靜態追查支持這點，多出來的 CPU 很可能不在壓縮本身：

- `slot_sites.json` 的 11 個 `ends` 站點被改成 `SLOT_MAX*4`（1016 格，**固定，不跟 active 數**）。它們是原廠 registry 的
  全表迴圈：`FUN_c0375900`（11 處呼叫）、`FUN_c0375be0`（14 處）、`FUN_c0375de8`（9 處）、`FUN_c0375178` 等，
  在 mutex 內逐格讀 registry，非空格再讀 frame `+0x1104`／`+0x1118`。
- 原廠是 96 格、cached heap；擴充後是 1016 格、NonCache 常駐區，每次掃描約 10 倍格數且每次讀取都不經 cache。
- 非空格數＝在途幀數。壓縮檔小，64 MiB 一批要累積更多檔，非空格更多；幀率越高，掃描越頻繁。
  這能同時解釋「OFF 正常、ON 飆升」「幀率越高越糟」「小 geometry 的 M12240 240p 鎖死」，而且與壓縮晶片無關。
- 尚未量測每幀呼叫次數，不能給出百分比；需 Unicorn 計數或上機 A/B 證實。

### 優化與泛用化方向（取代前文以尾表為主的順序）

1. **迴圈終點跟 active 數**：把 `ends` 移到 `slot_patch_count(n)`，寫 `n*4`（n 為 4 的倍數，imm 可編碼）。
   換 n 時 registry 已確認全空，邏輯不變。純離線可做、可用現有 ARM harness 驗證。
2. **池與 registry 放 cached 記憶體**，與原廠一致。
3. **能用原廠 96 格就不擴充**：以檔案數提前結算（EARLY_STOP_94 的 `N` 公式）適用所有 geometry／幀率，
   擴充只在計畫真的超過 96 時啟用，並在 OFF 還原原廠池——這是泛用性的核心，不靠逐模式調參。
4. 之後才是尾表（預備檔頭）與引擎設定等每幀固定成本。

## 補記 4：切法實測與拒絕閘門（[20261013-refusal-gate](../validation/20261013-refusal-gate/README.md)）

- 相機換成正式版 LOSS v0.2.0test，另裝 RES-Lab；以使用者自建的 HS280（RAW 1008×672，與 M12240 同）上機。
- **切法不是原因**：預設 512×336、垂直補白 512×352、整除 512×224、256×336、256×224（同 FHD 的 4×3）、128×112（48 格）
  六種全部每幀被拒，引擎約 2.2 ms 就放棄（完整一幀約 4.4 ms），end_position 0。下一步候選 1 的推測否定。

下一步：

2. 找 HS/M12 畫面寫入完成的時點（RWZM 完成、或 C038C77C 檔頭 DMA 前後），才可能讓這類模式真正壓縮。

## 補記 6：LOSS 從快取別名執行（已上機、採用）

Loader v3 的 sup 塊配在 USER／NonCacheBuffer（VA 0x4xxxxxxx，MMU 為 Normal 非快取）。同一實體記憶體在 VA +0x80000000
有可快取、可執行的對應。LOSS 改在 entry 切到快取別名後，FHD 59.94p ON 的總 CPU 90.4 → 85.7（OFF 76.6），
SRecFile 8.9 → 5.2，FPLCODE 6.2 → 2.1，trailer 1,178 → 394 µs／幀；檔案與機內回放正常。
見 `validation/20261013-cached-alias/README.md`。其他 sup（gyro、res-lab…）同樣跑在非快取塊，可能有同類收益，未查。

## 補記 7：預先準備的壓縮 IFD（共用檔頭，已上機、採用）

同一段錄影內，主 IFD 的 inline 值不變，所以壓縮 IFD 每段只建一次（存在快取記憶體）。每幀的工作只剩三件：比對檔頭、整字寫出 IFD 和切塊表、最後寫根指標。
trailer 394 → 56 µs／幀；FHD 59.94p ON 的總 CPU 85.7 → 83.9（正式版 90.4，OFF 76.6），SRecFile 2.9–3.0。
相機寫出的檔案和主機參考實作逐位元組相同，機內回放正常。見 `validation/20261013-prepared-trailer/README.md`。
