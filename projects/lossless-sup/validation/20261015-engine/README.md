## 實驗：keep_open（`keep-open-experiment/` 保存程式）

引擎已開（300D0074 bit0）就不 open，完成不 close，段落結束才 close；拒絕／錯誤仍立即 close。
離線：codec_job 38、frame_hold、header_tag、card_emulation、v3 全過。

上機（診斷版 `0c48cd6f…` ON，29.97p，2 段）：**每隔一幀被引擎拒絕（pattern 4）**——102 幀 52 壓縮、50 拒絕（存 RAW）；
`open` 平均 83 µs（＝每兩幀開一次），eoi+tiles 暴增到 350–560 µs。拒絕會 close，下一幀因重開而成功，再下一幀又拒絕。
→ **close＋open 會重置某個狀態，軟重置（300D03FC bit0）不夠。** 檔案都正確（`tag_failed 0`），失敗是安全的。

# 輕量重開實驗（同日，使用者要求；全部失敗，已還原）

實驗版 `build_v3_lossless.py --time-hooks --engine-reopen`（只在實驗中存在，程式另存 `light-reopen-experiment/`）：
引擎已開時，用下列步驟取代完整 open，完成後不 close，段落結束再 close。`engine_mode` 由 USB 寫入切換。`mode_take.py`，FHD 29.97p，每模式 1 段：

| 模式 | 每幀做的事 | 結果（`mode-*.json`） |
|---|---|---|
| 0 | 原廠：完整 close＋open | 102/102 壓縮；open 169 µs |
| 2 | `C0630480(0)`→`(1)`（區塊致能） | 54 壓縮／49 拒絕（pattern 4），eoi+tiles 552 µs |
| 3 | 2＋中斷 0x29 關開 | 55／48 拒絕，eoi+tiles 1,017 µs |
| 4 | 2＋電源時脈 `C0708C60(0/1)` | **引擎不再回報完成**：第 2 個工作 1.1 s 後判故障（lane 4），該段未能收尾，下一段整段 RAW |
| 5 | 2＋裝置資源 `C07095A8(5,0/1)`（重開機後單獨測） | 52／45 拒絕；段落正常收尾 |
| 6 | 4＋`C06304F0`（open 在通電後的 30000814 設定） | 同 4：引擎卡住、故障 |

**結論：每幀一定要照原廠完整的 close→open；拆開或跳步，不是被拒就是卡住。`open` 的 170 µs 省不掉。**
所有失敗都安全：被拒的幀照原樣存 RAW、卡住的段由 LOSS 判故障後其餘幀照原樣送出，`tag_failed` 一直是 0，相機沒有當機。
