# 2026-10-13: 超過 96 格會造成什麼問題（FHD 59.94p，以採用版為基礎）

基礎是採用版：快取別名＋預先準備 IFD，`0ba4cd52…`。這次只移植擴充槽機制：池和 registry 搬進狀態區，修補原廠指令字。
建置選項（`build_v3_lossless.py`，只供量測用）：
- `--expand-slots`
- `--slot-force N`
- `--no-writer-guard`
- `--slot-noncached`
- `--bulk-stock`

表的上限 `FPL_SLOT_MAX` 改為 288（使用者要求不用 1016）。不加選項時，建置結果仍是 `0ba4cd52…`。

## 結論

**lag 和卡死的原因是 bug，不是 CPU。**

先前「registry 掃描終點跟著有效格數」的修改（`20261013-registry-scan`）只改了 11 個掃描迴圈，
**id 的上限沒有一起改**，仍然是整張表的長度。這 3 個位置是：
- `C03764F4`：分配新幀 id 時往後找的上限；
- `C03757D8`：計數迴圈的上限；
- `C03753CC`：用 id 查表的上限。

結果：
- id 會分配到有效格數以上（實測：有效 96 格，id 是 96～182）。
- 掃描迴圈看不到這些幀，所以它們寫完後不會被刪除，描述子也不會還回池子（實測：池剩 9 個，registry 前 96 格全空，96～182 格都有東西）。
- 池用光時原廠以 vbuf 停錄，下一段接著出錯，或相機卡死。

snapshot 之前沒有發生，是因為格數依公式算（FHD 236、M12240 556），而測試都只錄 3～4 秒，幀數從來沒有超過格數。

**修正**：這 3 個上限也跟著有效格數（`slot_patches.py`）。格數是 96 時寫回原廠值。

- 寫入器防護（C037DF50..）在以上測試中都沒有使用。FHD 60p 輸入（約 60 MB/s）遠低於卡速，原廠的 128 張訊息票不會用光。卡速不足時仍需要這個防護，但它還沒單獨上機驗證過。

## 其他觀察

- snapshot 的 A 版（96 格、未擴充）FHD 60p 時 MRecMgr 是 26.5～29.7%，比採用版的 13～14% 高出約一倍。
  所以 snapshot 版本本身就比較重，這和擴充無關，是 snapshot 其他改動造成的（例如每個檔案都經過的批次決策 hook）。
- 同一張卡、同樣設定，不同開機之間 CamSch 會差 3～8 點，所以只能在同一輪內互相比較。

## 追加：固定 1016 格（同日晚）

把表長改回 `FPL_SLOT_MAX` 1016。`slot_capacity.h` 的註解已改正：之前寫成「288 是使用者的上限」是誤解，使用者說的是「測試時兩三倍就夠」。
建置 `v6/x1016bulk`（`--expand-slots --slot-force 1016 --no-writer-guard --bulk-stock`），`075065e2…`。

| 測試 | 結果 |
|---|---|
| FHD 59.94p，2 段 | 總 CPU 75.0／75.4；200/200、209/209；在途最多約 92 |
| OG3K 59.94p 3 s，2 段（同一次開機） | 約 2.7～3.1 s 以 `mem`（RAW 記憶體用完）自停；114/114、113/113 全部寫完；在途最多約 79；第 1 段後池 1016/1016 全部歸還，registry 0，slots.refused 0 |
| 使用者重開相機後，OG3K 59.94p 再錄 2 段 | `mem` 自停；134/134、127/127；在途最多約 83～85 |

結論：
- 格數開到 1016，CPU 不增加。
- 在途幀的上限由 RAW 記憶體決定。
- 記憶體用完時，原廠的 `mem` 停錄能乾淨收尾，下一段也正常。

**還沒測**：記憶體能容納超過 128 幀的模式（FHD 約 220、HS280 約 640）在卡速不足時的表現。
在途幀超過 128 時，原廠的寫入器訊息票（MPoolFixed<8,128>）可能會用光，這是 2026-10-13 卡死的機制之一。
這需要寫入器防護，而防護還沒單獨上機驗證過。
