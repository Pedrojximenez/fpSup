# fpSup-Gyro-HDMI 時間戳版 — 規格

2026-09-17。承 `GYRO_HDMI_INJECTION_DESIGN.md`(全 IMU 注入)與
`research/interfaces/notes/HDMI_RAW_FORMAT.md` §9–§11。

**這是那份設計的輕量先行版**:HDMI 只送時間戳,IMU 留在卡上連續記錄,
切片與對齊在後期做。酬載從 20,378 B/s 掉到 **18 B/frame**。

---

## 1. 為什麼先做這個

| | 全 IMU 注入(§11) | **時間戳版(本文)** |
|---|---|---|
| 每幀酬載 | 667–834 B | **18 B** |
| 區塊大小 | 8×8(勉強) | **32×32,餘裕 13×**(UHD) |
| 抗有損 | 4.6× 餘裕 | 壓倒性 |
| 卡上要不要寫 | 不寫(全靠 HDMI) | 寫,連續 |
| 失敗的後果 | 整段 IMU 沒了 | 退回現行 per-take 對齊 |

**管線完全相同** —— 時間戳版跑通,全 IMU 版就是同一套機制換大酬載。
所以這是正確的第一個里程碑,不是繞路。

## 2. 傳輸選擇:影像路線的 Y 通道

沿用 §0.29 的判斷,理由對時間戳更強:

- 使用者的 `AVerMedia ExtremeCap UVC` **15 種格式全是 4:2:0**,沒有 4:2:2
- **4:2:0 只砍色度,luma(Y)保持全解析度** → 資料放 Y 就原封保留
- 音訊路線已於 §0.28 判定不可行,不再考慮

**已驗證的像素容器**(`FUN_c00E23D0`,Thumb):

```
[struct+0x04] = W        [struct+0x08] = H
[struct+0x10] = framebuffer 位址
清除長度 = W*H*2 bytes,填 0x80008000
```

小端記憶體 = `00 80 00 80` → **偶數位元組 = Y,奇數位元組 = 色度**(YUY2 排列)。
`0x00` 是黑、`0x80` 是中性色度,與「清成黑畫面」一致。

## 3. 位置

`HDMI_RAW_FORMAT.md` §9.0(a):RAW 酬載只佔光柵約 75.9%,尾端有連續閒置區
(UHD ≈ 521 行,FHD 依同比例 ≈ 251 行)。**資料寫在閒置區,不碰 RAW 影像本身。**

⚠ **閒置區的存在與位置仍未實測**(§11.4 第 1 項)。緩解:注入位置做成可設定的
起始行,預設指向預測位置;一次擷取即可證實或推翻。

## 4. 酬載格式

```
u32  magic   0x66705453   'fpTS'   —— 自我同步,解碼器靠它找起點
u64  t_us    64-bit tick               —— 與卡上 IMU 串流同一個時基
u32  seq     幀計數                    —— 偵測掉幀
u16  crc     前 16 bytes 的 CRC-16
                                          共 18 bytes = 144 bits
```

時基**必須**用 `HDMI_RAW_FORMAT.md` §10.4 的 64-bit 組法:

```c
u32 t[2]; FUN_c002B4E0(t);          /* [0]=原始計數 [1]=溢位(秒) */
u64 t_us = (u64)t[1]*1000000ull + (u64)t[0]*100ull / DAT_c2efabd0;
```

**不要用 `FUN_c002B6E0`** —— 它截成 u32,約 71.6 分鐘繞回,連續記錄一定撞到。
`FUN_c002B4E0` 在 GyroData task 已由 Stage-5 實證安全。

## 5. 編碼:32×32 區塊,1 bit/格

逐像素 LSB 一定被有損壓縮與 4:2:0 毀掉,必須用大色塊。

| 模式 | 閒置區 | 格數 | 對 144 bits 的餘裕 |
|---|---|---|---|
| UHD | 3840 × 521 | 120 × 16 = 1,920 | **13.3×** |
| FHD | 1920 × 251 | 60 × 7 = 420 | **2.9×** |

**單一參數 32×32 就能涵蓋所有模式**,不必依模式切換。

**位元值取 limited-range 兩端**:

```
0 -> Y = 16      1 -> Y = 235
```

判定用中點 125。這樣即使擷取鏈做了 limited↔full range 轉換、輕度濾波或有損壓縮,
兩個值仍然隔得極遠。**不要用 0/255** —— 那會在 range 轉換時被夾。

餘裕拿來做重複:UHD 每個 bit 重複 13 次、FHD 重複 2 次,解碼取多數決。

## 6. 注入點

```
執行緒   XC_DispIntrObserver::XC_ThreadEntryMain   (task context,每幀)
緩衝取得 FUN_c00EA608(plane)  → 當前掃出中的 framebuffer
         ⚠ plane 中哪個對應 HDMI(ch0/ch1)未定,見 HDMI_RAW_FORMAT.md §13.4
```

**必須寫進「下一幀正要掃出的那一塊」** —— 有 double/triple buffer,寫錯塊會看到閃爍
或根本沒送出。lachgil 在 overlay 那份文件踩過同一個坑(只畫一個 buffer,UI 一換塊圖就消失),
他們的結論是常駐 pass 要**三塊都畫**。本設計可沿用同樣的保險做法。

每次寫完以 `FUN_c000E91C` 做快取維護。

## 7. 卡上這一側

- **連續記錄,不綁錄影**。HDMI-only 拍攝時相機沒有 take,沒有東西可以掛 per-take log。
- 格式沿用 `GYRO_FOLLOW_THE_FACTORY.md` 的 8-byte 定版(`i16 x, y, tag, z`)。
- 流量實測 **20,663 B/s 固定**(見 `out/gyroflow/` 的成對檔案):
  1 小時 74 MB、8 小時 595 MB。對 SD 卡的 94 MB/s 是 0.02%。
- **不要寫 CSV** —— 文字版是 2.4–2.8×(4 欄)或 3.9–4.3×(7 欄),而且沒有固定上界,
  數值位數隨拍攝動態變動。CSV 是輸出格式,不是儲存格式;轉檔時才產生,順便切片。
- 每個區塊錨點寫同一個 64-bit tick,與 HDMI 那側同源。

## 8. 後期對齊

1. 從擷取的畫面解出每幀的 `t_us`
2. 從卡上的 IMU 流取對應時間範圍的樣本
3. 殘差只剩**感光元件曝光 → HDMI 掃出的管線延遲 k 幀**,那是常數,
   拍一次甩動測一次就永久固定

現行 per-take 錨點誤差是 **470–570 ms 且每片不同**(見
`AUDIO_VIDEO_SYNC.md` / 記憶 `audio-video-sync-by-construction`)。
換成共用時基後,「每片不同」變成「固定偏移」—— 這才是這整套設計買到的東西。

## 9. 待驗證(依阻擋程度)

1. **閒置區是否存在、在哪、多大** —— `HdmiLimit` @ `0xC0437740` 可印出 RAW 實際幾何。
   **這是唯一的硬阻擋**,一次量測解決。
2. **Y 通道經擷取卡是否 bit-exact** —— 用自家 AVerMedia 直接測。
   §6 的校準法:**先跑非 RAW**(§4 證明線上容器相同),一般 UHD 輸出拍平場,
   確認整條擷取鏈保真度,再切 RAW。
3. `FUN_c00EA608` 的 plane 哪個是 HDMI(ch0/ch1)。
4. gyro 記錄器目前能否在非錄影狀態持續跑(`stop-path-keep-it-thin` 提過
   「順便讓功能不用錄影就能測」,可能已經可以)。

## 10. 相機端時間碼:評估過,不走

韌體有完整時間碼系統(`MenuItemTimeCodeRunMode` / `SetTimeCodeOutputSignalOnHdmi` /
`XC_TimecodeClass`),getter/setter 都找到了:

| | setter | getter |
|---|---|---|
| Hour | `0xC00614D8` | `0xC0061510` |
| Min | `0xC0061570` | `0xC00615A8` |
| Sec | `0xC0061608` | `0xC0061640` |
| Frame | `0xC00616A0` | `0xC00616D8` |
| RunMode | `0xC0061738` | `0xC0061770` |
| HdmiOut | `0xC0061868` | `0xC00618A0` |

**理論上最漂亮**:Free Run + HDMI 輸出時間碼,連注入都不用,Atomos/BMD 直接寫進 metadata。

**但不採用**,三個理由:

1. 這些 getter 走設定物件 vtable(`+0x368` Hour、`+0x374` Frame、`+0x378` RunMode)
   讀的是**存的設定值**,不保證是 free-run 的活計數器。活計數器在
   `XC_TimecodeClass` / `XC_TimecodeCountConverter`,而那兩個 RTTI 字串在打包名稱表裡,
   **沒有交叉引用可追**。
2. 解析度只有逐幀(25p = 40 ms)。夠指出是哪一幀,但我們自己的 64-bit tick 是 µs 級。
3. 多三個要上機才能答的未知數(Free Run 在不錄影時走不走、HDMI 是否真的帶出去、
   活計數器在哪),而影像路線的未知數**在使用者自己的擷取卡上就能測完**。

→ 留作備案。若影像路線的閒置區不存在,這是退路。
