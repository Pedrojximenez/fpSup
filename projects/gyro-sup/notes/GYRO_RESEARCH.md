## 1. 兩顆感測器

### 1.1 ICM20321 陀螺儀 <sub>實機驗證</sub>

```
0xC31E3FCC  →  P = 0x2E006004
                 P+0x60  →  環的基底 = 0x2E00644C
                 P+0x64  =  2500      (設定值,實際 2499.47)
                 P+0x68  =  131       (LSB/dps)
```

- 資料從 `基底+4` 開始,**600 筆 × 8 bytes = 0x12C0**
  (不是 `0x12C4` —— 多算四個位元組會讓每次繞圈拖進四個舊位元組)
- 每筆:`i16 X, i16 Y, i16 pad(=0), i16 Z`
- **head = `*(基底)` 是絕對指標,不是位移。** 最新完整樣本 = `*(基底) − 4`
- 600 筆在 2500 Hz = **240 ms**,對 20 ms 的回呼有 **12 倍餘裕**

> **`0x2E000000…` 是 OIS 副處理器(ARM926)的 RAM。** 樣本由副處理器產生,
> 主 CPU **從頭到尾沒有「收到」過任何一筆**。

### 1.2 MMA8452Q 水平儀 <sub>實機驗證</sub>

```
0xC377790C  i16 X       12-bit 右靠有號(sxth 然後 asr #4)
0xC377790E  i16 Y       ±2g,1024 LSB/g
0xC3777910  i16 Z       韌體已經做過軸重映射
```

- **只有一格,沒有佇列。** 新的直接蓋掉舊的 → **必須 hook**
- `CTRL_REG1` 在不同路徑寫成 `0x1D`(100 Hz)和 `0x09`/`0x49`(400 Hz),
  但實測**發布**只有 47.2 Hz —— **ODR ≠ 發布節奏**
- OIS 信箱那條 accel(`FUN_c01ec7f8`→`FUN_c01ee148`)是**死的 return stub** <sub>讀韌體</sub>

## 2. 為什麼陀螺不能逐筆 hook,水平儀卻必須 <sub>讀韌體</sub>

對稱的函式**確實存在**:

```
IMUDev_GYRO_ICM20321__v6 @ 0xC050CA98
    FUN_c01ec6f8(&local_24);                  // 三軸
    FUN_c050c5d0(param_2, local_24);          // 跟水平儀掛點後面那個是同一個函式
```

**但 `FUN_c01ec6f8` 只讀「現在值」**(三個 f32 在 `_DAT_c31e3fcc + 0x34/0x38/0x3c`),
環在 `+0x60`,它沒碰。呼叫它的是 20 ms 的 GyroData 回呼。

> **掛那個 hook = 一秒 50 筆,丟掉 98%。**

**反證**:600 筆(240 ms)的環,就是為了主 CPU 跟不上才存在的。

| | 有沒有緩衝 | 一筆不漏的唯一辦法 |
|---|---|---|
| 水平儀 | 沒有,一格快取 | **必須 hook** |
| 陀螺儀 | 有,600 筆 = 240 ms | **必須讀環** |

兩個**都是 hook**(都掛在回呼上),差別是水平儀伸手接參數,陀螺儀拿鏟子。

⚠️ **注意分清楚兩件事**:進到 stream 的**資料是 2500 Hz**(一筆不漏);
50 Hz 的是**我們的程式碼被喚醒的次數**。

## 3. 速率:四段實機量測 <sub>實機驗證</sub>

### 3.1 結果

```
加權平均 83.3989 筆/格   (2863 個間隔)
陀螺速率 2499.47 Hz      (比 2500 低 0.021%)
週期     400.0854 µs
```

| 片段 | 間隔數 | 平均 | 偏離 |
|---|---|---|---|
| ~21 s | 633 | 83.3981 | −0.0008 |
| ~15 s | 494 | 83.3988 | −0.0001 |
| ~45 s | 1388 | 83.3991 | +0.0002 |
| ~12 s | 348 | 83.3994 | +0.0005 |

**散佈 0.0005%。** 12 秒到 45 秒,答案不動。

### 3.2 兩把獨立的尺

| 方法 | 對照的時鐘 | 結果 |
|---|---|---|
| 600 s 長基線、21 點擬合 | **主機**(`--rate`) | 2499.520 ± 0.018 Hz |
| 2863 個影格間隔 | **相機自己的感測器**(`--take`) | 2499.466 Hz |

**差 0.0021%。** 兩把毫無關係的尺落在同一個數字上。

而且它們互相釘死:`2499.520 ÷ 83.3989 = 29.9709 fps`,而 29.97 是 29.97003
—— **「這段是 29.97 fps」不是假設,是推出來的。**

### 3.3 為什麼可以停手 —— 四道檢查

1. **每個長間隔都只是 83 或 84**(`min 83 / max 84`,四段皆同)。
   83 和 84 各幾次是**解出來的**:`n84 = VSUM − 83×VNF`,不是擬合。
2. **門檻沒有作用**。如果有半格被當成整格算進去,`min` 會低於 83。它沒有。
3. **重複觸發不會偏差**。拆成兩個短的 → 兩個都被丟掉 → 總和與個數同步減少 → 平均不動。
4. **首尾相消**。所有間隔的總和 = 最後一次 head − 第一次 head,
   中間每次讀取的誤差都抵銷,只剩頭尾各 ±1 筆 = **0.004%**。

### 3.4 舊結論全部推翻 <sub>已推翻</sub>

| 舊說法 | 實情 |
|---|---|
| 「硬體實測 2501.85 Hz」 | **錯**。+0.074%,差 130 個誤差棒,方向相反 |
| 「誤差 0.02%」 | 量值對,**符號相反**(是低於不是高於) |

### 3.5 影響與修法

用 400 µs 當週期,陀螺時間軸比真實**短 0.021%**,而且**漸進**:

| 片長 | 偏差 |
|---|---|
| 1 分鐘 | 0.4 格 |
| 3 分鐘 | **1.2 格** |
| 10 分鐘 | **3.8 格** |
| 30 分鐘 | 11.5 格 |

開頭永遠對,越後面越糟 —— 這是「有時候看起來對、有時候不對」的其中一個來源。

**修法免費**:gcsv 的 `tscale` 從 `0.0004` 改成 `0.0004000854`。

## 4. 換掉的三把壞尺(方法論)

這一節比結論重要:**每一把尺都給出過看起來合理的錯答案。**

### 4.1 `STREAM_GCOUNT` — 解析度 20 ms,不是 0.4 ms

陀螺生產者住在 20 ms 的回呼裡,每次一口氣 `+50`。計數器是**階梯不是斜坡**:

```
時間   0ms    20ms   40ms   60ms
計數   0      50     100    150
```

兩次曝光只差 33 ms,量出來是 **0 / 50 / 50 / 0**。尺比要量的東西還粗。

**改用韌體環的 head** —— 副處理器每 0.4 ms 推進 8 個位元組,是真正的斜坡。
(注意:**資料本身沒問題**,只有拿計數器當時鐘是錯的。)

### 4.2 min/max — 一個異常值就毀掉

`VMIN = 0`,因為某次兩個 Vd 之間 head 完全沒動。`VMAX = 84` 卻很乾淨。

### 4.3 全部間隔取平均 — 讀到 80.53

反推需要約 23 個 0 間隔。真相:**Vd 有 4.7% 的機率一格觸發兩次**(31/664)。

這也解掉了另一個謎:卡上 **953 次 Vd 對 900 格影片**多出 53 次,
不是我們漏算,是感測器中斷本來就會重複。

**用 64 筆當門檻把短的分開**,才得到 83.3989。而 §3.3 的四道檢查證明這個門檻不含判斷成分。

## 5. 錄影的開始與結束 <sub>實機驗證</sub>

```
開始  0xC01FBA28   FUN_c01fb918  ←  movRec
結束  0xC01FB880   FUN_c01fb640  ←  MovRecFuncStateREC__v36 case 1
```

**方向是量出來的,不是讀出來的。** 從呼叫點讀起來會覺得相反 ——
`movRec` 像「開始錄影」、`case 1` 像「進入 REC 狀態」。實際上:

> `movRec` 在錄影開始時把正在跑的**監聽音訊拆掉**;
> `case 1` 是**離開** REC 狀態時把它裝回去。

靜態分析分不出這兩種讀法。**兩次量測分得出來**:11 秒的片給 11.38 s、
3 秒的片給 4.40 s,間隔跟著片長走,而且 `0xC01FBA28` 兩次都先觸發。

兩個掛點都在**存 lr 的指令之後、所有 early return 之後**,
所以碰到它們的一定是真的開始/結束的片段。

### 錨點:六次量測

```
8.4 / 0.8 / 6.0 / 2.8 / 12.0 / 8.0  ms      平均 6.3,最大 12.0
```

**全部在一格(33.4 ms)以內。**

> ⚠️ 舊筆記的 **470–570 ms 不屬於這個觸發點**。那個數字是「我們的 50 Hz
> 輪詢發現 MovieRecording 旗標變高」量到的,而且只是從 Gyroflow 自動同步反推的。

## 6. 曝光事件:Vd 幀中斷 <sub>實機驗證</sub>

```
FUN_c0125478 @ IRQ 0x79     Thumb
    c0125478  E92D 4130   push.w {r4, r5, r8, lr}
    c012547c  F648 14C0   movw   r4, #0x89C0
    c0125480  F2CC 341D   movt   r4, #0xC31D     ← 掛這裡
```

- liveview 實測 **59.94 Hz** —— NTSC,不是 60.0,所以確實是感測器的影格節奏
- **IRQ 上下文**:不能有 syscall、不能阻塞。只做 LDREX/STREX 和 store
- Vd **在 liveview 也跑**,所以錄影開始的 hook 要把閂鎖歸零重新上膛

### 為什麼不掛寫檔那條路

**陀螺要對齊的是「光打到感測器」,不是「檔案落到卡上」。**

CinemaDNG 是 96 MB/s 的緩衝寫入,檔案落地比曝光晚幾百毫秒,而且不固定。
拿寫檔當第 N 格,等於把整條寫入管線的延遲折進陀螺的時間軸。

### 第一個 Thumb hook

`FUN_c0125478` 是 Thumb,所以分支是 **Thumb BLX**,立即數拆在兩個半字裡、
J1/J2 由符號推導。**編錯不會 fault,會跳進別的東西中間。**

clang 定不了(它留未重定位的佔位符),所以測試用**解碼韌體自己的 `bl`**
來釘住位元佈局 —— `0xC0125494` 解出 `FUN_c0128e50`,跟反編譯完全一致 —— 再把編碼器來回驗證。

`FrameExpos_s`(`0xC0315C18`)**試過並淘汰**:liveview 零次、錄影全程零次,不在曝光路徑上。

## 7. 記錄格式:固定 8 bytes + tag

```
0  i16 x    2  i16 y    4  i16 tag    6  i16 z
```

| tag | 意思 | 推進時間? |
|---|---|---|
| 0 | 陀螺儀 | ✅ +400 µs |
| 1 | 水平儀 | ❌ |
| 2 | (已淘汰的 FrameExpos) | — |
| 3 | 錄影開始 | ❌ |
| 4 | 錄影結束 | ❌ |
| 5 | Vd 曝光 | ❌ |

### 為什麼沒有時間戳

錨點來自回呼裡的 TickTimer 讀數,**它落後最後一筆樣本自己的延遲(0–1 ms)**。

> **2500 Hz 的硬體網格是準的,時鐘讀數才是抖的。**

每筆都寫時鐘讀數 = 把抖動撒到每一列,比什麼都不寫更差。
**位置就是時間**,整段只需要一個錨點。

### tag 那個半字是免費的 —— 已證實

韌體陀螺環的 pad **永遠是 0**。生產者不相信這件事:明寫 `tag=0`,
同時數來源 pad 不為零的次數。**跑過幾十萬筆,`bad pads` 始終為 0。**

### 已知誤差

陀螺在 20 ms 回呼裡整批附加,水平儀是即時的但靠著上一批的最後一筆
→ **水平儀被標早 0–20 ms,平均 10 ms**(是早不是晚)。
47 Hz 的重力向量 20 ms 內不會動,所以不修。

## 8. 韌體的寫卡架構 <sub>讀韌體</sub>

所有寫入經過 `XC_MediaFile::Write @ 0xC03660E8`,取同一把**不可搶佔**的卡鎖
(`XC_MediaDriverSdcard+0x3c`,槽 `0xC351EE18`)。影片、音訊、我們各寫各的檔。

### 音訊 —— 沒有雙緩衝 <sub>已推翻舊說法</sub>

```c
// AudioFileWriter::v1 @ 0xC01FBD40
while (true) {
  FUN_c036d9c0(this+0x20, ..., &job, 0, 0xffffffff);  // 阻塞在隊列,永不逾時
  FUN_c03660e8(file, job.ptr, job.len);               // 直接從指標寫卡
}
```

> ⚠️ **音訊 writer 自己一個緩衝區都沒有。** 「兩個 16 KiB 雙緩衝」是**錯的**,
> 而且那個錯誤誤導過設計方向。

真正的架構:**8 MB DMA 環(~40 s)+ 32 深指標隊列(零拷貝)+ 專屬 writer**
(`AudF_W @0xC01FD380`,優先級 6,堆疊 0x2000)。

**音訊不掉針的三個理由:高優先級 + 深環 + 阻塞式立刻醒。**
它是 IO-bound,等鎖時讓出 CPU —— 跟我們 writer(28)+ 每 5 ms 才醒剛好相反。

### 音訊的信封 <sub>實機驗證</sub>

一段 295 格的片:

```
影片   295 格          =  9.843 s
音訊   1924180 bytes   = 10.022 s   (+0.179 s)
```

**音訊也比影片長 179 ms** —— 只是比我們當初抓到的 1.595 s 緊 9 倍。
長度本身分不出那 179 ms 在頭還是尾;實務上 fp 的聲音是準的,所以幾乎確定在尾巴。

**關鍵理解**:音訊不需要知道正確的開始時刻,它只需要跟影片在**同一個事件**開始。
共模偏移是看不見的。**我們的陀螺只有在「寫出一個時間」時才會有這個問題。**

### 優先級(數字小 = 高)

| SRecFile | AudF_W | ImgCtrl | SRecMgr | **GyroData** | **我們的 writer** | RECMGRMV |
|---|---|---|---|---|---|---|
| 6 | 6 | 7 | 9 | **20** | **28** | 50 |

## 12. 安全規則

- **`mem read` 必須先取得同意**
- **沒有被要求就不要 commit**
- **錄影期實驗必須先斷開 daemon**
- 不要對大量片段的資料夾下 `dir`(`dir` 也**不能查單一檔案**,只能列資料夾)
- `getfile` 上限 32 MiB(40 MiB 會卡死配置器 → 重開機);`--size` 可略過 `dir`
- **絕對不要**執行 `delCinemaDng` / `deloneimg` / `delall`
- 注入區只有 `0xC072E064`..`0xC072EFA0`;**可寫不等於沒人用**
- **不要寫到 `pool+0x77000`** —— 開機就載好的常駐 PGEN(弄死過相機四次)
- `push` 一定要偶數個暫存器(奇數會在韌體的 `LDRD` 上 data abort → 凍結)
- `mem set` 會靜默丟寫入,**批次寫入必須回讀重試**
- **不要在活著的程式碼上覆寫** —— 一定先 `--restore` 解除分支再寫
