# Gyroflow 朝向字串 — 定案 `xyz`(三軸各自驗證)

> 2026-08-24。**訂正** `SIGMA_FP_INTERNAL_GYRO_ARCHIVE_2026-08-18.md` 裡列為「實測確認」的 `YxZ`。

## 一句話
正解是 **`xyz`** —— 三軸全部取負,亦即陀螺晶片相對相機**旋轉 180° 安裝**。
歸檔文件的 `YxZ` 是錯的(會把晃動放大 1.87 倍)。

## 驗證方式(三軸各自獨立確認)
三支各約 10 秒的單軸素材,每一欄都在**它佔決定性份量的那支片**上單獨定案:

| 素材 | 陀螺分佈 (dps) | 定的是 |
|---|---|---|
| `A001_011` 純水平搖 | X=18.0 Y=0.3 Z=0.2 | 第 1 欄 |
| `A001_012` 純俯仰 | X=0.3 Y=12.2 Z=0.2 | 第 2 欄 |
| `A001_013` 純傾斜 | X=4.4 Y=2.3 Z=19.0 | 第 3 欄 |

三支都用 `xyz` 通過。

## ★ 為什麼中間繞了那麼多冤枉路
中途試過 `YXZ` / `XzY` / `Xyz` 都被實機推翻,原因不只是猜錯,而是**測試本身被污染**:

**朝向字串會同時套用到加速計**,而**重力讓加速計在每一支片裡都有訊號**。
所以「純水平搖」只隔離了陀螺的 X 軸,**沒有隔離字串** —— 第 2、3 欄仍然作用在
加速計上,並透過 VQF 融合影響姿態。這就是為什麼 `XZY` 和 `XzY` 在同一支
純搖攝素材上會給出不同結果(照陀螺推理它們該一樣)。

**A/B 結果是在把 accel 從檔案裡拿掉之後才變得可重現的。**

→ 因此解析器**預設不輸出 accel**(`--accel` 才開)。陀螺和加速計是兩顆獨立晶片、
各自安裝方向不同,而 gcsv 只有一個 orientation 欄位服務兩者;陀螺的 `xyz` 已驗證,
加速計的軸向**尚未驗證**。

## Gyroflow 的實際慣例（原始碼，文件沒寫）
`src/core/gyro_source/imu_transforms.rs`：字串第 i 個字元指定**輸出第 i 格**取自哪個輸入軸，小寫取負。
```rust
fn orient(inp: &[f64;3], io: &[u8]) -> [f64;3] {
    let map = |o| match o { 'X'=>inp[0], 'x'=>-inp[0], 'Y'=>inp[1], 'y'=>-inp[1],
                            'Z'=>inp[2], 'z'=>-inp[2], _=>panic!() };
    [map(io[0]), map(io[1]), map(io[2])]
}
```
**關鍵**：`src/core/gyro_source/mod.rs:163` 再把它重排一次 ——
```rust
let omega = Vector3::new(-g[1], g[0], g[2]) * (PI/180.0);
```
所以 gcsv 欄位 → body 軸的對應是：**欄2 → body X（取負）、欄1 → body Y、欄3 → body Z**。

而 Gyroflow 的 body 軸是 **X = roll、Y = yaw、Z = pitch**（實機三次 A/B 定出來的，
不是常見的 pitch/yaw/roll 順序 —— 我一開始就是假設成那個順序才連錯三次）。

## 方法學教訓
1. **絕對相關係數不能定符號。** 舊值和我第一次的 `YXZ` 都栽在這裡。
2. **量測正確不等於結論正確。** 我量到的「哪顆感測器對應哪種物理運動」全部可靠，
   但套用時多加了「Gyroflow 三格 = pitch/yaw/roll」這個沒驗證的假設，於是連錯三次。
3. **隔離素材價值極高。** 三支各 10 秒的單軸素材（純搖 / 純俯仰 / 純傾斜）
   一次把焦距、符號、偏移全部量準；在一支三軸同時大幅甩動的素材上則繞了一小時還在猜。
4. **使用者的一句描述勝過一小時分析。**「變成逆時針旋轉」直接定出 body X = roll，
   那是我用光流怎麼算都算不出來的（光流量得到感測器語意，量不到 Gyroflow 內部定義）。

## 其他實機量測值
- **偏移不是固定值**：010→570ms、011→515ms、012→470ms、013→470ms，**逐片相差達 100ms**。
  先前「570 vs codex 的 575 所以是固定管線延遲」的判斷是**單一樣本推廣，錯誤**。
  → 解析器預設不烘偏移，交給 Gyroflow auto-sync（實測它找到 −531ms，與光流量到的 515ms 吻合）。
- **有效焦距 2451 px**（影像 1936×1090，水平 FOV 43.1°）。
  當成全片幅 40mm 會得到 48.3°，**過度修正 23%**；fp 的 1080p CinemaDNG 約讀出感光元件寬度的 0.88。
- **捲簾讀出時間**：光流估 ~3.0 ms（r=0.42，不夠硬）。
  **韌體有真值**：`FUN_c030c7f0()` @0xC030C7F0（無參數）→ `FUN_c0319f10()` →
  `(**(code**)(*(FUN_c0322e48(0) + 0xD0) + 0x3C))()`，即 sensor-timing vtable +0x3C。
  AF 的延遲補償公式用的就是它（`readout/2`，見 `AF_AE_INTERNALS.md`）。**待實機讀取**。

# 完整設定 — 逐項標註驗證強度

⚠️ **不要把整組當成已驗證。** 只有三項真的在相機上 A/B 過;
決定修正**幅度**的兩個參數(焦距、gscale)其實都還沒驗。

## 驗證狀態
| 參數 | 值 | 狀態 |
|---|---|---|
| `orientation` | `xyz` | ✅ **實測** — 三支單軸素材各自確認一欄 |
| 鎖定水平 roll 校正 | −90° | ✅ **實測** |
| 陀螺/加速計旋轉 | 0 / 0 | ✅ **實測** — 0 可行,+90 會讓畫面轉 90 度 |
| 捲簾時間 | 3.0 ms | ⚠️ 只證明「比 0 好」(果凍消失),**沒試過其他值** |
| 焦距 | 2451 px | ⚠️ 光流量測 r=0.997,但**沒在 Gyroflow 裡 A/B**。先後量出 2656 / 2451 兩值 |
| `gscale` | 0.000121385 | ❌ **沿用 codex 上一輪的值,本輪完全沒驗證** |
| `ascale` | 0.0009765625 | ❌ 規格書數字(1024 LSB/g),沒實測 |
| 偏移 | auto-sync | ✅ 實測逐片 470–570ms 不等 |

**焦距和 gscale 是直接相乘決定修正幅度的兩個數**,兩者都沒驗 ——
其中一個偏 20% 的話,另一個可以反向補償而看起來仍然「還行」,所以
**單獨看效果無法分辨**。要驗必須固定一個、掃另一個。

| 同步 | 每支片各跑一次自動同步 | 偏移逐片 470–570ms 不等,不能寫死 |

## 那個 90° 偏差的正確理解
症狀是「**穩定效果正常,但水平鎖定差 90°**」。這個組合本身就指出了答案:
穩定只用**相對旋轉**,整個座標系差一個固定角度會自己抵消;水平鎖定需要**絕對重力方向**,
固定偏移就原封不動顯示出來。

Gyroflow 積分器的起始姿態是寫死的 `from_euler_angles(FRAC_PI_2, 0, 0)`(繞 X 軸 90°),
那是為典型運動相機的 IMU 裝配預設的,跟 fp 差 90°。

**修的地方是「鎖定水平」自己的 roll 角度校正欄位(−90°)**,不是去轉 IMU 座標系。
我先後提過「只轉加速計 +90°」(讓畫面轉了 90 度)和「兩個一起轉」(多餘),兩個都繞遠路 ——
Gyroflow 本來就為這件事準備了專用欄位。

## 走過的三次彎路,共同的模式
1. **`YxZ`(歸檔值)** — 來自絕對相關係數,定不出符號。
2. **加速計 +90°** — 來自判別力很弱的數值解(多個候選在雜訊內並列),
   我卻用一個漂亮的行列式論證去包裝它,反而**提高**了對薄弱前提的信心。
   而且韌體的 `IMUDev_ACCEL_MMA8452Q__v7`(case 0–6 軸重映)本來就是反證,我三小時前才讀過。
3. **兩個 IMU 一起轉** — 機制推理正確,但沒先確認工具是否已經提供了更直接的手段。

共同點:**推導本身沒錯,錯在沒有先檢查前提有多硬,以及有沒有現成的東西可用。**

# 焦距與捲簾 — 改用韌體的 IMX410 模式表(訂正先前的量測值)

> **⚠️ 訂正 (2026-08-24):下面「= mode 111」是錯的。**
> 同解析度同幀率有**兩個**模式:106 (捲簾 10.556 ms) 與 111 (7.828 ms),
> 我當時把兩個候選當成一個。**焦距 2157 px 不受影響**(同幾何族,焦距相同),
> gscale 的訂正也不受影響 —— **只有捲簾停在兩個候選**。
> 詳見 `ONCAMERA_GCSV_AND_LENS_PROFILE.md`。

## 結論
```
1080p CinemaDNG @29.97 = mode 106 或 111 (未定)
  幾何   3032 x 1708   ( = 6064/2,全寬 2x2 縮減,不是裁切 )
  時序   hmax 330 cycles, vmax 7280 lines, 72 MHz
  → 焦距  1936 x 40 / 35.9 = 2157 px  (水平 FOV 48.3°)
  → 捲簾  10.556 ms (106) 或 7.828 ms (111)  ← 未定
```
來源:`codex/analyze_imx410_modes.py` 抽出的 70 個模式記錄
(`TABLE_VA 0xC0B5FDAC` / `GEOMETRY_VA 0xC0B59DC0` / `TIMING_VA 0xC0B59500`),
輸出在 `codex/analysis_imx410/`。**這份資料 2026-08-17 就做好了。**

## 訂正了什麼
| 項目 | 我的光流量測 | 韌體表 | 誤差 |
|---|---|---|---|
| 焦距 | 2451 px(判定為 0.88 裁切) | **2157 px(全寬)** | 13.6% |
| 捲簾 | 3.0 ms (r=0.42) | **7.828 ms** | 2.6 倍 |

**超採是誤判的原因。** `3032 = 6064/2` 是全寬 2×2 縮減,視角不變;
但從光流反推焦距時,它看起來就跟裁切一模一樣。長寬比可以確認:
`3032/1708 = 1.775`,輸出 `1936/1090 = 1.776`。

> **2026-09-11 訂正。** 原文這裡寫的是「全寬 2x2 **binning**」。
> 那個字用錯了 —— 本節的論證只證明「不是裁切」(視角不變),而
> **2×2 跳行同樣視角不變**,兩者從幾何分不出來。是不是電荷合併必須用雜訊量。
> 本文對焦距、捲簾、gscale 的訂正全部不受影響(那些只需要「全寬」這一點)。
> 2026-09-11 實測之後這個問題仍未定論,見 `SENSOR_READOUT_NOISE_2026-09-11.md` §5
> 的模型矛盾。另外該文 §1 指出:mode 106 與 111 之間真正的差別是**類比讀出設定**
> (106 安靜 R≈0.44、111 屬快速組),而 picker 的 29.97 槽填的是 106。

## 連帶訂正 gscale
光流實際量到的是**乘積 `focal_px x gscale`** —— 那才是可觀測量
(它決定「陀螺讀值 → 畫面位移幾像素」)。要拆開必須先有焦距。

codex 當初用**他們自己從同一批資料擬合的焦距**去拆,於是焦距的誤差
整個被吸收進 gscale。用韌體的獨立焦距重新拆:
```
0.000121385  →  0.000137923
偏離規格書(131 LSB/dps) 13.6%  →  3.5%
```
3.5% 對感測器個體差異合理,13.6% 不合理 —— **這本身就是舊值被污染的證據**。

## 對發佈版的意義
那張表涵蓋 **70 個模式**,每個都有幾何與時序。所以自動產生 lens profile
時只要知道拍攝模式就能查表,不必逐一量測 —— 4K、各種幀率、裁切模式全涵蓋。
