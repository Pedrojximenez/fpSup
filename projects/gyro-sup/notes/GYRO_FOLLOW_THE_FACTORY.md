# 照抄原廠:錄影開始、緩衝、寫入(2026-09-05 定案的方向)

> ⚠️ **2026-09-13 方向調整（使用者定案）→ 細節見 `../../../research/interfaces/../../../research/interfaces/notes/HDMI_RAW_FORMAT.md` §10、§12**
>
> **新架構**：gyro 改為**開機即開始連續記錄原始格式**，**不再轉 GCSV**；
> HDMI 外錄那條路上，gyro 直接**夾帶進 HDMI 內嵌音訊**隨幀送出。
> → 本文「待辦順序 §3 接 GYR 模式 + 停止後轉換 + 刪中間檔」的**轉換與刪檔步驟取消**。
>
> **支撐這個架構的三項新事實（皆已驗證）**：
> 1. **TickTimer 其實是 64-bit**。`FUN_c002B6E0`（µs）截成 u32，**71.6 分鐘就繞回**，不能用於開機到關機的連續記錄。
>    改用內層 `FUN_c002B4E0(u32 out[2])` → `out[1]` = 溢位計數（秒，u32 = 136 年）、`out[0]` = 次秒原始值：
>    `t_us = (u64)out[1]*1000000 + (u64)out[0]*100 / DAT_c2efabd0`
>    （`DAT_c2efabd0` 由 `FUN_c002B5B0` 初始化時算好）。此函式在 GyroData task 已由 Stage-5 實證安全。
> 2. **HDMI 內嵌音訊經實測為 48 kHz / 2ch / 16-bit 位元透明**（實拍 BRAW 全軌 1,285,284 sample 的 OR = `0xFFFF00`）。
>    只偷每 sample 低 **4 bit** 即得 **48,000 B/s**，是 raw gyro（2500 Hz × 8 B = 20,000 B/s）的 **2.4 倍**；
>    注入噪訊 −77 dBFS，低於實測噪訊底 34 dB，且低 4 bit 本來就是純噪聲（熵 0.996/4）。
> 3. **gyro 隨幀走之後，「切片」問題消失**——每幀自帶屬於它的 ~104 筆樣本（2500/23.976），
>    不需對時基、不需比對 GCSV、無漂移。只剩「感光元件曝光 → HDMI 掃出」的常數 k 幀延遲要校準一次。
>
> **已排除的通道**：BRAW 為 8:1 有損（實測 7.94:1）→ 塞像素不可行；
> timecode 軌只有一個起始值（`stsz` count=1）→ 無法每幀變動。

## 為什麼

用戶的判斷:「從開始錄影、暫存緩存、到寫入的方式,都應該參考錄影與錄音,
這才能貼近原廠設計,避免不必要的未知錯誤與冗長的測試。」

這和 2026-09-02 調查的結論一致,只是當時沒有轉向:

> stream 掉針的根源是「錄影期轉文字」本身。音訊能用高優先級 6,是因為它 IO-bound;
> 我們的 writer 是 CPU-bound,提優先級反而餓死陀螺擷取(prio 8 實測 96.92% vs prio 28 的 99.32%)。
> 真正照抄音訊 = 錄影期寫 raw、不轉文字、停止後才轉。

**這套架構是一個整體,挑著抄會更糟** —— 只提優先級是實測退步的。

## 逐項對照

| 環節 | 原廠音訊 | stream(現在) | 照抄後 |
|---|---|---|---|
| 觸發 | 錄影開始的單一事件 | 50 Hz 輪詢 MovieRecording 旗標 | 同一事件 |
| 緩衝 | 8 MB DMA 環 ≈ 40 s | 兩個 32 KiB 槽 ≈ 2.5 s | 池內 896 KB ≈ 45 s |
| 交接 | 32 深指標隊列,零拷貝 | 單槽交接 | 隊列 |
| 搬運工 | 專屬任務,prio 6,阻塞式立刻醒 | prio 28,每 5 ms 輪詢 | 有事就醒(wup_tsk) |

| 轉換 | 不需要(WAV 就是 raw) | — | 停止後一次 |

## 數字(全部實測)

- raw 二進位 2500 Hz = **19.5 KB/s**,比現在 1250 Hz 的文字(26.3 KB/s)還少。
- 池空位 896 KB ÷ 19.5 KB/s = **45 秒**緩衝。
- 文字最多只能再壓 10.6%(時間戳改成取樣序號),到不了目標 —— 超過一半的位元組是陀螺數字本身。
- 2500 Hz 文字實測會掉樣並**中斷錄影**(19.77 s 處 46.8 ms 的洞、106 筆)。
- 唯一的槓桿是「每張桌子要寫幾次卡」:3 次 → 掉 3402,1 次 → 掉 0。

## 同步:聲音和影片其實沒有「同步機制」

`TimeCodes`(0xC763)在整個韌體只出現一次,而且不在寫 DNG 標籤的模組(0xC00Cxxxx,那裡只寫
`FrameRate` 0xC764)。所以 CinemaDNG 影格**不帶時間碼**,WAV 也沒有東西可對齊 ——
**它們是靠同時開始**。

我們的陀螺沒有用那個瞬間:`S_START_US` 取自「50 Hz 輪詢發現旗標變高」的時刻,
比第一張影格早 470–570 ms **而且每支片不同**。這就是 Gyroflow 自動同步不可靠的來源 ——
偏移本身不是問題,**每次不一樣**才是。

診斷已上卡(2026-09-05):`logger.S` 的 `FPGYRO_FRAME_ANCHOR` 在錄影中偵測
`0xC343943C`(影像路徑每次曝光latch 的 raw 緩衝位址,閒置時為 0)第一次變非零的時刻,
`profilegen.S` 把 `start_us` / `frame0_us` / `delta_us` / `raw_addr` 寫進每支片的 JSON。
**還沒錄過,數字未知。**

## 三個零件都已存在

- `logger.S` GYR 模式:錄影期寫 raw,零掉針(已驗證)
- `gcsvgen.S`:機上把 GYR 轉成 gcsv(GFM6 區塊路徑,建置通過)
- `profilegen.S`:錄影期寫 JSON,已不碰鏡頭匯流排(700 ms/次的成本已消除)

缺的是:接成一條線、用相機的觸發點、轉完刪掉中間檔、量停止時間。

## 待辦順序

1. 錄三段診斷片,讀 `delta_us` 的離散程度 → 決定「減常數」還是「換錨點」
2. 若要換錨點:先看音訊啟動(`AudF_W@0xC01FD380`、8 MB 環的 arm)比影像路徑更安全
3. 接 GYR 模式 + 停止後轉換 + 刪中間檔
4. 量停止時間 vs 片長(30 s / 2 min / 5 min),對照用戶的 3 秒目標

## 不要重做的事

- 加大緩衝、三槽:**已測過**(用戶)
- 提 writer 優先級:**已測過,更差**(prio 8 = 96.92%)
- 縮 poll 5ms→1ms:**已測過,GCSV 完全不生成**(poll 是多個計時的基準)
- 2500 Hz 文字串流:**已測過,掉樣且中斷錄影**

# 記錄格式定版:固定 8 bytes + tag(2026-09-06)

## 格式

```
偏移  0   i16  x
      2   i16  y
      4   i16  tag      0 = 陀螺儀   1 = 水平儀
      6   i16  z
```

**兩種資料一樣長,沒有任何時間戳。** 陀螺儀與水平儀寫進**同一條有序資料流**,
tag 是唯一的判別。

## 為什麼沒有時間戳

原本打算陀螺儀記錄後面接一個 u32 時間戳(12 bytes),水平儀不接(8 bytes),
用長度差當判別。用戶指出這是錯的,而且程式碼裡本來就有答案:

> 每個區塊的錨點來自回呼裡的 TickTimer 讀數,**它落後最後一筆樣本自己的延遲
> (0–1 ms)**,所以區塊接縫會抖動最多約 0.5 ms。

也就是說 **2500 Hz 的硬體網格是準的,時鐘讀數才是抖的**。整套接縫機制存在的
目的就是「寧可相信網格,不要相信時鐘」。每筆都寫一個時鐘讀數等於把 0–1 ms 的
抖動撒到每一列上,比什麼都不寫更差。

所以:**位置就是時間**。往後一筆 = 晚 400 µs。整段只需要一個錨點。

水平儀沒有自己的網格(韌體以約 47 Hz 不等距發布),所以它也不配時間 ——
它插在它發生的地方,屬於它旁邊那一列。讀取器遇到 tag 0 前進 400 µs,
遇到 tag 1 不前進。

## tag 這個半字是免費的

韌體陀螺環的記錄本來就是 `x, y, pad, z`,而 pad **永遠是 0**
(gcsvgen.S 的註解「z sits past the pad」用了好幾個版本)。這是整個格式的
前提,所以 `gyro_stream_hook.S` 不相信它 —— 它明寫 tag=0,並且把來源 pad
不為零的次數記進 `STREAM_PADBAD`。**假設變成一個可以讀回來的數字。**

## 誠實的代價

20 ms 是韌體 GyroData 回呼自己的週期,**量過的**:`notes/projects/usb-shell-sup/../../usb-shell-sup/notes/TELEMETRY_HOOK.md`
記 1170 次 drain / 23.378 s = 50.0 Hz。不是我們選的數字。

陀螺儀生產者在那個回呼裡把整個 20 ms 的批次一次附加,而且是在它涵蓋的 20 ms
**結束時**才附加。水平儀在兩次回呼之間抵達,它自己是即時附加的,但它靠著的
那筆陀螺記錄是上一批的最後一筆。所以讀取器把它標成它所在區間的**開頭**:
**偏早 0–20 ms,平均 10 ms。是早不是晚** —— 落後的是陀螺記錄,水平儀繼承了
它的落後。

水平儀只用來餵 47 Hz 的重力向量,20 ms 內不會動,所以不修;但「位置就是時間」
是一個主張,這是主張的誤差大小,寫下來而不是藏起來。

真要修是免費的:hook 在附加樣本時順便 latch 韌體環的 head,陀螺儀生產者就知道
它是在批次的哪一格抵達,把它插進批次**裡面**而不是後面。代價是水平儀改成
先進小佇列、由陀螺儀生產者統一寫入 —— 順便連 LDREX/STREX 都不需要了。

| 檔案 | 內容 |

## 尚未量測:2500 Hz 到底多準

筆記裡有兩個互相矛盾的數字 —— 一處「硬體實測 2501.85 Hz」(差 0.074%),
一處「已驗證,誤差 0.02%」,兩個都沒留量測方法。差距不是無關緊要的:

| 誤差 | 3 分鐘 | 換算影格 |
|---|---|---|
| 0.02% | 36 ms | 約 1 格 |
| 0.074% | 133 ms | **約 4 格** |

而且它是**漸進的**,開頭對齊、越後面偏越多 —— 這是「自動同步有時候對有時候
不對」的另一個獨立來源。長基線可以量得很準:錄一段長片,比對陀螺樣本數與
影格數(影格率取韌體模式表的精確值)。**格式不受影響,可以之後單獨量。**

# 為什麼陀螺儀不能逐筆 hook(2026-09-06 查證)

**問題:** 水平儀是 hook 一個「參數帶著三軸」的函式。陀螺儀有沒有對稱的做法?

**答案:有那個函式,但它一次只給一筆,而且一秒只被呼叫 50 次。**

## 對稱的函式確實存在

```
IMUDev_GYRO_ICM20321__v6 @ 0xC050CA98
    iVar1 = FUN_c01ec6f8(&local_24);          // 三軸
    FUN_c050c5d0(param_2,        local_24);   // X
    FUN_c050c5d0(param_2 + 8,    local_20);   // Y
    FUN_c050c5d0(param_2 + 0x10, local_1c);   // Z
```

水平儀那邊掛的 `0xC050D498` 後面接的正是 `bl 0xC050C5D0` —— **同一個函式**。
兩顆感測器走同一套 IMUDev 框架,結構完全對稱。

## 但那個函式只讀「現在值」,不讀環

```
FUN_c01ec6f8 @ 0xC01EC6F8
    *param_1   = f32 @ (_DAT_c31e3fcc + 0x34)   // X
    param_1[1] = f32 @ (_DAT_c31e3fcc + 0x38)   // Y
    param_1[2] = f32 @ (_DAT_c31e3fcc + 0x3c)   // Z
```

環形緩衝在 `*(P + 0x60) = 0x2E00644C`,**這個函式沒有碰它**。
呼叫它的是 20 ms 的 GyroData 回呼(實測 50.0 Hz)。

> **掛這個 hook = 一秒 50 筆,丟掉 2450 筆(98%)。**

## 根因:陀螺樣本不是主 CPU 產生的

`0x2E000000…` 是 **OIS 副處理器(ARM926)的 RAM**(`notes/research/other/../../../research/other/notes/CAMERA_STATE_SOURCES.md`)。
陀螺樣本由副處理器寫進共用記憶體的環,**主 CPU 從頭到尾沒有「收到」過任何一筆**,
它只是每 20 ms 去環裡搬。

所以主 CPU 上**不存在**一個 2500 Hz、參數帶著陀螺樣本的函式可以掛。

反證也成立:**那個 600 筆 = 240 ms 的環,就是為了主 CPU 跟不上才存在的。**
如果主 CPU 每一筆都收得到,沒有人會蓋一個 240 ms 的水庫。

## 兩顆感測器的正確做法剛好相反

| | 有沒有緩衝 | 一筆不漏的唯一辦法 |
|---|---|---|
| **水平儀 MMA8452Q** | 沒有,`0xC377790C` 只有一格,新的蓋掉舊的 | **必須 hook** |
| **陀螺儀 ICM20321** | 有,600 筆 = 240 ms,對 20 ms 有 12 倍餘裕 | **必須讀環** |

這不是一個認真一個偷懶,是兩顆晶片接進系統的方式本來就不同。

## `gyro_stream_hook.S` 也是 hook

它掛的就是那個 20 ms 回呼。差別只在於:**水平儀伸手接參數,陀螺儀拿鏟子去環裡鏟。**
兩個都是 hook,陀螺這個 hook 手上要拿工具。

而且 **20 ms 對陀螺儀的時間精度零損失** —— 時間是靠位置算的(第 N 筆 = N × 400 µs),
不是靠搬運時刻算的。20 ms 唯一影響的是水平儀插在批次的哪一格。

256 records: 251 gyro, 5 accel
one accel every 50 gyro (2500 Hz against a measured 47.2 Hz is about 53)
100.4 ms of gyro in the stream

  [ 54]        0 us      -25     -88     -20
  [ 55]      400 us      -20     -88     -25
  [ 56]      800 us      -21     -79     -28
  [ 57]     1200 us      -24     -74     -29

| 數值 | 靜止、相鄰差幾個 LSB、平滑漂移 | 真的陀螺資料,不是雜訊/卡住/垃圾 |
