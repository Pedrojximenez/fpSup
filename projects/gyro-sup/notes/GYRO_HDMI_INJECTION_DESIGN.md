## 0. 音訊注入可行性 —— 原始碼追查結果（2026-09-14 更新）

### 0.1 已確定（seg0 靜態分析）

**(a) CPU 不可能直接寫 HDMI 音訊取樣。**
HDMI TX 的音訊暫存器在 **`0x302A0000`** 區塊（不是 `0x30190000`），
組態函式 `FUN_c00F1388` @ `0xC00F1388` 完整寫出：

```
0x302A0028 [19:0] = N          audio clock regeneration
0x302A002C         = CTS / 取樣率
0x302A1004 [1:0]   = 2         介面選擇
0x302A1034 [5:0]   = 2 或 3    聲道數（依 *param_1）
0x302A1000 bit0    = 1         最後才 enable
0x302A1010 [6:0]   = 0x77/0x75 靜音（FUN_c00F1750，bit1 = mute）
```

**整段沒有任何 DRAM 位址、沒有 sample FIFO、沒有 DMA base。**
取樣走內部硬體介面，主 CPU 只設定 N/CTS、channel status 與 enable。

**(b) 但「韌體產生的 PCM → HDMI 音訊」這條路徑確實存在。**
`FUN_c06B4B48` @ `0xC06B4B48`（在 `XC_MoviePlayInterface` 內）在**機內播放影片**時
呼叫 `HdmiAMute(hdmi, 0)` 解除 HDMI 音訊靜音 —— 也就是說**播放檔案的聲音會送上 HDMI**。
那份音訊來自播放路徑（`DspAudioDevicePb` 的 8 MB 環 → DSP），不是麥克風。

→ **HDMI 音訊不是硬接在麥克風 ADC 上，中間有 mux。**

**(c) 一般（非播放）狀態下，HDMI 音訊跟著擷取路徑。**
`FUN_c01F9BF8` @ `0xC01F9BF8`：靜音與否取決於**錄音器狀態**
（`FUN_c01FB2F8` / `FUN_c01FB558` 與 `+0x18` / `+0x19` 三個條件全為 0 才靜音）。

**(d) 所有音訊都由 DSP 仲介。** 擷取（`AsicAudioDevice` / `DspAudioDevice`）、
播放（`DspAudioDevicePb`）、提示音（`XC_Sound` → `FUN_c00D44C0` / `c00D4688` / `c00D46E8`）
全走 `c00D3xxx` / `c00D4xxx` 命令族。
類比編解碼晶片另由 `FUN_c00DAF70(reg,val)` 以 I2C 暫存器驅動
（`FUN_c00DA538` / `c00DA568` = 喇叭/耳機兩路獨立靜音，**與 HDMI 無關**）。

### 0.2 仍不確定，且 seg0 答不出來

**餵 HDMI 音訊介面的 mux 由誰決定，寫在 DSP（ARM926 副處理器）韌體裡。**
那是獨立的二進位，**不在 seg0**（已確認 `out/` 只有 IPL / MAIN / DAT1 / PTBL，
沒有 ARM926 映像）。

所以未解的是：**播放／提示音的 PCM 能不能在 live view + HDMI RAW 輸出的同時**
也送上 HDMI —— 而不只是在「播放影片」那個互斥模式下。

### 0.25 ★ 硬限制：**不可以替用戶靜音**（2026-09-15 使用者定案）

使用者的音軌必須保持可用。所以：

- ❌ **不能**把播放流「取代」麥克風送上 HDMI（先前設想的 192 kB/s 全頻寬方案作廢）
- ❌ **不能**把資料當成可聽訊號疊上去
- ✅ 只能做 **LSB 替換** —— 覆寫本來就是噪聲的低位元（§6）

**為什麼「疊加」在數學上就不可行**（不只是難聽）：

要不可聞就得壓在噪訊底之下。實機量測（`HDMI_RAW_FORMAT.md` §14.2）live view 噪訊底 ≈ −47 dBFS。

```
注入 −70 dBFS（安全不可聞）→ SNR = −23 dB = 5.0e-3
   C = B·log2(1+SNR) = 96,000 × 0.0072  =    692 bit/s =    86 B/s
注入 −50 dBFS（已貼著底，安靜場景會露出）→ SNR = −3 dB
   C = 96,000 × 0.585                   = 56,000 bit/s =  7,000 B/s
需求                                                      20,378 B/s
```

（B = 48 kHz × 2ch = 96 kHz）

→ **就算接受可聞的劣化，疊加法也給不到需要的頻寬，差 3–236 倍。**
LSB 替換之所以可行，是因為它不是「把訊號埋進噪聲」，
而是**置換已知是噪聲的位元**，得到一條乾淨的 N bit/取樣通道。

### 0.26 所以真正的問題換了

既然只能做 LSB 替換，需要的是**對送往 HDMI 的 PCM 取樣的精確寫入權**。
問題不再是「韌體的聲音能不能上 HDMI」，而是：

> **HDMI 音訊的來源是不是一塊 CPU 可寫的 DRAM 緩衝？**

若 HDMI 的取樣點在擷取 DMA 的 DRAM 緩衝**下游**，
改寫該緩衝的低位元就會傳到 HDMI（`AsicAudioDevice::v1` 配置 0x2F000 = 192 KB）。
若取樣點在**上游**（硬體直接從 ADC 串到 HDMI），則主 CPU 完全沒有施力點。

**這一點 seg0 答不出來**（mux 在 DSP 韌體裡），仍需實測。

### 0.27 提示音測試仍然值得做 —— 但它是**架構探針**，不是機制驗證

混音 ≠ LSB 控制，所以就算提示音上得了 HDMI，也不等於方案成立。
但它仍是目前最便宜、資訊量最高的一次觀測：

| 結果 | 推論 |
|---|---|
| **提示音出現在 HDMI 音訊裡** | DSP 在 live view 期間**確實在處理**那條流（非純硬體直通）→ 鏈路中存在可寫緩衝的機率大幅提高，值得繼續找 |
| **沒有出現** | 幾乎可判定 live view 的 HDMI 音訊是剛性硬體路由（ADC → HDMI），**LSB 注入無法從主 CPU 達成** |

做法（零副作用、不寫卡）：暫時把 `SetSoundAFVolume` 設非零 → `key S1ON` 半按數次 → 還原。
目前實測狀態：AF 音／快門音／計時器音皆為 0，只有 **REC 音 = 1**。

### 0.28 ★ 再確認的結論（2026-09-15）：音訊路線應判定為不可行

三條證據，方向一致：

**(1) HDMI TX 端沒有任何可寫入口。**（§0.1(a)）
`0x302A0000` 音訊區塊只有 N/CTS、channel status、enable、mute。
無 sample FIFO、無 DMA base。**主 CPU 從來不碰 HDMI 音訊取樣。**

**(2) mux 在 DSP 韌體裡，不在 seg0。**（§0.2）
`AsicAudioDevice::v1` 把擷取緩衝位址交給 DSP 回呼 `0xC00D4758`，
之後發生什麼事在 ARM926 映像裡 —— 該映像未從 `firmware/FP__V502.bin` 解出。

**(3) ★ 延遲論證 —— 新證據，指向「HDMI 取樣點在 DRAM 緩衝之上游」。**

```
擷取 DRAM 緩衝  0x2F000 = 192,512 B
48 kHz x 2ch x 16-bit   = 192,000 B/s
→ 該緩衝正好是 1.003 秒的音訊
```

若 HDMI 音訊源自這塊緩衝，**HDMI 監看的聲音會延遲約一秒** ——
沒有任何相機會這樣出貨。所以那塊 192 KB 是給**寫檔**用的緩衝，
而 HDMI 監看必然從更上游、低延遲的硬體路徑分接。
**那條路徑上沒有 CPU 可寫的位置。**

> 嚴格說這不是證明（DSP 內部仍可能有小型可寫緩衝），
> 但舉證責任已經反轉：**沒有任何正面證據支持音訊可注入，而有三條反向證據。**
> 結論：**音訊路線判定不可行，改走影像。**
> §0.27 的提示音測試仍可做為架構探針，但不再是專案的關卡。

### 0.29 影像路線：使用者的擷取卡改變了可行性判斷

實測 `AVerMedia ExtremeCap UVC` 的 15 種格式 —— **全部是 `420v`（4:2:0），沒有任何 4:2:2**。

這對 RAW 本身是壞消息（`HDMI_RAW_FORMAT.md` §8.4：4:2:0 會毀 RAW），
但對**藏資料**反而是關鍵的好消息：

> **4:2:0 只對色度做次取樣，luma（Y）保持全解析度。**
> 把資料放在**閒置光柵區的 Y 通道**，4:2:0 原封保留。

而且這條路線在**使用者自己的開發硬體上就能測**——
音訊路線從頭到尾都沒有這個條件。

### 0.3 ★ 驗證這件事**不需要外錄機**

只需要**任何一台有喇叭的 HDMI 裝置**（電視、帶音訊的螢幕、HDMI 音訊分離器）：

> fp → 電視，進 live view（不必是 RAW 模式），觸發一聲提示音（快門音／AF 嗶）。
> **電視發出聲音** → 韌體音訊在 live view 下會上 HDMI，本設計成立。
> **沒有聲音** → live view 下 HDMI 只吃麥克風鏈路，音訊方案作廢，退路見 §8。

第二個確認（同樣不需錄影機）：播放一段機內影片到電視，確認有聲音 ——
這會印證 §0.1(b) 的推論，並把「mux 存在」從推論變成實證。

### 0.4 若要從原始碼徹底解決

抽出 ARM926 DSP 韌體並分析其音訊路由。
NAND 分割 `ARM926_1` / `ARM926_2`（見 `research/.../FIRMWARE_INVENTORY.md`），
目前未從 `firmware/FP__V502.bin` 解出。這是一條大工程，建議先做 §0.3。

## 1. 範圍

**獨立版本，只做一件事**：HDMI RAW 模式下把 IMU 資料塞進輸出。

- **不內錄。** 所有資料都必須走 HDMI —— 卡上不會有平行的 gyro log 可以對。
- 不做 GCSV 轉換、不寫卡、不碰錄影路徑。
- 與 `fpSup-Gyro`（寫卡版）互斥，不共存。

## 2. 架構：生產端不動，只換消費端

現有 IMU 串流**已實機驗證**，原封沿用：

| 現有零件 | 作用 |
|---|---|
| `gyro/imu_stream.inc.S` | 位址與 tag 的唯一來源 |
| `gyro/gyro_stream_hook.S` | 284 B，掛 `0xC00D0794`，tag=0，2500 Hz |
| `gyro/accel_hook.S` | 92 B，掛 `0xC050D498`，tag=1，實測 47.2 Hz |

記錄格式（`GYRO_FOLLOW_THE_FACTORY.md` 定版，不改）：

```
偏移  0  i16 x
      2  i16 y
      4  i16 tag     0 = 陀螺儀   1 = 水平儀
      6  i16 z
```

**唯一要新寫的是消費端**：把這條 RAM 串流打包成自我同步的區塊，塞進音訊低位元。

```
[既有] gyro_stream_hook + accel_hook  →  合流的 8-byte RAM 串流
                                              │
[新寫]                          packetiser（§5）
                                              │
[新寫]                       音訊低位元注入（§6）
                                              │
                                    HDMI → 外錄機
```

## 3. 啟用條件：是狀態，不是事件

> **外錄流程不會按機身 REC 鍵**（`HDMI_RAW_FORMAT.md` §13 更正）。
> 開啟 HDMI RAW 後 fp 就持續輸出，起停在外錄設備，**fp 收不到通知**（無 CEC、無回傳通道）。
> 所以 `HdmiRecStart` @ `0xC0517D20` **永遠不會觸發，不要用它**。

注入器的閘門是兩個可輪詢的狀態：

```
*(u32*)0xC30783A4 == 2            HDMI 已連線（XC_DisplayHdmi +0x1F8）
HdmiOutputFormat == 1             RAW（menu slot 0x3B8，getter FUN_c005FCB8）
```

兩者皆真 → 持續注入。其餘時候不動音訊（避免無謂地污染內錄 WAV）。

## 4. 頻寬帳

```
需求  2500 Hz 陀螺 + 47.2 Hz 水平儀 = 2547.2 筆/s × 8 B = 20,378 B/s
容量  48000 × 2ch × 4 bit / 8            = 48,000 B/s
餘裕  2.35×      （與幀率無關 —— 兩邊都隨幀長等比縮放）
```

每視訊幀（UHD 23.976p，最壞情況）：需 850 B，可用 2,002 B。

---

## 5. 封包格式：必須自我同步

**外錄機會從任意時間點切入一條自由運行的串流。**
不能假設「片段開頭 = 資料開頭」，也**不能沿用寫卡版「整段只放一個錨點」** ——
那個錨點極可能落在片段之外。

每個區塊自帶錨點與同步字：

```
off  size  欄位
+0   u32   magic  = 'GHDM'          同步字，主機端掃描它重新對齊
+4   u64   tick   = 64-bit TickTimer（§7）
+12  u16   seq    區塊序號（遞增，wrap 16-bit）
+14  u16   n      本區塊的記錄筆數
+16  u16   crc    CRC-16，涵蓋 +0..+15 與酬載
+18  ...   n × 8 B 記錄（格式見 §2）
```

頭 18 B + 850 B 酬載 ≈ **868 B/區塊**，對 2,002 B 的容量是 2.3×。

**不做冗餘複製。** 區塊夠小且各自獨立，被片段邊界切斷最多損失一個區塊
（≈42 ms 的陀螺資料），主機端掃到下一個 magic 就繼續 —— 比複製划算。

區塊內仍然「**位置就是時間**」：往後一筆 tag=0 = 晚 400 µs，tag=1 不前進。
與寫卡版唯一的差別是**錨點頻率**：從每段一個變成每區塊一個。

## 6. 位元配置：每個音訊取樣對 = 1 byte

實測（`HDMI_RAW_FORMAT.md` §11.2）：fp 送 **16-bit**，錄影機存進 24-bit 容器，
低 8 bit 全程為 0（全軌 1,285,284 sample 的 OR = `0xFFFF00`）。所以可用的是上 16 bit。

偷每個 16-bit 取樣的**低 4 bit**：

```
audio frame n:  L[3:0] = byte n 的低 nibble
                R[3:0] = byte n 的高 nibble
```

→ **1 byte / 48 kHz 音訊幀 = 48,000 B/s**，算術乾淨，解碼不需要位元對齊。

代價（`HDMI_RAW_FORMAT.md` §12 實測）：
- 注入噪訊 **−77.0 dBFS**，低於該樣本實測噪訊底（−42.7 dBFS）**34 dB**
- 低 4 bit 本來就是純噪聲（熵 0.996/4）→ **覆寫的是噪訊，不是訊號**

> 若哪天噪訊變成問題：改偷 2 bit（−89 dBFS）仍有 1.15× 餘裕，但算術變髒（需跨位元組拼接）。
> **先用 4 bit。**

⚠️ **資料必須在任何音訊處理之前取出**：24→16 bit 截位沒問題（資料在高位），
但增益調整、正規化、重取樣都會毀掉 LSB。解碼器直接讀 BRAW/MOV 的原始 `in24` 取樣。

## 7. 時基：用 64-bit，不要用 `FUN_c002B6E0`

`FUN_c002B6E0()` 回傳 µs 但**截成 u32，約 71.6 分鐘繞回** —— 連續輸出一定會撞到。

用內層（`src/driver/TickTimer/src/TickTimer.cpp`）：

```c
u32 t[2]; FUN_c002B4E0(t);      // 內建重讀防競態
u64 t_us = (u64)t[1] * 1000000ull            // t[1] = 溢位計數 = 秒，u32 → 136 年
         + (u64)t[0] * 100ull / DAT_c2efabd0;  // t[0] = 次秒原始值
```

`DAT_c2efabd0` 由 `FUN_c002B5B0` 初始化時算好。
`FUN_c002B4E0` 在 GyroData task 已由 Stage-5 實證安全（`FUN_c002B6E0` 就是它的外層）。

錨點語意沿用既有慣例：**取自回呼裡的讀數，落後最後一筆樣本 0–1 ms**。
不要改成每筆都寫時間戳 —— `GYRO_FOLLOW_THE_FACTORY.md` 已論證那樣更差。

## 9. 待辦順序

1. **提示音測試**（§0）—— 決定整個方案生死。
2. 若通過：找 DSP 播放環的寫入點與節奏（由音訊消耗決定，**不是** display 中斷 ——
   那個只跟寫光柵有關）。
3. 實作 packetiser + 注入器，主機端解碼器比照 `gyro/imu_stream.py` 擴充。
4. 用一段實拍驗證：任意剪一段 BRAW，確認能重新對齊並解出連續的 IMU 串流。

## 11. 影像路線規格（2026-09-15 轉向後的主線）

### 11.1 位置

`HDMI_RAW_FORMAT.md` §9.0(a) / §11.3：HDMI framebuffer 為 **2 B/px**，
RAW 酬載只佔約 **75.9%**，光柵尾端有連續閒置區
（UHD ≈ 521 行；FHD 依同比例 ≈ 251 行）。
資料寫在該區的 **Y 通道**。

### 11.2 編碼：區塊，不是逐像素

目標錄影機是有損的（BRAW 8:1 實測 7.94:1；ProRes RAW 亦有損），
開發用擷取卡是 4:2:0。逐像素 LSB 一定被毀，**必須用大色塊 + 1 bit/格**。

| 模式 | 區塊 | 格數/幀 | B/frame | B/s | 對 20,378 B/s |
|---|---|---|---|---|---|
| UHD 23.976p | 16×16 | 7,680 | 960 | 23,017 | 1.1× |
| UHD 23.976p | **8×8** | 31,200 | 3,900 | **93,506** | **4.6×** |
| FHD 59.94p | **8×8** | 7,440 | 930 | **55,744** | **2.7×** |
| FHD 119.88p | **8×8** | 7,440 | 930 | **111,488** | **5.5×** |

→ **採 8×8 區塊**：全模式皆有 2.7× 以上餘裕，16×16 在 FHD 59.94p 會不夠（0.7×）。

### 11.3 相對音訊路線的優劣

| | 音訊 LSB | **影像區塊** |
|---|---|---|

### 11.4 待驗證

1. 閒置區的實際位置與大小（`HdmiLimit` @ `0xC0437740` 可印出 RAW 實際幾何）
2. Y 通道經擷取卡是否 bit-exact（是否有 limited↔full range 轉換）—— 可用自家卡直接測
3. `FUN_c00EA608` 回傳的 plane 中，哪一個對應 HDMI（ch0/ch1 待定，見 `HDMI_RAW_FORMAT.md` §13.4）
