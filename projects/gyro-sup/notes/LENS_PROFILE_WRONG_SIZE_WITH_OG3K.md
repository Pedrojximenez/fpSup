# 鏡頭 profile 在 OG3K 下尺寸錯誤 —— 機制與三個選項

2026-09-18。實例:網友的 `A001_939.json` 寫著 `3856x2170` + `mode 98` + `readout 12.435`
—— 前者是 UHD,後兩者是 OG3K30。**同一個檔案自相矛盾,而且沒有任何東西攔下它。**

## 1. 判定哪一半錯

`focal_px` 是決定性證據。用 `ONCAMERA_GCSV_AND_LENS_PROFILE.md` §2 的公式:

| 情境 | out_w | focal_px |
|---|---|---|
| UHD 3856×2170(mode 123,1×1) | 3856 | **1826.0** ← 檔案寫 1826.982 |
| OG3K 3024×2010(mode 98,2×2) | 3024 | 1432.0 |

主點也是 `(1928, 1085)` = 3856/2, 2170/2。**整組相機矩陣是替 UHD 算的。**

而 mode / fps / readout 是**實際量測**的(`S_MODE_RUN` 來自 `FUN_c032C720`),所以對。
→ **錯的是尺寸。**

## 2. 尺寸的兩條來源,兩條都會退回同一個錯答案

`pg_build`(`profilegen.S:951`):

```
r5 = [r10 + O_POST_W] ; r6 = [r10 + O_POST_H]
若兩者非零 -> 用它們
否則       -> bl pg_setting_dims          ← 設定 RAM + 16/10
```

**路徑 A —— 提早寫入(`lenscache.inc.S:103`)**

```asm
mov r0, #0
str r0, [r10, #O_POST_W]        @ pg_setting_dims fills these
str r0, [r10, #O_POST_H]
```

r39c 的「第 1-2 區塊就寫 JSON」設計**刻意**寫 0,因為那時 take 還沒開始,
除了設定 RAM 沒別的東西知道尺寸。

**路徑 B —— 收工後(`pg_post_snapshot`)**

`J_W/J_H` ← `S_GEOM_W/H`,而後者是在錄影中從 `GEOMETRY` (`0xC37CE210`) 鎖存的
(`logger.S:1381`)。但那個位址本身就不可靠 —— `gcsv_json.S:384` 與
`ring_task.inc.S:266` 都記著:

> 「1080p 時是 {1936, 1090, ...},**UHD 讀 0**,這裡一段 35 秒的 take 從頭到尾讀 0。」

讀到 0 → `S_GEOM_W/H` 保持 0 → `J_W/J_H` = 0 → **一樣退回 `pg_setting_dims`**。

**兩條路都通向設定 RAM,而 OG3K 用 hook 改錄影幾何、不更新設定 RAM。**

```
設定 RAM 仍是 UHD 3840×2160  →  +16/+10  =  3856×2170   ✓ 與檔案完全吻合
```

⚠ **不要再提議「改讀 `0xC37CE210`」** —— 那是已經試過並否決的死路,兩處註解都寫著。
(舊記憶筆記說它「解掉解析度缺口」,與實測相反;以程式碼為準。)

## 3. 三個選項

### (a) OG3K 更新 CameraMgrSetting —— 最正確,但不是我們的程式碼

把真實輸出尺寸(3008×2000)寫進 `FUN_c0206E98()` 回傳的 block `+0x40`
(`.h` 在 +0,`.v` 在 +4)。那是**兩條路徑都已經信任的來源**,而且在 take 開始前
就正確,提早寫入那條路也一起修好。

**風險**:該 block 是選單的動態影像尺寸設定,別的東西也在讀。而且
記憶 `camera-parameter-shell` 記著「改 `cam_movie_imagesize` 沒用,錄影開始會被刷掉」
—— 那是走 shell 的 setting 鏡像,直接寫 block 是不是同一回事**沒驗過**。

**這是 OG3K 的程式碼,要由負責 opengate 的人決定。**

### (b) 由模式推尺寸 —— 可行但把 OG3K 知識耦合進陀螺卡

`S_MODE_RUN` 可靠,而模式表(`0xC0B59DC0`,0x64 bytes × 70)機上查得到
(見 `per-mode-tables-at-runtime`)。但模式表給的是**感光元件讀出**
(mode 98 = 3032×2012),不是錄影輸出(3024×2010)—— 差 8/2,而那個關係
只有 OG3K 自己知道。→ **等於把 OG3K 的規則搬進陀螺卡,違反分離原則。**

### (c) ★ 不管怎樣都該做:矛盾就別寫

**真正的缺陷是「沒有人檢查」。** 產生器有能力知道 mode 98 的讀出是 3032×2012,
卻寫出一個宣稱 3856×2170 的檔案,而且**一聲不吭**。

最小修法:在 `pg_build` 尺寸定案後加一道檢查 —— 用 `S_MODE_RUN` 查模式表的讀出寬度,
若與將要寫入的 `calib_dimension` 差距超過合理範圍(例如 ±2 倍 binning 之外),
就**不要寫這個 profile**,或在 `note` 欄位標明尺寸來源不可信。

一個沒有 profile 的 take,使用者會去補;一個**看起來正常但錯 27% 焦距**的 profile,
使用者會直接用,然後怪穩定化不準。

### (d) ★ 正解:讀韌體自己的 canvas —— 使用者 2026-09-18 指出

「OG3K 設定長寬的位置,gyro 應該也能讀到」—— 對,而且**那個位置不是 OG3K 的**。

`FUN_c043A158`(live-view param 建構子):

```
0xC043A18C  r1 = [0xC0BD05D4 + selector*4]   ← profile id
0xC043A194  r0 = r4 + 0x5C                    ← canvas(param 的 RAM 複本)
0xC043A198  bl 0xC0439D18                     ← 把原廠 profile 列抄進 canvas
0xC043A19C  mov r0, r4                        ← OG3K 的 hook 就在這之後
```

**canvas 是韌體自己的東西** —— 原廠照樣會填,OG3K 只是在複製之後改 RAM 複本
(`og3kcanvas.S`:`.equ ROW, 0x5C`,`add r1, r4, #ROW`,原廠 PARAM 列一位元不動)。

所以陀螺卡讀 `param + 0x5C + 0x00/+0x04` 得到的是「**相機這次要錄的幾何**」,
UHD、FHD、OG3K 一體適用,**零耦合**:陀螺卡不需要知道 OG3K 存在。

| | |
|---|---|
| canvas | `param + 0x5C` |
| 錄影寬 / 高 | canvas `+0x00` / `+0x04` |
| 可見(裁切)寬 / 高 | canvas `+0x24` / `+0x2C` |

**注意**:不能改讀原廠 profile 表(FP3K 補的 `0xC0BE3F54` 那一族)—— OG3K 只改 RAM 複本,
原廠列還是 p83 的 3032×2012,讀它會拿到錯的值。

#### 還缺一步:執行期怎麼拿到 `param`

`FUN_c0423C48()` 回傳 `r4` = **`0xC375BA2C` 本身**,所以 MovSig manager 就在那個位址
(我們自己的 `HW_LOSSLESS_JPEG_CODEC.md:86` 也記著這個單例)。

lachgil 的 `sigma-fp-lab/docs/overlay` 實機量到的鏈是:

```
MovSig manager 0xC375BA2C -> core, param = [core+4], selector = [param+0]
實測 standby param = 0xC375E480(selector 5)、PIP = 0xC375E5F8(selector 23)
```

**`mgr -> core` 那一步的偏移還沒確定** —— 靜態解不出執行期指標,需要一次上機讀
(`mem read 0xC375BA2C` 附近幾個字,跟著指標走到 `+0x5C` 看是不是 3024/2010)。
**這是唯一剩下的未知數。**

第二個要確認的:提早寫入那條路在 take 的第 1-2 個區塊就產生 JSON,
那時 take 的 param 是否已經建好且是當次的。錄影開始會建構它,所以**大概**沒問題,
但沒驗過。

→ 拿到那個偏移之後,`pg_build` 的尺寸來源就從 `pg_setting_dims` 換成讀 canvas,
(c) 的一致性檢查留著當第二道防線。

## 4. 這次的處置

`A001_939.json` 已就地修正(備份 `.orig`):

```
尺寸   3856×2170  ->  3024×2010
focal  1826.982   ->  1431.978
主點   (1928,1085) -> (1512,1005)
```

`frame_readout_time` / `fps` / mode 未動 —— 本來就對。

**兩者視野相同**,正規化係數通用,只有焦距與主點隨解析度縮放。

⚠ 用的是 **3024×2010(DNG 檔頭)**,依據是能用的 FHD 案例(`calib_dimension` = 1936×1090,

則應改用該值(focal 變 1424.4)。**未在 OG3K 素材上實證。**

## 5. 2026-09-19 訂正:(d) 走不到,改用 DNG writer 自己讀的那兩個字

§3(d) 說「陀螺卡讀 `param + 0x5C` 就好,零耦合」。結構是對的,**實例是錯的**,
而且那個「唯一剩下的未知數」解不開 —— 三件事查證如下。

### 從全域走得到的 FieldAngle 是 live-view 那一個

```
0xC375D840 (LiveViewState 主管理器) +0x10
    ← FUN_c0436608 建構時填,值來自 configurator 單例 0xC375E8DC 的 vtable+0x14 工廠
```

錄影用的那一個是 `FUN_c0439740` 用 `FUN_c0439c10(0x16c)` 從池子配置的
(`XC_LiveViewFieldAngleTable`),經由 configurator vtable+0x14 的
`FUN_c043b038/238/408/638/828/988` 依請求分派。**沒有固定位址可走。**
它唯一現身的時刻就是 `0xC043A19C` 那個 hook 的 `r4`,而那個 hook 是 OG3K 的。

所以 2026-09-18 實測「走過去拿到 1936×1090」不是走錯路,是**那個實例本來就是預覽幾何**
—— OG3K 刻意把預覽 RWZM 留在原廠比例(見 `og3kcanvas.S` 的 `TARGET_WRITE_PREVIEW` 註解)。

### `pg_og3k_dims` 讀的 `0xC0731C18` 不是空地

全樹搜過:**open-gate 沒有任何一行寫它**。`og3kcanvas.S` 用的是
`0xC0731C08`(FLAG)、`0x0C`(PBFLAG)、`0x14`(BITLATCH)、`0xC0732A00`(LOG)。

更糟的是 `og3k_plan.py:58` 把回放表項 `PBENT = {6, 43, 222, "OG3K" 指標}`
放在 `0xC0731C10` —— 四個字,所以 **`0xC0731C18` 是那個表項的第三個字,值 222**,
而 `0xC0731C1C` 是 "OG3K" 字串指標。`OWNED` 表也把 `0xC0731C0C..0xC0731C20`
判給 `0xC0437AF8` 那個 hook。magic 比不中所以沒出事,但那條路**從來沒有可能成立**。

### 改用 `0xC38250E4`

`FUN_c06A5290` 蓋 IFD 時,tag `0x100`/`0x101` 取自
`(this->vtable[+0x48])(this)` = `FUN_c06999F0` 回傳的固定單例 **`0xC38250E4`**
的 `+0`/`+4`。**它就是檔頭**,所以 UHD / FHD / OG3K / 之後的 OG2K、OG4K 一體適用,
而且陀螺卡不需要知道 OG3K 存在 —— (d) 想要的零耦合,由這裡達成。

`gcsv_json.S` 的 `j_dng_dims` 早就這麼做了(commit dc730c5);這次把同一段
搬進 `profilegen.S` 取代 `pg_og3k_dims`,兩個版本的來源順序終於一致:

```
post-snapshot → pg_dng_dims → pg_setting_dims,再過 pg_dims_plausible
```

⚠ 仍然 **UNCONFIRMED**:vtable `0xC2E3A838` 與 `0xC2E3A7D4` 委派給這個單例,
`0xC2E3A938` 回傳 `this+0x18`,影片走哪一個靜態定不下來。界限檢查加
`pg_dims_plausible` 是防線,拿不到就退回設定。**待實拍驗證。**

### 「OG3K 主動發布」這條 —— 已否決,理由是耦合

canvas 只在 `0xC043A19C` 的 `r4` 現身,所以要走它,唯一可行的形狀是
**OG3K 在 record 路徑寫下 `{magic, t_us, W, H}`,陀螺卡去讀**。
技術上可行(發布位址得向 `og3k_plan.py` 要一塊沒人認領的 cave,不能用
`0xC0731C18`;而且要用普通 `str` 而非 `PUT` 巨集 —— `check()` 會拿 `PUT`
的集合去比對 `CANVAS_REC`,多一筆就建置失敗)。

**但那是耦合,2026-09-19 確認不要。** 它讓 lens.json 的正確性取決於另一張卡
有沒有載入、版本對不對、發布位址有沒有被 og3k 自己挪走 —— 而尺寸必須在
「只裝了陀螺卡」時就是對的。`0xC38250E4` 沒有這個問題:它是原廠韌體的東西,
誰改了錄影幾何都會反映在那兩個字上,所以不需要任何人配合。

→ **除非實拍證明 `0xC38250E4` 對影片不成立,否則不要回來走這條。**

## 6. 2026-09-19 再訂正:§5 的 `0xC38250E4` 是**靜態照片**的,而且恆為 0

§5 把 `0xC38250E4` 當成「檔頭本身」。**錯了**,而且 §5 自己標的那個
UNCONFIRMED 就是這件事 —— 現在解開了,答案是壞的那一邊。

### 證據鏈(全部靜態,可重驗)

```
FUN_c06A5290(this):
    vtable = [this + 0x14]
    p      = vtable[+0x48](this)
    tag 0x100 = p[0]        tag 0x101 = p[1]

CinemaDNG 的 vtable = 0xC2E3A938 = XC_StillFileFormatDng
    +0x48 -> XC_StillFileFormatDng::v16 (0xC06A5C88):  return this + 0x18

0xC38250E4 只由這兩個回傳:
    XC_StillFileFormatExif::v16   (0xC06A5D10)   ← vtable 0xC2E3A838 / 0xC2E3A7D4
    XC_StillFileFormatDummy::v16  (0xC069A050)
```

**兩個都是 StillFileFormat —— JPEG/Exif 靜態照片。** 影片的 DNG 走 `this+0x18`,
而那個物件是 `FUN_c06a64f8(0x8c)` **每個檔案 heap 配置**的
(`blk_c06.c:133590`,`[obj+0x14] = &DAT_c2e3a938`),沒有固定位址 ——
和 §5 判給 canvas 的死因一模一樣。

### 而且那個單例本來就是 0

`FUN_c06999F0` 是延遲初始化:

```
FUN_c0046080(0xC38250E4, &size, &origin, 0)
    size   = {DAT_c2e39504, DAT_c2e39508} = {0, 0}     → FUN_c0046030 寫進 +0x00/+0x04
    origin = {DAT_c2e394fc, DAT_c2e39500} = {8, 7}     → 寫進 +0x18/+0x1C
```

全映像沒有任何一處寫 `0xC38250E4 + 0/+4`。**它永遠是 {0, 0}。**

### 後果

`pg_dng_dims`(profilegen.S)、`j_dng_dims`(gcsv_json.S,commit dc730c5)、
以及 2026-09-19 加進 `ring_task.S` 標頭那一段,**三處都永遠取到 0**,
界限檢查擋掉,一律退回 `pg_setting_dims` / 選單設定。
行為與修改前完全相同 —— 沒有弄壞什麼,但也**沒有修好什麼**。

⚠ 所以 §5 那句「(d) 想要的零耦合由這裡達成」要收回。OG3K / OG2K 下
lens.json 的 `calib_dimension` 仍然是選單尺寸 + 16/10。

### 還沒排除的兩條

1. **自己掛一個唯讀 hook 去鎖存。** `FUN_c06A5290` 裡 `p = this+0x18` 正在
   暫存器上,那兩個字**就是**即將寫進 tag 0x100/0x101 的值。抄進陀螺卡自己的
   cave 即可,不需要知道 OG3K 存在,UHD/FHD/OG3K/OG2K/OG4K 一體適用。
   代價:出貨卡多第五個 hook,要上機驗。
2. **照 DNG writer 自己的方式問韌體。** 它在建構 format 物件前呼叫
   `FUN_c0437140(&out, kind, timestamp, 3)`(`blk_c06.c:133576`)取幾何,
   那是函式呼叫不是指標walk。代價:參數語意與回傳結構要先確定,而且它會配置
   /釋放(`FUN_c022edb0(&out, 2)`),盲呼風險高。

**教訓(第二次了)**:`FUN_c06999F0` 回傳固定位址,看起來像「檔頭的來源」,
但決定它是不是的,是**誰的 vtable 指向它**。§5 把「有固定位址」當成「是那個值」,
和 §3(d) 把「結構對」當成「實例對」是同一個錯。

## 7. 2026-09-19 探針:`FUN_c0437140` 可以呼叫,而且回傳活的幾何

`geomprobe.py`(專案根目錄)。USB shell 的 `callfn.py` 直接呼叫:

```
FUN_c0021C00()                          →  0xC30751D4
ts = FUN_c0021C40()                     →  0
FUN_c0437140(&out, 3, ts, 3)            →  out = 指標
FUN_c022EDB0(&out, 2)                   →  釋放
FUN_c032C720()                          →  mode_now
```

靜態模式待機讀到:

```
geom 0xC375DC34   6064 x 4042   mode 8   rest 0 0 6064 4042
```

**物件佈局與 `FUN_c0046030` 推的完全一致**,所以 `+0x00/+0x04` 就是
tag 0x100/0x101 的來源:

```
+0x00/+0x04   size      ← 要的就是這一對
+0x08/+0x0C   origin
+0x10/+0x14   size 再一次
```

指標每次呼叫都不同(重新配置),釋放乾淨,連續十餘次無異狀。
**呼叫機制本身成立。**

### ⚠ 但 `kind = 2` 會凍結相機

探針原本「兩個 kind 都問」。`kind 3` 正常,`kind 2` 之後 shell 就不回應了,
`mem_get` 全部 `None`,拔電池才回來。

DNG 寫入器是這樣選的:

```c
uVar3 = 3;
if (*(param_1 + 0x44) == 2) uVar3 = 2;      // param_1 = format 物件
FUN_c0437140(&local_18, uVar3, uVar1, 3);
```

**那是 format 物件上的條件,不是可以自由選的參數。** 沒有那個物件的情況下
傳 2,會走進一條它自己不會走的分支。探針已加 `assert kind == 3`。

同類的錯這份筆記已經記過一次(`CANVAS_MOVED_AT_C043A19C.md` §5:
`SPAN = 0x140` 讀過界凍結)。共通點都是**拿一個「看起來也合理」的值餵進韌體活路徑,
而沒有先證明呼叫端真的會那樣用**。

### 還沒證明的

待機讀到 6064×4042(全感光元件),合理但**不是錄影幾何**。要證明這條路成立,
需要錄影當下的讀數:

| 情境 | 該讀到 |
|---|---|
| CINE + FHD 錄影中 | 1936 × 1090 |
| CINE + UHD 錄影中 | 3856 × 2170 |
| **OG2K 錄影中** | **2016 × 1344** |
| **OG3K 錄影中** | **3024 × 2010** |

開放式問題還有一個:`ts = FUN_c0021C40()` 回傳 0。待機時可能本來就是 0,
但若錄影中仍是 0,要確認它是不是真的被當成時戳用。

## 8. ★ 靜態證明:`FUN_c0437140` 不是查表

使用者 2026-09-19 提的判準:**不要再追鏈子,去看拿到的東西本身能不能自成解析度。**
用已知的兩件事就封得掉,不需要上機。

全映像(seg0 + seg1,49 MB)搜相鄰字對:

```
3024 x 2010   OG3K 記錄尺寸      0 處   ← 不存在
2000 x 1334   OG2K 裁切尺寸      0 處   ← 不存在
3032 x 2012   p83 donor 原廠    12 處
2016 x 1344   OG2K 記錄尺寸     22 處   ← 感測器光柵,查表也給得出來

```

而 OG3K 實拍 DNG 的檔頭**就是 3024×2010**(`og3kcanvas.S` 檔頭記載,
2026-09-13 解檔驗證 `A001_036`:標頭 3024×2010、裁切 3008×2000 @ (8,5)、
StripByteCounts 9,117,360 = 3024×2010×1.5)。

檔頭由 `FUN_c06A5290` 從 `FUN_c0437140` 的產物寫出。**那個數字在韌體裡不存在,
所以只可能是 `og3kcanvas` 執行期寫進 canvas、再由這條鏈帶出來的。**

### 結論

`FUN_c0437140` 帶的是 canvas 的內容,**包括 hook 寫進去的**。

> **任何會改變 DNG 檔頭的東西,依構造必然改變這個查詢的答案。**
> 若不會,檔頭自己就錯了。

所以未來的自製規格(同樣在 `0xC043A19C` 寫 canvas)一樣看得到。這是除了
直接讀檔案之外最強的保證,而且沒有 §3(b) 那種「把 OG3K 的規則搬進陀螺卡」的耦合。

### 順帶訂正 §7 的測試計畫

§7 說「OG2K 錄影中該讀到 2016×1344」可以當驗證 —— **那是個爛測試**,
2016×1344 在表裡有 22 處,查表也湊得出來,分不出真假。要分辨得用 OG3K 的
3024×2010。**不過本節已經用靜態證掉了,那個測試不再需要。**

## 9. ★★ 解了:`kind = 2`,而且待機就答得出來

2026-09-19。`geomkind.py 2`,相機**待機中**(mode 8,沒在錄影):

```
ctx     0xC3074BE8
kind 2  out 0xC375DC34
        3024 x 2010     rest 0 0 3024 2010 8 5
```

**3024 × 2010 = OG3K 的記錄尺寸**,`8 5` = 裁切原點(3008×2000 置中)。
連續四次完全一致,沒有凍結。

對照 `kind = 3`:待機與錄影中都回 6064×4042(靜態全畫幅),200 筆無一例外。

### 正確的呼叫

```
owner = FUN_c0021C00()            → 0xC30751D4
ctx   = FUN_c0021C40(owner)       → *(owner + 0x5C) = 0xC3074BE8   ★ 要傳參數
        FUN_c0437140(&out, 2, ctx, 3)
        w = [out][0]   h = [out][1]        裁切原點在 [out][4]/[out][5]
        FUN_c022EDB0(&out, 2)     ← 不釋放每次漏 0xC0 bytes
```

物件佈局:`+0x00/+0x04` 尺寸、`+0x08/+0x0C` 0、`+0x10/+0x14` 尺寸、
`+0x18/+0x1C` 裁切原點。

### 為什麼這是對的答案

1. **不是查表** —— 3024×2010 在 49 MB 映像裡 0 處(§8),它是 `og3kcanvas`
   執行期寫進 canvas 的。查詢帶著它出來,所以**自製規格看得到**。
2. **零耦合** —— 韌體自己的函式,陀螺卡不需要知道 OG3K/OG2K 存在。
3. **待機就答得出來** —— 不必等錄影開始,所以 r39c 的「第 1-2 區塊就寫 JSON」
   早寫設計可以保留,不用改成收工後補。
4. 裁切原點也一併拿到,`DefaultCropSize` 想寫進 profile 也有料。

### 我走過的三個錯,都是同一類

| 錯 | 代價 |
|---|---|
| `0xC38250E4` 當成檔頭來源 | 那是靜態照片的單例,恆為 {0,0}(§6) |
| `FUN_c0021c40` 當成取時戳、傳 0 | 它吃參數,傳 null 讓 `FUN_c0436b80` 走過 null;**凍結一次** |
| `kind` 沒查證就兩個都試 | 配上 null context 正好踩中 kind 2 的分支;那次凍結是這兩個錯相乘 |

共通點:**把「看起來合理」當成「已經證實」**。三次都是使用者反問才停下來
(「想要零耦合」「我覺得這不可能吧」「6064x4042 很怪」),否則我會拿 null 指標
測出來的假數據去掛一個不需要的 hook。
