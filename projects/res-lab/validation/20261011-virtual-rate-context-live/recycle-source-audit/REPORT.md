# 94 張緩衝、寫檔通知與 SSD 資料位移：源碼核對

2026-10-11。持續錄製仍未修好。本輪沒有修改或安裝相機程式。

## 目前可以確認的結論

94 是原廠 RAW／描述子池的可用上限，並不是「累積 94 張才寫入」的門檻。
在保存的 1 MiB 寫入測試中，第一張已完成寫入、已發出 event 9，卻直到
238.774 ms 後才由錄影管理工作處理；期間這個工作又處理了 36 張標頭。
RAW 歸還分支和描述子釋放入口都出現在這個通知被處理之後。
池子在通知處理之前就已用滿並觸發 vbuf。

還有另一個關卡：event 8 要先由同一個錄影管理工作處理，下一張才會
排進 writer。因此不是只有「寫完後歸還慢」；連「下一張送去寫」也被
前面的標頭處理拖住。這是此次原生紀錄中直接可見的阻塞機制，尚不足以
指出與成功舊版本相比的唯一退化來源。

## 原廠程式的實際流程

本節位址以 `out/MAIN_c0000000.bin` 為準；反編譯文字在
`out/decomp/full/blk_c03.c`。函式名稱中的 vN 是反編譯器的虛擬方法編號。

| 原廠位址／函式 | 實際作用 |
| --- | --- |
| C0374268 / FUN_c0374268 | CinemaDNG 配置描述子時使用 96 槽池，要求剩餘量大於保留量；正常錄製最多 94 張在途。 |
| C0379E08 / vbuf | 無法取得所需緩衝時記錄 44445501 並停止；此處沒有「94 張觸發寫入」。 |
| C038BD98 / FUN_c038bd98 | event 5：準備逐張標頭，呼叫 C038C5F8，再交給 file creator。 |
| C037DD50 / XC_StillCreateFile__v2 | creator+1C 仍有目前張號時只放入待寫清單；+1C 為 -1 才呼叫 C0377008 排入 writer。 |
| C03A5348 / FUN_c03a5348 | 在真正進入 C069ADE0 寫檔之前發出 event 8。 |
| C0385760 / XC_StillRecCreateObs__v1 | 把接受／完成通知轉成 kind 2B 的 event 8／9，送到 MRecMgr。 |
| C03889E0 / XC_MovRecFunc__v3 | 同一個接收迴圈處理 event 5、8、9；沒有另一個專用回收消費者。 |
| C038C058 / FUN_c038c058 | event 8 呼叫 C037DF40(-1) 前進 writer；event 9 釋放檔案格式，再呼叫 C0377730 和 C0375030。 |
| C0376F20 / XC_StillCreateBase__v3 | 把 creator+1C 清成 -1，取待寫張，再呼叫 C037DD50。 |
| C03A55D0 / FUN_c03a55d0 | 寫入完成回呼只更新狀態並發出通知，沒有在這裡直接歸還 RAW。 |

原廠 queue wrapper C036D8E0 建立 attribute=1 的 mailbox。
追過原廠 SVC 表後，send 實作為 C00045B8（`blk_c00.c`）。其 attribute
bit 1 未設定時，把訊息接到尾端，確實是 FIFO。開啟優先排序時比較的是
message+4；這些訊息的 +4 都是 kind 2B，event 5／8／9 位於 +C。
因此不能靠直接開啟該 queue 的 priority attribute 來改善回收次序。

沒有安裝 queue 優先處理、直接 free、擴池或跨工作執行原廠回收的修補。
這些改法必須先保證控制／錯誤訊息順序與所有引用者已完成，否則會造成
還未讀完的 RAW 被覆寫。

## 保存的原生紀錄

`audit_recycle_path.py` 重讀四組 RECMGR／RECMGR2，使用 event 5 的世代、
張槽號和 RAW 位址配對，避免把重複使用的槽號當成同一張。
原始檔雜湊及逐張完整數據在 `traces.json`。

| SD 測試 | event 5 張數 | vbuf 前 RAW 歸還分支 | 首張 event 8 等待 | 首張 event 9 等待 |
| --- | ---: | ---: | ---: | ---: |
| native-280-finished | 94 | 0 | 129.826 ms | 224.682 ms* |
| native-280-bulk1-finished | 94 | 0 | 124.206 ms | 238.774 ms |
| native-280-v14-finished | 94 | 0 | 58.019 ms | 224.505 ms* |
| native-280-v14-gyrooff-finished | 101 | 7 | 9.145 ms | 13.521 ms |

\* 首張完成通知在 vbuf 之後發出，等待包含停止／排空流程，不能當成正常
錄製時的純 FIFO 延遲。

1 MiB 測試的首張（slot 83，RAW 53B00C00）時間線：

| 相對時間 | 事件 |
| --- | --- |
| 925.385 ms | 發出 event 8 |
| 931.741 ms | writer 返回 |
| 1049.591 ms | 管理工作處理 event 8 |
| 1049.636 ms | 下一張 writer 開始 |
| 1054.664 ms | 發出首張 event 9 |
| 1209.046 ms | vbuf，緩衝用滿 |
| 1293.438 ms | 管理工作處理首張 event 9 |
| 1293.680 ms | 首張 RAW 歸還分支 |
| 1293.700 ms | 首張描述子釋放入口 |

四組紀錄都有對應的 event 8／9 處理，沒有 C03A9580 的事件池不足警告。
觀察到的是延遲，不是這四組通知永遠遺失。原廠 send 回傳值沒有記錄，
不能據此保證所有未保存的試驗也沒有發送錯誤。

**更正先前標籤：99990005 是 C03A55C0 的 writer 返回紀錄。**
先前報告把它稱為 submitted，只能視為舊欄位名稱；不是 writer 開始、
實際媒體提交或持久化完成的時間。開始為 99990000，I/O 前為 99990004。

DEBUG 會改變排程；這些毫秒值不能當成無紀錄模式的效能基準。
RAW 歸還分支紀錄在 allocator 呼叫之前，22220000 也只是釋放函式入口。
完整 pool 返回要另看原廠池讀回；已有停止後 96/96 的觀察，但不足以排除
所有其他型態的記憶體洩漏。Gyro OFF 試驗有 7 張在 vbuf 前歸還，也證明
不能概括成「所有版本都完全不釋放」。

## SSD 批次寫入保留 RAW 位址

這輪追到先前尚未確認的實際後端：

`C063F048 -> volume+483C -> C0670338`。
volume 的五個工作函式由 C0644E30 經 C01EB8E0、C01F03E0、C01F4AB8、
C066CF98、C06703D8 取得。C0670338 並不複製影像，而是把實體 RAW 位址
及長度存入 C42F77D8 的 scatter 清單。C0670690 再逐段消費，最多每段
65536 bytes。C063F140 在批次媒體操作之後發出完成回呼。

所以寫入已接受、writer 返回、媒體完成、管理工作歸還 RAW 是不同時刻。
在媒體完成前強制歸還描述子，會讓 SSD 引用的位址指向被下一張覆寫的資料。

`test_native_recycle_contract.py` 實際執行上述原廠機器碼，三項離線核對通過：

1. FIFO 的 event 8／9 保留在前面 event 5 之後；priority 模式同 kind 也不改順序。
2. 前一張仍占有 creator+1C 時，下一張不送 writer；原廠 event 8 的前進呼叫後才送。
3. SSD 後端保存來源位址，1095168 bytes 分成 17 段；此受控輸入沒有額外插入前綴。

韌體 SHA 在 `native-arm-contract.json`；初始測試把我們的新 hook ABI 規則
套到原廠內部四位元組堆疊，以及少涵蓋一段 Thumb 返回尾端，故失敗。
修正測試邊界後三項通過，原廠程式未修改。初始與最終紀錄均保留。
這不模擬真正的排程、快取、USB TRB、DMA 或 SSD；也尚未證明錯位在何處形成。

## 最新 SSD 檔案已存在實際錯位

來源 `/Volumes/Untitled/CINEMA`，原檔未修改。
`preserve_h2_ssd.py` 保存每個檔案的 SHA256，以及第一／中間／最後原檔、
WAV／XMP。`../h2-ssd-host-evidence/manifest.json` 是完整清單。

| 段落 | DNG 數 | TIFF 在 0 | TIFF 在 19456 | TIFF 在 65536 |
| --- | ---: | ---: | ---: | ---: |
| A001_277 | 1 | 1 | 0 | 0 |
| A001_278 | 94 | 29 | 22 | 43 |
| A001_279 | 94 | 29 | 22 | 43 |

位移前的 bytes 都是 0。兩段的**數量分布相同**，每段內出現的位置相差
3 張，不能稱為每張的位置完全相同。壞檔無法從 byte 0 當正常 TIFF 開啟。
對位移後的 TIFF 做相對標籤解析，得到 1008x672、12-bit、Compression=1、
crop992x662@(8,5)、FrameRate30000/1001、StripOffset78848。
這個相對解析不是修好的 DNG，也未修改影像。

19456 恰好等於 DNG 原廠保留標頭 0x18000 減實際標頭 0x13400；65536
也與 SSD scatter 每段上限相同。這些是待驗證的對齊線索，不是已證明的
因果。不能只憑 TIFF 位移就斷言整個 RAW 一起平移，或宣稱某個尾端已永久遺失。

對照逐檔讀取前 128 KiB：先前 SSD A001_274(136)、275(128)、
276(134) 的 TIFF 全在 0；舊成功 A001_193 的 4809 張也全在 0。
其中 A001_276 的 v15 已確認 CPU 標頭與本地 4 MiB guard 生效；H2 v16
保留原廠 DMA 標頭與 64 MiB。參數、載體格率、批次量也不同，故不能
把這個對照直接歸因於 CPU／DMA 單一因素。

`ogc.c` 的 m12_high_entry 要求 S.VRATE 為23976／27972；H2 的 S.VRATE=0，
雖然 capture engine／sensor 實際239.76，仍跳過 CPU 標頭與批次 guard。
這是控制判斷沒有涵蓋 capture/native-rate 分離的具體缺口，未在本輪修改，
避免把原本要求的歷史參數對照偷偷改成另一套試驗。

這三段手動 SSD 試驗沒有完整 HDMI 或原生停止紀錄。使用者報告秒停，
94 個檔案本身不能獨立證明 native vbuf 或實際 sensor cadence。

## 下一項需要的直接證據

同一個確定版本／相同 H2 參數下，取得 header copy 的原始來源、RAW 目的、
writer 輸出 segment 起點，以及 SSD scatter 原始位址，才能分辨錯位是
在 header copy 前、writer 建段時、或 USB 消費 scatter 之後形成。
回收排程的修補也必須在這個引用所有權規則內進行，不能把「可用 94 張」
改大或提前 free 當作已修好。
