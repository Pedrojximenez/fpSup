# Sensor Lab RAW14 gain and receiver audit

2026-10-04 · Ver.5.02 firmware SHA-256 `92a8ee993f6c3d66c251e88d45a2ccd5135c6cf7342717784321c2ed506e2fb4`. Read-only audit of the stock image and current Sensor Lab source. No camera measurement or card change was made here.

## Gain dispatch

Sensor Lab maps its private profile ID 87 to a dynamically declared profile (`imx410_plan.py` `PRIVATE_PROFILE`). Stock `FUN_c043a1c8 @ 0xC043A1C8` assigns ID 87 no raw-movie flag. Sensor Lab therefore arms `og3kgs.S` at `0xC03A6DD8`: when CUSTOM `FLAG == 1`, it returns true only to the gain-dispatch caller of `FUN_c03a6dd8`, leaving the other consumer (`FUN_c03a66b0`, sensor reprogramming) on the stock path.

Stock `FUN_c039dde8 @ 0xC039DDE8` then reads the active format's `eRawBitType` at `FUN_c03ab240(param_1[2]) + 8`. Its raw-movie branch maps enum 4 to gain state 5, enum 3 to 6, enum 0 to 7, and **enum 1 (RAW14) through default to state 5**. The selector is the capture format, not the IMX410 mode ID. Subject to the CUSTOM hook actually firing at runtime, the same state applies to all eight RAW14 donors. State 5 is named `movie_raw_8bit`; this name does not prove its gain ladder is suitable for RAW14.

`XC_ImageSensorIMX410::v30 @ 0xC03239C8` switches state 5 to HCG at nominal ISO 640, state 7 at 3200, and state 4 never. `v31 @ 0xC0323A78` also uses different ISP digital-gain ladders for states 5 and 7. Both thresholds can be modified by per-unit OTP calibration. The prior OG3K measurement of a 2.675 EV shift and different `BaselineExposure` after correcting state 3 to state 7 used **RAW12**; it must not be assigned as a measured RAW14 loss. Nor is forcing state 7 automatically correct for 14-bit data: the stock RAW14 still path uses the 640-class threshold, while DNG exposure/black calibration and highlight behavior remain unmeasured for this movie path.

## Eight stock RAW14 receiver records

The receiver table is `0xC0B5C638`, 70 records of `0x38` bytes, indexed by the selected sensor mode. `FUN_c0320ab0 @ 0xC0320AB0` resolves the mode ID with `FUN_c0320f60` and passes that record to `FUN_c032d5e0 @ 0xC032D5E0`. The latter copies receiver `+0x19` into its local descriptor `+0x0B` (ARM `0xC032D674/678`) and receiver `+0x04` low byte into descriptor `+0x11` (`0xC032D6A8/AC`), then sends the descriptor to `FUN_c0635d40` and `FUN_c0635d58`. Thus selection of a RAW14 donor by the picker reaches its **own** stock receiver row; no current Sensor Lab hook changes these two receiver bytes.

| RAW14 modes | Stock receiver `+0x04` low byte | Stock receiver `+0x19` | Known context |
|---|---:|---:|---|
| M6, M95, M100, M122 | `0x08` | `0xC0` | Movie-style receiver row; Julien R120 used M100. |
| M0, M141, M129, M144 | `0x00` | `0x00` | Still-origin receiver row; not yet validated for RAW14 movie. |

These are exactly the two `(0x08,0xC0)` and `(0x00,0x00)` patterns found among all 70 Ver.5.02 receiver rows. In the hardware builder `FUN_c0632108 @ 0xC0632108` (and the second channel `FUN_c0632db0 @ 0xC0632DB0`), descriptor `+0x11 == 8` selects the `0x4444` branch at `0x300F020C`/`0x300F220C`; value 0 selects a different branch. Descriptor `+0x0B` contributes to `0x300F0244`/`0x300F2244`. The effect on pixel black level is an inference from the register path and the R120 analysis, **not** a measured RAW14 clip. RAW12 open-gate modes have recorded with the still-style row, so this table difference alone does not establish that RAW14 recording fails.

Copying the whole M100 receiver record to other modes is unsafe: its geometry and window fields differ. A possible future, conditional adapter would change only the two bytes in the **temporary 0x44-byte descriptor** after `FUN_c032d5e0` has copied all row fields, immediately before the first hardware call (`0xC032D870`). It must check CINE, CUSTOM, native RAW14, the exact selected mode ID/recipe, and only M0/M141/M129/M144; pass through all other contexts. Do not edit the shared stock table or change still capture. Even this two-byte adapter is a test hypothesis until its hardware and DNG effects are measured.

An [isolated candidate](../../../open-gate/build/raw14_receiver_candidate/receiver_descriptor.S) now implements that descriptor-only change; the normal Sensor Lab plan and card builder do **not** reference it. The [Unicorn test](../../../open-gate/build/raw14_receiver_candidate/test_receiver_descriptor.py) executes stock `C032D5E0` from its entry through the original two channel call sites, stubbing only memset, settings getters, manager lookup and the receiver hardware calls. Its [saved result](receiver_candidate_unicorn.json) confirms that M0/M141/M129/M144 change exactly descriptor offsets `0x0B` and `0x11`, while M6/M95/M100/M122, a RAW12 control, six non-target guards, the shared 70-row table and recipe remain unchanged. Both channels receive identical descriptors. Four injected variants (all modes, skipped native-bit guard, missing `0xC0`, wrong offset) were rejected by the same assertions. This proves the narrow ARM hook behavior in emulation, **not** safe MMIO configuration, sensor output, black calibration, file writing or recording on a camera. In particular, calling native settings getters inside receiver setup still needs a reentrancy audit before any integration.

**Review decision, 2026-10-04:** the descriptor-only hook and continuation behavior are sufficient as an offline candidate. RAW14 pixel black and highlight response are unmeasured, and the settings-getter call context is not yet proved safe. The candidate remains outside r86 and all installable cards until those questions are resolved.

## Minimum validation before claiming RAW14 exposure is correct

1. Run the stock receiver-descriptor builder offline for all eight modes and both channels, capturing the 0x44-byte descriptor at `FUN_c0635d40`/`FUN_c0635d58`. Assert that the four movie modes are unchanged; test the proposed two-byte override only for the four still-origin modes; compare every other descriptor byte to stock. Re-run with CUSTOM off and RAW12 to prove pass-through. Check original `FUN_c0632108`/`FUN_c0632db0` on scratch MMIO to confirm expected branch selection without hardware writes.
2. On a stable camera build, observe gain state **without changing it**. The existing `gsobs.S` shows the useful counters at `v30` (state and requested relative gain), but its old cave addresses overlap the current card. Relocate equivalent bounded logging into the shared USER allocation. Record active bit enum, mode ID, state, HCG result/register `0x05E1`, analog code `0x003D/0x003E`, both ISP digital-gain contributions, and a timestamp. Read the log after capture; the existing USB/card-I/O interaction makes live USB observation during recording unsuitable.
3. For each mode that can actually record, use matched dark and flat pairs at fixed shutter/aperture/light across ISO 100, 640, 800, and 3200. Check real RAW14 DNG `BitsPerSample`, `WhiteLevel`, `BlackLevel`, `BaselineExposure`, pixel black median/variance, clipping point, and lowest two data bits. `FUN_c02ca190 @ 0xC02CA190` derives the DNG BlackLevel tag from sensor state `+0x208`, scaling it `<<2` when bit depth is 14. A plausible tag (e.g. 1024) alone cannot prove the actual pixels were correctly clamped. Compare the four still-origin modes to a movie-style RAW14 control at the same illumination and native gain state. Full-height M0/M141 additionally require the separate validated low-rate control path before any recording claim.

**Current conclusion:** all eight stock modes are valid RAW14 sensor selections, but no on-camera RAW14 gain, black-level, or highlight result exists for this card. The six currently selectable modes have only picker/REC-preflight emulation; M0/M141 lack a selectable sub-20p recording path. The four still-origin modes have an additional receiver-configuration question. Do not generalize Julien's M100 result or the RAW12 OG3K exposure measurement to all eight modes.
