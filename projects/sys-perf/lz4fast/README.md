# lz4fast:UI 圖示 LZ4 解壓器替換(2026-10-19，離線)

目標：`.xci` 圖示的 LZ4 解壓變快，**輸出與原廠逐位元相同**，不改任何畫面行為。
狀態：離線完成，unicorn 對拍通過。**沒有上機、沒有寫卡、沒有 commit。**
**[靜]** = 反組譯；**[模]** = unicorn 實跑；**[推]** = 推論。

## 1. 原廠解壓器 [靜]

- 解壓物件 vtable 在 `0xC2DFA1B8`，指向 frame 解碼 `C05A7E50`(r0 ctx、r1 src、r2 長度、r3 dst、第 5 參數 dst 大小)。
  它讀 magic(`0x184D2204`)、`C05A7570` 解析 frame 描述，**只呼叫一次**區塊解碼 `C05A7630`(`C05A7EE0` 那個 `bl`)，
  接著讀 end mark 和(FLG&4 時的)content checksum，兩者都不檢查。
- `C05A7630(ctx, out_stream, in_stream, &FLG)`：stream = `{base, cur, size}`，回傳固定 0。
  - 讀 u32 區塊大小 `bs`(**最高位元的「未壓縮」旗標不檢查**，照樣當 LZ4 解)。
  - 迴圈條件：`pos(in) - start < bs`(無號比較)。`pos` = `C04D1408`，等於 `|cur - base|`(帶號判斷)。
  - token → 字面長度(`C05A7510` 處理 15 + 255 串)→ `C04D11E8` **一次一個位元組**地複製 → 輸入前進。
  - 用完 `bs` 就結束(最後一段只有字面)；否則讀 u16 offset、match 長度 +4，從 `out->cur - offset` 逐位元組往前複製
    (重疊時就是標準 LZ4 的重複語意；offset 0 會把目的位元組原樣寫回)。
  - FLG bit 0x10 時多讀一個 u32(block checksum，不檢查)。
  - **沒有輸出上限、沒有輸入上限**。每個位元組的複製都要讀寫一次 stream 結構。
- 呼叫者：`C05A7630` 只有 `C05A7EE0` 這一個 `bl`，沒有任何指標參照。

## 2. 替換 [靜]

- `lz4fast.S`：同一個 ABI，逐條重現上面的語意(含 `|cur-base|`、32-bit 進位、FLG 0x10、不檢查邊界)。
- 複製：位元組往前複製的語意下，若 `d = dst - src`(無號)≥ 16，一次搬 16 B 結果相同。
  `0 < d < 16` 時輸出以 d 為週期，先逐位元組寫 `D - d` 個(D = d 的倍數中第一個 ≥ 16 的)，之後改從 `dst - D` 讀，一次 16 B。
  `d == 0` 保留逐位元組。
- **只用整數暫存器，不用 VFP/NEON**：解壓可能在任何任務跑，不確定每個任務都開 VFP。
  非對齊的 `ldr/str/ldrh` 和原廠一樣用在同一批緩衝區上(原廠 `C04D1320`、`C04D12F8` 本身就做非對齊讀)。
- 控制區在映像開頭：`+0` enable(0 = 直接跳原廠 `C05A7630`，什麼都不碰)、`+4` 呼叫次數、`+8` 輸出位元組數。
- 修補：`C05A7EE0` 的 `bl C05A7630`(原字 `EBFFFDD2`)改成 `bl` 到 cave 內 8 B veneer(`ldr pc,[pc,#-4]; .word lz_block`)，
  veneer 要在 ±32 MiB 內(cave arena `C072E064..C072EFB4` 可以)。詳見 `patch.json`。

## 3. 結果 [模]

`python3 -B test_lz4fast.py`(約 50 秒)：

| 測項 | 結果 |
|---|---|
| 全部 2005 張 `.xci` 經真實的 `C05A7E50` 解碼(原廠 vs 修補後) | 回傳值與輸出緩衝區(含前後 256 B 護欄)逐位元相同，0 不符 |
| 799 個合成案例：offset 0–17/31–33/64/255/256/4096 × match 長度 4–600、字面 0–1000、隨機串流、FLG 0x10、截斷與謊報 bs、`base > cur`、輸出與輸入重疊(in-place ±1…64)、offset 超出輸出起點 | 整個輸入輸出區、兩個 stream 結構、r0、r4–r11、sp 全部相同，0 不符 |
| enable = 0 | 50 張對拍相同，快速路徑 0 次呼叫 |
| `--mutate` 8 個故意改壞的版本(phase 1、255 延伸、abs、FLG、尾巴、+4、門檻 16、字面前進) | 8/8 全部抓到 |

指令數(60 張隨機 + 最大 3 張，整個 `C05A7E50`，含 frame 解析)：

| | 指令 | 輸出 | 指令/位元組 |
|---|---|---|---|
| 原廠 | 19,465,389 | 1,480,484 B | 13.15 |
| lz4fast | 2,548,556 | 1,480,484 B | **1.72**(約 7.6×) |

(unicorn 指令數，不是時間。)

**測試踩到的坑**：unicorn 改程式碼的 `mem_write` 不會作廢已翻譯的區塊，所以「同一台模擬器先跑原廠、再改 bl」會一直跑原廠，
對拍永遠相同。現在原廠與修補版用兩台各自的模擬器，並斷言快速路徑的呼叫次數等於圖示數。

## 4. 上機驗證(未做)

1. 依 `patch.json`：配置器拿 8-byte 對齊區放 `lz4fast.bin`、cave.claim 8 B 放 veneer，讀回確認，`C000E91C` → `C000EABC`。
2. 讀回 `C05A7EE0` 必須是 `EBFFFDD2` 才改；改後讀回，再 `C000E91C` → `C000EABC`。宣告 4-byte 區段讓關機寫回。
3. 驗證：
   - 換頁(選單、QS、播放)截圖，與未修補時逐像素比較。
   - `+4` 呼叫次數有增加 → 真的有走到。
   - 原廠 UIC 計時 `uicMgr+0x198` bit0 的換頁 Load_Start/End，開關前後比。
4. 回退：寫 enable = 0(資料字，下一次呼叫生效)，或寫回原字。程式區保留到關機(可能有解壓正在裡面)。
