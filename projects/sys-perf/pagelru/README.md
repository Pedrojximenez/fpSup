# pagelru：畫面版面保留最近 N 個(2026-10-19,離線)

目標：A → B → A 換畫面時，不再把 A 整組重新解析。**沒有上機、沒有寫卡、沒有 commit。**
**[靜]** = 反組譯看到；**[模]** = unicorn 跑出來；**[推]** = 推論。

## 1. 先更正前提 [靜]

`UI_DRAW_CPU_COST.md` 說「頁面資源只快取一格(`C05663E8`)」。這個說法錯了：
- `UicResourceCache::v2`(`C05663E8`)要的名字來自 `C0565230`，它只會是三個之一：
  `QS_STILLlike` / `QS_CINE` / `QS_STILL`(表 `0xC2F2CBB4`，依相機模式)。
- 所以那一格是 **QS 版面的保活快取**，不是換頁快取；只在 CINE/STILL 切換時換。
  它正是 uishare 與 OG 操作的 RCACHE(`0xC37B7254`)。**不能、也不值得**在這裡做 LRU。
- 真正的換畫面在 uicMgr(`r7`)的 `C05DD540` 一段：
  - `C05DD5CA  bl C05D90F0(next)`：載入下一個畫面。
  - `C05DD670  bl C05D91A0(current)`：卸載原本的畫面。
  - 目前畫面在 `uicMgr+0x84C`、下一個在 `+0x850`、保留畫面在 `+0x848`(原廠已有的「保留一個」機制，未改)。

## 2. 版面載入 / 卸載語意 [靜]

| | 樹不存在(`[L+0xC]==0`) | 樹已存在 |
|---|---|---|
| 載入 `C05D90F0` | 解析(`C05E82F0` → `C05E6400`)、`C05D2E58` 初始化、`C05D9210` 收尾 | 參考數 +1、沿用；flag 1/2 時走一次 `C05D1F58` |
| 卸載 `C05D91A0` | — | 參考數 1:`C05D9250` 拆除，釋放樹，`[L+0xC]=0`;>1:只減 1(flag 2 時 `C05D2FA0`) |

- `[L+8]` 是名字，`[L+0xC]` 是樹，`[tree+0xC]` 是樹的參考數(`C05D00D8`)。
- 「樹已存在時載入」與「參考數 >1 時卸載」這兩條路，原廠每次開關 QS 都在走：QS 版面被快取多握一個參考。

## 3. 做法

兩個 Thumb `bl` 改成 Thumb `BLX` → 8 B ARM veneer → `pagelru.bin`(712 B，ARM，位置無關，只用整數暫存器)。

- **`pl_unload(O)`**(取代 `C05DD670` 的卸載):以下全部成立才接手 O 的參考、不呼叫卸載，否則原廠卸載照常：
  - 已啟用，且不在錄影(`C00178D8` +0x9C);
  - O 有樹，且樹的參考數為 1，也就是原廠這一呼叫會釋放它；
  - 名字不以 `QS_` 開頭：QS 版面屬於 RCACHE/uishare/OG,永遠不碰。

  滿了就先用原廠卸載淘汰最舊的，再把 O 放到最前面。
- **`pl_load(L)`**(取代 `C05DD5CA` 的載入):
  1. **先**呼叫原廠載入。樹還在，所以走參考數 +1 的沿用路。
  2. 若 L 在表裡，就把它移出，再呼叫一次原廠卸載交回我們的參考。這時參考數 ≥2，不會拆除。

  效果是這組「沿用載入 + 參考數 >1 卸載」跟原廠開關 QS 時走的一樣。停用時也照做，所以參考不會被遺留。
- **停用或錄影中**：下一次換畫面時，用原廠卸載放掉全部。

**控制區**(body+0):

| +偏移 | 欄位 |
|---|---|
| 00 | `PLRU` |
| 04 | enable(出貨 0) |
| 08 | 容量(0..4，預設 2) |
| 0C | 目前張數 |
| 10 | 命中 |
| 14 | 接手 |
| 18 | 淘汰 |
| 1C | 走原廠 |
| 20 | 最後原因 |
| 24 | 清空時放掉的張數 |
| 28 | 4 格(`[0]` 最新) |

最後原因：1 停用、2 錄影、3 空、4 沒樹、5 參考數≠1、6 QS、7 已在表、8 容量 0。

## 4. 測試 [模]

`python3 -B test_pagelru.py`：10/10 通過。`--mutate`：7/7 突變都被抓到。

**怎麼跑**：
- 真實映像，兩個站點寫成真正的 Thumb `BLX` 編碼，veneer 放在 cave arena 裡，所以 BLX 的距離檢查是真的。
- 每次換畫面都**以 Thumb 狀態執行韌體自己在站點的那條指令**，停在下一條。
- 檢查：回到 Thumb、sp 與 r4–r11 還原、呼叫韌體時 sp 8 對齊。進入時故意給 sp≡4。
- 原廠的 `C05D90F0`/`C05D91A0`/`C00178D8` 用 §2 的參考數模型代替。完整 UI 解析無法在相機外跑，**畫面像素沒有比對**。

**情境**：

| 情境 | 結果 |
|---|---|
| A→B→A | 原廠解析 3 次，新版 2 次，命中 1 |
| LRU 順序與淘汰 | 正確 |
| QS 版面 | 從不保留 |
| 被別人多握的版面(參考數 >1) | 不接手 |
| 錄影中 | 放掉全部 |
| 停用時 | 事件序列與原廠完全相同 |
| 停用後下一次換畫面 | 放掉全部 |
| 載入失敗 | 保留參考，之後仍正確交回 |
| 容量 0 或 >4 | 容量 0 走原廠，>4 截在 4 |
| 60 組隨機換畫面 | 每步不變量都成立：目前畫面有樹、保留的參考數正確、沒有洩漏、不超過容量；清空後存活的樹與原廠相同 |

**突變**(全部抓到)：
- 不排除 QS
- 不檢查參考數
- 命中後不交回參考
- 先卸載再載入(會釋放)
- 不淘汰
- 錄影不清空
- 容量 0 不擋

## 5. 相容性結論

- **站點沒有重疊**：repo 裡的 sup 沒有人碰 `C05DD5CA` / `C05DD670`；`.BIN` 二進位掃描也沒有。
- **掛在 `C05D90F0` 入口的 sup 仍正常**(uishare `qs_layer`、OG `ui_layout`、res-custom `ogc_shims`)：
  - 我們是**呼叫**它，不是繞過它。每次換畫面仍然各呼叫一次載入，它們看到的呼叫序列不變。
  - 它們只對「快取握的 QS 版面、參考數 1、不是目前或保留畫面」放手。QS 版面我們從不保留，所以條件不受影響。
- **掛在 `C05E6400`(解析記錄層)的 sup**：被保留的畫面不再重新解析，所以它們注入的內容維持第一次解析的結果。
  這跟原廠 QS 版面一直以來的行為一樣。若某個 sup 期望「每次開頁都重新解析才更新」，那頁會停在舊內容 [推，沒找到這樣的 sup，未上機證實]。
- **無法離線保證的行為差異**：
  - 被保留的畫面沒有經過原廠的拆除與重建，畫面內的狀態不會回到初始值，例如捲動位置、動畫影格、Lua 設的可見性。
  - 原廠的 QS 每次都是這樣沿用的，所以 UI 框架支援這種用法，但**其他畫面是否也都正確，要上機截圖比對才能確定**。
- **記憶體**：每棵樹多大不知道。容量預設 2、上限 4；錄影時放掉全部。沒有做低記憶體偵測，原因見記憶 allocator-not-across-recording。
- **CPU**：被保留的樹仍是「已初始化」狀態，可能繼續收到變數通知；QS 一直是這樣。要上機量待機 CPU 是否變高。

   - `C05DD5CA` 不是 4 對齊：關機還原要宣告 `C05DD5C8..C05DD5CF` 8 B，兩個字都填原廠值。`C05DD670` 是 4 對齊。

   - 原廠換頁 log 的 Load_Start/End(`log act GUI`)。
