# alphalut:`C0563BA8` 的 NEON 版(2026-10-20，離線)

**沒有上機、沒有寫卡、沒有 commit。** [靜] = 反組譯；[模] = unicorn 實跑；[推] = 推論。

## 1. 它在做什麼 [靜]

- `C0563BA8(r0 = 圖層 buffer(u16), r1 = rect {x,y,w,h}, r2 = stride(像素))`,ARM。
- 對矩形內每個 ARGB4444 像素做 **un-premultiply**:`A` 不變，R/G/B 各查表 `0xC0D0D684[A*16 + c]`。
  表就是 `T[a][c] = a ? min(15, 15c/a) : 0`(256 格全部核對過)。
- 迴圈：每列先處理一個未對齊的頭像素，再一次兩像素(32-bit 字)，最後一個尾像素。
  「跟上一個字相同就直接寫上次結果」只是加速：映射是純函式且 `f(0)=0`,所以全部重算位元組相同。
- **唯一呼叫者** `C0561734`,在 UIC drawer `C0561198` 裡：把這一輪所有 render 記錄的矩形用 `C0563AB0` 取**外接矩形聯集**,
  畫完後對聯集整塊做 un-premultiply。所以面積大的原因是「聯集」:兩個離很遠的 dirty 元素(例如時間碼 + 音訊表)會圈出一大塊。
- 兄弟函式 `C0563D50`(premultiply,表 `0xC0D0D784`,`T = a*c/15` 取整)只被 `C0560F08` 呼叫一次，不在熱點裡，沒換。

改成「逐 rect 處理、不處理聯集中間」**不建議**:聯集裡沒被這輪畫到的像素若也被處理，等於原廠本來就在重做這件事;
要省掉它得先證明 UIC 會重畫整個聯集或中間像素本來就是 straight alpha——沒證明，改了可能讓顏色漂移(行為改變)。

## 2. 替換 [模]

- `al_unpremul` 與原廠同 ABI。一次 8 像素:`vld2.8` 拆高低位元組 → `A = hi>>4` → 用 `vtbl` 從 16 格表取 `K[A]`(低、高位元組各一張表，
  `vzip` 成 u16)→ 每個通道 `min(15, (c*K)>>8)`(`vmul.i16` + `vshrn #8` + `vmin`)→ `vsli` 組回 → `vst2.8`。
  `K = 0,3840,1920,1280,960,768,640,549,480,427,384,350,320,296,275,256`,對 256 格全部等於原廠表(build 與測試都檢查)。
- 8 像素全 0 的塊直接跳過(結果不變，也不弄髒 cache line)。每列不滿 8 像素的部分用原廠同一段純量碼、同一張表。
- `w <= 0` 或 `h <= 0`(原廠會出現「未對齊 w=0 的列碰兩個像素」這種怪行為)、或 enable=0 → 原封尾跳原廠函式。
- 只用 d0–d15,自己保存 d8–d15(TK-OS 換任務/進中斷只存 d0–d15)。472 B,位置無關。

- `--mutate`:6/6 抓到(K 表錯一格、少 vmin、尾巴少一像素、0 塊指標少走、row stride 錯、少存 d8)。

## 4. 修補(`patch.json`)

- 一個**程式碼字**:`C0561734` 原字 `EB00091B`(`bl C0563BA8`)→ `bl` 到 8 B veneer(`ldr pc,[pc,#-4]; .word al_unpremul`),
  veneer 要在 ±32 MiB 內(cave arena `C072E064..C072EFB4` 可)。寫完要 D-clean + I-inv;關機還原宣告這 4 bytes。
- 控制區(+0):`'ALUT'`、版本、**+08 enable(預設 1)**、+0C calls、+10 NEON 塊數、+14 跳過的 0 塊、+18 fallback 次數。
