# 在畫面正中央畫一條穩定的橫線(純 shell 指令)

2026-09-20。**實機驗過**(LCD 用相機自己的截圖、HDMI 用 AVerMedia ExtremeCap UVC 擷取)。
[C] = 反編譯、[M] = 這次實機量到。

> 相關:[`SPLASH_BAND.md`](SPLASH_BAND.md)(OSD 圖層貼圖)、
> [`DISPLAY_OSD_MAP.md`](DISPLAY_OSD_MAP.md)(OSD 繪圖 API)。這份走的是**第三條路**,
> 跟 OSD 圖層無關。

---

## 0. 答案

```
display faceframe -8 288 2000 1     # LCD 正中央(第 341 列)
display faceframe -8 456 2000 1     # HDMI 正中央(第 540 列)
mem set 0x30190400 <原值 & ~2>      # 關掉內框(HDMI 那組 slot)
mem set 0x30190410 <原值 & ~2>      # 關掉內框(LCD 那組 slot)
display faceframe                   # 關
```

結果:**一條 1 px、橫貫整個畫面寬度、乾乾淨淨的線**,沒有別的東西。
畫的是顯示控制器的硬體矩形 marker,不在 OSD 圖層裡,GUI 重繪洗不掉。

那三個看起來很怪的數字都是必要的(§5 有完整說明):

| | 為什麼 |
|---|---|
| `x = -8` | 矩形的**左右直邊在 h=1 時會畫滿整個畫面高度**。`-8` 把左邊推出畫面外 |
| `w = 2000` | 同理把右邊推出去(超過畫面會夾到邊緣外) |
| 兩條 `mem set` | 一個 rect 會畫**兩個** slot(外框+內框)。`h=1` 時內框高度是負的,韌體**不更新它也不關它** —— 於是上一次的內框就一直掛在畫面上(就是那個橘色方框) |

**一條指令沒辦法同時讓兩個輸出置中** —— 兩個輸出的偏移量差 31 列(§3)。

## 1. 機制  [C]

`display faceframe` 的 handler `0xC03E4840` → `XC_DisplayFaceFrame` 單例 `0xC3435A54`
→ renderer → paste 物件 → HAL `FUN_c00e9fd8` → `FUN_c00e14f8` → 寫顯示控制器暫存器。

- `mgr+0x14 = 1` 是**強制開旗標**:相機自己的更新路徑(`FUN_c02efb68`)看到它就不會把框拆掉。
- renderer 是 **`XC_DisplayFaceFrameDoubleFrame`**([M] `mgr[1] = 0xC3436108`,
  `+0x1c` vtable = `0xC0B52FF8`):一個 rect 其實畫**兩個** slot ——
  外框 `(x, y, w, h)` 與內框 `(x+2, y+2, w-4, h-4)`(`FUN_c02f9a38`)。
  `h=1` 的時候內框高度變負 → 不畫,但 HDMI 上偶爾會留一條直的殘影(§5)。
- **最小尺寸 16**([M] `0xC343616C`):只在 **w < 16** 時才會把 w/h 一起撐成 16 並重新置中。
  所以 `w=1024, h=1` 不受影響。
- 參數就是 help 寫的 `rect{ 0 1 2 3 }` = `<x> <y> <w> <h>`;不帶參數 = 關。

## 2. 座標空間  [M]

paste 物件 `+0xc` 指到的 `{srcW, srcH}` 實機讀到 **`{0x400, 0x2AA}` = 1024×682**
(就是 UI/OSD 的畫面尺寸)。`FUN_c00e14f8` 會用各輸出自己的 dispW/dispH 換算,
但**淨結果兩邊都是斜率 1、只差一個偏移**:

| 輸出 | 畫面尺寸 | 換算 | 正中央的 y |
|---|---|---|---|
| LCD(相機截圖) | 1024×682 | `x_scr = x`、`y_scr = y + 53` | **288** → 第 341 列 |
| HDMI 1080p | 1920×1080 | `x_scr = x + 150`、`y_scr = y + 84` | **456** → 第 540 列 |

量法(兩點,皆 [M]):`display faceframe 200 100 600 300` 的外框 ——
LCD 量到 x 200..799、HDMI 量到 x 350..949 / y 184..483;
`0 456 2000 1` 預測 HDMI 540 / LCD 509,實測**兩個都分毫不差**。

- LCD 的 53 是上方黑邊(682 − 576 = 106,上下各 53);可用 y 範圍 **0..575**,
  再大就夾在第 628 列(畫面下緣)。
- w 給超過畫面(例如 2000)會夾到邊,拿來畫滿版橫線最省事。
- **HDMI 的 y 偏移比 LCD 多 31 列**,這就是同一條指令兩邊位置不同的原因。

## 3. 自我驗證的迴路(不用眼睛看)  [M]

**相機自己的截圖會把硬體 marker 拍進去** —— 這點原本以為做不到(marker 不在 OSD 圖層),
實測是可以的,所以整個校正完全可以在主機端閉環:

```python
sh('key CAPTUREON'); sh('key CAPTUREOFF')          # 約 2 秒落檔
sh(r'dir \DCIM\100SIGMA')                          # 取最後一個 SS__nnnn.JPG
# getfile.py <remote> <local> --size N
```

截圖是 1024×682,線就是一整列全黑的像素,`numpy` 一行就量得出來。
HDMI 那邊用擷取卡:`ffmpeg -f avfoundation -i "AVerMedia ExtremeCap UVC" -frames:v 20 ...`
(**第一張常常是黑的,抓 20 張取最後一張**;用裝置**名稱**不要用索引,索引會抓到別的攝影機)。

## 4. 硬體暫存器圖(0x30190xxx)  [C]+[M]

指標表在 seg1,值是真的 MMIO 位址,實機確認這一塊**讀得到**(不像 `0x3011xxxx` 全 0)。

| 用途 | slot 0..20 | slot 21..41 | 欄位 |
|---|---|---|---|
| 矩形 X | `0x30190480 + slot*8` | `0x30190550 + (slot-21)*8` | `(x1<<16) \| x2` |
| 矩形 Y | 同上 `+4` | 同上 `+4` | `(y1<<16) \| y2` |
| 顏色 | `0x30190420 + (slot>>3)*4` | `0x30190450 + …` | 每 slot 4 bits |
| 線寬/樣式 | `0x30190430 + …` | `0x30190460 + …` | 每 slot 4 bits |
| 致能 | `0x30190400`(group 0) | `0x30190410`(group 3→index 4) | bit = `slot % 21` |

- **只有致能暫存器讀得回來;矩形/顏色/樣式都是 write-only(一律讀 0)**。[M]
- `group = *(u8*)(0xC31D5C90 + slot)`;實機:slot 0..20 → group 0、slot 21..41 → group 3。
  `FUN_c00e6d90` 把 group≥3 的索引 +1,所以 group 3 用的是第 5 顆(`0x30190410`)。[M]
- `_DAT_c31d5a68 = 0` [M] → `FUN_c00e63b8` 走 else 分支,**用完整 slot 編號**(不取 %21)。
- 接 HDMI 之後兩組都會亮:LCD 與 HDMI **各用一組**,所以硬體上本來就是兩個獨立的矩形。
  這次實機:**slot 1/2 = HDMI、slot 22/23 = LCD**(poke slot 2 只影響 HDMI)。[M]
- 顯示時序:`0x30100500` / `0x30100530`(`&0x1FFF`+1 = 水平、`>>16 &0x1FFF`+1 = 垂直)。
  接上 HDMI 後 `0x30100500` 變成 **2200×1125**(1080p60 全時序),`0x30100530` 是 LCD 的 1260×715。[M]

### ⚠ 直接 poke 矩形暫存器不可靠 [M]
想「LCD 用指令置中、HDMI 用 `mem set` 另外擺」試了三次都失敗:
只寫 Y、Y+X 都讓 HDMI 那條線**整個消失**(致能位元還是 0x6)。
只有一次 X+Y 一起寫有畫出東西,之後重現不了。重下一次 `display faceframe` 就會恢復。
推測是硬體有 latch/commit 的順序要求,`FUN_c00e63b8` 之外還有沒追到的步驟。
**結論:用指令,不要 poke。** 要兩個輸出都置中目前沒有純 shell 的解。

## 5. 兩個會咬人的細節  [M]

### 橘色方框 = 沒被更新的內框
renderer 是 DoubleFrame,一個 rect 畫兩個 slot:外框 `(x,y,w,h)`、內框 `(x+2,y+2,w-4,h-4)`。
`h=1` → 內框高度 `-3` → `FUN_c00e14f8` 在 `local_2e < local_32` 那裡回 -1,
**既不寫它的矩形暫存器、也不清它的致能位元**。所以內框停在**上一次**的幾何,
而且 `display faceframe`(關)→ 再開,還會**原樣復活**(關只清致能,不清矩形)。

我就是這樣在畫面上留了一個 `display faceframe 200 100 600 300` 的橘色內框:
實測 HDMI 量到 (352..947, 186..481),正好是 `(202,102,596,296)` 套上 HDMI 偏移。

解法:下完指令後把內框那個 slot 的致能位元清掉 —— 外框 slot=2、**內框 slot=1**,
所以是 `bit 1`。要**讀-改-寫**(致能暫存器讀得回來),不要整顆寫死,
不然會順手關掉相機自己的 AF 框之類的東西。

### 左右直邊會畫滿整個高度
`h=1` 的矩形,上下橫邊正常是 1 px,但**左右兩條直邊是整個畫面高度**。
LCD 上它們落在第 0..5 欄和 1016..1023 欄(畫面最邊緣,不仔細看不到),
**HDMI 上右邊那條落在畫面正中間偏右(x≈1167),非常礙眼**。

解法:把 x1 推出畫面外。`display faceframe -8 …` —— **shell 的參數解析吃負數**
(`0xFFFFFFF8` 不行,會被當成大正數),配上 `w=2000` 讓右邊也夾出去。
實測 LCD 與 HDMI 的直邊都完全消失。

## 7. 粗線 / 色塊,以及在上面寫字  [M]

### 線寬 = 矩形高度,但**只有在 h ≤ 2×邊框厚度時才是實心的**

| h | LCD 實測 |
|---|---|
| 1 | 1 列 |
| 8 | 337..344,**8 列實心** |
| 16 | 333..348,**16 列實心** |
| 24 | 329..352,只有上下各 8 列 → **中間空心** |
| 32 | 325..356,一樣只有 16 列 |

邊框厚度來自**樣式尺寸暫存器**(這組**讀得回來**):

```
A 表  0x30190620 + idx*4        B 表  0x30190660 + idx*4        值 = h | (w << 16)
```

實機讀到(非零的才是有定義的樣式):

| idx | A 表 | 意義 | idx | B 表 | 意義 |
|---|---|---|---|---|---|
| 0 | 2201×1126 | **整個畫面**(HDMI 全時序) | 16 | 1261×716 | **整個畫面**(LCD 全時序) |
| 1 | 12×12 | 我們用的樣式(HDMI 邊框 12 px) | 17 | 8×8 | 我們用的樣式(LCD 邊框 8 px) |
| 2 | 6×6 | 內框用 | 18 | 4×4 | 內框用 |
| 3 | 3×0 | | 19 | 2×0 | |
| 4 | 0×3 | | 20 | 0×2 | |

所以 LCD 邊框 8 px → `h ≤ 16` 實心;把 `0x301906A4` 改成 `0x00200020`(32×32)、
`0x30190624` 也改成 32×32,`h=32` 就是**兩邊都實心的 32 px 黑色色塊**([M] 實測
LCD 325..356 共 32 列、HDMI 356..387 共 32 列)。

- paste 物件 `+9` 的**樣式編號**(外框預設 1)換成 0 → 尺寸變成「整個畫面」→
  **整片螢幕被塗黑**。這是個現成的全螢幕遮罩原語。樣式 5..11 全是 0,畫不出東西。
- ⚠ 改樣式尺寸是**全域**的:相機自己的 AF/臉部框也用樣式 1,會一起變粗。收工要還原
  (`0x30190624 = 0x000C000C`、`0x301906A4 = 0x00080008`)。

### 在色塊上寫字:`display text` 的位置**可以用 `mem set` 改**

這推翻了原本的假設。`mem set` **改得動程式碼區的立即數,而且立刻生效,不用清 I-cache**。

| 位址 | 原值 | 意義 |
|---|---|---|
| `0xC03E46A0` | `E3A05078` = `MOV r5,#0x78` | **文字 x**(畫面 x ≈ imm + 3) |
| `0xC03E4698` | `E3A08010` = `MOV r8,#0x10` | **文字 y**(畫面 y ≈ imm + 4) |
| `0xC0BB1208` | `0xFFFFF8B2` | 文字顏色(桃紅);`0xFFFFFFFF` = 綠 |

[M] 驗法:`0x10→0x60` 文字從 y20 掉到 y100(Δ80 = Δimm);`0x78→0xF0` x 從 123 移到 241。
`FUN_c03e4620` 裡那個 `{0,0,0x180,0x20}` 的矩形**不會裁切**,y 設到 328 照樣畫得出來。

ARM `MOV` 立即數是 imm8+偶數位 ror,所以不是每個數都寫得出來:
328 = `0x52 ror 30` → `E3A08F52`。

### 完整配方

```
mem set 0x30190624 0x00200020      # HDMI 邊框 12 -> 32
mem set 0x301906A4 0x00200020      # LCD  邊框  8 -> 32
display faceframe -8 272 2000 32   # 32 px 實心黑色塊,LCD 置中(325..356)
mem set 0x30190400 <值 & ~2>       # 關掉內框
mem set 0x30190410 <值 & ~2>
mem set 0xC03E4698 0xE3A08F52      # 文字 y = 328
mem set 0xC03E46A0 0xE3A050F0      # 文字 x = 240
mem set 0xC0BB1208 0xFFFFFFFF      # 綠色(桃紅是 0xFFFFF8B2)
display monitor 0 1
display osd 1 0x00000000           # ×3
display text MY_TEXT               # ×3,每次後面跟一條 display osd 1
```

⚠ **色塊是硬體 marker、字是 OSD 副層,兩者的穩定度不一樣。**
色塊撐得過 GUI 重繪;字撐不過 —— 切換相機模式就會被刷掉,要重下
(`display osd 1` + `display text` 各三次,因為圖層是三重緩衝)。
文字只吃 ASCII、不能有空白(用 `_`),16 px/字。

## 8. 字型與文字顏色  [M]

### 顏色 = **調色盤索引,只看最低一個位元組**

副層是 8bpp 調色盤,字形 blitter(`FUN_c052b620`)每個像素寫**一個位元組的索引**:

```
0xC0BB1208  低位元組 = 筆畫顏色索引   (字形 bit == 0 的地方)
0xC0BB120C  低位元組 = 底色顏色索引   (字形 bit == 1 的地方,預設 0 = 透明)
```

**高三個位元組完全沒用。** 原廠的 `0xFFFFF8B2` 其實是索引 `0xB2` = 178,
超出 30 筆調色盤 —— 它會顯示只是運氣。`0xFFFFFFFF` 是索引 255,同理。
我之前照 AYUV 去湊白色所以全部變透明,那個猜測是錯的。

30 個索引逐一實機掃過(`display palette 2 0` 印調色盤,底色是我們的黑色塊):

| idx | 實測 | | idx | 實測 | | idx | 實測 |
|---|---|---|---|---|---|---|---|
| 0 | 透明 | | 10 | 透明 | | 20 | `#497D46` |
| **1** | **`#FFFFFF` 白** | | 11 | 透明 | | 21 | `#4D884F` |
| 2 | 不透明黑 | | 12 | 透明 | | 22 | `#559655` |
| **3** | **`#A40A08` 紅** | | 13 | 透明 | | 23 | `#5CA25D` |
| **4** | **`#25D525` 綠** | | 14 | 透明 | | 24 | `#62AB62` |
| **5** | **`#03028C` 藍** | | 15 | 透明 | | 25 | `#69B96A` |
| 6 | 半透明黑 | | 16 | 透明 | | 26 | `#70C26E` |
| **7** | **`#444444` 深灰** | | 17 | `#243E22` | | 27 | `#77CF78` |
| 8 | 透明 | | 18 | `#2E542F` | | 28 | `#81E182` |
| 9 | 透明 | | 19 | `#3C693B` | | 29 | `#8AEF89` |

17–29 是綠色的亮度階梯,相機拿來給自己的綠字做反鋸齒。**能用的實色只有 1/3/4/5/7。**
索引 2 和 6 是黑色,畫在黑色塊上看不到,但在亮背景上可以當黑字。

### 字型只有一套,但描述元在 RAM,可以換

`DrawTextSimpleFont` 的描述元 `0xC37830E8`(**可寫**):

| 偏移 | 值 | 意義 |
|---|---|---|
| +0x00 / +0x01 | `0x20` / `0x7F` | 首字 / 末字(96 個字) |
| +0x02 u16 | 16 | **字寬**(也是每字前進的像素) |
| +0x04 u16 | 32 | **字高**(字形格高;實際筆畫只佔約 17 列) |
| +0x06 u16 | 2 | 每列位元組數 |
| +0x08 u16 | `0xBE0` | 表大小(blitter 沒用到) |
| +0x0C u32 | `0xC2F24558` | **字形點陣指標** |

`FUN_c052b4f8`:`字形位址 = (ch - first) × 每列位元組 × 字高 + 指標`,
所以一個字 64 bytes、96 個字共 **6144 bytes**。**bit 0 = 筆畫、bit 1 = 底色。**

**字型 id 1(`0xC37830C8`)不是第二種大小** —— `FUN_c052b310` 兩個實例都指向同一份
描述元;實機讀到它根本還沒建構(全 0)。所以**韌體裡沒有更大的內建字型**。

### 放大 = 自己上傳一份放大的點陣  [M] 已實作

blitter 一個字形像素只寫一個目的像素,**沒有縮放**。所以要放大就得換點陣:

1. 從 `out/seg1_c2ef6e00.bin` 的 `0xC2F24558` 取 6144 bytes,2× 最近鄰放大
   → 32×64 格、每列 4 bytes、共 **24576 bytes**。
2. `put(pool + 0x80000, blob)` 寫進池 —— 實測 **0.6 秒**(`putfile.put` 的 bulk 路徑)。
3. 改描述元(注意是 32-bit 字,欄位要合併):
   ```
   mem set 0xC37830E8 0x00207F20     # 字寬 16 -> 32
   mem set 0xC37830EC 0x00040040     # 字高 32 -> 64、每列 2 -> 4
   mem set 0xC37830F4 <點陣位址>
   ```
4. **還要放大 `display text` 的矩形**,否則一個字都不畫:
   `DrawTextSimpleFont::v1` 開頭就是 `if (rect.h < 字高) return 0;`。
   ```
   mem set 0xC03E46A8 0xE3A03040     # MOV r3,#0x40   矩形高 0x20 -> 0x40
   mem set 0xC03E469C 0xE3A0CB01     # MOV r12,#0x400 矩形寬 0x180 -> 0x400
   ```
5. 色塊也要加高:`display faceframe -8 256 2000 64`(邊框厚度要先調到 ≥32,見 §7)。

實測畫面:64 px 黑色塊 + 2× 白字,乾淨。3× 也可以(96×6×96 = 55296 bytes,一樣一秒內)。
放大是最近鄰,所以是方塊感;要平滑就得自己做字型點陣。

還原:`0xC37830E8=0x00107F20`、`0xC37830EC=0x00020020`、`0xC37830F4=0xC2F24558`、
`0xC03E46A8=0xE3A03020`、`0xC03E469C=0xE3A0CD06`。

## 9. 調色盤 —— 整張表在 ROM,256 筆  [C]+[M] (2026-09-20 二度更正)

`0xC0BB1208` 的低位元組是索引。原廠是 `0xFFFFFFFF`(索引 255,深綠)、字畫在 (0,0);
**`0xFFFFF8B2`(索引 178)是 fpSup 自己的 patch**(`fp_usb_shell/patches.py` 的 `SCREEN`),
連同 `MOV r5,#120` / `MOV r8,#16` 把字移開電池圖示。索引 178 = **#FF6668**。

### 表的位址與長度
層物件 core+0x30 = **`0xC0B520BC`**、core+0x34 = 30。但**表本身是 256 筆**,
索引 178 正好落在 `base + 178*4`。描述元只宣告 30 筆,所以 `display palette` 只印 30 行;
硬體 CLUT 是 256 筆,整張表都用得到。每筆 4 bytes = A, Y, U, V(U/V 對 128 的有號偏移)。

| 索引 | 內容 |
|---|---|
| 0–29 | `display palette` 公開的那 30 筆;實色只有 1/3/4/5/7 |
| **30–160** | **純黑(Y=U=V=0)的遮罩梯度**,120 筆、25 種 alpha,1/255 到索引 158 的全不透明。11 筆 alpha=0 |
| 161–255 | 第二個顏色區塊,約一半是半透明 |

### 驗證
256 個索引逐一 `display osd 1 0x000000<idx>`(fill 對 8bpp 層取低位元組當索引)
填滿整層、壓在不透明黑底上拍下來:**245/256 在 4 階以內吻合**,
不合的 11 個是最飽和的藍紫(BT.601 全範圍換算 vs 相機自己的轉換在色域邊緣分家)。
**ROM 裡的 AYUV 才是真值,RGB 只是預覽。**

### ⚠ 前兩次都量錯,錯的都是量法
1. **把索引畫成文字、取筆畫顏色** —— JPEG chroma 是半解析度,2 px 筆畫跟黑底平均掉,
   每個顏色都被拉暗又偏色(178 量成 `#895087`)。**細筆畫不能拿來量顏色。**
2. **判定 30–160 是空的** —— 它們是壓在黑底上看不見的黑色梯度。
3. 順帶:`mem set` 掉寫入導致某些列沒畫,量到的是實景,而且「顏色」跟著**列位置**
   週期性重複 —— 那個週期性是識破它的線索。

**教訓:能從 ROM 讀就別用拍的。** 我繞了三圈才想到去找表。

## 10. 用文字圖層畫色塊與細條的手法  [M]

> 開機橫幅本身的設計、取捨與未解問題移到 [`BOOT_BANNER.md`](BOOT_BANNER.md)。
> 這一節只留**手法**,那是顯示子系統的性質,跟那個橫幅做不做得成無關。

1. **ink 顏色 == 底色顏色 → 任何字元都變成實心色塊。**
   blitter bit0 畫筆畫、bit1 畫底色;兩個設成同一個索引,整格就是純色,
   **字元本身無所謂**(`XXXX` 就行),也不用改字形。
2. **字高是描述元欄位 `0xC37830EC` 的低半字**,改成 12 就是 12 px 的細格。
   實心格不看點陣內容,所以高度可以隨便設 —— 粗細就是這一個字。
3. **字格頂端 = y 立即數本身。** 先前筆記說的「畫面 y ≈ imm + 4」是**字形筆畫**
   在 32 px 格內的起點(第 4 列),不是格頂。畫實心格要用格頂算。
4. **調色盤有成對設計的**:`170` = `#00FEFE` 100%、`171` = 同一個青色 53%,
   拿來當「已完成 / track」剛好。索引 1 白 / 7 深灰也是一組。
5. **前綴覆蓋**:短字串畫在同一個 x 就是覆蓋前面幾格,所以
   `fpSup####` 灰 → `fpSup##` 白 → `fpSup` 桃紅 → `fp` 黃 可以疊出四種顏色,
   **不用改 x、不用墊位字元、不用改字形**。這是繞開 I-cache 的關鍵,見 BOOT_BANNER §2。
6. **`■` `□` 不能直接打**:字形表只有 ASCII 0x20–0x7F,`FUN_c052b4f8` 對超出範圍的
   字元**夾成第一個字(空白)**,所以 UTF-8 的 `■` 會畫成三個空白。
   真要方塊可以 `mem set` 覆寫字形(一個字 16 個 word,`0xC2F24558 + (ch-0x20)*64`,
   bit0 = 筆畫)—— 但有了發現 1 或 5 就不需要。
7. ⚠ **繪圖矩形寬度(`0xC03E469C`,預設 384)會讓超長字串整串不畫**,不是截斷,
   而且 shell 照樣回 `ok` 和 `output <字串>`。

⚠ **不能拿機身截圖判斷螢幕在閃** —— 它抓的是特定 buffer,會出現
「1 次有 / 2 次沒有 / 3 次有」這種無意義的圖樣。

### 第二個硬體矩形 —— 五次都失敗(2026-09-20)  [M]

目標:黑線當 track、另一條當進度條,兩個都是硬體 marker → 每步 1 條 display。
**沒做出來。** 試過的路與結果:

| 做法 | 結果 |
|---|---|
| 直接 poke 沒配置過的 slot(25)的矩形/顏色/樣式/致能 | 完全沒畫出東西 |
| 同上 + `FUN_c00e6d90` 裡的 **bit 28 latch**(`0x10000000`) | 一樣沒有 |
| `display focusarea 1` 借它配 slot | **跟 faceframe 共用同一個管理器 `0xC3435A54` 和同兩個 slot**,不會配新的;而且 `focusarea 0` 會把我們的線一起清掉 |
| `menu SetDisplayGridLines 1/3` 讓韌體配 slot | **有效** —— 致能從 `0x04` 變 `0x2C`/`0x7C`,slot 3/4/5/6(LCD 端 24/25/26/27)是韌體正式開的 |
| poke 那些已配置 slot 的矩形(± latch) | 線**消失**;使用者肉眼看到的是「格線越來越透明」—— 寫入有打到 slot,但改到的是透明度/顏色,不是位置 |

**結論:暫存器是活的,但光靠 poke 湊不出韌體建 paste 物件(`FUN_c02edf08` → `FUN_c02f1bd8`)
時做的完整設定。** 要第二個矩形得把那條配置路徑完整逆出來,不是 poke 幾個暫存器的事。

⚠ **方法論**:截圖比對只看到「第 511 欄變了」,是**使用者肉眼**看出「越來越透明」才知道
寫入其實有作用。**畫面的真相在螢幕上,不在截圖裡** —— 這一點在這份筆記裡已經栽了三次。

### ✅ `display faceframe` 在 AutoRun 開機期可用(2026-09-20 實機)  [M]

唯一的前提驗掉了。作法:把五行探針插進卡上 `AutoRun.txt` 的
`display monitor 0 1` 之後、第一個進度條畫面之前 ——

```
mem set 0x30190624 0x00180018
mem set 0x301906A4 0x00180018
display faceframe -8 264 2000 48
mem set 0x30190400 0x00000004
mem set 0x30190410 0x00000004
```

開機後**畫面中央確實出現黑色橫線**,文字進度條照常在左上角。
所以硬體 marker 在 AutoRun 早期就備妥,黑線不必退回用文字格畫。

改卡的方式:`getfile.py` 取下 `\AutoRun.txt` → 本機插行 → `putfile.py` 寫回 →
再 `getfile.py` 回讀比對 sha。實測寫回逐位元組相同。**比重建一張卡便宜得多。**
