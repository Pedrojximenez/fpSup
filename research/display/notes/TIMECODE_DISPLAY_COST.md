# 時間碼(影格欄位)顯示的成本(2026-10-16，離線)
> **⚠ 更正(2026-10-19)**:「UI 佇列積壓→逐則重畫」不成立。原廠每輪 `C0561198` 一次處理整個緩衝，同名變數在 `C0563F40` 的 64 格表就地覆寫，每輪只套用一次——積壓的只是 0x38 B 的便宜附加。時間碼的真正成本在 span 表 1 idx 7(`C06FBCD8`,ARGB4444→ARGB4444 混色)、每輪物件樹走訪、`C0563BA8` 與整層複製。見 `projects/sys-perf/uicoalesce/README.md`。

使用者覺得錄影時「微秒顯示」很吃資源。畫面上唯一會在一秒內變化的數字是**時間碼 HH:MM:SS:FF 的影格欄位 FF**，
本筆記假設講的是它。錄影計時 `LV_RecTimeH/M/S` 只到秒，快門 `LV_ShutterSpeed` 只在變更時才更新。
**[靜]** = 反組譯或 NBU 記錄直接讀到；**[推]** = 推論。相機上一項都沒量過。

## 1. 誰寫入：設定函式只是把訊息排進 UI 佇列，非同步處理 [靜]

- LV 模型類別的 vtable 位於 `0xC2DF5AEC`。編譯器慣例是 vptr 先指向 offset-to-top，第一個虛擬函式在 vptr+8。
  - 這可以由建構子 `C059CC90` 寫入 vptr 的方式確認，基底類別 `0xC2E3F410` 也同樣以 `0, typeinfo` 開頭。
  - 四個 setter 的位置：

    | setter | 函式 | vtable 位置 | 呼叫偏移 |
    |---|---|---|---|
    | `LV_TimeCodeH` | `C059E8C0` | `+0x120` | 0x128 |
    | `LV_TimeCodeM` | `C059E8E8` | `+0x124` | 0x12C |
    | `LV_TimeCodeS` | `C059E910` | `+0x128` | 0x130 |
    | `LV_TimeCodeFrm` | `C059E938` | `+0x12C` | 0x134 |
  - 完整的 126 個 setter 名稱表用 `scratchpad/perf/tc/` 的腳本可以重產。
- 每個 setter 都呼叫 `C059CCC8(this, 名稱, 值)`，流程如下：
  1. memset 一個 0x38 bytes 的訊息。
  2. `C055DD10` 填入 `{type=2, 名稱, 值}`。
  3. `C055E0F0` 取得 UI 佇列單例 `0xC378BF30`，第一次呼叫時才初始化。
  4. `C055E1E8` 在鎖內入列。佇列**上限 1500 筆**(`0x5DC`)，超過就丟掉該筆並印 log(類別 0x2000)。
- **生產者每次呼叫的成本很低**：一次 0x38 bytes 的 memset、入列、上鎖。真正的成本落在消費端(UI 任務)。
- **還沒找到是誰在呼叫影格的 setter，也不知道頻率**。這些方法是透過多層代理以虛擬呼叫叫用，直接搜尋位址找不到。
  合理推論是每個視訊影格呼叫一次，也就是 29.97 或 59.94 次/秒 [推]。上機確認方法見 §5。

## 2. 消費端：沒有 Lua，而是用「動畫影格選圖」[靜，NBU]

在 `LV_CINE_LARGE` 資源集(`0xC1E0A87E`)裡，物件 7365 `TimeCode` 的行為如下：

- 每個欄位由兩個元件組成：
  - `appVariableChangeEvent(LV_TimeCodeFrm)` 偵測變數改變；
  - `controlAnimation(apply-frame = LV_TimeCodeFrm)` 用變數值選擇動畫影格，影格就是數字圖 `font_M_0..9`(clip 29，60 格)。
- 時間碼區塊大小 309×47。每個數字圖 29×47，影格欄位的兩位數位於 x=251、280。
- 數字圖在開機時就由資源快取預載，**不需要解壓 LZ4**。
- 只有外部 TC 輸入時，`EX_Blink` 才會讓整塊時間碼半透明閃爍(clip 7)。
- 這裡完全沒有用 Lua。`LV_SysTime*` 系統時鐘才用 Lua(`string.format`、`gsub`)，它每秒只變一次。

## 3. 成本：問題不在畫兩個數字，而在讓 UI 每一輪都要重畫 [推]

- 繪製節奏固定是 48 ms 一輪(見 `UI_DRAW_CPU_COST.md` §1)，所以就算變數一秒改 60 次，**最多也只重畫 20.8 次/秒**。
- **每一輪的工作**：
  - 兩個數字的 dirty rect 約 2,726 像素。三重緩衝會和前幾個緩衝的 rect 取聯集，所以實際面積會更大。
  - 混色 span 每像素 40–58 指令，加上 ARGB4444 後處理(`C0563BA8`)，合計約 **0.15–0.3 M 指令/輪**，也就是 **3–6 M 指令/秒**。
  - 另外每一輪都要呼叫 **`C000E91C`**：L1+L2 整個清除，**全程關 IRQ 和 FIQ**。
- **關鍵差異**：
  - 不顯示影格欄位時，只有秒數在變，大約 **1 輪/秒** 會畫東西，其他輪 dirty rect 是空的，不畫也不清快取。
  - 顯示影格欄位時，UI 變成 **每一輪都畫、每一輪都清整個快取**，約 21 次/秒。
  - 推定最傷錄影的是整快取清除：每秒約 21 次關中斷，每次都把錄影任務的熱資料從快取趕走。純繪圖的 CPU 量反而不大。
- **佇列積壓 [推]**：錄影時 CPU 接近滿載，UI 任務排不到 CPU，影格訊息就以每秒 30–60 筆的速度累積。
  - 等 UI 任務醒來，必須逐筆處理積壓的訊息。影格值每筆都不同，所以每筆都會觸發通知和 apply-frame。
  - 積壓到 1500 筆時會開始丟訊息並寫 log。
  - 這可能和「UI 開越多，錄影越容易卡停」有關：UI 開得越多，消費端處理每筆訊息就越貴。

## 4. 優化候選

| # | 改法 | 是否改變原廠行為 | 風險 |
|---|---|---|---|
| A | 關閉時間碼顯示。`LV_TimeCode`=0 會把物件 7365 設為不可見，應該是選單裡的現有選項 | 否，使用者自己切換 | 無；可以直接拿來做 A/B 實測 |
| B | 繪製後只清 dirty rect 的範圍(`C000EB90`)，取代 `C000E91C` | 否 | 中：其他 drawer 寫的區域也必須算進去 |
| C | 入列時合併同名的待處理訊息，只保留最新值 | 否，畫面上看到的值相同 | 中：佇列結構與鎖都要摸清楚 |
| D | 錄影中把影格欄位降頻，例如只在 48 ms 邊界才 set | **是**(欄位跳動變粗) | 低 |
| E | 錄影中隱藏影格欄位，只顯示到秒 | **是** | 低 |

建議：先上機用 A 做 A/B，確認整快取清除的次數真的從約 21 次/秒降到約 1 次/秒；B 對所有 UI 都有幫助。

## 5. 上機驗證(唯讀為主)

1. **佇列流量**：序號在 `[0xC378BF30+0x29874]` = `0xC37B57A4`，每入列一筆加 1；
   佇列長度在 `[[0xC378BF30+0x2986C]]`。
   隔 1 秒讀兩次，就能得到每秒訊息數與積壓量。錄影中**不碰 USB**，這個量測只能在停錄前後做，或改用 hook 寫進環形緩衝。
2. **整快取清除次數**：在 `C000E91C` 掛計數器(或用 profiler)，比較 TC 顯示開與關。
3. **繪製時間**：uicMgr+0x198 bit0 開啟後，log 會印出每輪 Gui Render 的 µs。
