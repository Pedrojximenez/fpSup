# UI 繪圖有沒有硬體可以加速(2026-10-16，離線)

只讀 `out/seg0_c0000000.bin`。**[靜]** = 反組譯直接看到；**[推]** = 推論。沒有相機 I/O。
腳本：scratchpad `perf/hw/consts.py`(全映像 movw/movt + literal 常數表)、`blkname.py`、`perf/tcall.py`(Thumb BL/BLX/B.W + ARM 呼叫者)。

## 結論先講

**有兩個 DMA 引擎，原廠的 Display 函式庫已經包好「硬體 memcpy / 矩形複製 / 矩形填色」三支函式，但 UI 渲染器(UIC，`C06D…–C0700000`)完全沒用它們。**
它們做不了混色和仿射縮放，所以只能接手「整塊複製」和「單色填滿」；混色那一大塊仍要靠 CPU(NEON)。

| 引擎 | 位址 | 能做什麼 | 原廠包好的入口 | 誰在用 | 跟錄影搶？ |
|---|---|---|---|---|---|
| **COPY DMA**(ISP 的 SIES/COPY 區塊) | `0x30160200`，IRQ 0x20 | 線性 memcpy/memmove(每列最多 0x1FFE B × N 列)[靜] | `C00FBB90(desc)`；Display 函式庫包裝 `C071E2A0(dst,src,len)`、逐列矩形複製 `C071E410` | `MovRecState_CONT.cpp`(`C038C77C`)、Cinemagraph、`SigproHdr`、Display 函式庫 `C0710B98` 等 | **會**：錄影中 CONT 狀態在用，單一引擎 + 號誌 `0xC31D71B4` |
| **填色/搬移 DMA** | `0x30041000`(時脈閘 `0x300022A4`) | 以 32-bit 樣式填滿(位址以 word 計，`phys>>2`)[靜]；疑似也能搬移 [推] | `C00DB188(desc)`；Display 函式庫矩形填色 `C071E960`(每列 ≥2 KB 走硬體、否則 CPU memset，`C071EBD0`) | 只有 Display 函式庫(`C071030A` 等)[靜] | 沒看到錄影路徑用它 [推] |
| 顯示控制器 | `0x3019xxxx` | 每輸出 3 層硬體合成(LCD 層 3–5)、alpha、翻轉；OSD 層有 ARGB4444 主層與 8bpp 調色盤副層(`DisplayOsdLayer_ARGB_Idx256`)；**硬體矩形框** marker(樣式暫存器 `0x30190620/660`) | 既有筆記：DISPLAY_OSD_MAP、`hw-rect-overlay-markers` | 原廠 AF/臉框 | 合成本來就在跑，不額外搶 |
| ROTATE `0x301AD000`、DOF `0x301AC000`、BUF-D `0x301A` | 顯示/回放的影像緩衝路徑 | 旋轉、緩衝 DMA [推] | `C013A2B2` 一帶 | 回放/顯示管線 | 不在 LV 路徑(既有筆記) |
| ZOOM `0x3011A8xx`、R2Y、SIG 系列 | ISP | 縮放、格式轉換 | — | 即時影像管線 | **一定搶**，錄影中滿載，不考慮 |
| LJPEG `0x300D` | — | 無損 JPEG | — | 與 UI 無關 | 略 |

原廠 Display 函式庫的介面類別 `ImageDataUtilsSDKDrv`(vtable `0xC07281F4`)把它們包成三個方法：
`+4 copy(src,dst,len)` = `C00215B8`(COPY DMA)、`+8 copyRect(srcImg,dstImg)` = `C0021628`(2D，支援 8/16/32 bpp，`C00FBC98`)、
`+0xC fillRect(img,value)` = `C0021798`(填色引擎 `C00DB188`)。**[靜]**

## 每個方案能不能給 UI 用

1. **整層/大矩形清除改用填色引擎**(`C071E960` 或 `C0021798`)——**最可行**。
   - 目前 UIC 的清除(`C0528B40`)與圖層 fill(`C0722490`，一次一個 `strh`)都是 CPU。整層 1024×682×2 B ≈ 1.4 MB。
   - 硬體填色不佔 CPU，而且原廠自己已經用同一支函式。
   - 風險:DMA 寫入繞過快取，填之前要先 clean+invalidate 那段範圍，否則 CPU 的髒 line 之後會蓋回去；顏色要展開成 32-bit 樣式(ARGB4444 兩像素一組)；同步等待中 DrawThread 會睡，畫面不會更慢但流程要改成非同步才有收益。
2. **1:1 不透明貼圖、三重緩衝間的整塊同步改用 COPY DMA**——**可以，但不建議在錄影中用**。
   - 錄影的 CONT 狀態也用同一個引擎，UI 一搶就可能拖慢錄影，正好和使用者「UI 開越多越容易卡停」的方向相反。
   - 小圖示(幾 KB)時，DMA 設定 + 快取維護 + 中斷喚醒的固定成本可能比 CPU 複製還貴 [推]。只對大塊(換頁整層)有意義。
3. **時間碼之類常變的小元素放進獨立硬體層**——**目前看不可行**。
   - 每個輸出只有兩個 OSD 層，原廠都在用(主層 ARGB4444 + 8bpp 副層)；層是否支援「小視窗 + 位置偏移」沒查到暫存器證據。
   - 硬體矩形框只能畫空心/實心框(既有筆記)，不能畫數字。
4. **縮放/旋轉引擎做縮放貼圖**——**不可行**。ZOOM/R2Y 是即時影像管線的一部分，錄影與 LV 中一直忙；ROTATE 在回放路徑，格式是 YUV 影像緩衝。

**混色(source-over，40–58 指令/像素)與仿射取樣沒有任何硬體能接手**，這部分的退路是 NEON：
CPACR 已開 cp10/11，韌體本身有約 1.7 萬條 NEON 指令(例：`C0011638` 起)[靜]，ARGB4444 一次可處理 8 像素。

## 上機最小驗證(都不用錄影)

1. 讀 `0x30041000..0x3004102C` 與 `0x300022A4`：引擎閒置時的值、時脈閘狀態(參考 ljpeg-not-cold-callable 的教訓：先確認時脈/電源域本來就開)。
2. 用 `callfn` 呼叫原廠 `C071E960` 在**自己 claim 的緩衝區**填一塊(不是圖層)，讀回驗值；量呼叫前後時間。
3. 讀 COPY 號誌 `0xC31D71B4` 的狀態：待機與錄影中各讀一次，確認錄影時是否被占用(錄影中不碰 USB 的規則仍適用，只能錄完看計數)。
4. 若 1–2 通過，再在圖層上試整層清除，對照 Gui Render µs(uicMgr+0x198 bit0)。

## 沒做到的

- `0x30041000` 引擎除了填色是否支援搬移(`C00DB2F8` 一族)沒追完。
- 沒確認 Display 函式庫(`C070E000–C0722000`)裡用 COPY DMA 的 `C0710B98` 是哪個畫面功能(呼叫者 `C0310554`，推測回放)。
