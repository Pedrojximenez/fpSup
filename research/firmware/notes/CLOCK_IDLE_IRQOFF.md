# 時脈、idle 任務、關中斷區段(2026-10-16,離線)

靜態分析 `out/seg0_c0000000.bin`、`out/IPL.raw`、`out/decomp/ipl_v7.c`。沒有相機 I/O。
【靜】= 直接看反組譯；【推】= 推論。工具在 scratchpad `perf/f3/irqoff.py`、`perf/tmovwt.py`(Thumb/ARM movw+movt 掃描)。

## 1. 時脈與 DVFS

**結論：沒有找到執行期間調 CPU 頻率(DVFS)的程式碼，待機不會讓 CPU 變慢。**【推，證據強】

- `udelay`(`C0000A08`,參數單位 µs)用的是「每 µs 幾圈」的校正值 `[0xC3033260]`。
  這個值只在 `C00008C8` 寫一次【靜】:用計時器第 2 通道量 11000 圈與 1000 圈的差，存成大約 16 倍的「每 µs 圈數」。
  呼叫者只有計時器初始化 `C0016958`【靜】。整個映像只有兩處碰這個位址(寫 `C00009EC`、讀 `C0000A14`)【靜】。
  CPU 頻率若在執行期間改變，所有 udelay 都會跟著錯，所以 CPU 時脈應該是開機後就固定【推】。
- 執行期間會重新設定的 PLL 是 **0x30000034**(`C0127BE8`)【靜】。
  它先停掉 0x30048000/0x30050000/0x30051000/0x30059000 這幾個 SIG/ISP 區塊，寫 PLL，等 `[0x30000000]` bit 8 鎖定，
  再脈衝 `0x30000870` bit 0。`C0127C80` 會先比對目標值，相同就不改。這是**影像管線的 PLL**,依感光元件模式切換，不是 CPU【推】。
- `0x30000048`(`C00DA378`)用到 8000/24000 這類 kHz 數值，像是音訊或周邊 PLL【推】。
- IPL 的 **DDR PLL 在 0x30000064**【靜，`ipl_v7.c` 約第 3380 行】:參考頻率 24 MHz,f = 24 × N / M / 2^P。
  支援的設定有 400、533、666、700 MHz,其他值落到預設 796 MHz;算式與四個常數一致。
  實際用哪一個由 IPL 參數 +0x34 決定，參數表不在 dump 裡，所以 **DRAM 頻率未知**。
- 時脈閘門 0x30000800–0x30000B20 有大量讀改寫(0x30000814 有 20 處、0x30000800 有 16 處等)。
  電源域開關在 `C01F1C00`(0x300A3004),閘門是逐區塊開關，不是降頻【推】。
- 選單有 ECO 模式(`MenuItemPowerSaveEcoMode`、shell `pw_save eco`),實際效果沒有分析。
  如果它會降低 LV 或 LCD 刷新率，會**看起來**比較卡。請使用者先確認選單裡 ECO 沒有開。
- **上機驗證**:讀 `[0xC3033260]` 一次，換算 CPU MHz(≈ 值 / 16 × 每圈週期數，每圈 1–2 週期)。
  待機、選單、錄影各讀一次，值應該完全相同；讀 `0x30000034` 看不同模式下 ISP PLL 有沒有變。
- **不建議改 PLL**:CPU PLL 的暫存器沒有確認，改錯就是磚。

## 2. idle 任務(inittsk)

**結論：不是 CPU 浪費來源。**【靜】

- `inittsk`(`C0001C60`)初始化完會呼叫 `C00166E0`:建立並啟動優先權 20、堆疊 0x8000、入口 `C00207F8` 的任務，
  然後自己變成 idle 迴圈 `C0016698`:`for(;;){ di; if(!([0x30010300]&1)) CP15 WFI(C0000CC8: mcr p15,0,r0,c7,c0,4); ei }`。
- 核心的 dispatcher 在 `C0000D6C` 另有一個無任務迴圈，它的 hook `C0016690` 是空的(`bx lr`),實際上所有閒置時間都由 inittsk 吃掉。
  所以 tskmon 裡 inittsk 的百分比就等於 idle 百分比。
- ARMv7 的 `WFI` 指令在整個映像裡出現 0 次，只用了舊式 CP15 c7,c0,4。
  它在 A7 上是真的睡眠還是當成 NOP,會影響功耗與發熱，**不影響效能**:idle 只在沒有工作時才跑【推】。
- `0x30010300` bit 0 為 1 時不進 WFI(可能是除錯 / JTAG 旗標)【推】。

## 3. 長時間關中斷的區段

對 `C000EC14`(di,344 處)/ `C000EC24`(ei,385 處)配對，得到 336 對，再看區段內有沒有迴圈和呼叫。

| 等級 | 區段 | 內容 | 判斷 |
|---|---|---|---|
| ★ 最長嫌疑 | `C000E91C`(全 L1+L2 clean+inv)、`C000E9B8`(全 clean) | 函式本身全程 IRQ+FIQ 關，set/way 走過所有 line | 一次可能幾十到幾百 µs【推，L2 大小未知】;58 / 6 個呼叫點。`C0500A68` 遇到 ≥10 KB 就會走到這裡 |
| ★ | MONITCYC 等 16 個循環處理器 | 在計時器 IRQ 內執行(不會巢狀),每 2 ms 一次 | 回呼總時間全部算成中斷延遲【推】 |
| 中 | `C01F1C00`(id 0xB)電源域開關 | 關中斷後忙等 `[0x300A3004]` bit 0 | 只在模式切換時發生，時間由硬體決定【推】 |
| 中 | `C01EF5E8` / `C01EF19E` | 關中斷內 udelay 100 µs / 20 µs,並碰 0x30002034/38(`C00112B8`) | 電源 / 時脈切換路徑【推】 |
| 低 | `C0659974`(5×1000 次取樣)、`C065A7DE`(udelay 500 µs × N)、`C065ADDE`(125 µs)、`C0659DD4`(50 µs) | 有統計 min/max/sum,呼叫的 `C01EE148`/`C01EE150` 是空 stub | 像測試 / 校正命令，不在常態路徑上【推】 |
| 低 | `C000xxxx` 的核心服務(例如 `C0006158`、`C00090C0`) | 走訪佇列，區段 < 0.7 KB | 正常的 T-Kernel 臨界區 |
| 低 | 範圍快取操作 `C000EA54`/`EB28`/`EB90` | 逐 line、全程關中斷 | 經包裝函式 `C0500A68` 時最多 10 KB = 160 line,短 |

`dis_dsp`/`loc_cpu` 的服務碼沒有逐一盤點(未做)。

### 優化候選(按價值排序)

1. **把 `C0500A68` 的 10 KB 門檻改成用範圍操作**(或把門檻拉到接近 L2 大小)。
   同時減少「整個快取清掉之後重新填回」的成本和長時間關中斷。
   - 風險：範圍操作的總時間會隨 size 線性增加，但同樣全程關中斷，所以大 buffer 要分段開中斷。
   - 正確性：clean+inv 一定要涵蓋整個 buffer。
2. MONITCYC 的回呼若可以拉長週期(例如 2 ms 改成 4 ms),中斷負擔減半。
   - 風險：按鍵與裝置監看的反應會變慢(每個回呼原本 14 ms 一次)。

### 上機驗證法

- 在 `C000E91C` 進出點掛計數器並讀 1 MHz 計數器(`C002B6E0`),量每秒幾次和每次幾 µs;待機、選單、錄影各量一次。
- 從 CCSIDR 讀 L2 大小(callfn 呼叫一段 mrc)。
- 量中斷延遲：比較 tick 處理器實際進入時間與計時器到期時間的差。PC_SAMPLER_HOOKPOINTS 的取樣器順便記錄 `[0x30xxxxxx]` 計數即可。
