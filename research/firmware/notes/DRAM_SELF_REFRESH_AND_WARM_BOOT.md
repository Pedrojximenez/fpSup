# 軟重開為什麼留得住資料 —— DRAM self-refresh,預設 15 分鐘

2026-09-17。回答「為什麼暖開機注入區還在」,並評估能不能靠它砍掉二次開機時間。
全部從 `out/MAIN_c0000000.bin` 靜態讀出,標明推論處。

---

## 1. 開機只清 BSS,不清 DRAM

啟動碼在 `0xC0000688` 載入兩個字面值再呼叫 memzero(`0xC00006C0`,通用
`memzero(r0=起, r1=迄)`):

```
清零範圍   0xC3000000 .. 0xC38D6FB0   =  9,269,168 bytes (8.8 MB)
```

**整個開機路徑只清這 8.8 MB。** 其餘 DRAM 一個位元組都沒動。

順帶解掉 `FORMAT.md` 裡一個沒人知道是什麼的常數 —— 它記著
「其他常數:`0xC3000000`(RAM 上緣)、`0x008D6FB4`」。後者就是 **BSS 大小**
(`0xC38D6FB0 − 0xC3000000 = 0x8D6FB0`;筆記的值多 4,是邊界符號的寫法差異)。

注入區全部落在韌體映像區,離 BSS 差 40 MB:

```
loader 0xC072DE64 · payload 0xC072E064 · park stub 0xC072EFB4
shell worker 0xC072F050 · 狀態字 0xC072F000      ← 清零碰不到任何一個
```

## 2. 但真正的機制是 DRAM self-refresh,而且它是可設定的功能

韌體有三個 shell 命令(命令表 `0xC0BC45AC`,格式 `{name, usage, handler}`):

```
sys selfrefresh [on/off]                              handler 0xC040F878
sys selfStopTime 600 : [unit = sec / 0 = default]     handler 0xC040F948
sys selfConfig    (印出 SelfRefreshSetting)            handler 0xC040F9C0
```

`selfConfig` 印三行:`Enable`、`Stop Timer (sec)`、`DebugSetOffSec`。

**設定結構**:`0xC0021508()` 取得管理物件,`[obj+0x18]` 指向設定,
基底 `0xC307523C`(大小 `0x410`,屬 `XC_CommonSave.cpp` 的使用者設定區):

```
[cfg+0x01]  Enable          首次初始化寫 1 → 預設開啟
[cfg+0x04]  Stop Time (秒)  ← 見 §3,這個值不會被用到
```

## 3. ★ 停止時間預設 900 秒,而且使用者設的值是死的

建構子 `0xC0023948`:

```
0xC00239C8  mov r0, #0x384           ; 900 秒 = 15 分鐘
0xC00239D0  str r1, [r4, #0x6c]      ; 內建預設停止時間
0xC00239D8  strb r1, [r4, #0x70]     ; = 0(Enable getter 先檢查這個)
```

getter `0xC0024310` 讀了使用者設的 `[cfg+4]` 進 r4,然後:

```
0xC0024358  mov   r0, #0      ← 寫死 0
0xC002435C  cmp   r0, #0      ← 恆真
0xC0024360  cmpne r4, #0      ← 不執行
0xC0024364  beq   → 回傳 [r5+0x6C]
```

條件是 `(r0 != 0 && r4 != 0 && r4 <= 0xA8C0)`,但 `r0` 硬寫成 0,**永遠回傳內建的
900 秒**。`sys selfStopTime` 寫進去的值就躺在那裡沒人讀。死路裡的
`0xA8C0 = 43200` 秒 = 12 小時是這個功能本來的上限。

看起來是編譯期關掉的功能(`#if 0` 退化成 `mov r0,#0`),不是 bug。

## 4. 所以「留得住什麼、留多久」

| | |
|---|---|
| **機制** | DRAM 保持 self-refresh,內容不掉 |
| **預設開啟** | 是(`[cfg+1]` 初始化為 1) |
| **維持多久** | **900 秒 = 15 分鐘**(內建,改不動) |
| **保住什麼** | 整片 DRAM,除了開機會清的那 8.8 MB BSS |

**⚠ 推論,非靜態證實**:映像區每次**冷**開機要從 NAND 重新 LZSS 解壓覆蓋,
所以冷開機注入區會被原廠位元組蓋掉。軟重開留得住,是因為它沒重跑解壓 ——
SoC 從 DRAM 還活著的狀態恢復。解壓在 IPL(NAND 上另一個分割),**不在 MAIN 裡,
看不到**。三件事支持這個推論:實測資料會留、開機固定 4.7 s(解壓 49 MB 不可能這麼快)、
清零範圍確實碰不到注入區。

### 可以直接驗的預測

**關機超過 15 分鐘再開,注入區應該就不在了;15 分鐘內應該還在。**
不需要 shell、不需要改任何東西,關機計時再開機看行為即可。
這同時驗證 900 秒這個數字和上面那條推論。

## 5. 對二次開機時間的意義

實測基準(記憶 `boot-time-levers`):**固定 4.7 s + 每命令 38 ms**,
發布版 113 條 → 約 **9.0 s**。

若暖開機能確認注入區完好而跳過全部區段寫入,省下的就是那 4.3 s ——
**9.0 s → 約 4.7 s**。

**但必須先解決一件事**:怎麼知道注入區是完好的。這正是
`warm-restart-keeps-the-cave` 記錄的那個 bug 的反面 —— 當時是「已經做過了」的旗標
跨開機沒清,害第二段錄影一按就停。同一個現象,這次要拿來用而不是被它咬。

**不能用單純的旗標。** 需要的是簽章:

```
magic + 版本 + 對實際 payload 的 CRC
```

三者都對才跳過注入。理由:
- 冷開機後那塊是原廠位元組,不是零 —— 單純比對「非零」會誤判
- 舊版本的卡留下的 payload 會通過旗標檢查但內容是錯的,版本必須進簽章
- self-refresh 過期後的 DRAM 內容未定義,CRC 是唯一能擋住半毀 payload 的東西

**另外要想清楚**:韌體補丁(寫進映像 code space 的那些)也在同一區,所以推論上
它們也一起留著 —— 意思是暖開機時相機可能**已經是改過的狀態**,AutoRun 還沒跑。
這對「跳過注入」是好消息,但也意味著任何「開機時是原廠狀態」的假設都不成立。

## 6. 待驗

1. §4 的 15 分鐘預測(關機計時法,零成本)
2. 暖開機時映像是否真的沒重載(只能實機看注入區內容)
3. `sys selfConfig` 的實際輸出 —— 會一次印出 Enable / Stop Timer / DebugSetOffSec,
   直接對照本文的靜態讀數
4. `[cfg+0x70]`(Enable getter 先檢查的那個 byte)什麼時候會被寫非零 —— 那是唯一
   能讓 self-refresh 報告成停用的路徑

## ★ 實機量測 2026-09-17(USB shell,使用者同意下進行)

### 靜態讀數全部證實

```

  Enable            = YES
  Stop Timer (sec)  = 900        ← 正是 0xC00239C8 的 mov r0,#0x384
  DebugSetOffSec    = -1
sys selfrefresh
  now setting = on
mem get 0xC00239C8 = E3A00FE1    ← mov r0, #0x384,跟反組譯一致
```

→ §2/§3 的解讀**不是推論了**:self-refresh 預設開啟,內建視窗 900 秒。

### 但標記撐不過 10 秒的電源開關

兩個位址,一個在韌體映像內、一個在外:

| 位址 | 區域 | 結果 |
|---|---|---|
| `0xC072FA00` | 注入區(映像內) | 三次全部變回 `00000000` |
| `pool+0x60000`(絕對 `0x45086680`) | 映像外 | 三次全部變回**同一組殘值** `54911A58 1A56A11A F11A57E1 58B11A57` |

排除過的變因:

- **不是卡片蓋掉的** —— usbshell 卡的 VSHL 只寫到 `0xC072F698`,AutoRun 在
  `0xC072F600..0xC072FC00` 一條 `mem set` 都沒有。
- **不是快取騙人** —— 第二輪寫完呼叫 `0xC000E91C`(D-cache clean)與
  `0xC000EABC`(I-cache invalidate),兩者都回傳成功,結果一樣。
  (第一輪沒做這步,當時的「沒保留」不可採信。)

映像外那塊**每次還原成逐位元組相同的內容**,是「開機確定性重寫」而不是衰減。

### 池基底每次不同

```
0x44F6FE00  →  0x45026680  →  0x45026680
```

證實 loader 動態讀 `0xC3757A7C` 是必要的,不能快取。

### ⚠ 與使用者觀察衝突,未解

使用者明確表示:**og3k 的殘留是真的,重開機進度條還沒跑完就已經有一部分在,而且會被執行。**
這跟上面三次量測直接矛盾,而 `warm-restart-keeps-the-cave` 那則記憶說的也是同一件事。

**沒有解決之前,不要把「不保留」當結論。** 目前最可能的差異是**時間**:

> `Stop Timer = 900` 可能只在 eco / sleep 這類低功耗狀態才進 self-refresh,
> 全關機根本沒進。那樣殘留就是純物理的 —— DRAM 不更新時電荷撐幾秒到幾十秒,
> **快速開關撐得過,10 秒撐不過**。我三次都讓使用者等了 10 秒。

下一步:同樣的標記,**啪一下關立刻開**。還有一個沒排除的變因是
**USB 連著可能讓相機走不同的關機路徑**(維持供電),必要時拔線再測。

### 對 warm boot 的影響

`--warm-boot` 的 hook 實測**沒有觸發**(進度條重跑了整份 AutoRun)。
在上面的矛盾解決之前,那條路既不能宣告成立、也不能宣告失敗。
`--retain-ram` 那條補丁本身是對的(改的確實是 `sys selfConfig` 印出來的那個值),
但它能不能延長實際的保留視窗,取決於全關機到底有沒有進 self-refresh —— **未證實**。

# ★★ 2026-09-18 第二輪:第一輪的結論是錯的

第一輪(上一節)說「標記撐不過 10 秒的電源開關」,並據此判定暖開機載入不可行。
**那是採樣偏誤。** 20 個探針全部落在開機本來就會重寫的地方:

- `0xC072xxxx`–`0xC073xxxx` = 韌體映像,每次開機從 NAND 解壓覆蓋
  (這一輪直接證實了:寫進 `0xC0024358` 的補丁開機後變回原廠 `E3A00000`)
- 池 + 0x50000… = 每次還原成逐位元組相同的殘值,那是確定性重寫

**BSS 之後**(`0xC38D6FB0` 以上)一個探針都沒放 —— 開機只清
`0xC3000000..0xC38D6FB0` 這 8.8 MB,映像只覆蓋到 `0xC2F30800`。

## 量法

`scratchpad/dram_survival.py`。跟配置器要最大的一塊(class 0 USER,實測
16 MiB 給、32 MiB 拒),每 64 KiB 埋一個位址衍生的標記,清快取,**把記憶體
還回去**,重開後讀原位址。還回去是刻意的:要問的是內容活不活得下來,
不是佔著不放。

三種失效分得很開,這是第一輪沒做到的:

| 讀到 | 意思 |
|---|---|
| 標記 | 保住 |
| 其他真實資料 | 被開機時的配置吃掉 —— **空間**問題 |
| `FFFFFFFF` | 浮空匯流排,那裡不再是記憶體 —— **時間**問題 |
| `00000000` | 被清零(實際一次都沒出現) |

## 結果

| 關機 | 補丁 | 結果 |
|---|---|---|
| 幾秒 | 無 | **128/128 全保** |
| 5 分鐘 | 無 | 頂端 **12,224 KiB 全保**;底部 4,160 KiB 被配置吃掉 |
| 10 分鐘 | 無 | 頂端 **12,992 KiB 全保**;`unmapped` 一個都沒有 |
| 28 分鐘 | 無 | 0/256,202 個 `FFFFFFFF` |
| 25 分鐘 | 有 | 0/256,199 個 `FFFFFFFF` ← **決定性的一輪** |
| 53 分鐘 | 有 | 0/256 |
| 拔電池 | 無 | 0/128,全部 `FFFFFFFF` |

5 分鐘一個位元不掉 → **DRAM 有待機電源、自我更新是開著的**;純電荷撐不了 5 分鐘。
900 秒(15 分鐘)那個視窗因此很可能就是真正的機制。

## 停止時間的補丁:改 getter,不是改建構子

`patches.py` 的 `RETAIN` 改 `0xC00239C8`(建構子)——**開機後補下去沒有任何效果**,
物件早就建好了,而補丁自己又活不過下次開機。

正確的目標是 getter `0xC0024310`:

```
0xC0024350  ldr r1, [r1, #0x18]      設定物件 = 0xC307563C(不是 0xC307523C)
0xC0024354  ldr r4, [r1, #0x4]       使用者值,即 DebugSetOffSec
0xC0024358  mov r0, #0               ← 寫死 0,條件永遠不成立
0xC0024360  cmpne r4, #0
0xC0024368  movw r1, #0xA8C0         43200 秒 = 12 小時,本來的上限
```

`0xC0024358` 改成 `mov r0,#1`(`E3A00001`)+ `sys selfStopTime 43200`,
`sys selfConfig` 的 `Stop Timer` 立刻從 900 變成 43200。**實測通過。**
getter 在關機時才被呼叫,所以補丁當次就生效,不用等下次開機。

`DebugSetOffSec` 就是 `[cfg+4]`,在設定區裡,**會進 flash 跨開機留著**。

## ★ 補丁沒有用 —— 它只改報告出來的數字

**25 分鐘 + 補丁,全滅。** 25 分鐘在原廠 15 分鐘視窗之外,`sys selfConfig`
報 `Stop Timer = 43200`,DRAM 仍然在視窗過後就不是記憶體了。

排除掉的變因:失效的 199/256 讀到 `FFFFFFFF`(不是記憶體)而不是 `other`
(被別人用掉),所以「埋完到關機之間相機把那塊配給別人」不是原因。

### 為什麼沒用 —— 反組譯給了確定的答案

停止時間 getter `0xC0024310` 只有兩個呼叫者:`0xC040FA28`(`sys selfConfig`,
只是印出來)和 `0xC0023E24`,後者是唯一的真實消費者:

```
0xC0023E24  bl  0xC0024310        取停止時間
0xC0023E2C  str r1, [r4, #0x6c]   存回物件
0xC0023E34  cmp r1, #0            ← 只比較「是不是零」
0xC0023E38  beq 跳過
0xC0023E40  bl  0xC0023928        取位元遮罩
0xC0023E4C  orr r1, r1, r2        ← OR 進 [sp+0x20] 的旗標
...
0xC0023EA0  add r1, sp, #0x10     旗標結構
0xC0023EA8  blx 0xC0122610        交給低功耗那一層(Thumb)
```

**那個秒數從頭到尾沒有進到任何結構裡。** 它對下游的唯一貢獻是
「非零 → OR 一個位元」。900 和 43200 走同一條路。

所以這不是單純的「`#if 0` 關掉功能」:**邊界檢查(非零、≤ 0xA8C0)
完整保留,但數值的消費端從來就沒接上。** `mov r0,#0` 只是讓它連布林
都退回內建值。

### 往下挖到底了:MAIN 裡沒有硬體

```
0xC0023900..0xC0024400   XC_SelfRefresh 整段   周邊常數:無
0xC00CDCB0 / 0xC00CDD58  電源層                無
0xC0122610 → 0xC0122F90  XC_PWRS(Thumb)       無
```

從停止時間一路到 `XC_PWRS`,**整條鏈沒有一個 `0x3xxxxxxx` / `0x2xxxxxxx`
周邊位址**。MAIN 裡這一套只是記帳:把布林 OR 成旗標字交給電源層。
真正讓 DRAM 進自我更新的動作跟 LZSS 解壓一樣不在 MAIN 裡,應該在 IPL
(NAND 上另一個分割,我們沒有)。

**`sys selfStopTime` 這條路到此為止,不用再試。**

### ⚠ 「15 分鐘」這個數字沒有證據力

本文前面(第一輪)從 `mov r0,#0x384` 推出「視窗 900 秒 = 15 分鐘」。
**那個推論現在站不住** —— 既然那個數值只被拿來做非零判斷、沒有消費者,
它就不能用來預測真正的保留時間。

實測(2026-09-18,五輪):

```
 5 分鐘   12,224 KiB 保住
10 分鐘   12,992 KiB 保住,整塊 16 MB 都還是真的記憶體
25 分鐘   全滅,199/256 讀到 FFFFFFFF
```

**真正的界線在 10 到 25 分鐘之間,未測完。** 轉變很陡:10 分鐘時一個
`unmapped` 都沒有,25 分鐘時幾乎全是。不是漸進衰減,是整片一次消失。

要用這片記憶體的話這個數字必須量出來,**不能引用 900** —— 那個常數已經
證明沒有消費者。

量測時間要量「關機多久」,不是「埋標記到檢查多久」—— 中間包含相機開著的
時間,我第一次判讀就是栽在這裡。

## 可以用的結論

- **視窗長度未知(5 分鐘保住、25 分鐘全滅),裡面有 12 MB 完整的記憶體。**
- 開機從堆積低端吃掉的量很穩定:三輪 4,160 / 3,392 / 3,392 KiB,**約 3.4 MB**。
  東西放在配置區塊的上半部就躲得開。
- 位址不能寫死、不能用「非零」判斷(冷開機是 `FFFFFFFF` 不是 `0`)——
  見 [[warm-restart-keeps-the-cave]]。

# 為什麼最後還是走設定區(2026-09-18 決定)

熱記憶體有 12 MB、而且完全不碰 flash,但**對「縮短開機」這個目標它比設定區差**:

| | 設定區 | 熱記憶體 |
|---|---|---|
| 空間 | 456 bytes | ~12 MB |
| 位址 | 固定 `0xC3075264` | **每次開機不一樣**(實測 `0x454D2E80` → `0x454CCA40` → `0x451266C0`) |
| 撐過拔電池 | ✓ | ✗ |
| 冷開機讀到 | 相機的設定值 | `FFFFFFFF`(所以「非零即有效」會直接跳進浮空匯流排) |
| 代價 | 寫一次 flash | 無 |

`store_boot` 能壓到 36 個字,是因為它知道要去哪裡看。熱記憶體要先跟配置器要
一塊再找簽章,**引導碼只會變大** —— 而引導碼每多一個字,AutoRun 就多一條
`mem set`,那正是要省的東西。

所以:**開機加速走設定區;熱記憶體留給真的需要空間的東西**,而且要能說出
是什麼才動它。目前沒有東西需要 12 MB(loader 是 428 bytes,og3k 的 3188 筆
全落在每次開機都被 NAND 重寫的映像區,存哪都得重做)。

混合解法(設定區放 4 bytes 指標 + 熱記憶體放本體)可行,但 flash 還是碰了,
「完全不碰 flash」那個唯一的優勢就沒了。
