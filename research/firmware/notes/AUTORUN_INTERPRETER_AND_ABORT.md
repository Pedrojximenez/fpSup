# AutoRun 解譯器,以及怎麼從命令裡把它停掉

2026-09-17。為了「暖開機跳過整份 AutoRun」而追出來的。使用者的設計:
**hook 一個 shell 命令,AutoRun 第一行就呼叫它;有 hook 表示注入區還在,
驗過簽章就把解譯器停掉,後面全部不跑。**

結論:**成立,而且中止只要寫一個 byte。** 以下全部靜態讀出。

> **⚠ 2026-09-18 實機更正:中止只寫一個 byte 是不夠的,還欠一個彈出。**
> §4 那句「寫旗標讓韌體自己收尾,少一個我們要負責正確的步驟」是錯的 ——
> 收尾的彈出**被同一個位元組閘著**,清了它就等於跳過彈出,`depth` 降不回 0,
> USB shell 就起不來(worker 活著但回覆送不出去)。修法與實測表在
> `projects/usb-shell-sup/notes/AUTORUN_STORE_BOOT.md` §6。
> 整條「設定區 + 中止」已經做出來並實機通過,同一份筆記。

---

## 1. 為什麼非停不可

AutoRun 是**逐字元**讀的檔案,行數固定在卡上。前面放檢查**無法讓韌體跳過後面的行** ——
除非把解譯器本身停掉。而使用者實測「時間全花在 `mem set`」,那 76 條寫的是
304 bytes 的 loader(4 bytes/命令),所以能省的就是幾乎整份 AutoRun。

## 2. 呼叫鏈

```
0xC03DA3F8  判斷要不要跑,是則 → 0xC03DA758("\AutoRun.txt", 1)
0xC03DA758  配置 0xA8 bytes 的 ctx(0xC03DB420)→ 0xC03DA510
0xC03DA510  開檔、初始化 ctx、註冊回呼        ← 不是迴圈,是註冊
0xC03DA600  ★ 每次取一個字元                  ← 迴圈的心臟在這
0xC03DA700  收尾:關檔、取消註冊
```

腳本管理單例 `0xC3756940`(在 BSS 內,每次開機重建)。

## 3. ctx 佈局(0xA8 bytes,堆積配置)

```
+0x80  檔名緩衝
+0x90  ★ 執行中旗標(u8)
+0x94  檔案物件
+0x98  檔案絕對位置
+0x9C  0x80 緩衝內的位移
+0xA0  檔案大小(64-bit,搭配 +0xA4)
```

## 4. ★ 中止機制

`0xC03DA600` 的第一件事:

```
0xC03DA60C  ldrb r1, [ctx+0x90]
0xC03DA610  cmp  r1, #0
0xC03DA614  beq  → 回傳 r5 = mvn 0 = -1      ; EOF
```

**`[ctx+0x90] = 0` → 下一個字元回 EOF → 解譯器走自己的正常結束流程。**

`0xC03DA700`(收尾)也印證這個語意:關檔、清 `+0x94`,然後
**`if ([ctx+0x90]) 取消註冊`** —— 所以 `+0x90` 就是「已註冊/執行中」。

> 另一條路是直接呼叫 `0xC03DA700(ctx)`。**不建議** —— 寫旗標讓韌體自己收尾,
> 少一個我們要負責正確的步驟。
>
> **⚠ 這段推論錯了。** 收尾的「取消註冊」是 `if ([ctx+0x90]) bl 0xC0420D90`,
> 跟中止用的是同一個位元組:清零 → 彈出被跳過 → 註冊項永遠留著、`depth` 降不回 0。
> 所以寫旗標**沒有**少一個步驟,它是把那個步驟變成我們的債。
> **誰清那個位元組,誰就欠那個 `CALL 0xC0420D90`**,而且要在清零之前呼叫。
> 症狀只在 USB shell 卡上顯現,查了一天 —— `AUTORUN_STORE_BOOT.md` §6。

## 5. ★ 怎麼在命令裡拿到 ctx

ctx 是堆積配置的,位址每次不同。但註冊時進了一張全域表。

`0xC03DA510` 準備的 36-byte 結構(先從範本 `[0xC2F20FBC]` 複製 9 個 word,再覆寫):

```
+0x00  範本
+0x04  每行回呼      = 0xC03DA7A8
+0x08  結束回呼      = 0xC03DA7C8
+0x0C  ★ ctx
+0x1C  檔名指標(ctx+0x80)   ← 註冊時檢查非零,否則報錯 0x4B
+0x20  byte = 1
```

`0xC0420CC8` 註冊進:

```
表基底   0xC2F20FC0
深度     [0xC2F20FC0 + 0x21C]     最大 15(>= 15 報錯 0x4A)
步幅     36 bytes(depth*9 << 2)
entry    = 0xC2F20FC0 + depth * 36
```

**佈局自洽的佐證**:15 × 36 = 540 = `0x21C` —— 深度計數器正好接在陣列尾端。

註冊時**先遞增深度再算位址**,所以有效索引是 1..15,索引 0 不用。
`0xC0420D90` 取消註冊:把 `[entry+4]` 換成空函式 `0xC0420C20`,再遞減深度。

### 取得 ctx 的兩種寫法

```c
/* A. 直接取堆疊頂 —— 短,但若有巢狀腳本會拿錯 */
u32 base  = 0xC2F20FC0;
u32 depth = *(u32*)(base + 0x21C);
u32 ctx   = *(u32*)(base + depth*36 + 0x0C);

/* B. 掃描,自我驗證 —— 建議用這個 */
for (int i = depth; i >= 1; --i) {
    u32 e = base + i*36;
    if (*(u32*)(e + 4) == 0xC03DA7A8)      /* AutoRun 的每行回呼 */
        { ctx = *(u32*)(e + 0x0C); break; }
}
```

**用 B。** 它靠「每行回呼等於 `0xC03DA7A8`」確認這筆真的是腳本解譯器,
而不是碰巧在堆疊頂的別的東西。多幾條指令換掉一整類誤判。

## 6. 完整流程

```
AutoRun 第 1 行:  <被 hook 的命令> <magic>

冷開機:沒 hook → 命令照常執行(或回錯)→ 第 2..N 行完整載入
暖開機:有 hook → 我們的程式碼跑
                  ├─ 驗簽章:magic + 版本 + payload 的 CRC
                  ├─ 確認 VSHL.BIN 內容已在位
                  ├─ 找 ctx(§5 寫法 B)
                  └─ *(u8*)(ctx + 0x90) = 0   → 當場結束
```

**簽章不能只是旗標。** 冷開機後注入區是**原廠位元組不是零**,比對「非零」會誤判;
舊版卡留下的 payload 會通過旗標檢查但內容是錯的,版本必須進簽章;
self-refresh 過期後 DRAM 內容未定義,CRC 是唯一擋得住半毀 payload 的東西。
見 `DRAM_SELF_REFRESH_AND_WARM_BOOT.md`。

## 7. 查過但不可行的:批次寫入

找過有沒有命令能一次寫超過 4 bytes,好連冷開機一起加速。**沒有。**

最接近的是 `0xC04064C0`(`<id> <檔名>`):開檔、配置 size+128KB、讀進緩衝、
然後 `blx [obj+0x10]` 交給 **id 指定的物件**寫出去 —— 目的地是**分割區**,
不是任意位址。旁邊的 `read id size` / `write id srcAddr size` 同一組。
那是燒分割區的工具,對我們沒用而且危險。

→ **冷開機的 76 條 `mem set` 是硬成本。** 唯一的槓桿是**把 loader 寫小**:
304 bytes = 76 條,砍到 150 bytes 就是 38 條。bootstrap 只需要「開檔、讀、跳」,
其餘都可以外包給 VSHL.BIN 的第二階段。這條跟暖開機的 hook 不衝突,可以疊加,
而且對**每次**開機都有效。

## 8. 待驗 → 已驗(2026-09-18)

- ~~`[ctx+0x90] = 0` 的實機行為~~ → **成立,但要自己補彈出**(見上面 §4 的更正)。
- 巢狀腳本時深度會不會 > 1 —— 仍未遇到;§5 寫法 B 已經對這件事免疫,實作用的就是 B。
- ~~loader 能砍到多小~~ → 現行 264 bytes(66 字),走設定區的組態 464 bytes(116 字);
  AutoRun 實際要寫的只有 **29 字的引導碼**。細節在
  `projects/usb-shell-sup/notes/AUTORUN_STORE_BOOT.md`。

§7 結尾那句「冷開機的 76 條 `mem set` 是硬成本」**已經不成立** —— 設定區跨電源循環
存活,所以第二次以後的冷開機也只要 29 條。唯一還是硬成本的是**第一次**。
