# 輪詢與忙等：靜態清單(2026-10-16，離線)

只讀 `out/seg0_c0000000.bin`，沒有相機 I/O，**也沒有任何頻率或耗時的量測**。
每條標「靜態」(反組譯直接看到)或「推論」。這份是 PC 取樣 profiler 的候選清單，不是熱點結論。
腳本在 scratchpad(`dly.py`、`spin3.py`、`txref.py`)，邏輯都寫在下面。

## 0. 更正：「Cyc thread」其實是週期處理器，r2 是週期不是優先權

`research/rtos/notes/TASK_PRIORITY_MAP.md` §2a 把包裝函式 `0xC0370808` 的第 3 個參數當成 itskpri。
**這是錯的**(靜態)：

- service 0x8047 → `C000C6B8`。它把描述子 +0x0C 存到控制塊 +0x10、+0x10 加上 64-bit 系統時間 `0xC301EAE4`、
  檢查 attr bit 1(TA_STA)。這就是 µT-Kernel `tk_cre_cyc` 的 T_CCYC：`exinf, cycatr, cychdr, cyctim, cycphs, dsname`。
- 名字對得上：`Uvc16ms`=16、`Uvc33ms`=33。
- 所以 0x8047/0x8049/0x804A/0x8048 = cre/sta/stp/del_**cyc**。這也解釋了「拿它建任務會凍結」：
  週期處理器跑在計時器中斷的情境，不能阻塞。

16 個週期處理器(週期 ms，**處理器本體在計時器中斷情境執行**)：

| 週期 | 名稱 | 建立處 | 本體 | 備註 |
|---|---|---|---|---|
| **2** | MONITCYC | `C068336C` | `C0683330` | 建完立刻 sta(`C0370900`)。本體是 7 格輪轉表，每格最多 5 個回呼(`C0683430`)，所以每個回呼每 14 ms 跑一次。註冊者在 `C02DD9xx`/`C02E0xxx`/`C02E32xx`(按鍵／裝置監視) |
| 14 | KeyChat | `C02DD1B4` | `C02DDA68` | |
| 16 | CYC_DRAW | `C0527990` | `C05276F0` | 計數，每 N 次(預設 3)通知 DrawMgr |
| 16 / 33 | Uvc16ms / Uvc33ms | `C04D8AEC` / `C04D8AD4` | r5 | UVC 用，是否常開未知 |
| 20 | GyroCycl | `C00D0650` | `C00D0720` | 已知(陀螺 20 ms) |
| 33 | DngPlayT | `C05BFCD0` | `C05BF488` | CinemaDNG 播放 |
| 50 | RECMGRMV、OSD_CYC | `C0395DD0`、`C04C9B40` | | |

**要上機驗證**：哪幾個在跑。控制塊從 `0xC301EAF8` 的 free list 取出，+0x0C=活動旗標、+0x10=週期，
走一遍就知道。MONITCYC 每秒 500 次是最值得量的一個(每次中斷的進出加上輪轉表)。

`dly_tsk` 共 201 個呼叫點(包裝 `C03705D8` 加 stub `C01F89C4`)。在迴圈裡的有 52 個，**幾乎全部是「等某條件成立再重試」**
(鏡頭 Lmount*.cpp、SD、USB UAC)，只在那個操作進行中才轉。沒有找到常駐的短週期 dly 輪詢任務。
`C03F6968` 裡有 6 個 `dly 3 ms` 的等待迴圈，是同一個函式的多個分支，值得在 profiler 裡留意。

## 2. 硬體忙等迴圈

掃描條件：迴圈 ≤6 條指令、無 BL、無寫入、基底暫存器在迴圈內不變、讀同一位址再條件跳回。
ARM 碼裡沒有真正的命中，**真的忙等全在 Thumb 碼**(Socionext 驅動，沒有 assert 字串，很難歸屬)。下表都是**無上限**的(沒有逾時計數)：

| 迴圈 | 等什麼 | 呼叫者數 | 備註 |
|---|---|---|---|
| `C01DA838`(函式 `C01DA808`) | `[0x3027F214] == 0x11` | **26** | 只在 `[0x3027F210]` bit 4 = 1 時忙等，否則用 `wai_flg` 阻塞。呼叫者在 `C01A0xxx`、`C0638xxx`，往上 4 層是 SigproMgr.cpp。**最可能在常態路徑** |
| `C0651C82` 等，`C0651C40`–`C0659xxx` 共約 60 個 | 16-bit 暫存器，基底 `0x21801002`(+0x20 bit 0、+0x2E…) | 7(僅 `C0651C40`) | 推論是 SD/eMMC 類主機控制器(SDHCI 式 16-bit 暫存器)，IPL 也用 0x2180xxxx |
| `C01EE640` 等，`C01EE540`–`C01EE9A8` 約 25 個 | 經 `0xC31F78xx` 存的暫存器指標，寫命令後等狀態位 | 3 / 1 | 某個序列介面驅動，未識別 |
| `C01F190C` | `[base]` bit 0x10，**夾在 `C01F89A0`/`C01F89E8` 之間**(推論是關中斷／開中斷) | 1 | 關著中斷忙等 = 中斷延遲 |
| `C00FFEC8`、`C0127C20` | `[base+0x800] \|= bit`，再等 `[base]` 同一 bit(基底解得 0x30000000) | 1 / 1 | 時脈或重置控制。往上 5 層是 IMX410 / I2C 設定，屬於初始化 |
| `C0121DF6` 等 7 個(`C0121DB0`…) | RAM 表 `0xC2F146E8 + 0x10*n` 指到的暫存器，set 之後等 ack | 0(函式指標) | 電源域或時脈閘請求 |
| `C0121B72` | `[[r6+0xC]]` bit 0 | 3 | 往上 9 層到 XC_MediaDriverSdcard.cpp |
| `C01ECB90`、`C01EE002`、`C01F1C26`、`C066EE8C`、`C072D1F8` | 各自的狀態位 | 1 | 未歸屬 |

## 3. 結論與界線

- 待機時沒有看到明顯的常駐輪詢任務：主要任務都用 `wai_flg` / 訊息永遠等，週期工作集中在 16 個週期處理器。
- 週期處理器裡只有 **MONITCYC(2 ms)** 的頻率高到值得懷疑，但它每次做多少事要上機量。
- 硬體忙等裡 `C01DA808`(26 個呼叫者、SigproMgr 下面)最可能在影像處理常態路徑上，**而且它有阻塞版本**。
  如果忙等分支常走，改走 `wai_flg` 分支是可行的優化方向，前提是先搞清楚 `0x3027F210` bit 4 的意思。
- 上面沒有一條量過次數或時間。PC 取樣 profiler 是用來確認或推翻這張表的工具。

要上機驗證的事：
1. 走 cyc 控制塊，列出在跑的週期處理器與週期。
2. 待機與錄影時讀 `0x3027F210` bit 4，看 `C01DA808` 走哪一支。
3. 在 `C01DA808` 和 MONITCYC 本體加呼叫計數器(或用 profiler)，取得每秒次數。
4. 讀 IRQ 0x79 一秒內的觸發次數，確認 LensCycl 是否每畫格一次。
