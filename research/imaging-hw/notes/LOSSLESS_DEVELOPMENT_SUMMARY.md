## 1. ★ 壓縮在管線的哪裡 —— 壓完就不能再縮了

這是規劃時最容易搞錯的一點,先講。

```
感測器讀出
    ↓
CRCT 校正鏈 ──> Vbin / Hbin / Hbin2      ← 縮減都在這裡
    ↓
RWZM 重取樣                               ← 縮減都在這裡
    ↓
DRAM 裡的 CinemaDNG strip(打包 12-bit)   ← 幾何到此定案
    ↓
0x300D 無損 JPEG 引擎                     ← 壓縮發生在這
    ↓
SD / SSD
```

引擎讀的就是 hook 點 `FUN_c069ac88` 手上那塊 strip(`INCAMERA_LOSSLESS.md` §0 [C]),
也就是**已經過 hbin/vbin/RWZM 的最終像素**。

**⚠️ 所以:壓縮之後不能再做 hbin、vbin 或 RWZM。** 三個理由,任一個都足夠:

1. **硬體順序**:那三者是 CRCT 管線上的級(`0x300F08xx` / `0x300F09xx`),
   物理上在寫進 DRAM 之前。壓縮引擎在 DRAM 之後。沒有回頭路。
2. **資料型態**:引擎輸出是 Huffman 位元流,不是像素。任何縮減都得先完整解碼,
   而相機的影片路徑根本沒有這條解碼路(§8)。
3. **尺寸帳**:壓縮不改變幾何,只改變位元組數。要改幾何就得回到 CRCT 去改,
   那是另一組欄位、另一份文件(`CRCT_PATH_SELECTOR_SOLVED.md`)。

⇒ **規劃順序永遠是:先決定幾何(感測器模式 + hbin/vbin + RWZM),再談壓縮。**
反過來做的話,壓縮率算出來是對的,但那是在一個還沒定案的畫幅上算的。

## 2. 引擎的成本模型(上機實測,±2 µs)

```
t(µs) = 2,179  +  4,954.40 × 對齊Mpix  +  40.926 × tile數
        └每次呼叫   └ 201.8 Mpix/s        └ 每個 tile
```

三項都是真的,而且**分得開**(用同光柵、不同 tile 數的控制組拆出來的)。
「對齊 Mpix」是**補滿 tile 之後**的像素數,不是有效像素。

### 已推翻的舊數字

| 舊值 | 狀態 |
|---|---|
| 32 Mpix/s | ❌ 那是 watchdog timeout,不是吞吐 |
| 169.7 Mpix/s | ⚠️ 不算錯,但它是 **256×256 下的等效速率**,把 per-tile 成本攤進了每像素。拆開後是 201.8 + 40.93 µs/tile + 2.18 ms/call |
| 300 Mpix/s 天花板 | ⚠️ 推論值(1 px/clk @300 MHz),實測 201.8 |

**做任何預算都用三項模型,不要用單一 Mpix/s。**

### tile 幾何可以用成本函數直接搜,但少一個約束會搜錯

搜尋空間是引擎自己的 guard:tileW 32..512 步進 32、tileH 偶數且 ≤512、tile 數 ≤326
(表頭缺口容量)。**再加上 TIFF 要求 TileLength 是 16 的倍數**(§14.7 說「非 16 倍數
是相容性實驗,不是預設」)。

⚠️ 少了 16 倍數那條,搜出來的解會**比實測最佳更快但不合法**:
FHD 得 512×364(13.75 ms)而非 512×368(13.87)、OG3K 得 512×504(33.84)而非
512×512(34.33)。加上約束後,四個格式的最佳解與時間**全部逐一重現**。

### 最佳 tile 幾何(最小化上式)

| 格式 | 最佳 tile | tiles | 時間 | vs 256² |
|---|---|---|---|---|
| FHD 1936×1090 | **512×368** | 12 | **13.87 ms** | −17.4% |
| OG3K 3024×2010 | **512×512** | 24 | **34.33 ms** | −7.9% |
| UHD 3840×2160 | 480×432 | 40 | 44.91 ms | −12.9% |
| 6K 6064×4042 | 512×512 | 96 | 130.8 ms | −8.3% |

少 9 個 tile 比少 0.035 Mpix 值錢 —— 這是 per-tile 那一項的直接後果。

### ★ 引擎接受的位元深度 —— 沒有 8-bit,而且非法值直接失敗

`FUN_c062fff8`(Thumb,`0xC062FFF8`)開頭就把 initStruct[2] 的 bitdepth code
攤成四個分支,逐指令:

```
c0630038  ldr  r0, [r5, #8]      ; bitdepth code
c063003a  subs r0, #1
c063003c  blo  c063004c          ; code 0  -> 12 bits
c063003e  beq  c0630052          ; code 1  -> 14 bits
c0630040  cmp  r0, #2
c0630042  blo  c0630058          ; code 2  -> 16 bits
c0630044  bne  c063005e          ; ★ 其他任何值
c0630046  movs r2, #0 / #0xa     ; code 3  -> 10 bits

c063005e  movs r0, #1            ; ★ 返回 1
c0630060  b    c0630200          ;   直接跳過所有設定,到共用 epilogue
```

返回值慣例確認過:成功路徑 `c06301fe movs r0, #0`,而幾何 guard 失敗
(`c06300c4 movs r0, #1`)走的是**同一條**失敗路徑。**1 = 失敗。**

⇒ 兩層意義:
1. **沒有任何 code 代表 8-bit** —— 只有 12 / 14 / 16 / 10 四個值。
2. **傳未定義的 code 會立刻失敗**,跟寬度不是 8 的倍數同等待遇。

而 **RAW 輸出路徑有 8-bit**:`smallraw_bit` 的分支印 14 / 12 / 10 / **8** / other
(`out/decomp/rawpath.c` 附近)。

**所以 8-bit 與無損壓縮是兩條互斥的降頻寬路線,不能疊加。**
8-bit 是有損、零引擎時間、省 1/3;壓縮是無損、吃掉大半幀預算、省 1/2。
FHD 29.97 實例:12-bit 未壓縮 97.2 → 8-bit 未壓縮 65.6 → 12-bit @2:1 49.8 MB/s。

## 4. ★ 現行架構是串行的,兩邊必須相加

同一個 worker **先 blocking encode,再同步 SD flush,返回後才取下一幀** [C]。
所以引擎 duty 和卡速**不是兩個可重疊的資源**。

```
frame service time = encode + write      ← 現行架構
```

| 模式 | 預算 | encode | write@94 | 串行合計 | 判定 |
|---|---:|---:|---:|---:|---|
| FHD 23.976 | 41.71 ms | 13.87 | 13.4 | **27.3 ms** | ✅ 最安全首測 |
| FHD 29.97 | 33.37 ms | 13.87 | 13.4 | **27.3 ms** | ⚠️ 94 可試,66 邊緣 |
| OG3K 23.976 | 41.71 ms | 34.34 | 35.7 | **70.0 ms** | ❌ |
| UHD 23.976 | 41.71 ms | 44.91 | — | — | ❌ 卡在引擎 |

**要管線化(encode/write 分開 worker)才能談 OG3K。** 那不是調 tile 能解的。

| | 未壓縮 | 2.525:1 | 2.0:1 | 1.5:1 |
|---|---|---|---|---|
| FHD 30p | 97.2 | 39.9 | 49.8 | 65.6 |

## 5. 動態抽幀 —— 能算,但不能當成透明的壓縮細節

公式(`ADAPTIVE_FRAME_COMPRESSION.md`):

```
f = min(1, 引擎每秒能壓的幀數 / 格率)
平均碼率 = 未壓縮 × (1 − f × (1 − 1/壓縮比))
```

**格式上合法** [C]:CinemaDNG 一幀一檔,`Compression` 是 per-IFD,
同一段裡有些幀壓有些不壓完全合規,沒有幀被丟掉。

**但有三個問題,都不是算式能解的** [C/I/P]:

1. **峰值沒降**。抽幀降的是平均,未壓縮那幾幀仍然是原始速率。
   卡的瓶頸是持續寫入,所以「平均省 25%」≠「原本會斷的現在不會斷」。
2. **機內回放不吃**。`FUN_c05c1880` 只讀 `StripOffsets`,不讀
   `TileOffsets` / `Compression` / `TileWidth`。主機端驗證過的 tiled
   `Compression=7` **不能假設放回相機會播**。
3. **時間軸會壞**。連號寫出 → 被抽掉的時間消失、動作加速;保留號碼 → 檔號缺口,
   播放器行為未驗證;重複上一幀 → 保住時間但失去 I/O 收益。
   真正保留拍攝時間需要 per-frame timestamp / VFR index / sidecar。

⇒ **安全的產品分法只有三種**:整段固定低一級 fps、壓縮片標成只能匯出並附 sidecar 時間軸、
或另做能理解 VFR 的回放層。在其中一條完成前,這支線維持研究 probe。

## 6. 非整張壓縮(實驗性)

「一幀壓一部分」在**算術上**可以把 f 從整幀粒度變成連續值,
好處是**峰值也跟著降**(每幀大小一致,而不是大小交替)。

但它在**格式上不合法**:一個 IFD 要嘛是 tiled `Compression=7`,要嘛是未壓縮 strip,
沒有「半張壓縮」的表示法。要做就得自訂容器或 sidecar,而那就回到 §5 的回放問題。

模擬器提供這個開關,是為了讓「平均 vs 峰值」的差別看得見 —— 不是說它可以直接做。

## 9. 感測器模式表(模擬器的格式來源)

`0xC0B59DC0`,70 筆,`0x64` bytes 一筆。模擬器直接用它,不是手選幾個代表值。

```
+0x00 模式 id   +0x04/+0x08 光柵   +0x2C/+0x30 輸出裁切(多數為 0)
+0x34/+0x38 裁切原點   +0x3C 位深旗標   +0x40 ★ 標稱格率
+0x44/+0x48/+0x4C/+0x50 四個合併倍率
```

★ **`+0x40` 就是格率**,對照實測值全中:mode 3→30(實測 29.97)、
mode 121→25(24.9997)、mode 98→78(77.27)、mode 97→40(39.16)、mode 0→20(19.13)。
**它是標稱值,不是精確值。**

**13 種光柵**:6064×4042、6064×3412、6064×2022、5712×3216、4176×2174、3968×2640、
3032×2012、3032×1708、2088×1174、2016×1344、2016×1136、2016×672、1984×1320

**17 種格率**:18, 20, 24, 25, 30, 40, 48, 50, 60, 70, 78, 80, 90, 100, 105, 120, 240

### ★ 一個感測器模式 = 八張表、252 個字

描述子 `0xC2F1E654` 開頭列了**七張 70 筆的表**,加上 register record 共八張。
**八張都帶 mode id、八張都用同一個列號索引**(不是拿 id 去查),
而每張的 stride 就是「到下一張表的間距 ÷ 70」—— 它們背靠背排在一起。

| 表 | 位址 | stride | u32 | 會變 | 內容 |
|---|---|---|---|---|---|
| timing | 0xC0B59500 | 0x20 | 8 | 5 | hmax/tail/vmax ✅ |
| metadata | 0xC0B59DC0 | 0x64 | 25 | 21 | 幾何/標稱格率/合併 ✅ |
| C | 0xC0B5B918 | 0x08 | 2 | 2 | {類別 2–7, mode id} ❓ |
| D | 0xC0B5BB48 | 0x28 | 10 | 6 | 四組 packed u16 + 20/60/120 ❓ |
| E | 0xC0B5C638 | 0x38 | 14 | 9 | 大的 packed 值 ❓ |
| F | 0xC0B5D588 | 0x14 | 5 | 2 | 一個 0x1xxxx 旗標 ❓ |
| G | 0xC0B5DB00 | 0x68 | 26 | 25 | 含第二個 mode id;某些列有 6064/4042 ❓ |
| register | 0xC0B5FDAC | 0x288 | 162 | 133 | 寫進感光元件的設定 ❓ |
| **總計** | | | **252** | **203** | |

⇒ **懂的只有 timing 與 metadata(33 字 / 26 會變);其餘六張共 219 字、177 會變,全部沒有名字。**
open gate 在感測器層的所有操作都走 timing,沒碰過那六張。

### ★ register record 解開了:161 個感光元件暫存器

它**不是** `{位址, 值}` 對,也不是 162 個不明參數。三條證據:

1. 當成 u32 對:兩邊都變(66/81 與 67/81)—— 位址欄不該這樣。
2. 當成 u16:**上半字 70 個模式全是 0**,11,340 個值**沒有一個超過 252**。
3. `FUN_c03258c8` 直接證實 —— 它對一筆記錄做 **161 次** `FUN_c0322c70(暫存器, 值)`,
   **暫存器位址是寫死在那個函式裡的常數**,不在表裡:

```
record[mode]  word 0       mode id
              word 1..161  各一個 8-bit 值

FUN_c0322c70(reg, val) → FUN_c0322cb0:
    buf[0] = reg >> 8 ;  buf[1] = reg ;  buf[2] = val
    ⇒ I2C:16-bit 暫存器位址 + 8-bit 值
```

暫存器範圍 `0x0001`–`0x08B7`,161 個各不重複,分布在七個頁
(高位元組 0/2/4/5/6/7/8,各 34/6/38/42/4/35/2)。另有一次常數寫入 `reg 0xCE = 0`。

⇒ **結構解開,語意未解**:知道每個值進哪個暫存器,但不知道那些暫存器做什麼 ——
那需要 IMX410 的暫存器表,不公開。m98 vs m117 的差異因此變成
**79 個具名暫存器**而不是 79 個匿名的字。

### ⚠ metadata 幾乎不能拿來判斷「這兩個模式一不一樣」

**m98 vs m117 是反例,而且是使用者從實拍差異反推出來的。**
兩者在 metadata 上幾乎相同 —— 同光柵 3032×2012、同 merge (2,2,2,2)、同 3:2、同 12-bit ——
但八張表加起來 **203 個會變的字裡有 118 個不同**:

```
register 79/133   G 20/25   metadata 8/21   E 4/9
timing    3/5     C  2/2    D        1/6    F 1/2
```

metadata 那 8 個差異裡有 5 個只是 crop 欄位歸零。
**真正決定讀出行為(含像素合併的實際效果)的東西在 register record 與 table G,而那兩張都沒解開。**

⇒ 教訓:**用 metadata 做模式比較會系統性低估差異**。任何「這兩個模式應該一樣」的推論,
都要先 diff 全部 203 個會變的字。網頁上有現成的比較工具。

### ★ 時序表解開了(2026-09-21 稍晚)

捲簾與真實格率不在 metadata 裡,在**描述子的第一張表**:

```
0xC0B59500,70 筆,stride 0x20,★ 與 metadata 用同一個列號索引
  +0x00  mode id      +0x04  hmax, tail(兩個 u16)     +0x08  vmax
  每幀週期 = hmax × (vmax−1) + tail 個時脈 @ 72 MHz
  捲簾     = hmax × 高度 / 72 MHz
```

⚠️ **先前把 stride 當成 `0x40` —— 那是兩筆的長度**,於是往外走每次跳過一筆、
id 只湊到一半、還會走過頭撞進 metadata 表,因此一度被判定為「解不開」。
描述子前兩個 `{指標, 筆數}` 是 `{0xC0B59500, 70}` 與 `{0xC0B59DC0, 70}`,
間距剛好 70 × `0x20`,不用猜。

**九個獨立記錄過的數字全部對上**:mode 12(3.08 ms / 239.760240 fps)、
8(6.16)、139(8.31)、98(12.44)、3(24.98 / 29.97)、121(24.9997 fps)、
97(39.16)、0(19.13)、106(10.556)。

捲簾全表範圍 **3.08 – 51.14 ms**。

⚠️ **光柵 ≠ 壓縮輸入尺寸。** 中間還有 hbin/vbin 與 RWZM(§1)。
例:mode 106 光柵 3032×1708,經 RWZM 1600 之後才是 CinemaDNG 的 1936×1090。
模擬器把縮減做成獨立的下拉,算出來是 1936×1092 —— 差的兩行是實際路徑還有裁切。

## 10. 模擬器

本文的計算做成了網頁:`fpSup/explainers/lossless-compression.html`。
它把 §2 的成本模型、§3 的比例範圍、§4 的串行架構與 §5/§6 的兩種粒度
接成一個可調的預算試算。
