# 抽幀壓縮(opportunistic compression)—— 可行性與拆分評估

2026-09-15。提案:**錄影時壓縮引擎忙就直接輸出未壓縮的幀,引擎一空下來就
立刻處理最新的那一幀。** 本文評估它的可行性,以及它能不能和 OpenGate 拆開來做。

信心標記沿用姊妹文件:**[C]** 反編確認 · **[I]** 推論 · **[P]** 需上機實測。
基礎事實出自 `RAW_COMPRESSION_RESEARCH.md`,不在此重述。

---

## 0. 結論

**可以拆,而且應該拆。** 唯一真正的耦合是機內回放。

但**在設計之前要先量一個數字**:壓縮引擎的真實吞吐。它決定這個功能是
「省一半頻寬」還是「幾乎沒省」,而目前只知道它在 32–300 Mpix/s 之間。

---

## 1. 提案本身在格式上是合法的 [C]

CinemaDNG 是**一幀一個檔**,而 `Compression` 是 per-IFD 標籤
(`1` = 未壓縮、`7` = 無損 JPEG)。所以:

- 同一段素材裡有些幀壓縮、有些沒壓縮,**格式上完全合法**
- 每個檔獨立可解,不需要容器層做任何配合
- 沒有幀被丟掉 —— 壓不到的幀照樣寫出去,只是未壓縮

原廠現況:**錄影從不壓縮**(FHD/UHD CinemaDNG 都是 `Compression=1`),
只有拍照 DNG 用 `Compression=7`。所以這是把既有引擎接到一條沒用過它的路上。

---

## 2. 幾何守衛三種格式都過 [C]

引擎的守衛是「寬 8..0x4000 且為 8 的倍數、高 2..0x4000 且為偶數」:

```
OG3K   3024 x 2010    3024 = 8×378 ✔   2010 偶數 ✔
UHD    3856 x 2170    3856 = 8×482 ✔   2170 偶數 ✔
FHD    1936 x 1090    1936 = 8×242 ✔   1090 偶數 ✔
```

**同一份實作對三種格式通用,不需要為 OpenGate 特製。**

---

## 3. ★ 節省幅度完全取決於一個未知數 [C floor / P true]

設引擎吞吐 `T`(Mpix/s)、每幀像素 `P`、格率 `R`,則能壓到的比例

```
f = min(1, T / (P × R))
平均資料率 = raw × (1 − f/2)
```

OG3K30 的像素率 = 3024 × 2010 × 29.97 = **182.2 Mpix/s**:

| 引擎吞吐 | f | 273 MB/s → | 省 |
|---|---|---|---|
| ≥182 | 1.00 | 137 MB/s | 50% |
| 91 | 0.50 | 205 MB/s | 25% |
| 32(已知下限) | 0.18 | 249 MB/s | **9%** |

UHD 的像素率是 250.8 Mpix/s,門檻更高。

**32 Mpix/s 是 `FUN_c062f6f8` 的 watchdog 逾時算出來的下限,不是量到的吞吐。**
真實值未知,而上表顯示結果差了五倍以上。

> **所以第一步不是設計,是量。** `RAW_COMPRESSION_RESEARCH.md` §10 已經指定了
> 方法:idle 狀態下的 IRQ-0x29 計時探針。不碰錄影路徑、低風險,而且量完才知道
> 這功能值不值得投入。

---

## 4. 能不能和 OpenGate 拆開

### 可以拆的理由

| | OpenGate | 抽幀壓縮 |
|---|---|---|
| 動的東西 | 幾何:感測器模式、畫布、DNG 標頭 w/h/crop | 寫入路徑:strip 內容 + `Compression` 標籤 |
| 掛點 | `0xC043A19C` 畫布、`og3ksel` 旗標、PARAM | `0x300D0000` 引擎 + DNG writer |
| 交集 | **只有 DNG writer 一點** | |

而且它**對原廠格式的價值一樣大** —— UHD 12-bit 是 373 MB/s,壓到 ~190 就能
脫離「必須外接 SSD」。綁在 OpenGate 底下反而限縮了它的適用範圍。

### ⚠ 唯一真正的耦合:機內回放

相機有無損 JPEG 的**解碼**器(`FUN_c05a69e0`),但
**CinemaDNG 的回放路徑吃不吃 `Compression=7` 是未知的 [P]**。

而機內回放正是 OG3K 這一輪才修好的東西
(見 `projects/open-gate/notes/OG3K_PLAYBACK_PROFILE_CLASSES.md`)。

**所以壓縮必須用獨立的卡做。** 回放一旦壞掉,才能立刻分辨是壓縮還是 OpenGate
的責任;綁在一起出問題時兩邊都要重查。

---

## 5. 三個實作上的坑

**① 編碼函式是阻塞的 [C]。** `FUN_c05a6920` 會阻塞到完成。
「壓縮的同時繼續收下一幀」必須放在獨立的工作任務,不能在幀回呼裡直接呼叫。

**② 單一引擎、沒有 mutex [C]。** 錄影中若使用者按快門拍照,兩邊搶同一顆引擎
會**卡死 IRQ 0x29,需要重開機**。必須自己做互斥。
(`RAW_COMPRESSION_RESEARCH.md` §3 把這列為唯一風險,原話是「只在 idle 時叫」——
本提案正好要在非 idle 時叫,所以這條風險被提升了,不是繼承而已。)

**③ 壓縮後大小事前未知 [I]。** 未壓縮幀的大小是固定的,壓縮幀要等壓完才知道。
若 DNG writer 預先配置 strip 大小或預先算檔案長度,混合長度會需要改寫入邏輯。
寫入端的實際行為還沒查。

---

## 6. 還有一個沒被討論的好處 [I]

抽幀壓縮的輸出是**混合序列**,而卡的瓶頸是「持續寫入速率」不是「平均」。
如果引擎吞吐落在中段(f 約 0.3–0.7),資料率會**逐幀跳動**而不是均勻降低。

對一張撐不住的卡來說,**跳動的峰值仍然是原始速率** —— 換句話說
「平均省 25%」不等於「原本會斷的現在不會斷」。

這件事要在設計階段就想清楚:**目標是降低平均值(錄更久),還是降低峰值
(不會斷)?** 前者抽幀壓縮做得到,後者做不到。

---

## 7. 建議的順序

```
1. 量吞吐(idle,IRQ-0x29 探針)         ← 沒有這個數字,後面都是猜
2. 確認 CinemaDNG 回放吃不吃 Compression=7
3. 確認 DNG writer 能不能接受變動長度
4. 錄影中的互斥設計(與拍照搶引擎)
5. 才是抽幀排程本身
```

**1 和 2 都不需要碰 OpenGate,也不需要改錄影路徑。**
