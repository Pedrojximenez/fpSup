## 1. 感測器讀出模式

模式容器 `0xC0B5FDA4`(70 筆,register record `0x288` bytes);
metadata 表 `0xC0B59DC0`(`0x64` bytes 一筆)。

```
+0x00 模式 id   +0x04/+0x08 光柵   +0x2C/+0x30 輸出裁切
+0x34/+0x38 裁切原點   +0x3C 位深   +0x40 格率類別
+0x44/+0x48/+0x4C/+0x50  四個欄位,全讀模式是 1、縮減模式是 2/3/6
```

可用的 3:2 幾何(其餘是 16:9 或更扁):

| 光柵 | 相對全寬 | 例:模式 / fps / 捲簾 |
|---|---|---|
| 6064×4042 | 1.00 | 121 @24.9997、3 @29.97、97 @39.16、0 @19.13(RAW14) |
| 3968×2640 | 1.53 | 靜止畫用 |
| 3032×2012 | 2.00 | **98 @77.27 (12.44 ms)**、117 @99.90、11 @105.40、143 @18 |
| 2016×1344 | 3.01 | 8/139 @59.94、148 @69.97、149 @79.98、150 @89.93、147 @100.15、**56 @119.88 (6.16 ms)** |

16:9 與其他:6064×3412、5712×3216、4176×2174、3032×1708、2088×1174、
2016×1136、2016×672、6064×2022、1984×1320。

**捲簾只有這一層能改善。** 後面兩層都在讀出之後,不影響捲簾與感測器頻寬。

⚠ metadata 的 `+0x44/+0x48` 精確語意仍未定;`+0x4C/+0x50` 已確認是
有效 X/Y geometry scale,但只證明座標倍率,不能分辨 charge binning、skipping
或其他 sensor reduction。它們和 §2 的 CRCT 列舉不是同一套編碼。

## 2. CRCT 的 hbin / vbin —— ★ 主要發現

### 來源:PARAM 四個欄位

```
PARAM +0x58   預覽 hbin        PARAM +0x5C   錄影 hbin
PARAM +0xC4   預覽 vbin        PARAM +0xC8   錄影 vbin
```

由 `FUN_c0438018` 填進 `XC_LiveViewDispParamWithRaw` 描述子的
`+0x50/+0x54`(錄影)與 `+0xA8/+0xAC`(預覽),
在 `PreExpos_s` 以 `FUN_c022ee10` / `FUN_c022ee90` 轉成倍率。

### 列舉 → 倍率(從轉換函式讀出)

```
hbin  FUN_c022ee10:  0 → 1      1 → 3      2 → 5      其他 → assert + 無窮迴圈
vbin  FUN_c022ee90:  0 → 1      1 → 3      其他 → assert + 無窮迴圈
```

**水平可以 ÷3 或 ÷5,垂直只能 ÷3。hbin 沒有 ÷2。**

指令層級驗證過(不是 Ghidra 的誤讀):

```
cmp r1,#0 → mov r1,#1     cmp r1,#1 → mov r1,#3     cmp r1,#2 → mov r1,#5
```

`0xC022EC00..0xC022F200` 範圍內沒有第二對轉換函式(那一帶其他的 `mov r1,#N`
是解構子的參數與 assert 行號)。

**÷2 存在,但不在 hbin:感測器的 2×2 geometry reduction(6064→3032)和
RWZM 2048 各有一份。** 前者究竟是合併或跳讀尚未解。看起來是刻意分工 ——
÷2 用感測器做最省(讀出前就減半,連捲簾一起省),
CRCT 補的是感測器做不到的奇數倍率。

**垂直比水平少一檔,所以維持 3:2 只有 `hbin=3 + vbin=3` 一種組合**
(÷5 配 ÷3 會變成 606×670)。

⚠ **寫入非法值不是畫面壞掉,是相機當場鎖死**(`FUN_c0011100` 之後 `while(true)`)。

### 倍率怎麼用

`PreExpos_s` 的尺寸公式把它當除數:

```c
out = ((rwzm_h >> 1) + ((in + (hbin >> 1)) / hbin) * 0x400) / rwzm_h;
```

先除 hbin,再除 rwzm/1024。**兩段相乘。**

### 硬體暫存器

```
主管線  0x300F0800  垂直控制      0x300F0840  水平控制(hbin 代碼)
        0x300F0810/0814/0818/081C   四個 32-bit 參數
        0x300F0850/0854/0858/085C   四個 24-bit(疑似係數)
        0x300F0820 / 08C0 / 08C4
副管線  0x300F2800 / 2810 / 2814 / 2840 / 2850   —— 精簡版,只有一個係數槽
```

驅動:主 `FUN_c0633b30`、副 `FUN_c0633da0`。

### 原廠實際用量

```
錄影 hbin/vbin   306 個 profile 全部是 0 —— 從未使用
預覽 hbin/vbin   17 個 UHD profile 是 1(÷3),lv rwzm 同時是 unity
```

那 17 個都是感測器 6064×3412 的 UHD profile:**拍 UHD 時的即時取景就是
hbin÷3 + vbin÷3 做出來的,RWZM 完全沒開。** 硬體路徑是通的、在生產環境每天跑,
只是沒用在錄影。

## 3. RWZM

```
PARAM +0x60 / +0xD0   預覽 H / V        PARAM +0x64 / +0xD4   錄影 H / V
```

**值 ÷ 1024 = 縮減倍率。`≤ 1024` 一律當 unity**(`if (*param_2 < 0x401)`)。

原廠用過的值:

```
預覽:  1023  1280  1500  1536  1600  2048  3072
錄影:  1023  1500  1600                        ← 上限 1.5625×
```

FP3K 專案實測把錄影設到 **2048(×2)** 可行。×3 沒人做過。

硬體:主 `0x300F0900/0908/090C`(`FUN_c0633e60`)、
副 `0x300F2900/2908/290C`(`FUN_c0633f20`)。
低半字 = 比率,高半字 = 由比率算出的相位:

```
比率 1600 → 0x00E00640      比率 2048 → 0x00000800(相位 0)
```

相位算法:`r = ratio & 0x3FF; if (r < 0x201) r = 0x400 - r; phase = 0x200 - (r >> 1)`。

## 4. ★ hbin 與 RWZM 互斥

```c
if (((rwzm 有作用) && hbin_code != 0) && (FUN_c0633d70() == 0)) {
    hbin_code = 0;                    /* hbin 被清掉 */
}
```

`FUN_c0633d70()` 讀 `0x300F0870 == 1`,寫它的只有 `FUN_c0633d30`,
而**全韌體三個呼叫點傳的都是 `0`**。

**所以在原廠韌體裡,RWZM 一開,hbin 必定被關掉。要並用必須自己設 `0x300F0870`。**

## 5. 六選一的 mux

3-bit 欄位,a0 在 `0x300F06B0`、a7 在 `0x300F06D0`:

```
0 CrctGainToBufA    1 CrctCrmfToBufA    2 CrctVbinToBufA
3 CrctHbinToBufA    4 CrctHbin2ToBufA   5 CrctSpcToBufA
```

它選「從校正鏈的哪一點把緩衝拉出來」。RWZM 不在這個 mux 裡,
它掛在另一個緩衝 `bufa1`,只有開關。

`Crmf` 是一個 RAW 修正級,和 `dclp`、`defect_collect`、`pdaf_correct` 同一族,
都有 shell 開關(`imager crmf_off <flag>` 等)。**Crmf 與 Spc 的實際作用未確定。**

⚠ **選了 Hbin ≠ 正在做 binning。** mux 檔位和 binning 級的 bypass
(`0x30100980`)是兩件事,可以互相矛盾。

## 6. 組合起來能做什麼

以 OG3K 的感測窗 3032×2012 為例:

| 手段 | 輸出 | 3:2 | 已證實 |
|---|---|---|---|
| 原樣 | 3032×2012 | ✔ | ✔ |
| hbin÷3 + vbin÷3 | 1010×670 | ✔ | 預覽側已證實,錄影側從未使用 |
| hbin÷5 + vbin÷3 | 606×670 | ✘ | 同上,而且比例壞掉 |
| RWZM 2048 | 1516×1006 | ✔ | FP3K 做過(在別的感測窗上) |
| RWZM 3072 | 1010×670 | ✔ | 沒人做過 |
| hbin + RWZM 同時 | — | — | **被仲裁擋住**(§4) |

換感測器模式則另外給 6064×4042 / 3968×2640 / 3032×2012 / 2016×1344 四種 3:2,
而且**只有這一層能改善捲簾**。

## 7. 還沒定案

- `Crmf` 與 `Spc` 各是什麼修正
- `Hbin` 與 `Hbin2` 的差別(主管線只有一組水平 binning 暫存器 `0x300F0840`,
  所以 Hbin2 不是第二組暫存器)
- metadata `+0x44..+0x50` 的 1/2/3/6 是描述還是指令
- `0x300F0850..085C` 四個 24-bit 值是不是係數
- `0x300F0004` bit8(來自 reduction record `+0x2D`)
- 錄影側 hbin 從未被原廠使用過 —— 意味著**沒有任何一段原廠影片可以拿來當對照**
