## 1. ★ 類比指紋:70 個模式分三群,這才是暗部雜訊的來源

感光元件暫存器表在 **`0xC0B5FDAC`**,70 筆 × `0x288`(648) bytes,順序與時序表相同。
`codex/analyze_imx410_modes.py` 從反編譯的 `FUN_c03258c8` 取出 writer map,
把 648 bytes 解成 **161 個真正的 IMX410 暫存器位址**。

用 **`0x0400`–`0x05ff`(類比區)當指紋**分群:

```
安靜組 40 個   3, 7, 10, 27, 88, 97, 98, 101, 102, 106, 121, 123, 143, 151 ...
快速組 22 個   8, 9, 11, 12, 56, 58, 89, 103, 104, 105, 111, 112, 117, 118 ...
第三組  8 個   0, 6, 95, 100, 122, 129, 141, 144
```

實測的讀出雜訊底線(ISO100,DN):

```
mode 117  快速組   R = 0.965
mode  98  安靜組   R = 0.551
mode   7  安靜組   R = 0.455
mode 106  安靜組   R = 0.437
```

**mode 117 是 100 fps 的監看模式,屬快速組。我們把一個高速監看模式拿來當 29.97
錄影用,連它的吵讀出一起繼承了 —— 這就是 open gate 暗部噪點的真正來源。**

對照 SIGMA 自己的選擇:mode **106** 和 mode **111** 同為 3032×1708 @29.97,
106 在安靜組、111 在快速組,而 **picker 的 29.97 槽填的是 106**。他們知道要選哪個。

3032×2012 這個幾何底下,安靜組只有 **98 和 143**(都是 `ACQ_` 類)。

## 2. ★ 648 bytes 拆成兩個正交區塊

```
區塊 A  讀出設定   77 個字,0x00xx(15) + 0x02xx(2) + 0x04xx(33) + 0x05xx(28)
        117→98 與 117→7 把這 77 個字改成「完全相同的值」
        → 98 和 7 共用安靜設定;117 和 11 共用快速設定
        → 117 vs 11 全表只差 2 bytes(mode_id 與 +0x10)

區塊 B  縮減倍率   28 個字,+0x000/004/00C/014/038 與 +0x1F8..+0x274
        97→98 與 3→117 把這些改成「完全相同的值」,跨越不同讀出設定
        reg 0x0793 = 倍率本身      1 / 2 / 3
        reg 0x0717 = 倍率的兩倍    2 / 4 / 6
        reg 0x0792 = 0x10 / 0x22 / 0x30
```

**兩塊互不干涉**,理論上可以分開移植(例如把安靜設定搬進 mode 117 而不動縮減)。

## 5. ★★ 沒解開的矛盾 —— 讀到這裡的人請先看這節

**mode 98 與 mode 106 的暫存器完全同一組**(同樣的 2× 縮減設定、同一個類比指紋),
差別只在下游 RWZM 與行窗。所以 `a_98 / a_106` 應該就等於 FHD 重取樣核平均的樣本數:

```
a_98  = 0.01352   RWZM = 1.0(我們改的),沒有重取樣
a_106 = 0.00396   RWZM = 1.5625×

a_98 / a_106 = 3.41
```

**但 1.5625× 縮小一個輸出像素最多只有 2.44 個輸入樣本可平均。3.41 > 2.44,
物理上不可能。**

同一套模型算出的另一個數字:

```
原廠 FHD(2× 讀出) vs 原廠 UHD(1× 讀出),兩者重取樣比幾乎相同(1.566 / 1.573)
a_FHD / a_UHD = 0.329   →  2× 那一層每像素收 3.04 顆感光點
                            (純跳行應為 1.00,2×2 合併應為 0.25)
```

**所以 `σ² = a·S + R²`、`a = c/k` 這個模型漏了東西。** 可能的破口:

- FHD 路徑上另有一層降噪
- RWZM 不只一級縮放
- 每個模式的 DN 正規化常數 `c` 其實不同
- 區塊統計在不同輸出解析度下有偏差

**在補上這個洞之前,「2× 是跳行還是合併」沒有答案。** 本文其他結論(類比指紋、
mode 98 的 +1.5 EV、可逆性)都是直接量到的,不受影響;只有「每像素幾顆感光點」
這一項不可信。

### 想解開的話:唯一乾淨的量法

兩邊都關掉重取樣,比較 1× 模式與 2× 模式:

```
2×  mode 117/98,RWZM = 1.0   已有(clip 065 / 066)
1×  某個 1:1 模式,RWZM = 1.0  需要,但見下一節 —— 不能直接用 mode 3
```

1× 模式的原生輸出必須小到能塞進畫布,否則溢位(§6)。可行做法是把 mode 3 的
vmax 改慢到 ~7 fps、畫布 hook 改成 6064×4042,資料率降到約 258 MB/s。未做。

## 6. 坑:RWZM unity + 1× 模式 = 當機

**實測:picker 填 mode 3、RWZM 留 unity、畫布 hook 釘 3032×2012 → 開始錄影後
幾乎立刻凍住,USB 整個消失,要拔電池。**

```
感光元件送出   6064 × 4042
RWZM           1.0,不縮
緩衝區         3032 × 2012   ← 幾何 hook 的 base
```

每行 6064 個像素進 3032 個像素的緩衝區,溢位。

社群那份 FP3K 從一開始 RWZM 就是 `0x800`(2.0×),先縮再進緩衝區,所以不會踩到。
**任何 1× 讀出模式配 RWZM unity 都會這樣。**

## 8. 量測方法(可重用)

`codex/opengate/measure_photodiodes.py`

- 連續兩格相減 → 消掉場景與固定圖案,剩下純時間雜訊
- 切 32×32 區塊,取**最平坦的低分位**(排除運動)
- 依訊號分箱做 `σ² = a·S + R²` 擬合 → 斜率 a(光子)與截距 R(讀出)分離
- **一支 clip 要取 8–12 組畫格對取中位數**。只取一對的離散可達 2×,
  取 12 對可降到 1.04–1.10×
- ISO 必須相同才能互比(R 在 DN 上隨類比增益放大)

方向性測試(V/H 高頻能量比)可以偵測**單方向**合併,但**對 2×2 對稱合併不靈敏**:

```
在實際畫面上人工套合併,V/H 相對未處理
  水平 2 點相加   0.519×   ← 靈敏
  垂直 2 點相加   2.207×   ← 靈敏
  2×2 四點相加    1.132×   ← 幾乎不動
```

亮度也不能判:韌體把每個模式正規化到同一曝光刻度,合併會被除掉。實測
1× 與 2× 模式在同曝光下亮度比 1.00。
