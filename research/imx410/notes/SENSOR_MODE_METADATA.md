## 2. ★ `+0x60` readout cluster —— 四個讀出家族及其變體

`+0x60` 的數值與縮減 tuple、HMAX、位深和三個類比暫存器指紋群完全對應。
這個**相關性**由 70 筆資料確認;但尚未找到直接讀取 `+0x60` 的 consumer,
所以「readout cluster」仍是高信心推論,不是韌體命名。

```
+0x60   線時 hmax     位深 / geometry        類比指紋
 16     911           RAW14,1× / 大裁切      第三組
 17     445 / 450     RAW12,1× / 大裁切      quiet 組
 18     445 / 450     RAW12,÷2               quiet 組
 19     330 / 360     RAW12,÷2               fast 組
 20     445           RAW12,÷3               quiet 組
 21     330 / 395     RAW12,÷3               fast 組
 22     445           RAW12,÷3 / Y scale 6   quiet 組
 23     330           RAW12,÷3 / Y scale 6   fast 組
```

在 RAW12 的 ÷2、÷3 家族裡,`+0x60` 會把 quiet/較長線時與 fast/較短線時分開:

```
÷2   quiet = mode 98    fast = mode 117
÷3   quiet = mode 139   fast = mode 8 / 56 / 147 / 148 / 149 / 150
```

quiet 與 fast 群不只 HMAX 不同,還有 77 個 readout/analog 欄位不同,所以不能把
低噪因果只歸給較長線時。實測佐證:使用者比較同為 3032x2012 的 mode 98 與
mode 117 時,fast 指紋的 **117 雜訊明顯較差**;這證實類比指紋分群有實際畫質意義,
但尚未隔離是哪一個暫存器造成。

在 **2016x1344** 現有模式中,quiet 指紋只有 M139/59.925p;
70/80/90/100/119.88p 都採 fast 指紋。這是出貨表的選擇,不是「quiet 必然不能超過
60p」的硬體證明:M132、M134 都能以 HMAX 445 跑 119.88p,只是有效高度較短。

M139 若硬套 119.88p,總週期 600,600 cycles 中 active rows 已用
`445 × 1344 = 598,080`,只剩 2,520 cycles(約 5.7 行),而它的 vblank code 是 100。
兩者的落差強烈支持「不先做 quiet 120p」,但 `+0x5C` 的精確單位/約束仍未完全解出。
100p 仍有約 274 行等效餘裕,離線資料沒有排除它,但必須實機驗證。

## 3. 時序公式

```
frame_cycles = hmax × (vmax − 1) + tail          時脈 72 MHz
捲簾(有效行讀出) = hmax × 光柵高 / 72   微秒
```

`tail` 是微調欄位,原廠用它精確命中廣播格率。例:

```
mode 106 (FHD 29.97)   hmax 445  vmax 5398  tail 735
445 × 5397 + 735 = 2,402,400 = 72e6 / (30000/1001)     精確
```

70 筆原廠 timing 使用過 16 種 tail:

```
330 / 360 / 395 / 445 / 450 / 515 / 585 / 735 / 795 / 911 / 1035 / 1145 /
1185 / 1255 / 1915 / 2151
```

## 5. 70 個 logical mode 怎麼組織

這 70 筆不是 70 種完全獨立的畫質。要分三層看:

1. **70 個 logical mode ID**:名稱、metadata、timing 都可各自不同。
2. **16 個 geometry family**:以三組 geometry、明示 crop 與 margin 的完整 tuple 分組。
3. **24 個 161-register fingerprint**:只比較 `FUN_c03258c8` 寫入的 IMX410
   register;不含 timing、metadata、receiver 記錄與下游路由。

所以「同一個 P 組」只代表這 161 個 table-fed register 完全一樣,
不代表整條相機 pipeline 相同。ROM/CSV 交叉驗證結果是 **70 logical modes →
16 geometry families → 24 register fingerprints → 3 analog fingerprints**。

### 5.3 名稱可以、不能怎麼解讀

- `ACQ` 與 `MONIT1` 是兩個韌體名稱族;全表是 ACQ 12、MONIT1 58。
- `_HD` 與 firmware aspect label 16:9 在這 70 筆中完全一致。
- ACQ 名稱的 `_CROP` 與 `+0x58=1` 一致。
- ACQ 的 `_MIX` 與 2x2 geometry scale 一致,但 **MIX 不足以證明 charge binning**。
- `_CONTINUOUS` 六個 mode 都在約 18 fps。
- `_LOWP` 的精確物理意義未解,而且不等於 quiet。
- 名稱內的數字不是可靠的實際 fps;例如 M11 名為 120,實際只有 105.402p。

### 5.4 RAW-depth 與 2x reduction block 的雙韌體交叉驗證

用真正同家族的 Q12 ACQ sibling 配對,而不是只挑相近光柵,可把 2x block 分得
更乾淨:

```
M97  → M98    full ACQ
M142 → M143   full ACQ_CONTINUOUS
M130 → M131   crop ACQ
M145 → M146   crop ACQ_CONTINUOUS
```

四組分別有30/30/29/29個不同 register;共同交集29個,而且每個 old→new 值都一致。
其中 `reg 0x0001` 是 RAW12 1x=`0x2A`→RAW12 2x=`0x39`;排除這個 selector 後,
剩下28個有四組獨立先例的 2x core。`reg 0x0016` 只在兩組 full pair 改變,
crop pair 完全不變,所以它不是通用 2x switch,也不是 bit-depth enum。

四組可直接比較的 RAW14→RAW12 1x pair(M0→M97、M129→M130、M141→M142、
M144→M145)則共享同一組38-register depth delta;continuous pair 另多
`reg 0x0016`,但不屬共同 depth core。兩個共同 block 的地址交集**只有
`reg 0x0001`**。

Sony A7 III 的 IMX410 register patch table 提供獨立交叉驗證:兩組重複出現的
RAW-depth transition 各有同一組47-register delta;唯一明確2x column 的 reduction
delta有31個 register。兩組地址交集同樣只剩 `reg 0x0001`。但 Sony 的 requested
mode ID、patch column 和 register value 是三個不同命名空間,不可互抄;例如 requested
ID `0x2F` 映到 column 13,該欄實際 `reg 0x0001=0x15`,而2x column 18 實際是
`0x24`。SIGMA M98 的 mode ID 是十進位98(`0x62`),實際 `reg 0x0001=0x39`。

兩份 firmware 都只有 RAW14 1x 與 RAW12 2x,沒有 RAW14 2x donor。這不證明 silicon
絕對做不到,但表示 combined selector 沒有任何表內值可引用;尤其不能把 `0x38`
當成已證 bitfield 外插,也不能用 RAW12 的 `0x39` 冒充 RAW14 2x。

## 7. 名稱映射與還沒解的

模式名稱已能完全離線映射。`FUN_c031fd70` 直接以 mode id 索引名稱指標表;
固定 32-byte 字串槽從 `0xC0B575CC` 的 mode 0=`ACQ` 開始:

```
name(mode_id) = 0xC0B575CC + mode_id × 0x20
M97  = 0xC0B581EC  ACQ_12BIT
M98  = 0xC0B5820C  ACQ_12BIT_MIX
M139 = 0xC0B5872C  MONIT1_60_LOWP5
```

不需要從 metadata 找另一個名稱索引,也不需要 USB shell 才能辨認名稱。

仍未解:

- `+0x44/+0x48` descriptor pair A 的精確物理語意;目前只確認 AF/分類 consumer。
- `+0x4C/+0x50` 是有效 X/Y geometry scale,但究竟是 charge binning、skipping
  或其他 reduction 核仍不能由 metadata 單獨判斷。
- `+0x60` 的確切韌體名稱/consumer;「readout cluster」目前是全表相關性推論。
- `+0x5C` 已知名為 vblank,但其單位與所有約束關係尚未完全反編。
- `+0x0C`/`+0x10`/`+0x1C`/`+0x20` 全 70 筆都是 0,用途不明。
- 三組 geometry pair 的各自用途;尤其 M100 的第三組為唯一不等於主光柵的例外。

## 8. 2K / 3K / 4K OpenGate 畫質路線

### 8.1 先把三種「超採樣」分開

| 路徑 | 發生位置 | 會不會改善 sensor RS / 頻寬 | 定義 |
|---|---|---|---|
| sensor direct | IMX410 讀出 | 只有這層可能 | 直接選擇 1x/2x/3x 已知模式 |
| 機內 supersampling | IMX410 全讀出後的 RAW-domain RWZM | 不會 | 先讀 6K,在寫檔前縮小 |
| 後製 supersampling | 電腦軟體 | 不會 | 相機必須先把完整 6K RAW 寫出 |

OpenGate 在本文指「接近 6000x4000 正常靜態照片的全幅 coverage,且輸出接近
3:2」,不只看檔案尺寸或 `full/crop` enum。

### 8.2 結論表

| 目標 | 建議路線 | 畫質潛力 | sensor RS | 目前證據 / 風險 |
|---|---|---|---:|---|
| 2K Balance | **M139 direct** | quiet、原生約 2K、低負擔 | 8.31 ms | stock sensor mode;低風險 |
| 2K HQ | **M98 → RWZM 1536(1.5x)** | 較多上游樣本,可能減少 alias/noise | 12.44 ms | 原廠預覽有同路徑先例;錄影組合待測 |
| 2K MaxIQ 實驗 | **M3 full 6K → RWZM 3072(3x)** | 細節/抗疊紋理論上限最高 | 24.98 ms | 原廠預覽有 3x 先例;錄影 3x 未驗證 |
| 3K Balance | **M98 direct** | quiet;暗部改善已實測 | 12.44 ms | 現行最合理出貨基底 |
| 3K MaxIQ 實驗 | **full 6K → RWZM 2048(2x)** | 主要期待細節/疊紋改善 | 24.98 ms | full-height+2x 已有實機錄影先例;畫質尚未定量 |
| 4K OG | **full 6K → RWZM 約 1.5x** | 唯一有現成證據的真全幅 4K 路線 | 24.98 ms | 需新輸出畫布、RAW 1536 與頻寬實測 |
| 4K crop | M130 3968x2640 direct | 尺寸接近 4K,但視角窄 | 16.32 ms | stock;不是 OpenGate |

「MaxIQ」是實驗目標,不是已證明畫質。現有光子轉換模型仍有矛盾,
所以 full-read + RWZM 可先預期細節與 aliasing 改善,不能先宣告雜訊會改善幾 EV。

### 8.3 2K:quiet direct 是基準,兩種超採樣是研究支線

- M139 是唯一 2016x1344、full、3x3、Q12 mode;60p 以下應保留整組
  readout fingerprint,只移植 timing。M8/56/147–150 是較快的 F12 支線。
- M98 + RWZM 1536 是中間路線:3032x2012 先縮成約 2K。p83 預覽原生已有
  2024x1341 / active 2000x1334 的先例。
- M3 + RWZM 3072 從 6064x4042 縮成約 2K;p41/42/81/82 預覽已有
  2016x1344 / active 2000x1334 先例,但 recording 3x 未用過。
- M131/M146 來自 3968x2640 crop,已排除。M140/M9/M12 只有一半垂直樣本,
  不會比 M139 更好。

M139 的電影格率只需 timing 移植;`+0x0A` 必須保留 ÷3 家族的 `6`:

| fps | HMAX / tail / VMAX |
|---:|---|
| 23.976 | 445 / 585 / 6748 |
| 24.000 | 445 / 1145 / 6740 |
| 25.000 | 450 / 450 / 6400 |
| 29.970 | 445 / 735 / 5398 |
| 48.000 | 445 / 795 / 3370 |
| 50.000 | 450 / 450 / 3200 |
| 59.940 | 445 / 1035 / 2698 |

M139 quiet 100p 從 frame budget 看還有約 274 行 blank,可列為 timing-only 實驗;
quiet 120p 只剩約 5.7 行,與 `vblank=100` 明顯矛盾,不建議。

### 8.4 3K:M98 已是正確基底

- M98 對 M117 同場景實測:讀出雜訊 0.551 對 0.965 DN,降低 1.75x;
  極暗 3 DN 訊號約 +1.50 EV,400 DN 約 +0.18 EV。代價是 RS 9.22 → 12.44 ms。
- 23.976–59.94p 保留 M98/Q12 整組讀出,只借 quiet ÷2 timing;100p 才回到 M117。
- M143 和 M98 是同 quiet、同幾何、同 RS;它的 18p VMAX 不會自動帶來額外畫質。
- full 6K + RWZM 2048 產生約 3032x2020 / active 3000x2000。這個 full-height
  2x 組合已有 207 張連續 DNG / 8.625 s 實機先例,並有強的 full-FOV 證據;
  但還沒有完成配對 MTF、aliasing、讀噪實測。

### 8.5 4K:不必只靠後製,但沒有直接 sensor mode

Sony 官方 basic-drive 表列出 6064x4040、4160x2160、2020x1342、3032x2012,
還有 3032x4040 / 6064x2012 的不對稱模式;沒有約 4K 3:2 或 1.5x reduction。
fp 的 70 筆也只有 1x/2x/3x(及 Y=6)。所以:

- **不做**:直接把 metadata 改成 4K,或猜一個未知的 1.5x sensor register 值。
- **可做**:以 6064x4042 Q12 full-read 為 source,在寫檔前用 RWZM 約 1.5x。
  這是機內 RAW-domain supersampling,不是電腦後製。
- **已有前例**:M151 和 M3 的 161 個 sensor register 完全相同;過去 F1 實驗已把
  M151 24p 的 metadata、input window 與 56-byte receiver record 改成 M3
  full-height,再以 RWZM 2048 錄出 207 張連續 DNG。4K 可重用這個已驗證的
  full-height exact-24p 前端,只把下游改成約 1.5x 與 4K 畫布。
- **尚未驗證**:RAW 錄影使用 RWZM 1536、4K buffer/stride、長時間寫入與畫質。

合理的第一版目標是 RWZM `1536`(1.5x)、CinemaDNG raster **4016x2676**、
DefaultCrop **4000x2666 @(8,5)**。這沿用影片 `raw = active +16/+10` 慣例,
並對應 6000x4000 active 約 1.5x 縮圖。精確 Bayer phase、邊緣 coverage 與
縮放捨入必須以 DNG/readback 定案。

RAW12 未壓縮寫入量:

| 格率 | 4016x2676 4K OG | 6064x4042 6K RAW |
|---:|---:|---:|
| 23.976p | 386.5 MB/s | 881.5 MB/s |
| 24p | 386.9 MB/s | 882.4 MB/s |
| 25p | 403.0 MB/s | 919.2 MB/s |
| 29.97p | 483.1 MB/s | 1101.9 MB/s |

對照 stock UHD 3856x2170 RAW12/29.97p 約 376.2 MB/s,4K OG 24p 只高約 2.8%,
因此是第一個應測的格率;29.97p 高約 28.4%,不適合第一輪。直寫 6K RAW 連 24p
都需 882 MB/s,而 [SIGMA 官方規格](https://www.sigma-global.com/en/cameras/fp/)
列的是 USB 3.1 Gen1(5 Gbit/s gross),所以標準影片格率下
「錄 6K 再回電腦軟體縮」在介面上就不成立。後製路線只適合單張、低格率,
或未來先解決無損壓縮與錄影頻寬。

### 8.6 哪些參數真會改畫質

- `VMAX`:只改幀間隔;同曝光下不改讀噪、空間解析或捲簾。
- `HMAX`:改線時與捲簾,但 quiet 不是 HMAX 單獨造成,不要單改一個值。
- readout fingerprint:對暗部讀噪有實測影響;應整組移植或用 stock mode。
- RWZM:可能改善降採樣與 aliasing,並降低最終檔案速率;不改 sensor 頻寬或 RS。
- CRCT hbin/vbin:也在讀出後;錄影側未驗證,不應優先。
- metadata geometry、`full/crop`、RAW bit enum:都是描述/分派資料,
  改了不會自動產生新的 sensor geometry 或 RAW14 transport。
- gain state:用 ACQ mode 錄影時必須維持明確的 raw-movie gain dispatch;
  現況 RAW14 enum1 會落到 state5(8-bit),不是可接受的預設。否則 HCG 切換與
  高光容量會污染所有 mode 畫質比較。

### 8.7 RAW14 @29.97p 的界線

full 6064x4042 RAW14 的 HMAX 固定 911,active-row readout 是 51.14 ms;
零 blanking 理論上限也只有 19.55p,stock M0 是19.127p。29.97p 的33.37 ms
frame budget 裝不下。M6 的4176x2174 RAW14可達29.97p,但它是16:9 crop。
70筆與Sony basic-drive表都沒有RAW14的2x/3x reduction完整 donor;下游RWZM也不能
縮短sensor讀出。因此已知的 full-read/downstream 路線做不出 full-FOV
**14-bit OG 29.97p**,現階段不可交付。唯一剩下的是未證實的 sensor-side RAW14 2x
reduction:數學上讀出 budget 足夠,最乾淨的四角是 M141(RAW14 1x)、M142(RAW12 1x)、
M143(RAW12 2x)與未知的 RAW14 2x;M6 只捐贈29.97 timing。28-register reduction core
與 M143 receiver 參數可以離線拼合,但唯一同時屬於 depth/reduction block 的
`reg 0x0001` 沒有 combined 值,而 metadata `+0x60` 也沒有 RAW14 2x cluster
先例;兩者都必須當成 hard gate,因此仍沒有完整 donor。官方與stock表強烈顯示
**沒有已知或已發布支援**,但尚未證明 silicon 一定拒絕。它只應列為高風險
discovery experiment,不能寫成已知參數組合;bounded one-frame RAM probe 完成前
也不能啟動實機 candidate。把12-bit sample 裝進14-bit DNG只會改容器,不會增加
ADC精度。

具體 OpenGate 組合、位址與測試順序放在
`projects/open-gate/notes/OG_2K_3K_4K_QUALITY_OPTIONS.md`,不放進這份共用 sensor 筆記。

## 6. ★ 時序記錄的完整欄位圖 —— 裡面有感測器視窗(2026-09-15)

時序表在 **`0xC0B59500`,每筆 `0x20` bytes**,索引與 metadata 表相同。
先前只解出 `+0x04` 的 hmax/tail 與 `+0x08` 的 vmax,把 `+0x08` 高半當成
不明的「x」。**全部解開之後,`+0x0C`/`+0x10` 是感測器視窗:**

```
+0x00  模式 id
+0x04  hmax     | tail    << 16
+0x08  vmax     | x_start << 16        ← 高半就是 x_start,不是不明欄位
+0x0C  x_end    | y_start << 16
+0x10  y_end
+0x14  0x00003FFF     70 筆全部相同
+0x18  0x0003FFFF     70 筆全部相同
+0x1C  0
```

**驗證:70 個模式全部符合**
`x_end − x_start == metadata 光柵寬` 且 `y_end − y_start == metadata 光柵高`。
零例外,所以這不是巧合。

```
 mode          光柵  x_start  x_end  y_start  y_end   說明
    0   6064x4042        8    6072       40    4082   全片幅 ACQ
   98   3032x2012        4    3036       20    2032   OG3K 的基底
  139   2016x1344        6    2022       14    1358   OG2K 的基底
  131   1984x1320      528    2512      366    1686   3:2 APS-C
```

座標單位是**該模式合併後的輸出像素**,不是光電二極體。

### 6a. 這代表視窗是可程式化的,不必換模式 [I]

`fmttable` 本來就在寫這個記錄(`+0x04` 與 `+0x08`)。
**多寫 `+0x0C` 與 `+0x10` 就能把視窗設成任意大小**,不需要另外找一個
剛好是那個尺寸的原廠模式。

這推翻了「換視角就得換感測器模式」的假設。目前 OG3K 寫 x_start=4、
OG2K 寫 x_start=6 —— 那部分一直是對的,只是當時不知道它是什麼。

⚠ 尚未實機驗證。感測器可能對視窗有對齊/最小值限制,而且改視窗會改
有效行數,vmax 與 tail 要跟著重算。

## 7. mode 131 與 mode 98 的完整差異(2026-09-15)

回答「Super35 能不能用 mode 131 做」而做的逐字比對。

**25 個 metadata 字裡 13 個不同,但沒有一個與讀出方式有關:**

```
不同   模式 id · 三組 geometry(全是 3032x2012 → 1984x1320)
       明示裁切 3000x2000@(16,6) → 0(無) · full/crop 0 → 1 · vblank 40 → 50

相同   位深 RAW12 · 標稱 fps 78 · redA/redB 2/2 · X/Y scale 2/2
       aspect 3:2 · readout cluster 18 · hmax 445 · tail 445
```

時序記錄也只差視窗與 vmax:

```
          hmax  tail  vmax  x_start  x_end  y_start  y_end
mode  98   445   445  2094        4   3036       20   2032
mode 131   445   445  2068      528   2512      366   1686

x 偏移 524 = (3032−1984)/2   y 偏移 346 = (2012−1320)/2   → 完全置中
```

**mode 131 = mode 98 的置中裁切,沒有第二個差異。**
合併方式、線時、類比指紋(cluster 18 = quiet)全部一樣。
