# 幀率是 vmax,不是模式 (2026-09-10, USB shell 實機驗證)

> 這一輪的目標:3032×2012 3:2 @29.97 錄影(open gate 的低成本版本)。
> 感光元件那一側**做完了**,畫布那一側沒有。下面每一條都是在實機上讀回來的。

## 一句話

**幀率不是感光元件模式的固有屬性,是時序表裡一個 u16。** 改它不動捲簾,
而且韌體自己就有兩筆只差 vmax 的記錄可以佐證。

---

## 1. ★ 時序表 `0xC0B59500`

每筆 `0x20` bytes,70 筆,索引與模式表相同。

```
+00  mode_id  u32
+04  hmax     u16    行時間(72 MHz 時脈週期)  → 決定捲簾
+06  tail     u16    最後一行的修正
+08  vmax     u16    一幀總行數                → 決定幀率
+0a  ?        u16    2×2 模式=4,1×1 模式=8
+0c  行長     u16    = 寬 + 4
+0e  首行     u16
+10  末行     u16    末行 − 首行 = 影像高度
+14  ?        u16    0x3FFF
+18  曝光上限 u16    0xFFFF —— 70 個模式全都是「無限制」
+1a  ?        u16    3
```

**模型:`frame_cycles = hmax × (vmax − 1) + tail`,`fps = 72e6 / frame_cycles`。
70 個模式全部吻合,無例外。**

首末行的差對得上每個模式的高度(mode 3 是 40→4082 = 4042;mode 106 是
172→1880 = 1708;mode 123 是 354→3766 = 3412)。

### 這張表是直接可寫的

`FUN_c0320fc8` 顯示表基底是**存在結構裡的指標**(`*(obj+0)`),本來規劃「複製到
RAM 再重指基底」。**不需要** —— `0xC0B59xxx` 那一段實機上直接 `mem set` 就寫得進去,
寫完 `mem get` 讀得回來。

表目錄(實機驗證,`0xC343B588` 就是感光元件物件,`FUN_c03255f8` 直接回傳它):

```
0xC343B588 → 0xC2F1E654 → +0x00 時序表 0xC0B59500  +0x04 count 70
                          +0x08 幾何表 0xC0B59DC0  +0x0c count 70
                          +0x10 0xC0B5B918   +0x24 0xC0B5BB48
                          +0x40 0xC0B5C638   +0x48 0xC0B5D588
0xC343B58C = 現行模式    0xC343B590 = 前一個模式
```

### vmax 不在感光元件暫存器塊裡

mode 98(77.27 fps)與 mode 143(18.00 fps)的 `0x288` 暫存器記錄逐 byte 比對:
**648 bytes 裡只有 2 個不同** —— offset 0(mode_id 本身)與 offset 0x10。
2094 和 8988 這兩個 vmax 值在記錄裡**完全不存在**。

offset 0x10 = `imager mode_list` 的 `vblank` 欄的一半(98→20/40、143→50/100、
3→35/70)。跨 70 個模式與 fps **無相關**(值 35 橫跨 18–120 fps),所以是
**最小消隱要求**,不是幀率。我們要的 vmax 遠大於它,不構成限制。

**所以 SIGMA 出貨了兩個模式,一個 18 fps 一個 77 fps,送進感光元件的暫存器是同一份。**

## 2. 目標模式選 117,不是 98

`imager mode_list` 的命名把類別分得很清楚,而 **picker 三張表裡填的全是 `MONIT_` 類**
(mode 106 = `MONIT1_30_HD_LOWP3`、mode 7 = `MONIT1_30_HD_LOWP`)。

| No | 名稱 | enum | size | fps | 捲簾 |
|---|---|---|---|---|---|
| 003 | `ACQ_12BIT_MIX` | 98 | 3032×2012 | 77 | 12.435 ms |
| 057 | `ACQ_12BIT_CONTINUOUS_MIX` | 143 | 3032×2012 | 18 | 12.435 ms |
| 041 | `MONIT1_120` | 11 | 3032×2012 | 105 | 9.221 ms |
| **042** | **`MONIT1_100`** | **117** | **3032×2012** | 100 | **9.222 ms** |
| 004 | `MONIT1_30` | 3 | 6064×4042 | 30 | 24.981 ms |
| 005 | `MONIT1_25` | 121 | 6064×4042 | 25 | 24.981 ms |

`ACQ_*` 是靜態擷取路徑。把它塞進錄影 picker 是跨類別的賭注,沒有必要 ——
117 同樣是 3032×2012 3:2 full,**捲簾還好 26%**,而且只要改一個欄位。

### 實際下的 patch

```
時序 mode 117 (index 41 @ 0xC0B59A20):
  0xC0B59A28  0x00040888 → 0x00041C70     vmax 2184 → 7280,hmax/tail 不動
  → 330 × 7280 = 2,402,400 cycles = 29.97003 fps(0 ppm)

picker 三張表的 idx7(3032×1708 @29.97,現行 FHD 槽):
  0xC0BE5888 / 0xC0BE5A28 / 0xC0BE5BC8   106 → 117
```

`hmax 330 / vmax 7280` 正是韌體裡 mode 111 已經在用的時序,兩半都是出貨組合。

### 驗證

改完之後相機自己的表就變了:

```
改前  042,MONIT1_100,0117,12,3032x2012,010010,0100,009222,...,3: 2,full
改後  042,MONIT1_100,0117,12,3032x2012,033366,0030,009221,...,3: 2,full
```

`frame` 033366 與出貨的 mode 111(3032×1708 @29.97)**完全相同**,捲簾維持 9.221 ms。

**實錄一段後 `0xC343B590` 讀回 117** —— 感光元件真的用 3032×2012 3:2 全高、
vmax 7280 錄了。

## 3. ★ picker 三張表的結構

`0xC0BE5810` / `0xC0BE59B0` / `0xC0BE5B50`,各 26 筆 × 16 bytes,
`+0x08` 是感光元件模式。**排列是 (讀出幾何 × 幀率)**:

```
idx 0-3    6064x3412  1x1   29.97 / 25 / 24 / 23.976     模式 7 / 123 / 151 / 101
idx 4-12   3032x1708  2x2   59.94 / 50 / 48 / 29.97 / 25 / 24 / 23.976 / 119.88 / 100
                            模式 27 / 115 / 220 / 106 / 125 / 218 / 109 / 58 / 89
idx 13-16  4176x2174  1x1
idx 17-25  2088x1174  2x2
```

`+0x0C` 是指向字串表的指標,不是設定。

### 這順帶解掉 sensor-lab-sup 唯一的未解項

`projects/sensor-lab-sup.md` 說「1080p29.97 同時符合模式 106 與 111,模式索引欄位還沒找到」。
**picker 表就是答案:FHD 29.97 那一格填的是 106,而 mode 111 根本沒出現在 picker 的
任何一張表裡。** 所以 FHD 29.97 CinemaDNG 的捲簾是 **10.556 ms**,不是 7.828。

這也是 gyro sup 鏡頭 profile 缺的那個數字。

## 4. 畫布:又排除了幾條,而且訂正了文件

### `+0x48` 那句是錯的

`projects/open-gate.md` 寫「`+0x48` 從頭到尾沒變(FHD 0、UHD 4),而幾何永遠跟它一致」,
並稱之為 load-bearing observation。**實測 `+0x48` 在 FHD 和 UHD 都是 0。**

拿 0/4 的是 **`+0x08`**,而且它**跟著幀率走**,不是解析度(fps enum 4 → 0,fps enum 3 → 4)。
先前那個 diff 同時動了解析度和幀率,兩個變因混在一起。

### 控制良好的對照(同為 29.97,只差解析度)

主設定 block 在 `0xC3074BE8`(`*(0xC3075230)`):

```
FHD 29.97 → UHD 29.97
  +0x00  1920 → 3840
  +0x04  1080 → 2160
  0x80 bytes 內其餘完全相同
```

**沒有隱藏的解析度欄位。**

### `menu SetMovRecSize` 的真實語義

> ⚠️ **訂正:下面這段是行為描述,機制在當時還沒找到,而且描述錯了。**
> 真相是轉換表只認列舉 **2 和 3**,其餘全部落到「Invalid MovSize」什麼都不做 ——
> 不是「進了 UHD 就保持 UHD」。見 `CANVAS_IS_NOT_THE_SETTINGS_BLOCK.md` §1。

之前所有「不穩定」都是沒控制起始狀態:

```

2 永遠回 FHD
到 UHD 29.97 的可靠路徑 = 2 → 3 → 0
```

**這條路繞得過選單層的 SD/SSD 限制** —— 選單裡選不到的 UHD 29.97,從這裡設得到。

## 5. raw_zoom 是數位變焦,不是縮放器

> ⚠️ **2026-09-10 訂正,而且這一條代價很大。** 下面整節的結論是錯的 ——
> **它是在即時取景上測的,而即時取景的 base 等於感光元件,整個階段是退化的**
> (`bef_size = min(zoom × base, 感光元件)`,base 就是感光元件,所以怎麼設都看不出差別)。
>
> 在**錄影路徑**上,profile 122 的 RWZM 是 `0x640` = 1600 = **1.5625× 的實質縮小**,
> 正是它把 producer 的有效區釘在 1936 寬。把四個欄位改成 unity `0x400`
> (`0xC0BD9A34` / `0xC0BE1684` / `0xC0BD9EFC` / `0xC0BE1B4C`)之後,
> 畫面才填滿 3032×2012 —— **open gate 的最後一塊就是這個。**
>
> 教訓:**在退化的情境裡測出「沒有效果」,不能推廣成「這個東西沒有作用」。**
> 見 `CANVAS_MOVED_AT_C043A19C.md` 與 `projects/open-gate.md`。


一度以為可以用非等比 raw_zoom 把 3:2 擠進 16:9 畫布(變形壓縮)。**不成立。**

`imager mode_now` 印的那組值來自:

```
bef_size_h = hvbin_h × ((raw_zoom_h × base_h + 0x200) >> 10)
bef_size_v = hvbin_v × ((raw_zoom_v × base_v + 0x200) >> 10)
             ↓ min(結果, 感光元件尺寸)
offset     = (感光元件尺寸 − bef_size) >> 2 << 1
```

**`min` 的對象是感光元件邊界,不是輸出畫布** —— 我一開始讀成畫布,那是錯的。
所以這段是「裁多少、從哪開始」,不是「縮到多大」。

實測三條:

```
下限常數 DAT_c0bb4a04 = 1024        低於 1.0 的值直接被夾掉
zoom_v = 512  → 印出 1024,bef_size 不變
zoom_v = 2048 → 印出 2048,bef_size 仍是 1344(被感光元件高度封頂)
```

`[0x2C]/[0x2D] = 100/100` 就是 `lv_zoom_top`/`lv_zoom_bottom` ——
這整段是即時取景數位變焦的百分比路徑。**它只能往內裁,永遠不能往外縮。**

真正的「讀出 → 畫布」縮放是另一個階段,還沒找到。

## 6. 探針:借 echo 呼叫韌體函式並倒出結構

`scratchpad/ispcfg.S` + `runispcfg.py`（212 bytes）。照現行 `fpSup/fp_usb_shell/asm/shellcmd.S` 的形狀：

```
put(0xC072F800, code)            帶寫入驗證
mem set 0xC0BAC2F8 → 0xC072F800  借 echo handler
fpsh echo                        跑一次,dispatcher 的 task 裡
mem set 0xC0BAC2F8 → 0xC03D99A0  finally 還原
mem get 0xC072FA00               讀結果
```

跑在 task 環境,所以 payload 內部配置記憶體(`FUN_c04370e8` 會配 0xC0 bytes)沒問題。
結果區用 `0xC072FA00`,避開 `0xC072F700`(技能檔第 5 條:範本共用那塊)。

### ★ 它解掉了一個手動讀不可能解的問題

`FUN_c04375c8(obj) = *(obj+8)` 指向一個**輪替中的緩衝**。用 `mem get` 分兩次讀
(先讀 `*(obj+8)`,再讀它 `+4`)會抓到兩個不同時刻的值,拼出來的位址是垃圾 ——
我因此讀到 `0x217808` 並以為反編譯錯了。**在 payload 裡一次讀完就正確:**

```
obj 0xC375D840 → *(obj+8) = 0xC375E5F8 → +4 = 0xC375E654    三次執行都相同
raw_zoom h @ 0xC375E6B4    raw_zoom v @ 0xC375E724   (值 1023)
```

**教訓:凡是要走兩跳以上的指標鏈,不要用主機端分次 `mem get`。**
