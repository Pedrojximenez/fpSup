# 改完 UI 之後,什麼時候生效

2026-09-29。**「位置不重要,讀取時機才重要」** —— 這份把三層的時機講清楚。

## 一張表

| 你改的東西 | 什麼時候被讀 | 什麼時候生效 | 證據 |
|---|---|---|---|
| **enum→state 配對表** `0xC2E4020C` | **每次求值**(`0xC06CCD10`) | **立刻,下一次重繪** | 實機(`README.md` §4) |
| **NBR 資源的內容** | 消費端拿著 handle(絕對位址)直接讀 | **原地改、長度不變 → 下次打開那頁就生效,不用重開機** ✅ 實機 |
| **NBR 目錄項**(資料位移 / 長度) | **只在第一次查找時**用到 | ❌ **執行期改了沒用**,handle 已經發出去了 |
| **NBU 記錄**:物件、屬性、影像陣列 | **每組資源集只解析一次** | 要嘛趕在解析之前,要嘛逼它重新解析 | 實機(§5c 全部零命中) |
| **解析後的 heap 物件** | —— | **改了留不住**(擁有的螢幕被釋放就沒了) | 實機(§4,144 MB 掃不到) |

## ⚠ 先釘住一個硬事實:從卡片沒有辦法更早(2026-09-29,使用者實測)

**AutoRun 的 `mem set` 是開機後約 8 秒才執行,那時 UI 已經載入了。**
而且這不是可以優化掉的:

- `0xC03DA420` 就是**啟動 AutoRun 的那一條 `bl`**(`XC_ShellScriptAutoRun` 裡,
  stock word `0xEB0000CC`)。Fast Start 2 的 loader hook 換掉的就是它 ——
  所以 loader hook **跑在同一個時間點**,只是省掉 AutoRun 直譯器的時間,
  **不會更早**。
- `README.md` §6 早就寫過同一件事:**「AutoRun is later than the stock NBR/resource pass」**。

**所以「趕在解析之前」這條路,從卡片是走不通的。** 這不是實作沒做好,是位置就在那裡。
剩下的只有三條:**(A) hook 解析器**、**(B) 逼它重新解析**、**(C) 改那些「晚一點才讀」的東西**。

## NBR 那一層:為什麼 AutoRun 這麼晚還來得及

`.cvm` 的路徑字串**只存在於 NBR 名稱池**,程式碼與 Lua 裡一個都沒有;
UI 記錄引用的是**短名**(`B2_5_4`,在 NBU 字串池 `0xC18CA000`),
路徑是執行時拼出來的,再用 FNV-1a 去查目錄。
tag `0x1000A`(46,528 筆「資源引用」)指的全是 `animationClip` 這種**類別名**,
**不是檔案** —— 所以 CSV 不是在資源解析那一趟被拉進去的。

**實證**:fpSup-Formats 那張卡沒有 entry point,所有寫入都在載入時完成(AutoRun 之後),
而它的六列選單在相機上是好的(rc3「six rows, tiles, strip」)。
**所以那個目錄項的改寫,在 AutoRun 之後打下去仍然生效** —— CSV 是開畫面時才讀的。

> 這是從別人實機驗證過的卡推出來的,不是我們自己測的。

**而且這一點特別重要**:Formats 的三個 NBU hook 是掛在**記錄解析器**上的,
CSV 與目錄那兩個寫入是普通的 section,**一樣在 ~8 秒才寫進去**。
它的六列選單在相機上會出現 —— **所以 CSV 確實是在 8 秒之後才被讀的**,
否則那六列不可能出現。**「8 秒太晚」不能拿來解釋 CSV 那一半沒生效。**

## NBU 那一層:這裡才是時機陷阱

**解析度陣列開機後不再重建。** 掛著 append hook 試過:QS 重繪(一次 314 個元素)、
`gui scr set 1_03_CINE`、換走再換回、MENU 開關、`SetRecMode`、`STILL`/`CINESW` ——
**命中 0**。所以:

- **target bitmap 全 0 = 時機沒對上,不是畫不出來。** 一包做好的東西如果一個目標都沒命中,
  那是遲到了,不是畫錯了。
- 兩個可用的手段:
  1. **趕在前面** —— hook 記錄解譯器 `0xC05E6400`,在它解析那一筆時換掉(og3k / FP3K 的路);
  2. **逼它重新解析** —— og3k 額外掛 `0xC05D90F0`(佈局載入器),
     **把 hook 之前就建好的 Quick Set 佈局丟掉,下次載入才會重新解析**。
- 「某些 screen-specific 的集合是延遲解析的」這件事是真的,但**是逐筆記錄的問題**,
  沒有一個全域的「AutoRun 早或晚」答案。只有**那一筆的位址加指紋命中**才算數。

## 我們那三個寫入,各屬於哪一層

`menu_row_patch.py --append` 產生的三個寫入:

| 寫入 | 層 | 生效時機 |
|---|---|---|
| 新 CSV(`0xC12C7CF8`) | NBR 資源 | 下次建立那一頁 |
| 目錄改指向(`0xC0D4DE04`) | NBR 目錄 | 同上 |
| controller 最大值(`0xC1A709BC`) | **NBU 記錄** —— 在資源集 **`B2_5`** 的第 1368 筆(tag `0x1000E`,body +32) | **`B2_5` 被解析那一刻** |

第三個是唯一有時機風險的:它是一筆 NBU 記錄裡的 float。
但 fpSup-Formats **就是用同樣的方式在 AutoRun 時寫同一個位址**,而它的六列**可以選中** ——
所以 `B2_5` 是在**打開設定頁時**才解析的,不是開機那一趟。**我們的第三個寫入也來得及。**

⚠ 這是推論,**不是我們實機量到的**。第一次上機要特別確認「那一列選得中」。

## 實際流程

```
插卡 → 開機 → loader 寫入各 section(同時 journal 原本的字)
                ↓
      MENU → 錄影 → 解析度   ← 這時候才建立那一頁:
                                讀 B2_5 的 NBU 記錄(拿到 controller max 2.0)
                                拼出 ../MenuB12/.../B2_5_4.cvm → FNV-1a → 目錄
                                → 讀到我們那 121 bytes → 三列
```

**不用重開機就會生效**(只要那一頁還沒被建過)。如果在改之前已經打開過那一頁,
就要讓它重建 —— 最保險是重開機。

## 怎麼還原

loader 把**每一個動過的韌體字**都 journal 起來,**關機時寫回**,所以:

- 正常關機 → 韌體回到原廠(被犧牲的 `L_resolution_480p.xci` 也回來)。
- 拔卡 + 拔電池 → 一定乾淨。
- ⚠ **插著 USB 關機會變成保留狀態**,而且撥開關關機**連韌體補丁都可能留著**
  (見 `warm-restart-keeps-the-cave` 的紀錄)。要確認乾淨就拔電池。

## ★ 2026-09-29 第一手實機證據 —— 上面三件推論有兩件成立

open-gate 的 IMX410 版在**開機後用 USB shell 打 RAM**(不是卡片 loader),
然後不重開機、只離開選單再進去。改的是位元深度清單(`B2_5_2`,3→4 列)
與格率清單(`B2_5_5`,9→10 列)。

| 觀察 | 結論 |
|---|---|
| 游標**到得了**新的那一列 | controller max 生效,**不用重開機**,也不用在 AutoRun 之前 |
| 選第 10 列 → 韌體跳出「SD 卡不能用這個幀率」 | CSV 列數生效;而且 enum↔列 配對表搬家成功,**韌體正確認出那是 240**,連原廠的媒體閘門都套用了 |
| **新的那一列完全沒有被畫出來** | NBU 那一層沒動,所以沒有視覺表現 |
| 選第 4 列(14 bit)→ 選單卡住,REC 鍵可強制退出,再進選單正常 | 未解,見下 |

所以:

- **`B2_5` / `B2_5_2` / `B2_5_5` 確實是打開那一頁時才解析的。**
  這一條原本是「從別人的卡推的」,現在是我們自己量到的。
- **不重開機、只離開再進那一頁就會重建。** 原本的第二個問號,答案是會。
- **CSV 沒有被快取住**(圖示那邊會,CSV 不會)。第三個問號,答案是不會。

★ **而且它把 `README.md` routes 裡 R3 的那句警語變成實測:**

> not: make a new row selectable on its own (the Settings controller max has to grow)
> **or draw a new tile (that needs the NBU side)**

**「選得到」與「看得到」是兩件獨立的事**,而 R3 只給你前者。
資料那一層(CSV + 目錄 + 配對表 + controller max)可以讓一列**在邏輯上完全成立** ——
有正確的列舉值、走正確的閘門、跳正確的錯誤訊息 —— 而畫面上一片空白。
