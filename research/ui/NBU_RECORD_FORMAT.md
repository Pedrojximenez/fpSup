# NBU / NBR 記錄格式 —— 完整參考

2026-09-29。Ver.5.02 專用。這份是「格式本身」的參考;怎麼用它去改東西看
[`RESOURCE_REPLACEMENT.md`](RESOURCE_REPLACEMENT.md)、[`QUICK_SET.md`](QUICK_SET.md)、
[`SUBMENUS.md`](SUBMENUS.md)。導航從 [`UI_NAVIGATOR.md`](UI_NAVIGATOR.md) 進。

**出處標記**:🟢 = 在模擬器裡跑原廠程式碼得到的;🔵 = 從反編譯讀出來、但還沒逐欄跑過;
⚪ = 還沒讀。工具 `tools/nbu_probe/`(37 測試)與 `tools/nbr_stock.py`(34 測試)。

---

## 1. 兩個容器,一種格式 🟢

| | 位址 | 版本 | 內容 |
|---|---|---|---|
| **NBU** | `0xC18C0460` | `0x01090000`(1.9) | UI 記錄 |
| **NBR** | `0xC0D22400` | `0x01050000`(1.5) | 圖示、字型、選單 CSV、字串表 |

容器 = `magic(4)` + `版本(4)` + `空字(4)` + 一串記錄。

```
NBU 0xC18C0460            NBR 0xC0D22400
  tag 1      176,160 B      tag 1        177,572 B   名稱池(2,260 條建置路徑)
  tag 0x10001  7,088 B      tag 2     11,817,672 B   目錄 + 資料
  結束             8 B      tag 0x20001  81,844 B   ⚪
                            結束              8 B
```

**NBU 的 20 MB 記錄區不是一個線性容器。** 最上層只有字串池 + **221 筆資源集索引**,
每個螢幕是索引裡的一筆、各自一段記錄流。索引存在 [`nbu_sets.json`](nbu_sets.json)。

## 2. 記錄框架 🟢

**每一筆記錄都是 `{u32 BE tag, u32 BE size, body…}`,`size` 含這兩個字。**

- 全樹 **221 個資源集、303,597 筆記錄**,**220 個集合首尾相接一個位元組不差**。
- 結束記錄是 `FF FF FF FF 00 00 00 08`。
- **大小是位元組粒度**(reader 可以讀單一位元組),body 不知道 tag 就不能當 word 走。
- 因為自帶長度,**拆開／換掉／插入／重新輸出不需要逐 tag 的文法**:
  `nbu_format.split()` / `join()`,改 body 之後 `size` 自己算。

## 3. 解析 context(0xB8 bytes)

韌體自己的建構子 `0xC05E5FE0` → `0xC05E5F20` 建的 🟢。

| 位移 | 索引 | 內容 |
|---|---|---|
| +0x00 | [0] | 版本(資源集是從上層**繼承**的,不是讀出來的) 🟢 |
| +0x04 | [1] | **讀取游標**(byte offset) 🟢 |
| +0x08 | [2] | app 物件;`+0x60` 與 `+0x888` 會被用到 🟢 |
| +0x0C | [3] | 擁有者;解譯器把做好的 arena 寫進 `owner+0x0C`(`0xC05E68EA`)。給 0 會寫穿空指標 🟢 |
| +0x10 | [4] | 字串池大小 🟢 |
| +0x14 | [5] | 字串池基底 = `0xC18C0474` 🟢 |
| +0x1C | [7] | 錯誤旗標(MainB2 整頁解完是 0) 🟢 |
| +0x20 | [8] | 來源大小(非 0 選記憶體 reader) 🟢 |
| +0x24 | [9] | 來源基底 🟢 |
| +0x30 | [0xC] | 配置器物件 🟢 |
| +0x34..0x40 | [0xD..0x10] | **四個讀取方法**,見下 🟢 |
| +0x44 | [0x11] | 原廠呼叫端寫 `0xC05E6029` 🔵 |
| +0x48 | [0x12] | 物件數(MainB2 = 193) 🟢 |
| +0x4C | [0x13] | 第二個物件數(`app+0x890` 為 0 時是 0) 🟢 |
| +0x50 | [0x14] | 填入索引 🔵 |
| +0x54 | [0x15] | 物件指標陣列,大小 `([0x12]+[0x13])*4` 🟢 |
| +0xA8/AC/B0 | [0x2A/2B/2C] | tag `0x10001` 用:筆數 / 陣列 / 名字 🟢 |

### 四個讀取方法(記憶體來源) 🟢

建構子按來源種類裝兩組;記憶體那一組是:

| 位移 | 位址 | 做什麼 |
|---|---|---|
| +0x34 | `0xC05E5D78` | 讀一個 **signed byte**,游標 +1 |
| +0x38 | `0xC05E5DB8` | 讀一個 **big-endian u32**,游標 +4 |
| +0x3C | `0xC05E5E38` | 複製 n bytes |
| +0x40 | `0xC05E5EA8` | 跳過 n bytes |

`0xC05E5E20` 把同一個字重新解讀成 float(所以 `0xC1A709BC` 的 `40 A0 00 00` = 5.0)。
`0xC05E5B58` 是 pool offset → 字串:用 `ctx+0x10` 做邊界檢查、加上 `ctx+0x14`。

## 4. tag 目錄

`case N` 是 `0xC05E6400` 內 `0xC05E6460` 那個 switch 的第 N 支,**N = tag − 0x10001**。
數量欄:全 UI / MainB2。

| tag | case | 是什麼 | 數量 | 狀態 |
|---|---|---|---|---|
| `0x10001` | 0 | 資源集索引(只在最上層) | 1 / — | 🟢 |
| `0x10002` | 1 | 配置標頭 | 221 / 1 | 🟢 |
| `0x10003` | 2 | **物件**,**固定 36 bytes** | 36,379 / 193 | 🟢 |
| `0x10004` | 3 | value/binding → `FUN_c05e8070` | 37,513 / 199 | ⚪ |
| `0x10005` | 4 | 屬性 + 動畫鍵 | 26,326 / 120 | 🔵 |
| `0x10006` | 5 | 屬性(多一個值) | 47,314 / 209 | 🔵 |
| `0x10007` | 6 | 屬性(layout) | 211 / 1 | 🔵 |
| `0x10008` | 7 | 屬性 + 巢狀 key list | 164 / 0 | 🔵 |
| `0x10009` | 8 | 屬性(短) | 89,068 / 430 | 🔵 |
| `0x1000A` | 9 | **animationClip**(全樹只有這一種) | 46,528 / 159 | 🟢 名字 |
| **`0x1000B`** | **10** | **影像／動畫群組** | **11,383 / 52** | **🟢 逐欄** |
| `0x1000C` | 0xb | value/binding → `FUN_c05e8070` | 0 / 0 | ⚪ |
| `0x1000D` | 0xc | 屬性(和 case 6 同形) | 0 / 0 | 🔵 |
| `0x1000E` | 0xd | value/binding → `FUN_c05e8070` | 6,863 / 20 | ⚪ |
| `0x110xx` | — | 整塊配置後複製的表 | 1,406 / 7 | ⚪ |
| `0xFFFFFFFF` | — | 結束,回傳 1 | 221 / 1 | 🟢 |

另外兩支不在 `N = tag − 0x10001` 這條線上,是 `> 0x20000` 的分支 🔵:
`0x20001`(變數定義迴圈,MAINB2 筆記講的那個)、`0x20002`、`0x30001`、`0x30003`、
`0x1FFFE`、`0x2FFFE`(app 變數註冊,呼叫 `0xC05DB308`)、`0xFFFE`。

### tag `0x10001` —— 資源集索引 🟢

```
u32 名字, u32 count,
count x { u32 a, u32 名字, u32 b, u32 c, +4 個 float(版本 > 0x105FFFF) }
```
每筆產生一列 0x2C bytes 的 `{FNV-1a, 名字指標, 從 0xC18C0460 起的位移, …}`,按 hash 排序。
**221 筆。** `MainB2` 的 hash `BDD26684`、pool offset `0x1A3B8`、位移 `0x76FF04`
與手算完全相同。

### tag `0x10002` —— 配置標頭 🟢

```
u32 objects, u32 objects2, u32 classes,
classes x { u32 名字 pool offset, u32 實例數 }
然後還有四組計算 arena 大小的迴圈 🔵
```
MainB2:3,028 bytes = 757 個 BE word(解譯器一個不漏地讀完)、23 個類別、
`objectBase` 193 = `objects`。**加物件就要改這張表。**

### tag `0x10003` —— 物件 🔵

```
u32 a, u32 b, u32 c, u32 d, u32 parent, u32 名字, u32 e(版本 > 0x105FFFF)
```
**全樹 36,379 筆全部正好 36 bytes**(8 表頭 + 7 個 u32)—— 這把上面的 token 排列從
「讀反編譯」升級成算術上唯一成立的解。🟢

`FUN_c05cf808(ctx[3], e, a, c, b, &out)` 造物件;`out+0x24 |= 0x1BFE`、`out+0x18 = d`。
**`parent == 0` 那一筆就是 root**(→ `ctx[0x2D]`);否則接到父節點底下。
物件的**類別名**(`MenuItem_Select` / `MenuItem_Jump` / `MenuItem_SelectJump`…)
就在這一種記錄裡 —— 見 [`SUBMENUS.md`](SUBMENUS.md)。

### tag `0x10009` —— 短屬性 🔵

```
u32 名字, u32 keys, u32 群組名, u32 owner, u32 sub, u32 flags
然後 keys 筆動畫鍵(由 FUN_c05e7b60 讀掉,鍵的內容 ⚪)
```
`FUN_c05d1928(owner, sub, &out)` 找子物件,`FUN_c05e8028(...)` 建屬性。
**89,068 筆,最常見的一種。**

### tag `0x1000A` —— animationClip 🔵(名字 🟢)

```
u32 名字, u32 count, u32 名字2, u32 owner, u32 v
然後 count 組(每組至少兩個 token)⚪
```
`FUN_c05d9e80(app, 名字)` 取的是**類別**,`FUN_c05d5968(...)` 綁定。

⚠ 訂正:這不是「檔案引用」。**全樹 46,528 筆的第一個名字全部都是 `animationClip`**,
一種都沒有別的。所以它是動畫片段記錄,不是通用資源引用。

**UI 記錄裡沒有任何一筆指向檔案。** `.cvm` / `.nloc` / `.xci` 的路徑**只存在於 NBR 名稱池**;
UI 記錄引用的是**短名**(`B2_5_4` 在 NBU 字串池 `0xC18CA000`),路徑是執行時拼出來再算
FNV-1a 查目錄的。這正是為什麼資源改寫在 AutoRun 之後打下去仍然來得及 ——
見 [`HOW_CHANGES_TAKE_EFFECT.md`](HOW_CHANGES_TAKE_EFFECT.md)。

### tag `0x1000B` —— 影像／動畫群組 🟢 **逐欄**

```
u32 nA, u32 nB, u32 nC, u32 群組名, u32 owner
nA x { u32 資源名, u32 a, u32 b, u32 c, u32 d, u8 e }
nB x { u32 名字, u32 值, u8 旗標, u32 額外(旗標為真) }
nC x { u32, u32 }
u32 名字2(版本 > 0x102FFFF), u32 尾碼(版本 > 0x105FFFF)
```

**全 UI 11,383 筆全部解得開、一個位元組不剩。** 這是整份文件最強的驗證:
任何一個欄位寬度錯了都會剩下位元組。

- 它是**唯一**會呼叫 `FUN_c05e2988`(image_container_new)的 tag ——
  就是 `README.md` §5c 講的 case 10。
- 解析度那兩個群組(`20_/21_MV_Resolution`)每筆都是 `nA = 1`、**`b = 33`**。
  33 就是 §3 說的「兩狀態曲線終點」,**第三個狀態要 66**。
- 「加一個 UI 狀態」= `nA += 1` 再加一筆 entry,**而且每一個伴隨屬性都要跟著加**。

### tag `0x10005` / `0x10006` / `0x10007` / `0x1000D` 🔵

同一個家族,都以 `FUN_c05e8028` 建屬性、`FUN_c05e7b60` 讀動畫鍵:

```
0x10005: u32 名字, u32 keys, u32 名字2, u32 owner, u32 flags
         ⚠ 傳給 FUN_c05e7b60 的是 keys − 2(版本 ≥ 0x1020000;更舊的版本是 −1)
0x10006: u32 名字, u32 keys, u32 v, u32 名字2, u32 owner, u32 flags   ← 六個
0x10007: u32 名字, u32 keys, u32 名字2, u32 owner, u32 flags   (+FUN_c05e80f8)
0x1000D: 與 0x10007 同形,但先 FUN_c05d9fd0(app) 取一個東西,且沒有 FUN_c05e80f8
```
⚠ 這幾個是照著反編譯抄的,**還沒用「解碼→重編碼逐位元組相同」驗過**。

## 4b. 類別名住在哪裡

配置標頭(`0x10002`)與物件記錄(`0x10003`)裡的類別名(`objectBase`、`drawText`、
`layoutFlexBox`、`MenuItem_SelectJump`…)在 NBU 字串池裡;**類別本身是帶 vtable 的外掛物件**,
描述子在程式碼區,例如:

```
0xC0600E40  "layoutFlexBox" / "Standard" / "Standard item flexible box layout"
0xC05FA960  "flexBoxItem"   / "Standard" / "Standard flexible box item"
```

前面幾個小函式(`movs r0,#n; bx lr`、`movw/movt; bx lr`)是回傳分類與名字指標的 getter。
要知道某個類別**怎麼排版/怎麼畫**,入口就在這裡。

## 5. 模擬器能證明什麼、不能證明什麼

`tools/nbu_probe/` 跑的是相機**自己的** `0xC05E6400`,只把外部服務換成 Python 替身,
而且**沒登記的呼叫會炸並印出位址**。已驗證的鏈:

- MainB2 整頁 **1,392 筆記錄**解完,最後游標正好落在 MainB3 的起點、錯誤旗標 0;
- Python 拆出來的邊界與韌體**完全相同**,`join()` 回去**逐位元組相同**;
- 三個手算值(MainB2 的 hash/pool offset/位移、MainB2 與 MainY4 的頁面邊界)一字不差。

**證明不了**:GUI 會不會把結果畫出來、某個螢幕什麼時候被解析、
替身取代掉的原廠函式原本會做什麼。**本文沒有任何一項在相機上驗證過。**

## 5b. 生效時機

改完什麼時候生效是另一個問題,分三層,整理在
[`HOW_CHANGES_TAKE_EFFECT.md`](HOW_CHANGES_TAKE_EFFECT.md)。一句話:
**配對表立刻、NBR 資源開畫面時才讀、NBU 記錄每組只解析一次**。

## 6. 還沒解的

- `0x110xx` 七種表的內容(整塊複製,沒解)。

- `0x10005`/`0x10006`/`0x10007`/`0x1000D` 要補「重編碼逐位元組相同」的驗收。

## ★ NBU 資源集也能改指向 —— 一個大端字(2026-09-29)

`RESOURCE_REPLACEMENT.md` 解掉的是 **NBR** 目錄(圖示、字型、選單 CSV)。
**NBU** 那一側有**同構的**一張表,而且同樣可以改指向。

```
索引表  0xC18EB49C .. 0xC18ED05C    221 列 x 0x20 bytes,大端,按 FNV hash 遞增

  +0x00  u32  FNV-1a(集合短名)         查表的 key
  +0x04  u32  名稱在字串池裡的位移
  +0x08  u32  1
  +0x0C  u32  **集合位移 —— 從 0xC18C0460 起算**   ← 改這個
  +0x10  u32  0
  +0x14  u32  0
  +0x18  u32  0x400
  +0x1C  u32  0x2AA

例:B2_5(整個「記錄設定」頁,含五列與它們的彈出清單)
  列 @ 0xC18ECA9C   hash 0xD570BB11   位移 0x19C130 -> 0xC1A5C590
  集合 0xC1A5C590 .. 0xC1A792FB   118,123 B   1952 筆記錄
  ★ 寫入點 0xC18ECAA8
```

(這張表就是先前筆記裡「221 筆畫面宣告 @ `0xC18EB48C`」的那一張 ——
欄位語意現在釘住了:那個「page-offset」就是 `+0x0C` 的集合位移。)

### 為什麼這重要

`README.md` 的 routes 裡,**R0(直接改資源資料)**的 `not:` 欄寫著:

> get the edited set into the camera by itself: that is R3 (the resource-directory
> redirect), whose record fields are still untraced

**現在 traced 了,而且不是 NBR 那張表,是 NBU 自己的這張。**
所以 R0 有了自己的載入路徑:

```
1. 離線把 B2_5 拆開、插入新列要的記錄、join 回去      nbu_format.split/join
   (R0 已量過:220/220 個集合首尾相接,MainB2 逐位元組重現)
2. 放到有空間的地方
3. 改 0xC18ECAA8 一個大端字
```

**不需要 R2 那 2538 words 的私有 pack 與三個 Thumb hook。**

### 加一列在 NBU 這側要付什麼

把 `B2_5` 裡五個清單依列數比對(它們在同一個集合裡,是乾淨的對照組):

```
列數   0x10003 物件   0x10004   0x10005   0x1000B 影像陣列   0x1000E 控制器
 2         42          42        29            6                10
 3         44          44        29            6                12
 9         62          62        45            9                13
```

**每多一列要多兩筆物件記錄(0x10003)與兩筆 0x10004。** 不是改個計數就好。
長清單(9 列)另外多了 0x10005 與影像陣列,推測是捲動/游標相關,未追。

### ❌ 上機否定:**索引在執行期不會重讀**(2026-09-29)

單字對照實驗。把 `B2_6`(音訊設定)的位移欄指到 `B2_5`(記錄設定)的集合,
完全退出選單再進去:

```
0xC18EC9C8   0x9b8e1b00 -> 0x30c11900      BE 0x1B8E9B -> 0x19C130
             音訊的集合     記錄設定的集合
```

**結果:音訊設定完全正常,一點變化都沒有。** 還原後也正常。

所以要把兩件事分開講,它們**不一樣**:

| | 執行期改 RAM 有沒有效 |
|---|---|
| 集合**內容**(記錄本身,例如控制器上限) | **有** —— 開頁時重讀,上機驗過 |
| 集合**位址**(索引的 `+0x0C` 位移欄) | **沒有** —— 開機後就固化了 |

**第二輪,加上強制重載:**

`UicResourceCache`(`0xC0D0EFC8`)有一份固定的快取名單 ——
`QS_CINE` / `QS_STILL` / `B1_2_1` / `B2_3` / `B3_1` / `B3_5_5` / `B2_1_3` / `B5_2`
加上一堆字型 —— **`B2_5` 與 `B2_6` 都不在裡面**,所以不是這個快取擋著。

```
gui gc            → 是 **Lua** 的 GC(LUA_GCCOLLECT…),動不到解析後的 C++ 物件
gui lang 1 → 7    → 換語言再換回來,整個 UI 重建
結果:音訊設定仍然完全正常
```

★ **所以集合位址連「整個 UI 重建」都撐得過去** —— 它是在開機/容器載入那一趟
綁定的,之後不再回頭查索引表。

順帶一個佐證:整個 ROM 裡**沒有任何程式碼引用 `0xC18C0460`**(NBU 容器基底),
所以基底本身是執行期拿到的,索引也是那時候走完的。

⚠ 這一輪**沒有確認語言真的在畫面上切換過**(只確認指令有回應),
所以「換語言 = 完整重建」這個前提是推的,不是看到的。

★ 所以「改指向」在**執行期打 RAM** 這條路上**不通**。

⚠ **這不代表開機時改也沒用。** 卡片 loader 是在 UI 初始化**之前**寫入的,
那個時機沒有被這個實驗否定。但我們現在的打法(開機後 USB shell 打 RAM)
用不了這條路。

### 還沒驗證
