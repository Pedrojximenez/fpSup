
**選一個新列會選得到、會送出正確的列舉值、會走正確的閘門 —— 然後收合摘要一片空白。**

## CSV 的形式:兩件會讓一列「選得到但看不見」的事

兩個都是 2026-09-29 實機分辨出來的,而且都不是機制問題,是格式問題。

### 1. 結尾 CRLF 不能省

```
✅ …\r\n4,0308,Popup,1,2\r\n      四列都畫出來
❌ …\r\n4,0308,Popup,1,2          只畫三列 —— 最後一列沒被 parse
```

原廠有三個 `.cvm` 確實不以 CRLF 結尾(`B2_3` / `B4_1_3_04` / `B4_1_3_4_1`),
所以那是合法的形狀 —— 但**最後一列會被吃掉**。先前為了把 117 B 塞進 116 B 的槽
拿掉了它,那就是整個「看不見」的原因。

### 2. 欄位要**整欄拿掉**,不能留空

```
✅ NO,TEXT,Popup,Enabled,Enabled2      1,0305,Popup,1,2       畫得出來
❌ NO,TEXT,Popup,IMAGE,Enabled,Enabled2  1,0305,Popup,,1,2    畫不出來
```

要空間就把整欄從表頭一起拿掉。`.cvm` 的欄位由第一行決定(全機 13 種表頭),
少一欄是合法的 —— fpSup-Formats 自己的 CSV 連 `Popup` 欄都沒有。

⚠ 連帶:**任何解析 `.cvm` 的程式都要依表頭找欄位,不能寫死索引。**

## 位址綁定:三個都在開機時固化

今天三個獨立的實驗,答案一致:

| 改什麼 | 執行期打 RAM |
|---|---|
| CSV 內容(既有列的文字) | ✅ 有效 —— 探針把 `0313` 改成 `ZZZZ`,畫面就變 |
| CSV 內容(加列) | ✅ 有效 —— 形式對的話 |
| NBU 記錄內容(controller max) | ✅ 有效 |
| **NBR 目錄項的資料位移**(repoint) | ❌ 無效 —— 韌體仍讀原本的 CSV |
| **NBU 集合索引的 `+0x0C`** | ❌ 無效 —— 連換語言重建整個 UI 都撐得過去 |

★ **所以「原地改」是執行期唯一有效的形式**,而它夠用 —— 只要新內容塞得進原槽。
塞不下就得騰(拿掉欄位),而不是搬家。

⚠ **這不否定開機時 repoint。** 卡片 loader 在 UI 初始化**之前**寫入,
fpSup-Formats 就是這樣出貨的。只有「開機後用 USB shell 打 RAM」這條路不行。

## 驗證用的最小實驗(照做就能複製)

```
1. 探針:把既有一列的 TEXT 換成等長的字面字串,原地、不動別的
        變了 → CSV 路徑通;沒變 → 停下來查寫入/時機
2. 加列:拿掉 IMAGE 整欄騰空間,保留結尾 CRLF,原地寫回,改描述子長度
        **先不要動 controller max**
        列出現、選不到 → 一切如預期
3. 補 controller max → 選得到
4. 選下去 → 收合摘要空白,那就是 NBU 那一半,要 R2
```

## 舊版錯在哪(留著當教訓)

第一次上機時,位元深度第四列與格率第十列都「選得到但看不見」,
我據此寫了「畫列要 NBU」。那個推論有兩個沒控制到的變因:

- 位元深度那份 CSV **沒有結尾 CRLF**(為了塞進槽);
- 格率那份 CSV 的 IMAGE 欄是**留空**而不是拿掉。

兩個都會讓那一列不被 parse,而症狀與「NBU 不畫它」**完全一樣**。
接著我用 repoint 做第二次驗證,但 repoint 本身在執行期無效,
所以那次「第三列沒出現」也什麼都沒證明 —— **兩個失敗的實驗疊起來,
看起來像一個很強的結論。**

真正解開它的是一個**只需要單一機制**的探針(改既有列的文字)。
教訓:**先做一個只動一個變因的實驗,再談結論。**
