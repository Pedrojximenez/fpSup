# 補丁下去了,畫面沒變 —— 怎麼分辨是哪一種

> **2026-09-29 已結案:那一次的真因是 CSV 的形式,不是機制。**
> 最後一列少了結尾 CRLF(為了塞進槽裡拿掉的),那一列就整列不見;
> 而中間那次用 repoint 的測試什麼都沒證明,因為 **repoint 在執行期無效**。
> 補回 CRLF、改成原地等長之後,第四列出現而且選得到。
> 規則見 [`RESOURCE_REPLACEMENT.md`](RESOURCE_REPLACEMENT.md)〈替換 CSV 的規則〉。
> 下面的分辨法仍然有效,留著給下一次用。

2026-09-29。症狀是「實機測試沒有真的改到 UI」。下面按**機率**排,每一條都附
「怎麼分辨是不是它」。**先做第 1 條,它同時是最常見也最容易被跳過的。**

---

## 1. 寫入根本沒進去(最常見)

`mem set` **會靜默掉指令**。這在本專案有獨立紀錄,而且是批次寫入的預設假設 ——
一段 121 bytes 的 CSV 是 31 條 `mem set`,只要掉一條,內容就是壞的。

**怎麼分辨:逐字回讀。** 讀取是可靠的,掉的只有寫入。

```
mem read 0xC12C7CF8 128     # CSV,逐 byte 比對你送出去的內容
mem read 0xC0D4DE04 8       # 應該是 00 5A 58 F8 00 00 00 79(視長度而定)
mem read 0xC1A709BC 4       # 應該是 40 00 00 00(三列 = BE float 2.0)
```

**三個位址都對得上,才可以往下找。** 對不上就是這一條,重送 + 再回讀,直到全對。
做成卡片的話走 loader 的 VBIN section,不要用 `mem set`。

## 1b. ⚠ 已知前提:AutoRun 在開機後約 8 秒,UI 已經載入(使用者實測)

這一條**不是原因清單的一項,是所有分析的前提**,而且無法靠換手法繞過:
`0xC03DA420` 就是啟動 AutoRun 的那條 `bl`,Fast Start 2 的 loader hook 換掉的就是它 ——
**跑在同一個時間點,只是比較快,不會更早**。`README.md` §6 也早就寫了
「AutoRun 晚於原廠的 NBR/resource pass」。

**但這不能解釋 CSV 那一半沒生效**:fpSup-Formats 的 CSV 與目錄寫入也是普通 section、
一樣 ~8 秒才寫,而它的六列在相機上會出現 —— 所以 **CSV 是 8 秒之後才被讀的**。
它的三個 hook 掛在**記錄解析器**上,管的是 NBU 那一半,不是 CSV。

所以:**列沒出現 = 還是要從第 1 條(寫入沒進去)查起**,不要先怪時機。

資源是**建立那個畫面時**才讀的。如果測試流程是「開機 → 先去看了一次選單 →
下補丁 → 再看一次」,第二次看到的可能是已經建好的那一份。

**怎麼分辨:改完之後重開機,再第一次進那一頁。** 變了就是這一條。

## 3. 改的是 NBU 記錄,而它早就被解析過了

`0xC1A709BC`(controller 最大值)**不是資源,是一筆 NBU 記錄**
(資源集 `B2_5` 第 1368 筆、tag `0x1000E`、body +32)。
NBU 記錄**每組資源集只解析一次**,解析完再改就沒用。

**症狀很好認:列出現了,但選不到**(游標跳過去 / 停在第 2 列)。
FP3K 當初踩的就是這個。**如果列有出現、只是選不到,那 CSV 是成功的,失敗的只有這一個字。**

**怎麼分辨:** 看列有沒有出現。
- 列沒出現 → 問題在 CSV / 目錄(第 1、2、5 條)
- 列出現但選不到 → 問題在 controller 最大值(這一條)

## 4. 改的是「解析後的東西」,那留不住

直接改序列化 UI 記錄的位元組,對**已經建好的畫面**一點效果都沒有 ——
本專案實測過:三次直接改 image 位元組,**零變化**;而改 enum→state 配對表
(`0xC2E4020C`)立刻生效。解析後的元素物件更糟,它們跟著螢幕物件一起被釋放,
之後掃 144 MB 一個都找不到。

**怎麼分辨:** 你改的位址落在哪一區?`uinav.py at <addr>` 會告訴你,
順便告訴你那一區**什麼時候被讀**。

## 5. 目錄項改了,但資源被快取住

圖示那邊確定會快取 —— 沿用原廠名字,快取後端就沒有理由重新解碼,
所以合成的名字必須是**新的**。**`.cvm` 有沒有同樣的快取,我們沒驗過。**

**怎麼分辨:** 重開機之後第一次進那一頁就是新內容 → 是快取;
重開機也沒用 → 不是這一條。

## 6. 改對了地方,但那不是畫面的來源

`.cvm` 的路徑只存在於 NBR 名稱池,UI 記錄引用的是短名(`B2_5_4`),
路徑是執行時拼的。`B2_5` 第 1301 筆是一個 tag `0x10003` 物件,**名字就叫 `B2_5_4`** ——
清單物件在 NBU、列的內容在 CSV,兩邊都要對。

**怎麼分辨:** 把 CSV 改成明顯不同的東西(例如把第 1 列的文字換成字面字串
`ZZZTEST`)。**連原本那兩列的文字都不變 → CSV 根本沒被讀**,問題在第 1、2、5 條;
第 1 列變了、第 3 列沒出現 → CSV 有讀到,問題在列數/最大值。

> 這一招是整份文件最有用的一步:**先證明 CSV 真的被讀**,再談加列。

## 建議的最小實驗順序

1. **只改一個位元組**:把 `B2_5_4.cvm` 第 1 列的 `0313` 換成字面 `ZZZZ`(**長度不變**、
   不用改目錄、不用改最大值)。工具直接產:

   ```
   python3 research/ui/tools/menu_row_patch.py --probe 1 --text ZZZZ --autorun
   → 1 個寫入、89 bytes、就寫在原地 0xC0F8E7EC,大小與原廠相同
   ```

   長度不一樣會被擋下來(等長是這個實驗成立的前提)。回讀確認。重開機,進選單。
   - 第 1 列變成 `ZZZZ` → **CSV 路徑通了**,直接跳到第 3 步。
   - 沒變 → 停在這裡,問題在寫入或快取,不要往下加東西。
2. 沒變的話:`mem read` 逐字比對;確認是在**重開機後第一次**進那一頁。
3. 通了之後再加第三列(CSV 變長 → 需要改目錄的 8 bytes),但**先不要動 controller 最大值**。
   - 列出現、選不到 → 一切如預期,最後再補最大值。
   - 列沒出現 → 問題在目錄那 8 bytes(回讀、確認位移是**相對 `0xC0D22400`** 的)。

**每一步只改一件事,每一步都回讀。**(見 `freeze-postmortem-discipline` 的老規矩。)

## 已知還沒驗證的假設

這份配方裡有三個地方是**推論**,不是我們量到的:

- `B2_5` 是延遲解析(從 fpSup-Formats 的卡推的);
- `.cvm` 沒有資源快取;
- 我們算的 8 bytes 目錄改寫在相機上行為與 Formats 相同(位元組相同,但那是它的內容)。

第 1 步的 `ZZZ` 實驗會一次把前兩個問題都答掉。
