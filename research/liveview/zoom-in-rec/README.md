# 實驗 A:錄影中放大 —— 先把 UI 的門拆掉,看畫面動不動

`../zoom-magnify-chain.md` 的下一步。目的只有一個:把「政策禁止」和「機制不允許」
分開。現在兩個未知綁在一起,這個實驗把它變成一個。

## 改什麼

兩個字,都在 canZoom 自己的呼叫點上 —— **不動被呼叫的函式本體**,所以錄影中其他也在
問這兩個函式的程式碼(`FUN_c04843b0`、`MenuQsHandler::v11` 等)行為完全不變。

| 位址 | 原廠 | 之後 | 這道門 |
|---|---|---|---|
| `0xC04A569C` | `EBFFFE05` BL `FUN_c04a4eb8` | `E3A00000` mov r0,#0 | 「正在錄影」 |
| `0xC04A579C` | `EB00079D` BL `FUN_c04a7618` | `E3A00000` mov r0,#0 | 會跳 3 秒提示的那道 |

兩處後面都緊接 `cmp r0,#0`,所以把回傳值做成 0 是安全的替換。

第二道門一起拆,是因為它的語意還沒定(見研究筆記第 6 節),而它**有可能**就是錄影中
在擋的那一道。分兩次上機只為了知道是哪一道在擋,資訊價值不值得多一趟。

## 用法

相機要在跑帶 USB shell 的卡(`fpshd` 起著,`fpsh ping` 有回應)。

```sh
./apply.py --check     # 只回讀
./apply.py             # 裝上
./apply.py --revert    # 還原
```

腳本自己守著起點:只從原廠狀態裝、只從 patch 狀態拆,中間值就中止。寫完回讀對不上
會直接喊停 —— `mem set` 會靜默掉寫入,沒回讀就等於沒寫。

改的是 ROM 位址上的**指令**,所以相機端 stub 在寫完之後做 D-cache clean 到 PoC
再 ICIALLU。少了這一步,回讀給你新值而畫面照舊擋,是最會騙人的一種失敗。

全部在 RAM,抽電池即還原。

## 上機的順序(照這個走)

1. `./apply.py`,確認兩行都印 `patched`
2. 相機上手動開始錄影,放大也在相機上按 —— 這個實驗要看的是畫面,
   不需要在錄影期間下任何 shell 指令
3. 三個入口都試:放大鍵、半按觸發的 AF 放大、轉對焦環觸發的 MF 自動放大
4. 停止錄影,`./apply.py --revert`

## 怎麼判讀

| 看到的 | 意思 | 下一步 |
|---|---|---|
| **畫面真的放大了** | 只是政策性禁止 | 加守衛做成功能:只在錄影中放行放大,其餘不動 |
| 出現放大框/放大 UI,畫面不動 | latch 確認 | 走 B(改預覽 profile 可見視窗)或 C(OSD 放大鏡窗) |
| 完全沒反應 | 還有第三道門沒找到 | 回頭看 `FUN_c04a5650` 剩下的四個條件 |
| 跳出 3 秒提示 | 第二道門仍在擋,或它根本不是這條路徑 | 重讀那兩個字確認真的寫進去了 |
| 錄影中斷 / 凍結 | 放大送出的 UserSetting 廣播在錄影中是不安全的 | 結束實驗,B 與 C 都不碰這條路徑 |

**錄下來的檔案也要看**:畫面放大了但檔案沒放大,和兩邊都放大,是完全不同的結果 ——
前者可用,後者會毀掉素材。

## 風險

放大會 `FUN_c0021c50` 把整份 `XC_UserSetting`(0x5E4 bytes)廣播給 20 個 observer。
錄影中沒有人測過這件事。可能中斷錄影,可能凍結(要拔電池),也可能什麼事都沒有。
**先用不要的卡、不要的素材測。**
